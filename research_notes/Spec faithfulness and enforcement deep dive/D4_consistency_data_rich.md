# D4. Consistency for data-rich APIs with environment actions

Scope: alternatives to GR(1) realizability for checking "for every environment move, some allowed response exists" in a data-rich store API spec (handles, profiles, lifecycle, concurrent callers, out-of-band actors, faults, cancellation); how to handle mode variables without losing locality; cost at tens of operations × tens of clauses; and what changes in the verified edition's §2.2 (T2), gate G4 and §3 check map.

Conventions used on every finding: **grade** (A / A-pre / A-workshop / B / C / D / own trial); **FT** = full text read (yes/no); **n/setting**; **correct** = what "correct" meant in the source; **transfer** = *direct* (library/API behaviour specs), *analogous* (other spec domains), *inference*; **agents** = agent/LLM measurement; **TA** = tool or method authors evaluating their own tool; **V** = vendor. Downloads are in the scratchpad (`.../scratchpad/d4/`), trial scripts in `.../scratchpad/d4_trial/`.

## Q1. Alternatives to GR(1) realizability and their precedents on APIs or storage systems

### Takeaway
The question "for every environment move, some allowed response exists" has a well-studied **one-step form**. In Event-B it is the feasibility and deadlock-freedom proof obligations; in AGREE/JKind and Kind 2 it is the "extend"/viability check of realizability over integers and reals. With an inductive invariant, this one-step form is *sufficient* for realizability of safety contracts (Gacek et al.'s viability theorem). It decomposes exactly per environment move, it handles data through SMT or constraint solving, and measured runs take 0.1–2.3 s per component or model (TA). rt-consistency as implemented in Ultimate ReqAnalyzer/Hanfor does **not** split inputs from outputs, so it is not the "∀ environment move ∃ response" check that the verified edition's check map attributes to it. No source applies any of these checks to a library or storage *API* spec. The nearest precedents are an Event-B file-system model and a BPEL purchase-order process under ProB's constraint-based deadlock checking.

### Cited Findings

**A. One-step response existence: realizability over theories (AGREE/JKind, Kind 2)**

- Gacek, Katis, Whalen, Backes, Cofer, **NFM 2015** (LNCS 9058; Crossref-verified). They define realization condition 4 as "∀s, i. Reachable_A(s) ∧ A(s, i) ⇒ ∃s′. T(s, i, s′)" ("responsive to all valid inputs"). They define viability coinductively, "Viable(s) = ∀i. A(s, i) ⇒ ∃s′. G_T(s, i, s′) ∧ Viable(s′)", with Theorem 1: "A contract … is realizable if and only if ∃s. G_I(s) ∧ Viable(s)". The algorithm is k-induction over quantified formulas: a base check over-approximates viability and refutes, an extend check under-approximates it and proves. Implementation: JKind + Z3; "it is possible that for one of the checks, Z3 returns unknown". Grade A; FT yes; TA (Rockwell Collins/UMN). — [arXiv 1502.03005](https://arxiv.org/pdf/1502.03005)
- Same paper, motivating evidence (directly on "plain consistency passes, response existence fails"). There were six graduate teams of four students on a microwave in AADL/AGREE: "only one of the teams had written component-level requirements that could be implemented. The other teams had requirements which were inconsistent under certain input conditions … This error was not caught despite an analysis built into an early version of AGREE that checks contracts for consistency, i.e., whether the conjunction of a system's guarantees is satisfiable." On the GPCA infusion manager, a mode-related conflict (mode 0/1 ⇒ flow 0, versus alarm level 3 ⇒ flow = KVO) "was not discovered by the regular consistency check in AGREE". In QFCS OSAS, two fault-response guarantees (`ccdl_failed ⇒ gain′=1`, `osas_failed ⇒ gain′=0`) conflicted; the error "eluded the engineers who originally drafted the requirements as well as the engineers who formalized them". n = 3 case studies, 20 component contracts; setting: avionics, medical device, classroom; correct = implementation exists (realizable confirmed by synthesis, unrealizable "manually confirmed … no spurious results"); transfer *analogous*; agents: human-only evidence; TA. — [arXiv 1502.03005](https://arxiv.org/pdf/1502.03005)
- Same paper, cost (Table 1): 18 of 20 contracts decided in **0.1–1.762 s**. Two were "unknown" at the **1000 s** tool timeout. Base-check depth for every result was **0 or 1 step**: "the number of steps that the base check required to provide a final answer was not more than one". Grade A; FT yes; TA. — [arXiv 1502.03005](https://arxiv.org/pdf/1502.03005)
- Larraz & Tinelli, "Realizability Checking of Contracts with Kind 2" (arXiv 2205.09082, technical report; no peer-reviewed venue found). On failure it returns a deadlocking computation and a conflicting set of guarantees, using generic quantifier elimination for LIA/LRA in Z3/CVC4. Evaluation: 159 benchmark contracts from Katis et al.'s synthesis-benchmarks, 2-minute timeout. Kind 2 solved "a strictly larger superset of the problems solved by JKind". 15 problems were excluded: 2 rejected by syntax, and 13 where the tools disagreed on semantics of unguarded `pre`. Conflict and deadlock generation for 22 unrealizable contracts added 37 s (87 → 124 s, "43% overhead"). Example deadlock: G5 (cancel ⇒ minutes = 0) versus G9 (decr ⇒ minutes − 1) when both buttons are pressed. Grade A-pre; FT yes; n = 159; correct = agreement with JKind and no external ground truth; transfer *analogous*; human-only evidence; TA. — [arXiv 2205.09082](https://arxiv.org/pdf/2205.09082)

**B. One-step response existence: Event-B / B (Rodin, ProB)**

- Hallerstede & Leuschel, "Constraint-based deadlock checking of high-level specifications", **TPLP 11(4–5) 2011** (ICLP 2011; Crossref-verified). The deadlock-freedom PO is "A ∧ I ⇒ G_e1 ∨ … ∨ G_en (DLF)". The negation "A ∧ I ∧ ¬G_e1 ∧ … ∧ ¬G_en (DLN)" is solved by ProB's constraint solver. The counterexample state "is not necessarily reachable from the initial states. However, this state is allowed by the axioms and invariants". The tool restricts the search with a "predicate of interest P" and "filter[s] out any event that can obviously not fire given P", which "can sometimes result in a much better decomposition of the formula into independent sub-components". It also partitions the formula into connected sub-components and ignores components unrelated to any guard. Grade A; FT yes; TA. — [arXiv 1109.2015](https://arxiv.org/pdf/1109.2015)
- Same paper, Bosch cruise control (Deploy). The model had 78 constants, 121 axioms, 62 variables, 59 invariants, **80 events with 855 guards**, and 79 variables or constants with infinite domains. The DLF PO ran to 34 A4 pages and gave Rodin a "Java Heap Space Error". ProB found deadlocks in **1.07–2.32 s** of solving (**9.98–11.92 s** including loading), for the predicate of interest Counter=10. Explicit model checking found only an uninteresting deadlock (Counter=1) in 50.41 s and "failed to find a counter example after running for almost 4 hours" for Counter=10. The authors frame "a deadlock means that the system can be in a state for which no action was foreseen by the engineers". Grade A; FT yes; n = 1 industrial model plus 14 benchmark models; correct = a solution of DLN exists; transfer *analogous*; human-only evidence; TA with an industrial user.
- Same paper, benchmarks (Fig. 5) include **"FMCH02 … second refinement of a file system model with 6 constants, 8 axioms, 7 variables, 12 invariants, and 9 events"**: deadlock found in 0.00 s at carrier size 1, and no deadlock in 0.53 s at size 2. A BPEL purchase-order business process (15 events, 59 guards in the final version) was "believed to be free of deadlocks" until ProB found one. It took "5 iterations to finally obtain a deadlock free version", and constraint solving took 0.03–0.37 s per version against model checking that was inconclusive at 1423 s. For version 5, a proof of deadlock freedom succeeded "however, it turned out that a wrong proof obligation was generated". This is the nearest storage/service precedent found. Grade A; FT yes; transfer *analogous* (a file-system model and a service process, not an API behaviour spec).
- Event-B feasibility (FIS) PO: Event-B wiki, "Revisiting Feasibility POs". FIS is "supposed to work as a filter and prevent models from containing magic actions". The page documents a soundness flaw in Rodin's FIS for refined machines with witnesses ("the flaw in the proof obligation comes from the presence of the two hypotheses together"). Grade B (tool wiki); FT yes; transfer *analogous*. — [Event-B wiki](https://wiki.event-b.org/index.php/Revisiting_Feasibility_POs). The general FIS form "I ∧ grd ⇒ ∃v′. BA(v, v′)" was seen in search extracts only (lead, not verified in full text).
- Event-B Flows plug-in wiki: deadlock-freedom POs in the Bosch case formed "a large disjunction in a goal comprising several hundreds of terms". Grade B; FT yes. — [Event-B wiki](https://wiki.event-b.org/index.php/Flows_Plug-in)
- VDM "satisfiability"/implementability PO (∀ inputs and states satisfying pre ∃ result and state satisfying post and inv): search extracts only, from course slides. **[lead; not read in full]** — [Oliveira slides](https://www.di.uminho.pt/~jno/ps/vdm06sl.pdf)

**D. rt-consistency (Ultimate ReqAnalyzer / Hanfor)**

- Langenfeld et al., **RE 2019** (A; FT yes; TA + Bosch). rt-inconsistency is encoded as a reachable error location guarded by the negated "Non-Deadlock-Condition" of the parallel composition of phase-event automata. Because that condition "is growing exponentially in the number of component automata", the tool checks "all c-sized subsets … Note that not all rt-inconsistent requirement sets are detected, because deadlocks caused by more than c requirements are not checked". The evaluation used **c = 2**, a 300 s timeout per non-trivial check, and 72 h for the large Bosch set. The conclusion lists as *future work*: "by adding additional information in form of discrimination of input, output, and internal observables, we can extend our algorithm … with a completeness analysis that detects missing treatment of input observable ranges". As implemented in 2019, rt-consistency therefore quantifies over runs without an environment/system split. — [RE 2019 PDF](https://people.irisa.fr/Nicolas.Markey/PDF/Papers/re2019-LDWHP.pdf)
- Post & Podelski, GI 2011 abstract (B; FT yes, 2 pages, German). Three properties: inconsistency, trivial consistency, and rt-inconsistency, applied in a case study of 6 Bosch automotive projects. — [GI 2011](https://fb-swt.gi.de/fileadmin/FB/SWT/Softwaretechnik-Trends/Verzeichnis/Band_31_Heft_1/GI2011_Post.pdf). Post, Hoenicke, Podelski FASE 2011 (original definition): **[unreachable]** (Springer returned an empty file).

**E. SMT/synthesis "modulo theories" for data-rich reactive specs**

- Rodríguez & Sánchez, "Boolean Abstractions for Realizability Modulo Theories", **CAV 2023** (Crossref-verified; read as the arXiv extended version). The method replaces theory literals by Booleans plus an extra requirement capturing realizable "reactions". The brute-force version needs "a number of SMT queries that is doubly exponential in the number of input literals". The evaluation covers six industrial-inspired specs plus a synthetic one, split into "clusters" of literals that share no variables, with 2–7 literals per cluster (up to 12 in Fig. 3). All Boolean abstractions were checked by Strix "in less than 7 seconds", and abstraction time dominated. Grade A; FT yes; TA; transfer *analogous*; human-only evidence. — [arXiv 2310.17292](https://arxiv.org/pdf/2310.17292)
- Finkbeiner, Heim, Passing, "Temporal Stream Logic modulo Theories" (arXiv full version; FoSSaCS 2022 per the search result, venue not Crossref-verified → treated as A-pre). This is **satisfiability**, not realizability. Satisfiability is "neither semi-decidable nor co-semi-decidable" across the theories considered. On 570 random formulas: 513 SAT, 29 timeouts at 30 s. Application benchmarks ran 0.25 s–940 s (Approx. P. T. Arbiter). FT yes; TA; transfer *analogous*. — [arXiv 2104.14988](https://arxiv.org/pdf/2104.14988)

**H. Own trial (grade: own trial; transfer *inference*, synthetic)**

- Setup: Z3 4.x via z3-solver 5.3.2, Python 3.13. The synthetic store API state has lifecycle (4 values), profile (3), handle state as `Array Int→Int` (4 values), an out-of-band cancel flag `Array Int→Bool`, a fault flag, used/quota integers, a request (handle, arg), and a response (5 codes, new handle state, quota delta, Int return value). There are 6 shared clauses (lifecycle, frame, quota, fault, value, released) plus m per-operation clauses (guarded forcing and permission clauses, with linear data relations). Check B per operation is "Inv(s) ∧ request ⇒ ∃ response. clauses ∧ Inv(s′)". It is asked as the negation, either with all response variables universally quantified ("quant"), or with the finite response tags enumerated and only the Int return value quantified ("enum"). Check A is the plain conjunction (consistency). Script: `scratchpad/d4_trial/trial.py`.
  - **Cost.** 40 operations × (40 + 6) clauses: whole-spec feasibility took **1.32 s** ("enum", about 0.033 s per operation) or 0.34–0.74 s ("quant"); consistency took 0.13 s. 10 × 16: 0.22 s. 20 × 26: 0.49 s. 40 × 26: 0.99 s.
  - **Solver incompleteness.** "quant" returned **unknown on 1 of 40** operations in one run. "enum" returned no unknowns.
  - **Injected defects.** (D1) "an op on a cancelled handle must succeed and consume quota", and (D2) "success forced while `val < arg` and `val = used + arg·c`". Both passed plain consistency (sat) and were flagged infeasible by check B in 0.005–0.027 s, with a concrete counterexample state. Deletion-based minimisation took about 0.6 s: D1's core was 1 named clause (it conflicts with the post-state invariant `used + du ≤ quota`), and D2's core was 3 clauses.
  - **Anecdote, n = 1 author.** The clause generator, written to be conflict-free "by construction", contained three unintended conflicts that check B found and plain consistency passed for all operations. Two were pairwise: "profile error" vs "cancellation in progress", and "quota exhausted" vs "profile error". One involved three clauses: quota vs profile vs fault, each allowing a different error code with an empty intersection. These are error-precedence conflicts typical of failure-category tables. A c = 2 subset check (RE 2019 setting) would miss the 3-clause one (*Inference*).
  - Limits: synthetic, author-written; linear integer arithmetic and arrays only; no sets, sequences or quantified "for all handles" invariants (the invariant is instantiated at the requested handle only); no interleaved invoke/return; no reachability confirmation of counterexample states.

### Inferences
- *Inference (theory, from Gacek Theorem 1 plus the Event-B DLF/FIS shape).* If an invariant Inv holds initially and the one-step check "∀s, i. Inv(s) ∧ A(s, i) ⇒ ∃s′. G(s, i, s′) ∧ Inv(s′)" is valid, then every Inv-state is viable, so the contract is realizable. This is Gacek's under-approximating "extend" direction at k = 0. A failure may be spurious when Inv admits unreachable states (Hallerstede & Leuschel say the same about DLN). A failure is confirmed by a bounded reachability check (Gacek's base check; TLC/Apalache). So the one-step check is the right *first* gate, and bounded model checking is the confirmation step, not the reverse.
- *Inference.* For an API, the environment move is "a caller issues request r of operation k (or an out-of-band actor or fault acts)". The universal quantifier distributes over operations, so the whole-spec check is **exactly** the conjunction of per-operation checks. No partitioning heuristic is needed, and the only coupling is the shared invariant. This is why the earlier concern about mode variables (FRET-style partitioning by shared variables) does not arise for the one-step form; see Q2.
- *Inference.* Environment actions without a system response (fault injection, out-of-band delete, cancellation request) need a separate PO, "every environment action preserves Inv", analogous to Event-B INV. Without it, a fault can drive the state outside Inv, and later response-existence checks become vacuous for exactly the post-fault states.
- *Inference.* rt-consistency remains useful for timed requirement patterns (timeouts, "within t"). As implemented, though, it checks that the *conjunction* can always be extended, not that the *system* can answer every *environment* input. It can therefore miss the Gacek-type failures where a clause pins an output that only a cooperative environment avoids (e.g. a cancel input arriving with a fault input). Treat it as a timing-consistency gate, not a response-existence gate.
- *Inference.* Full temporal realizability (Kind 2/JKind, Spectra, Boolean abstraction, TSL) is needed only for clauses whose obligations span steps (eventual completion, termination under a timeout assumption). For the instant-level and transition-level forms of a store API, the one-step check carries the load.

### Gaps
- No source applies response-existence (FIS/DLF/realizability) to a **library or storage API behaviour spec**. The nearest are an Event-B file-system model (FMCH02, 9 events) and a BPEL process, both analogous.
- Interface automata full text [unreachable]; no API application read.
- Machine closure (Abadi–Lamport) not researched: no full text fetched.
- TLC's official semantics for `ENABLED` in invariants: only community threads (C).
- No neutral (non-TA) benchmark for any of these checkers. All efficacy figures are author-reported.
- Concurrency with interval operations (separate invoke/return): no source measures response-existence checks over pending-operation state.

## Q2. Mode variables without losing locality, and cost at tens of operations × tens of clauses

### Takeaway
Three evidenced ways keep mode-heavy specs local. First, **decompose by environment move** (per event or operation), so mode variables are read-only context, not connectors (Event-B POs per event; ProB; own trial). Second, **slice by a mode predicate of interest** (ProB: events that cannot fire under P are filtered out, giving better decomposition). Third, **make modes first-class** with an exhaustiveness ("defensive") check and a mode-reachability graph (CoCoSpec/Kind 2, qualitative). Partitioning by shared variables (FRET's connected components) is the approach that mode variables defeat, and FRET's own fix (study mode-transition logic separately) is unpublished future work. Measured cost for one-step checks at this scale is seconds per model (ProB: 80 events / 855 guards in 1–2.3 s; Gacek: ≤ 1.8 s per component; own trial: 40 × 46 in 1.3 s). By contrast, full rt-consistency or monolithic realizability runs take minutes to hours.

### Cited Findings
- FRET compositional realizability, **FM 2021** (A; FT yes; TA). Decomposition is by "connected components" of a graph whose edges link requirements sharing state variables. Theorem 2 "requires the assumption A to be independent of state". "Our decomposition method returned a single SCC for the LMCPS NN, LMCPS TSM, and the Infusion Manager specifications. One reason that contributed to the unsuccessful decomposition was that requirements were connected through mode variables. In the future, we plan to study whether large mode-related specifications can be analyzed modularly, by studying the mode-transition logic separately from the intra-mode requirements." For GPCA they replaced one 8-valued `Current System Mode` variable with 8 Boolean mode variables, plus added mutual-exclusion requirements (12 → 26 requirements). n = 3 projects; transfer *analogous*; human-only evidence. — [NTRS](https://ntrs.nasa.gov/api/citations/20210015352/downloads/FM2021_CR_Compositional_Realizability_in_FRET%20(6).pdf)
- Hallerstede & Leuschel, TPLP 2011 (A; FT yes; TA). Predicate of interest P plus filtering of events "that can obviously not fire given P (e.g., any event that has Counter=5 in its guard given P = Counter=10)" can "result in a much better decomposition of the formula into independent sub-components". Connected-component partitioning drops sub-formulas unrelated to any guard. The Bosch model has 80 events, 855 guards and 62 variables: 1.07–2.32 s of solving per version. This is the only measured mode-sliced, response-existence-type check at tens-of-operations scale found. Transfer *analogous*. — [arXiv 1109.2015](https://arxiv.org/pdf/1109.2015)
- Champion, Gurfinkel, Kahsai, Tinelli, "CoCoSpec: A Mode-aware Contract Language for Reactive Systems", **SEFM 2016** (A; FT yes; TA). Modes are (require, ensure) pairs. The "defensive" meta-property "G(A ∧ G ∧ ⋀{R_i ⇒ E_i}) ⇒ G(⋁{R_i})" must be valid: "If it does not hold, a situation unspecified by the contract is reachable, hence the contract is incomplete". Deliberate under-specification is to be "formalized explicitly", as a mode with empty ensures. On the NASA TCM autopilot case study (qualitative): "it quickly became impossible for us to trust a contract without examining the mode reachability graph first". The graph revealed "only idle modes would be reachable", unexpected transitions, or "deadlocked states". Compositional analysis proved the Autopilot contract in about 80 s, against a linearised monolithic run that was "inconclusive after running for one hour". That figure is for *verification*, not realizability. n = 1 case study; transfer *analogous*; human-only evidence. — [CoCoSpec PDF](https://homepage.cs.uiowa.edu/~tinelli/classes/5810/Fall20/Papers/Cham16.pdf)
- Gacek et al., NFM 2015 (A; TA). The GPCA infusion-manager conflict is a **mode × input** conflict: modes 0/1 force flow 0, while an alarm input forces the KVO rate. The plain AGREE consistency check missed it; one-step realizability found it in 0.2 s at depth 1. — [arXiv 1502.03005](https://arxiv.org/pdf/1502.03005)
- Rodríguez & Sánchez, CAV 2023 (A; TA). Literals are Booleanised per "cluster" of literals sharing no variables, at a cost doubly exponential in the cluster's literal count in the worst case. The evaluated clusters hold 2–7 (Fig. 3 up to 12) literals. — [arXiv 2310.17292](https://arxiv.org/pdf/2310.17292)
- Langenfeld et al., RE 2019 (A; TA). Full rt-consistency over the parallel composition is exponential in the number of automata, hence c-subsets with c = 2. Full Bosch runs took 48 s to 4h14m (figures from the verified edition, V5-05/06). — [RE 2019](https://people.irisa.fr/Nicolas.Markey/PDF/Papers/re2019-LDWHP.pdf)
- Own trial (own trial; *inference*): all 40 operations share lifecycle, profile, handle state and quota. A shared-variable partition would therefore give one component, yet the per-operation checks stayed at about 0.03 s each, and whole-spec cost grew roughly linearly in the number of operations (10 → 40 ops: 0.22 → 0.99 s at fixed clause density). Script `scratchpad/d4_trial/trial.py`.

### Inferences
- *Inference.* Mode variables defeat **variable-sharing partitions** (FRET, Boolean-abstraction clusters, ReqAnalyzer subsets). They do not defeat **move-indexed decomposition**, because each one-step obligation is posed per environment move with the full mode state as a free (universally quantified, invariant-constrained) context. Cost then scales with (number of operations) × (solver time for one operation's clauses plus shared clauses), and mode variables enlarge only the per-check formula.
- *Inference.* Per-mode slicing (ProB's predicate of interest) is the second lever. Run the per-operation check once per mode cell of interest (lifecycle phase × profile) when a single check times out or returns unknown. This also makes counterexamples readable, as CoCoSpec's mode-level blame assignment argues qualitatively.
- *Inference.* The FRET future-work idea (mode-transition logic separately from intra-mode requirements) corresponds, for a store API, to two checks. (i) The state × operation transition table, i.e. lifecycle/handle typestate, is complete and deterministic where it must be: G3 already has this. (ii) The per-operation, per-mode response existence over data clauses: the new G4a below.
- *Inference.* Locality is lost again for (a) quantified global invariants over all handles (e.g. "no two live handles share a resource"), where ∀∃ alternation inside the solver risks "unknown" (Gacek, FRET and own trial all report unknowns); (b) multi-step obligations (timeouts, eventual completion), which need full realizability or bounded liveness; (c) interval operations with pending state.

### Gaps
- No measured evidence of mode-sliced *realizability* (as opposed to deadlock checking) at tens × tens on an API.
- The FRET mode-transition/intra-mode split is announced, not published (searched; none found).
- No study measures false-alarm rates of invariant-relative one-step checks (unreachable counterexample states) on realistic specs. ProB notes the issue but gives no rate.
- Cost figures for quantified global invariants over handle collections were not found or measured.

## Q3. Mapping to the verified edition's T2 gates (§2.2, G4) and check map (§3): what changes

### Takeaway
The verified edition's environment-actions cell rests on "rt-consistency / realizability", and its Pipeline B expects hours-long full runs because mode variables connect requirements. The full texts read here support three changes. First, split G4 into a per-operation **response-existence gate (G4a)** relative to an inductive invariant, plus a confirmation step (bounded reachability) and full realizability only for multi-step clauses. Second, relabel rt-consistency as a timing-consistency check without an input/output split. Third, downgrade "mode variables force hours-long full runs" to "they defeat variable-sharing partitions; move-indexed decomposition stays local". Everything below is *inference* that maps analogous evidence onto a store API.

### Cited Findings (baseline text quoted verbatim before each qualification)

## Self-check
- **Possible misreading of the brief.** The brief asks for alternatives to GR(1) realizability. This track argues the one-step (invariant-relative) form is enough for most store-API forms. That is a reframing, *Inference*, resting on Gacek's viability theorem. It holds for safety contracts with an inductive invariant, not for multi-step obligations. Readers should not take G4a as replacing realizability for timeout and termination forms.
- **Possible misreading of a source (RE 2019).** I read the future-work sentence as meaning the 2019 rt-consistency has no input/output split. The sentence actually ties the split to test generation and "completeness analysis that detects missing treatment of input observable ranges", not to rt-consistency itself. The definition in the paper reads, verbatim: "A set of requirements is rt-inconsistent if and only if there exists a finite prefix of an interpretation (modelling a system computation) such that there does not exist any extension of this prefix which satisfies all requirements in the set". Both prefix and extension range over *all* observables, so the extension may rely on the environment cooperating. The definition makes no environment/system split, so the conclusion stands (*Inference*: rt-consistency neither implies nor is implied by realizability). Still, the original FASE 2011 definition was not read.
- **Possible misreading (Gacek).** "Base check depth ≤ 1" describes these 20 contracts, not a general bound. I use it only as cost evidence.
- **Hallerstede & Leuschel.** DLF is global deadlock freedom (some event enabled), not per-request response existence. I treat its predicate-of-interest variant as the analogue of per-mode slicing, and its machinery as applicable to per-operation FIS-style checks. That transfer is *Inference*.
