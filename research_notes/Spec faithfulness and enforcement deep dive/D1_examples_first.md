# D1. Examples-first validation against correct ("wheat") and wrong ("chaff") implementations or specs, plus disconfirming search §4(a)

Scope: checking examples, tests or check sets against correct and deliberately wrong implementations or specs; measured results; transfer to temporal, stateful and concurrent behaviour; replication of Cunha & Macedo; rejected alternatives as negatives; evidence that the approach fails or costs too much for behaviour specs.

Conventions. Every finding carries: **grade** (A / A-pre / A-workshop / B / C / D); **FT** (full text read yes/no); **n/setting**; **"correct" meant**; **transfer** (*direct* = library/API behaviour specs, *analogous* = other spec domains, *inference*); **agents** (whether LLMs or agents were measured on this step); **indep.** (source independence). "TA" = tool authors evaluating their own tool. All Brown PLT papers (Wrenn, Krishnamurthi, Prasad, Nelson, Greenman) are TA for Examplar, Forge and PICK. Downloads are in the scratchpad folder `d1/` (not in the repo).

Baseline texts referred to (verbatim, from `reports/Spec faithfulness and enforcement verified.md`):

Mean per-requirement detection: 62 % (N=1), 83 % (N=2), 90 % (N=3), 93.6 % (N=5), counted only over requirements with complete valid suites …"
- B2 (§2.1 check list): "2. **Rejected-option refutation**: the distinguishing behaviour of each rejected option must be refused. Analogue: negatives; mutant rejection. No source uses rejected alternatives as negatives; that mapping is *Inference*."

## Q1. Wheats and chaffs: Examplar and follow-ups, Forge `example`/`test expect`, Alloy4Fun follow-ups, similar methods

### Takeaway
Wheat/chaff checking has a well-documented ten-year line in programming education (Brown PLT). It splits a check set's quality into **validity**: the suite accepts every wheat, and with several wheats every allowed variant. It also measures **thoroughness**: the share of chaffs rejected, where chaffs encode *conceptual misreadings*, not syntactic mutants. That is the same pair the baseline calls positive and negative checks. The line's most important result for this project is the measured danger of a **single** wheat: tests that over-fit one correct implementation pass it and are wrongly trusted. Forge carries the mechanism into Alloy-style specs, but only with one wheat, no chaffs in the evaluated course, and **no `example` support in Temporal Forge**.

### Cited Findings
- **Examplar mechanism (validity and thoroughness).** "A suite is valid if it accepts (i.e., its assertions pass) all correct implementations." Asserting underspecified behaviour is a named form of invalidity: "asserted underspecified behavior (e.g., asserting that a sorting implementation is stable, if that was not specified)". "If the problem specification leaves any behavior underspecified, it is necessary to run suites against multiple correct implementations in order to accurately identify invalidity." The paper's median example uses one wheat that errors on empty input and one that returns 0. "Provided that the set of wheats completely exercises the space of underspecified behaviors permitted by the specification, accepting all wheats guarantees that a suite is valid." Chaffs for examples "should exercise logical misunderstandings that students are likely to make", e.g. mean and mode as chaffs for median. — [Wrenn & Krishnamurthi, ICER 2019](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar/paper.pdf) (DOI 10.1145/3291279.3339416). Grade A; FT yes; n = 67 students in 2018 vs a 2017 cohort; correct = passes instructor wheats/chaffs; transfer *analogous* (deterministic functions); agents: human-only; indep.: TA.
- **Examplar applicability limits, stated by the authors.** Correctness must be "a well-defined, binary property". There was no wheat for the oracle-writing assignment Sortacle: "it is impossible to craft a true wheat". Expressibility fails for floating-point answers. On nondeterminism: "if the wheats and chaffs loaded into Examplar are non-deterministic, Examplar may provide students with differing feedback between runs … The allowance of non-determinism should therefore be realized by loading Examplar with multiple wheats that differ in their behavior, but are individually deterministic." — [ICER 2019 §9](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar/paper.pdf). Same grade and flags.
- **Who tests the testers: single vs multiple wheats.** The paper names "over-zealous" tests, which are "overly liberal in what they supply for inputs" or "overly conservative in what they accept as outputs". One instructor implementation ("AlgSing") lets over-zealous tests through whenever they happen to match it. Adversarial multiple wheats ("AlgMult") screen them out. Share of student implementations labelled faulty, Axm / AlgSing / AlgMult: DocDiff 34/98/46 %, Nile 35/97/35 %, Filesystem 22/52/26 %, MapReduce 28/89/57 %. Share of student suites trusted, AlgSing → AlgMult: DocDiff 90→81 %, Nile 28→0 %, Filesystem 94→71 %, MapReduce 79→35 %. "For each assignment we constructed between two (for Nile) and seven (for MapReduce) adversarial implementations." The authors explored only four assignments "because constructing multiple adversarial implementations is a potentially time-consuming process". How the wheats should differ: "Different instructor implementations should reflect different scenarios allowed by the specification … might admit more inputs than the specification requires, or might produce outputs that are consistent with the specification in different ways." The same screening should apply to tests from any source: "from colleagues, by crowdsourcing, by the instructors themselves, etc.—should all pass through the same adversarial process". The process also "improved the assignments themselves". — [Wrenn, Krishnamurthi & Fisler, ICER 2018](https://cs.brown.edu/~sk/Publications/Papers/Published/wkf-who-tests-testers/paper.pdf) (DOI 10.1145/3230977.3230999). Grade A; FT yes; n = 4 assignments, 38–91 students each; correct = agreement under the reconciled Axm/AlgMult labelling; transfer *analogous*; agents: human-only; indep.: TA.
- **Examplar applied to formal specs (Forge).** Forge's testing constructs are: `example` ("concrete instances that should satisfy a given formula"); assertions (`is necessary for` / `is sufficient for`); `test expect` blocks ("a given run will be either satisfiable or not", e.g. a non-vacuity check); and suites. Forge can "run all of these testing constructs against hidden known-correct models", and "students receive an instance illustrating the mismatch". Footnote: "We adopt this terminology, although we use only wheats." The course "supplied only one wheat because, from our perspective, models are not overconstrained by implementation details in the same way that programs are". "The example construct is currently only available in Froglet and Relational Forge, not in Temporal Forge." The cause is that partial instances "cannot yet be specified at the per-state granularity in Temporal Forge". — [Nelson et al., Forge, OOPSLA 2024](https://cs.brown.edu/~sk/Publications/Papers/Published/ngp----forge/paper.pdf) (PACMPL 8 OOPSLA1, Art. 116). Grade A; FT yes (testing sections and evaluation); n = 92 (2022) + 64 (2023) students; transfer *analogous*; agents: human-only; indep.: TA.
- **Forge documentation, current.** "The example keyword is not supported in Temporal Forge." The docs also say: "We generally suggest using assertions rather than test-expect blocks if you can do so." — [Forge docs, Testing](https://forge-fm.github.io/forge-documentation/latest/testing-chapter/testing/). Grade C (official tool docs); FT yes (page fetched via the fetch tool, which summarises); transfer *analogous*; indep.: TA/vendor.
- **Examplar inside the IDE (Koli 2020).** The IDE hides the code file behind "Begin Implementation" and shows wheat/chaff feedback on every run. "Of 703 logged run sequences in which students clicked Begin Implementation, 363 (51.64%) clicked Begin Implementation before clicking Run for the first time." Of the 98,932 run intervals that edited tests or code, only 6,883 (6.96 %) edited both. With a new metric (mean implementation-interval thoroughness), "the miit of the median student ranged from 2/5 to 5/6". The instructor told students to catch "most of them" and move on. — [Wrenn & Krishnamurthi, Koli Calling 2020](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-stud-write-test-no-coercion/paper.pdf) (DOI 10.1145/3428029.3428060). Grade A (5-page short paper); FT yes; n ≈ 59–64 students, 17 projects; no control group; transfer *analogous*; agents: human-only; indep.: TA.
- **Mining wheat failures for chaffs (Making Hay, Koli 2022).** The method logs examples that fail the wheats, manually clusters the good-faith failures, and generalises each cluster into a chaff. Contributions: "numerous wheat failures (about 30%) appear to be good-faith efforts based on misunderstandings". The authors collected 1,622 wheat-failing examples (Nile 319, DocDiff 1,303), coded by two coders with Cohen's κ > 0.8. Classsourcing found 17 potential misconceptions in Nile and 11 in DocDiff; the paper says "The experts (course staff) missed most of these". Fig. 2 counts, Nile/DocDiff: classsourced-only 16/9, both 1/2, expert-only 6/3. Classsourcing also "drawn attention to chaffs that seldom arose in practice, one of which had an undiscovered bug". In the Forge U-Tree problem, one chaff "meant to allow asymmetric trees but included a minimal-connectivity constraint that rejected basic asymmetric examples". — [Prasad, Greenman, Nelson, Wrenn & Krishnamurthi, Koli Calling 2022](https://cs.brown.edu/~sk/Publications/Papers/Published/pgnwk-making-hay-wheats/paper.pdf) (DOI 10.1145/3564721.3564726). Grade A; FT yes (two-column extraction garbled; numbers cross-checked against the layout text); n = 2 programming problems + 1 Forge problem (12 wheat failures); transfer *analogous*; agents: human-only; indep.: TA.
- **Conceptual mutation testing (Programming 2024).** This workflow clusters wheat-failing examples ("wfes") semantically by running each against a set of mutants, then turns the clusters into chaffs. Cost: "There were over 4,000 wfes in total. Of these, we analyzed 277 wfes … it represents one month of work from two experts … This is not a task that we can offload to non-experts (such as Mechanical Turk workers)." Noise: "about 70 % of student examples are typos and other low-level mistakes". Outcome: chaffs built from 2020 data and deployed in 2022 put far more wfes into 1- or 2-chaff clusters. DocDiff went from 2.39 % (2020) and 2.33 % (2021) to 23.86 % (2022). Nile went from 0 % and 5.68 % to 10.61 %. Filesystem went from 4.28 % and 4.65 % to 11.73 %. Z-tests were significant except Nile 2021 vs 2020. "Our 2022 methodology reduced chaff suite size without reducing the rates of small-m feature vectors." The authors did not try program synthesis or LLMs for generating chaffs: "Until now, we have not tried to apply program synthesis techniques, whether using formal logic or large language models". — [Prasad, Greenman, Nelson & Krishnamurthi, Programming 8(2) 2024, art. 7](https://cs.brown.edu/~sk/Publications/Papers/Published/pgnk-conceptual-examplar/paper.pdf) (DOI 10.22152/programming-journal.org/2024/8/7). Grade A; FT yes (method, cost and evaluation sections); n = 3 assignments × 3 semesters; transfer *analogous*; agents: not used (explicitly); indep.: TA.
- **Wheat/chaff-style grading of specification predicates (PBT).** Students write `is-valid` predicates (oracles) for relational problems, "those for which an input may admit multiple valid outputs". These are graded by decomposing the property into sub-properties, with one test suite per sub-property. On Toposortacle, "nearly half (46 %, or 91 students) received perfect scores, and the vast majority (over 80 %, 91+70=161 students) missed no more than one subproperty". The most common failure was relying on length instead of vertex identity (the Enforce-Not-Disjoint suite). — [Wrenn, Nelson & Krishnamurthi, Programming 5(3)](https://cs.brown.edu/~sk/Publications/Papers/Published/wnk-use-rel-prob-pbt/paper.pdf). Grade A; FT partly (method and Toposortacle results); transfer *analogous*; agents: human-only; indep.: TA. A follow-up automated this with Hypothesis- and SAT-based generators. The two generators found different errors ("in some rows, Hypothesis found 6, 7, or 12 errors that sat did not; in others, sat found 2 or 4 novel errors"), and "the manual suites still find some errors that automation misses". — [Nelson et al., Programming 6(2) 2022](https://cs.brown.edu/~sk/Publications/Papers/Published/nrsdwk-auto-targ-test-pbt-pred/paper.pdf). Grade A; FT partly (abstract, comparison passages); transfer *analogous*; indep.: TA.
- **Alloy4Fun follow-ups (from the Cunha & Macedo group).** (i) *Synthesizing Test Cases for Narrowing Specification Candidates* generates a test suite that, "once classified by the user as desirable or not, narrows down the set of candidates to at most one specification". The benchmark is 28 Alloy4Fun requirements (3 exercises), with candidate sets of the oracle plus the N−1 most frequent wrong student specs, N = 4…28. "With 28 candidates the median size of |T| for the non-optimal algorithm was 14." The optimal algorithm's time grows "at a cubic rate", the non-optimal at a quadratic rate. Scope 3 appeared "close to ideal". Limitation: the prototype "does not accept the extensions introduced in version 6 of Alloy, namely mutable elements and temporal logic". On their own LLM paper the authors write: "these generated tests are a weak characterization of the requirement and there is no guarantee that they allow a unique formal specification". — [Cunha & Macedo, arXiv 2511.19177](https://arxiv.org/abs/2511.19177). Grade A-pre (no venue found; Crossref lookup found nothing, Semantic Scholar rate-limited); FT yes (evaluation, related work); transfer *analogous* (structural); agents: none; indep.: TA. (ii) History-based Alloy hint generation (FM 2024) and temporal repair for Alloy 6 (SEFM 2022, "two exercises with 38 challenges and totalling 3671 submissions") were found as search leads only — [FM24](https://haslab.github.io/SpecRep/pubs/FM24.pdf), [SEFM22](https://haslab.github.io/SpecRep/pubs/SEFM22.pdf) — **not read** (SEFM22 downloaded, not analysed). The figures come from search extracts.
- **Mutation-based assessment of a test set against chaff-like faulty specs, temporal (μAlloyτ).** See Q3.

### Inferences
- *Inference*: the baseline's "positive / negative checks" are Examplar's "validity / thoroughness", with one difference. Examplar measures validity against wheats; the baseline's spec-blind checks are validated against nothing until the spec exists. **Cunha & Macedo are themselves a single-wheat design.** Their "Valid" metric adds "the oracle specification as a fact to the model, and check[s] if the run command has the expected outcome" ([arXiv 2510.23350 v2 §4](https://arxiv.org/abs/2510.23350), FT yes for these passages). The 88–90 % detection figure (B1) therefore assumes a hidden correct oracle (the wheat) that removed invalid tests first. A real pipeline has no oracle. It needs a wheat substitute, such as reviewed variants of the reference model, or a triage step.
- *Inference*: Forge's argument for one wheat ("models are not overconstrained by implementation details") fits declarative structural predicates, whose semantics is a single relation. It fits an **executable Python reference model** less well, because a reference model must fix every unspecified choice (ordering, error kinds, timing, interleaving). That is exactly the over-zealous-test setting Wrenn et al. measured.

### Gaps
- Wrenn's dissertation (Brown 2022, "Executable Examples…", cited as [Wrenn 2022] in the Forge paper) was not located or read.
- Venue of arXiv 2511.19177 not verified.
- No study was found that quantifies how many wheats suffice, i.e. coverage of the underspecified space. The ICER 2019 guarantee is conditional on wheats that "completely exercise" that space.

## Q2. Measured results: detection of wrong specs or tests, over-strict examples, cost, agent use

### Takeaway
Detection is measured mainly through validity and thoroughness of human-written suites, not through wrong *specs*. Cunha & Macedo and μAlloyτ are the exceptions. The over-strict side is the best-measured part. Single-wheat screening trusted 28–94 % of student suites, against 0–81 % with adversarial wheats. Examplar cut invalid final suites from 30.3 % to 6.7 %. Cost sits in curation: two to seven adversarial wheats per assignment, and one expert-month per 277 analysed wheat failures, about 70 % of which are noise. Agent measurements exist only for spec-level analogues (Cunha & Macedo; PICK with LLM candidates). No study runs LLM-written examples against wheats and chaffs of an *implementation*.

### Cited Findings
- **Validity gains, ICER 2019.** On five comparable assignments, the share of invalid final suites fell from 30.3 % (2017, n = 320) to 6.7 % (2018, n = 269): χ²(1, N = 589) = 52.373, p < 0.01, φ = 0.303, odds ratio 0.16. By form of invalidity, 2017 suites were "12.9 times more likely" to accept "some—but not all—wheats" (the authors read this as "almost certainly asserting underspecified behavior"), 6.1× more likely to fail all wheats, and 1.3× more likely to fail to compile or run. Thoroughness did not decline: 89.2 % vs 91.0 % of final chaffs caught, measured with 57 final chaffs vs 26 Examplar chaffs. Suite size did not change (Welch t = 0.67, p = 0.504). Implementation correctness was "Inconclusive" (63.2 % vs 68.2 %, χ² = 2.94, p = 0.086). Students clicked Run Tests 26,211 times. — [ICER 2019](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar/paper.pdf). Grade A; FT yes; cross-year comparison, not randomised (the authors' threats section); transfer *analogous*; agents: human-only; indep.: TA.
- **Over-strict screening, ICER 2018.** See the Q1 numbers. The headline: on MapReduce, adding student tests screened by a single wheat raised implementations labelled faulty "from 28% … to 89%". Adversarial wheats "reduced the fraction of student test suites trusted for assessing implementations from 79% to 35%". — [ICER 2018](https://cs.brown.edu/~sk/Publications/Papers/Published/wkf-who-tests-testers/paper.pdf). Grade A; FT yes.
- **The wheat itself can be over-strict, and so can a chaff.** In the Forge `river` assignment, students asked whether a solution-state predicate needed the flashlight location: "This was a good critique of our wheat, which was arguably over-constrained." The authors conclude: "It is also vital that a wheat not over-constrain." Ten critiques were received for `river` and five for `memory`. Logs held 760 (river) and 1,168 (memory) runs where student tests disagreed with the wheat. "Roughly 90% of students' submissions for river and memory referenced the wheat." Fewer than 20 students opted into logging. — [Forge OOPSLA 2024 §7.3](https://cs.brown.edu/~sk/Publications/Papers/Published/ngp----forge/paper.pdf). Grade A (formative evaluation, "We do not claim to measure learning efficacy"); FT yes. The buggy U-Tree chaff, which rejected valid instances, is in [Making Hay §5](https://cs.brown.edu/~sk/Publications/Papers/Published/pgnwk-making-hay-wheats/paper.pdf).
- **Users misread invalidity feedback on semi-specified outputs.** From 1,247 assignment-tagged forum posts: 110 concerned unspecified behaviour (58 unspecified inputs, 60 semi-specified outputs). 105 questions cited Examplar invalidity feedback (28 specified, 29 unspecified inputs, 43 semi-specified outputs). "Of the 23 postings to TweeSearch about its semi-specified behavior, 16 explained that they had individually tested every possible ordering—all of which were (correctly) rejected as invalid". "Multiple students mis-attributed the invalidity of their over-constrained tests to unspecified inputs." Hiding the wheat count was "counterproductive". Stated scope limit: the problems "do not involve state or other side-effects". Posts were coded by one person. — [Wrenn & Krishnamurthi, Koli Calling 2021](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar-unspecified/paper.pdf) (DOI 10.1145/3488042.3488072 per PDF). Grade A; FT yes (results, discussion); transfer *analogous*; agents: human-only; indep.: TA.
- **Cost of curation.** Two to seven adversarial wheats per assignment ([ICER 2018](https://cs.brown.edu/~sk/Publications/Papers/Published/wkf-who-tests-testers/paper.pdf)). One month of two experts for 277 of more than 4,000 wheat failures; about 70 % noise ([Programming 2024](https://cs.brown.edu/~sk/Publications/Papers/Published/pgnk-conceptual-examplar/paper.pdf)). Making wheats early has a side benefit: "Providing Examplar instances forced the course staff to finalize the wheats … This process uncovered major issues in four assignments, before they were released to students." ([ICER 2019 §10](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar/paper.pdf)).
- **Agent use, spec level (baseline source, re-read).** Cunha & Macedo state in v2 that the study covers "structural requirements of simple domain models". "Alloy 6 also allows the declarative specification of behavioral requirements using temporal logic. However, our experiment focuses on structural assumptions." Their future work: "We also plan to evaluate the effectiveness of this approach for generating test suites for validating behavioral requirements, namely requirements to be specified with temporal logic." — [arXiv 2510.23350 v2](https://arxiv.org/abs/2510.23350); venue FM 2026, [Springer chapter](https://link.springer.com/chapter/10.1007/978-3-032-26204-2_15) (venue per search result, matching the verified report). Grade A; FT yes (scope, metrics, conclusion re-read); agents: yes (GPT-5 etc.); indep.: the authors also built Alloy4Fun.
- **Agent use, LLM-generated candidates checked through user-classified distinguishing scenarios (PICK).** PICK generates several candidates instead of one and uses "formal language containment properties to generate distinguishing concrete scenarios", which users rate. It ran on Prolific with 50 participants per condition, in three domains: regex, ABAC, LTL. Classifying scenarios "significantly improves user accuracy across regexes and access-control policies". PICK users were "2-4 times as likely" to eliminate all candidates on ABAC; the authors read this as surfacing "no solution" instead of a subtly wrong one. — [Prasad, Austen, Fisler & Krishnamurthi, ECOOP 2026](https://www.siddharthaprasad.com/papers/pafk-pick.pdf) (DOI 10.4230/LIPIcs.ECOOP.2026.7 per PDF). Grade A; FT yes (method, studies, threats); transfer *analogous*; agents: LLM-generated candidates for regex and ABAC; the LTL candidates were human-sourced; indep.: TA.
- **Agent-generated chaffs, adjacent lead.** GPT-4o-generated buggy submissions for intro exercises are "not significantly different from real student data with regard to test case failure distributions" (8,598 real submissions, 2,405 incorrect). — [Leinonen et al., arXiv 2411.10455](https://arxiv.org/abs/2411.10455). Grade A-pre (venue not verified); FT partly (abstract, data, conclusion); transfer *inference* for chaff generation, since it matches failure distributions, not misconceptions; agents: yes; indep.: independent of Brown.

### Inferences
- *Inference*: B4's "about 4 % wrong generated tests" was measured *after* oracle screening, and the oracle is a single wheat. Where the spec leaves behaviour open (the not-promised items of B3), a single-wheat screen lets over-strict checks through. ICER 2018 is the measured case: single-wheat trust of 28–94 % against multi-wheat trust of 0–81 % of suites. For a behavioural API with allowed variants, the share of over-strict record-derived checks is therefore not bounded by 4 %. It is observable only with several allowed variants.
- *Inference*: "over-strict" has three sources in this literature. Each needs its own control: tests (multiple wheats), wheats (critique channel; Forge), and chaffs (a chaff that rejects valid instances; Making Hay). A pipeline that validates only the check set inherits the other two.

### Gaps
- No study measures LLM- or agent-written *examples* run against wheats and chaffs of an *executable implementation*. [Ashok Kumar & Lan, AAAI AI4ED workshop, arXiv 2402.07081](https://arxiv.org/abs/2402.07081) generates tests from buggy/correct student-code pairs (grade A-workshop); only its abstract was read, so it is a lead only.
- No head-to-head comparison of chaff sources (human, mined, LLM) on detection of *spec* misreadings.

## Q3. Transfer to behaviour specs (temporal, stateful, concurrent); allowed-variant and forbidden-variant checks; multiple wheats

### Takeaway
The mechanism is defined generally. The allowed-variant check is literally "accept every wheat"; the forbidden-variant check is "reject each chaff". Multiple wheats as allowed variants is measured, but only for deterministic functional programs with under-specified inputs and outputs. For temporal behaviour there are three measured analogues: (a) classifying distinguishing traces among candidate LTL formulas (PICK); (b) oracle-derived mutant-killing tests against real faulty temporal Alloy specs (μAlloyτ, about 91 % detection, about 67 tests per exercise); (c) positive and negative scenario induction of LTS behaviour models (QSM). No source measures examples-first validation of a *stateful or concurrent API* spec. Tooling for temporal *examples* is missing even in Forge.

### Cited Findings
- **Allowed-variant check = accept all wheats; forbidden-variant check = reject each chaff** — definitions in [ICER 2019 §3](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar/paper.pdf) and the adversarial-wheat design in [ICER 2018 §5](https://cs.brown.edu/~sk/Publications/Papers/Published/wkf-who-tests-testers/paper.pdf). Evidence on several wheats: Q1/Q2 numbers. Transfer *analogous* (deterministic, side-effect-free functions).
- **Nondeterminism must be realised as several deterministic wheats**, or feedback becomes flaky ([ICER 2019 §9](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar/paper.pdf)). The Koli 2021 problems "do not involve state or other side-effects", and the authors write that removing that restriction "makes 'automated taing' much harder" ([Koli 2021 §7](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar-unspecified/paper.pdf)).
- **Temporal Forge has no `example`.** Students shifted to `test expect`: "Students tended to favor test expect far more on their midterm and final projects; in the latter case, it may be because example was unsupported in Temporal Forge" ([Forge OOPSLA 2024 §7.3.3](https://cs.brown.edu/~sk/Publications/Papers/Published/ngp----forge/paper.pdf); [docs](https://forge-fm.github.io/forge-documentation/latest/testing-chapter/testing/)). Students also raised "concerns about the conceptual load of infinite traces" (same paper, §7.1).
- **Distinguishing traces for LTL (PICK).** Candidate formulas were taken from earlier misconception studies, where LTL-trained participants wrote them. Traces were sampled from set differences using Spot. Crowd novices with no assumed LTL knowledge classified traces and never saw formulas. On RedOnce, novices beat both earlier studies (Fisher p < 0.001, OR ≈ 6.3). Pooled: "novices achieved 56.0% (84/150), compared to 43.3% (104/240) in P23 and 44.0% (59/134) in FM24", which is non-inferior at a 10-point margin. On candidate elimination, accepting at one vote made "large percentages of participants" eliminate all candidates; a threshold of two cut this by "an average of 27% … with a min of 4% and a max of 52%". — [PICK, ECOOP 2026 §4.4](https://www.siddharthaprasad.com/papers/pafk-pick.pdf). Grade A; FT yes; n = 150 novice responses (3 problems × 50) vs public data from two earlier studies (non-randomised, historical control); correct = matches the ground-truth formula; transfer *analogous* (propositional LTL over three lights); agents: candidates human-sourced, so the LTL arm is human-only; indep.: TA.
- **Classifying traces is easier than writing formulas.** "Trace Matching was the easiest question across the board and Write Formulas was the hardest; even the FTAI respondents submitted a fair number of incorrect formulas." The paper reports "several mistakes, even among experts". — [Greenman et al., FM 2024, LTL misconceptions](https://cs.brown.edu/~sk/Publications/Papers/Published/gpdzdkmnz-miscon-finite-infinite-ltl/paper.pdf). Grade A; FT partly (abstract, results summary); five survey deployments over three years; transfer *analogous*; agents: human-only; indep.: partly TA (same group).
- **Mutation-based test sets against real faulty *temporal* specs (μAlloyτ).** Benchmark: the two temporal Alloy4Fun models (Trash, Train), 3,669 submissions over 37 exercises, deduplicated to 2,307 + 683 faulty models. The tests kill all non-equivalent mutants of the *oracle*, so they are spec-derived, not spec-blind. "The 'Grouping' configuration detects 62% or more of the fault submissions per exercise and averages a detection rate of 89.75% for the trash exercises, 84.3% for the train exercises for a combined average of 87.24%." Overall, "μAlloyτ is able to detect 90.8%" of faulty submissions, and the "Combined" configuration reaches 90.97 %. One exercise (train12) detected neither of its 2 faults. This "generates on average 67.3 tests: 26.65 tests on average for the trash exercises and 115.12 tests on average for the train exercises", in 40.7 s on average. Caveat in the paper: "These test cases do [need] a human to provide the oracle". Threat: results "may not generalize to faulty models made by expert users". — [Jovanovic & Sullivan, MODELS 2023](https://scopelabuta.github.io/files/Models2023-B.pdf). Grade A; FT yes (evaluation); correct = differs from the Alloy4Fun oracle; transfer *analogous* (temporal, first-order); agents: none; indep.: TA, but a different group from Cunha & Macedo.
- **Positive and negative scenarios for behaviour models (QSM/ISIS).** A DFA/LTS is induced from end-user positive and negative MSC scenarios, plus generated "scenario queries" the user classifies. On three textbook RE case studies with a simulated perfect oracle, the counts of accepted Q+ and rejected Q− queries for RPNI vs blue-fringe were: Mine Pump 1/30 vs 1/4; Train 4/83 vs 5/5; Phone 5/172 vs 6/17. RPNI missed the target or produced unauthorized paths on Mine Pump and Phone; blue-fringe found the target in all three. "The number of rejected scenarios tends to be much larger on these test cases than the number of accepted ones. This observation confirms the usefulness of scenario queries." Domain knowledge (fluents, goals) cut the number of queries. On synthetic data at 3 % training, QSM-blue-fringe reached 95 % classification accuracy vs 67 % for plain blue-fringe. — [Dupont, Lambeau, Damas & van Lamsweerde, Applied AI 22 (2008)](https://webperso.info.ucl.ac.be/~pdupont/pdupont/pdf/QSM_AAI_08.pdf). Grade A; FT partly (abstract, method, §6 tables); transfer *analogous* (behaviour models, LTS); agents: none (oracle simulated); indep.: TA.

### Inferences
- *Inference (supports B3, with a qualification)*: B3's "A *deliberately not promised* item needs two witnesses with different outcomes" is what Examplar's multiple wheats implement, and ICER 2018 measures the benefit. B3's "one positive per allowed outcome" works **against the spec**, as a satisfiability check: Alloy-style `run … expect 1`, Forge `test expect … is sat`. It does **not** work against an executable reference model as concrete expected values. A deterministic Python reference model realises one allowed outcome. Each concrete positive for another outcome fails, as in the TweeSearch case where every ordering was "(correctly) rejected as invalid". Positives on semi-specified outputs that run against the reference model must be written as membership predicates (relations, as in the relational-PBT papers). Separate reference-model variants (wheats) must realise the other allowed outcomes.
- *Inference*: for concurrent or interleaving behaviour, ICER 2019's rule (deterministic wheats only) means each allowed schedule or interleaving choice becomes a separate deterministic wheat, e.g. a fixed scheduler seed or a fixed resolution policy. The variant count can grow quickly. No source measures this.
- *Inference*: on the forbidden-variant side, behaviour evidence points to *candidate-differencing* (PICK, narrowing, μAlloyτ, QSM queries) more than free-form example writing. Scenarios are generated from differences between a correct reading and plausible wrong readings, then classified. This fits rejected options (Q5): each rejected option is a candidate whose distinguishing traces must be refused.
- *Inference*: μAlloyτ needed about 67 tests on average (up to about 115 per Train exercise) for about 91 % detection on temporal specs. Cunha & Macedo needed 6 tests per requirement for about 88–90 % on structural ones. The settings differ (oracle-derived vs NL-derived, exhaustive mutant-killing vs targeted), so this is no measured cost ratio. It does suggest temporal faults need many more distinguishing cases.

### Gaps
- No study on wheat/chaff validation of stateful API specs, of Hypothesis `RuleBasedStateMachine` examples, of Quint `run` tests, or of TLA+ trace examples as a validation instrument. A dedicated search found none; tutorials only.
- No measurement of how many wheats a temporal or concurrent spec needs.
- Wheat/chaff validation of trace-level examples in Electrum or Alloy 6 classrooms: none found.

## Q4. Replication of Cunha & Macedo, or a measured equivalent, in a behavioural domain

### Takeaway
**No replication exists** as of this search (2026-10-29). The authors list temporal requirements as future work, and their own follow-up tool excludes Alloy 6 temporal operators. The nearest measured equivalents in a behavioural domain differ in key respects. μAlloyτ is temporal but oracle-derived. PICK covers LTL with human-sourced candidates and trace classification, not spec-blind test writing. QSM uses LTS scenarios with a simulated oracle.

### Cited Findings
- Future work, not done: "We also plan to evaluate the effectiveness of this approach for generating test suites for validating behavioral requirements, namely requirements to be specified with temporal logic." — [Cunha & Macedo v2](https://arxiv.org/abs/2510.23350). Grade A; FT yes.
- The narrowing prototype "does not accept … mutable elements and temporal logic" — [arXiv 2511.19177](https://arxiv.org/abs/2511.19177). Grade A-pre; FT yes.
- A targeted search for LLM-generated test cases for Alloy 6 or temporal requirements returned only these papers, μAlloyτ, and an LLM Alloy-repair study ([arXiv 2404.11050](https://arxiv.org/abs/2404.11050), not read). — search, 2026-10-29 (leads only).
- Measured equivalents: μAlloyτ (90.8 % of 2,990 temporal faulty student models; spec-derived tests); PICK LTL (56 % vs 43–44 %); QSM (Q3).
- Data for a replication exists. The two temporal Alloy4Fun models (Trash, Train) with 3,669 submissions over 37 exercises are public and were used by μAlloyτ ([MODELS 2023](https://scopelabuta.github.io/files/Models2023-B.pdf)).

### Inferences
- *Inference*: a direct replication is cheap and well defined. Rerun the Cunha & Macedo protocol (NL requirement + domain model → N positive and N negative *traces*) on the Trash and Train exercises, and compare detection with μAlloyτ's oracle-derived 90.8 %. This would be the single most useful new measurement for the baseline's core mechanism. It is still structural-to-temporal Alloy, not an API.
- *Inference*: until then, B5's R1 rests for behaviour specs on analogues only. The transfer label stays *analogous* at best.

### Gaps
- Only one source family (Cunha & Macedo) measures spec-blind NL→test generation against wrong specs. This sub-question has a single-source answer.

## Q5. Rejected alternatives as negatives (ADRs, design rationale, QOC/IBIS, negative requirements, misuse cases)

### Takeaway
I found **no study** that derives negative tests from documented design alternatives or decision records and measures the result. This confirms B2 and B5-R2 ("inference (no source does this)") and does not challenge them. The nearest measured analogues use *plausible alternative readings* as negatives: conceptual chaffs, candidate differencing, negative scenarios. Misuse-case test generation exists, but I did not read it in full.

### Cited Findings
- No source: searches on ADR/rejected-alternative negative tests returned only practitioner posts ([DEV Community post](https://dev.to/masondelan/record-why-an-approach-was-rejected-and-when-to-revisit-it-20op), grade D, FT no). Searches on misuse-case or "shall not" studies returned leads only: Misuse Case Programming (Limerick; [listing](https://pure.ul.ie/en/publications/a-natural-language-programming-approach-for-requirements-based-se/)), Boise State misuse-case test models ([listing](https://scholarworks.boisestate.edu/cs_facpubs/128)), all **not read**.
- **Closest analogue: chaffs as misreadings.** Chaffs "should exercise logical misunderstandings", e.g. mean for median ([ICER 2019](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar/paper.pdf)). In the 2024 workflow, mutants are built from "an English sentence that describes a characteristic … observe or invent ways that students can misunderstand the characteristic … and create a mutant that reflects the misunderstanding" ([Programming 2024 §10.5](https://cs.brown.edu/~sk/Publications/Papers/Published/pgnk-conceptual-examplar/paper.pdf)). Grade A; transfer *inference* to rejected options.
- **Closest analogue: alternative readings as candidates.** PICK's candidates are alternative readings of one prompt (day-month vs month-day in the date example). The scenarios that distinguish them are what users classify ([ECOOP 2026](https://www.siddharthaprasad.com/papers/pafk-pick.pdf)). Narrowing does the same with the most frequent wrong student specs as candidates ([arXiv 2511.19177](https://arxiv.org/abs/2511.19177)).
- **Closest analogue: negative scenarios in behaviour models.** "A negative scenario captures a behavior that may not occur." Rejected queries outnumbered accepted ones in all three case studies (Q3) ([QSM 2008](https://webperso.info.ucl.ac.be/~pdupont/pdupont/pdf/QSM_AAI_08.pdf)).
- **Caveat from the expert-vs-data comparison.** Expert-designed chaffs predicted misconceptions that never occurred (expert-only 6 in Nile, 3 in DocDiff) and missed most observed ones ([Making Hay](https://cs.brown.edu/~sk/Publications/Papers/Published/pgnwk-making-hay-wheats/paper.pdf)).

### Inferences
- *Inference (qualifies B2/R2, does not challenge them)*: a documented rejected option is an *expert-designed chaff*. Making Hay predicts two things. Rejected options will cover misreadings the decision-makers anticipated. They will miss misreadings that only show up in practice, here as agent or spec-writer misreadings. Some will never be triggered, like the expert-only chaffs. Rejected-option negatives therefore complement other negatives and should not be the only source. They should be supplemented by negatives mined from check failures (classsourcing analogue: mine record-check failures of the spec writer or agent).
- *Inference*: Examplar's chaff design rule ("favor logical errors over programming errors", per Making Hay §1) fits rejected options well. A rejected option is by definition a coherent alternative design, i.e. a "logical" variant, which suits a forbidden-variant check: some check must fail on each rejected-option variant.
- *Inference*: B5's overturn criterion for R2 ("Rejected-option negatives mostly duplicating positive-scenario failures, or mostly over-strict") can be operationalised with Wrenn-style measures. Thoroughness gain is the share of rejected-option chaffs killed only by rejected-option checks. Over-strictness is the share of rejected-option checks that fail some allowed-variant wheat.

### Gaps
- No empirical study of negative tests derived from ADRs, QOC, IBIS or design-rationale records. The baseline's mapping remains *Inference*.
- Misuse-case-derived test studies were not read; their detection numbers are unknown here.

## Q6. Disconfirming §4(a): evidence that examples-first validation fails, or costs too much, for behaviour specs

### Takeaway
There is no direct evidence that the approach *fails* for behaviour specs, because no one has measured it there. There is concrete evidence of **cost and fragility**, which grows with under-specification and with temporal expressiveness. Curation costs are large: about 70 % of failures are noise, one expert-month per 277 failures, and up to seven wheats per assignment. Wheats and chaffs themselves can be wrong. Over-incentivised example writing may cost implementation time. Users misattribute invalidity on semi-specified outputs. Mainstream tooling lacks temporal examples (Forge). Accuracy in temporal domains stays modest even with tool support (PICK LTL 56 %).

### Cited Findings
- **Cost:** see Q2 (two to seven wheats; one month of two experts per 277 wfes; ~70 % noise; not offloadable to non-experts). Grade A; TA.
- **Possible harm to implementations:** in FileSystem, implementation correctness "declined precipitously in 2018"; the authors "believe Examplar may have monopolized students' time with test development" (with half the time allotted, a confound). On chaff count: "Too few, and students may prematurely conclude that they are 'done' … Too many, and students may divert too much time". — [ICER 2019 §11](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar/paper.pdf). Grade A.
- **Fragility on semi-specified outputs:** students tested all orderings; 16 of 23 TweeSearch posts; misattribution ([Koli 2021](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar-unspecified/paper.pdf)).
- **Wrong wheats and chaffs:** an over-constrained Forge wheat ([OOPSLA 2024](https://cs.brown.edu/~sk/Publications/Papers/Published/ngp----forge/paper.pdf)); a buggy U-Tree chaff ([Koli 2022](https://cs.brown.edu/~sk/Publications/Papers/Published/pgnwk-making-hay-wheats/paper.pdf)).
- **Tooling gap for temporal examples:** `example` is unsupported in Temporal Forge (2024 paper and current docs). The Alloy narrowing prototype excludes temporal logic. μAlloyτ needed about 67 tests per exercise (up to about 115 per Train exercise), each needing a human oracle decision.
- **Modest accuracy in temporal tasks:** PICK novices 56 % pooled on three small LTL problems; RedOnOff and RedBlue were not significant vs earlier studies ([ECOOP 2026](https://www.siddharthaprasad.com/papers/pafk-pick.pdf)). LTL formula writing is hardest even for experts ([FM 2024](https://cs.brown.edu/~sk/Publications/Papers/Published/gpdzdkmnz-miscon-finite-infinite-ltl/paper.pdf)).
- **Examples overfitting and gaming:** "it might be an attempt to game the system with a nonsense example that trivially catches all the chaffs" ([Making Hay §1](https://cs.brown.edu/~sk/Publications/Papers/Published/pgnwk-making-hay-wheats/paper.pdf)). Examplar hides wheat outputs because "a student may be overly tempted to intentionally write failing assertions to discover what the behavior of wheats is" ([ICER 2019 §4](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar/paper.pdf)). *Inference*: an agent with access to the reference model can do the same unless information flow is restricted (cf. D5).
- **Oracle problems:** where correctness is not binary (oracle-writing assignments), "it is impossible to craft a true wheat" ([ICER 2019 §9](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-examplar/paper.pdf)). In Koli 2020, oracle-writing assignments without validity/thoroughness feedback "uniformly involved fewer-than-typical implementation and testing intervals" ([Koli 2020](https://cs.brown.edu/~sk/Publications/Papers/Published/wk-stud-write-test-no-coercion/paper.pdf)).

### Inferences
- *Inference*: the costs scale with the size of the allowed-variant space (wheats) and the misreading space (chaffs). Both are larger for behaviour specs than for the deterministic functions studied: more unspecified orderings, error choices and interleavings. So disconfirming §4(a) finds *cost risk*, not refutation.
- *Inference*: the observed noise rate (~70 % of human wheat failures are typos and similar) is a human phenomenon and probably lower for agents. Agents add the gaming risk if they can query the wheat.

### Gaps
- No measured failure of examples-first validation on a stateful or concurrent spec, because no measurement exists in either direction.
- No cost data for building allowed-variant wheats for a stateful API.
