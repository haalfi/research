## Extension points: adding tools, MCP servers, skills, plugins, agents and workflows without touching the core

### Takeaway
Current harnesses add capability through declarative, file-based packages. A plugin is a directory with a manifest, and a marketplace is a git repo with a `marketplace.json`. These packages bundle skills, subagents, hooks and MCP servers, and they install at user, project or org scope without any change to the core loop. Claude Code's plugin and marketplace system is the most fully documented example. Agent Skills (an open standard since December 2025), GitHub Copilot custom agents and the MCP Registry follow the same "drop-in package plus catalog" pattern.

### Cited Findings
- **Established.** A Claude Code marketplace is "a directory or repository with a `.claude-plugin/marketplace.json` file that lists your plugins and where to fetch each one". It can be private, can list any number of plugins, and "an administrator can require it on every machine". Plugin sources can be a relative path, `github`, `git-subdir` (monorepo), `url`, `archive` (zip over HTTPS), `npm`, or `command`. Git sources can be pinned to a `ref` or `sha`. — [Claude Code: Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)
- **Established.** Plugins carry hooks, monitors, mods (JavaScript running inside Claude Code), MCP and LSP servers, a `bin/` directory added to the Bash `PATH`, and skills, commands and agents that "enter Claude's context as instructions". — [Claude Code: Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- **Established.** Marketplaces support a `claude plugin validate` CI-style check, plugin dependencies or "bundle" plugins, and `relevance` signals so the harness suggests a plugin when a project matches. — [Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces); [Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org)
- **Established.** Agent Skills (published 2025-10-16) are "organized folders of instructions, scripts, and resources that agents can discover and load dynamically": a directory with a `SKILL.md` that has `name` and `description` YAML frontmatter. Progressive disclosure is "the core design principle that makes Agent Skills flexible and scalable". Only the metadata is loaded at startup, and the body and extra files load when they are relevant. An update dated 2025-12-18 says Anthropic "published Agent Skills as an open standard for cross-platform portability". — [Anthropic Engineering: Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- **Established.** GitHub Copilot custom agents are "specialized versions of the Copilot agent that you tailor to particular tasks and workflows". Each is defined as a Markdown profile with YAML frontmatter that can restrict tools and "can also configure MCP servers for that agent". Profiles "can be shared at repository, organization, and enterprise levels", and the Copilot CLI also supports personal profiles. Precedence "depend[s] on the environment" and is documented in a separate reference that was not read. — [GitHub Docs: About custom agents](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-custom-agents)
- **Established.** The MCP Registry (preview announced 2025-09-08) is "an open catalog and API for publicly available MCP servers", backed by an open-source OpenAPI spec. Anyone can build a compatible **sub-registry**. Public client "marketplaces" can augment upstream data, and enterprises with strict requirements get "a single upstream data source they can build upon" for private registries. Moderation works by denylisting, and the preview "does not provide data durability guarantees". — [MCP blog: Introducing the MCP Registry](https://blog.modelcontextprotocol.io/posts/2025-09-08-mcp-registry-preview/)
- **Established (vendor case).** Spotify exposes Backstage (its internal developer portal) capabilities "as MCP servers and CLI tools" so that Claude can look up component owners, read docs and contact teams. Here the existing internal tool catalog became the agent's tool catalog. — [Spotify Engineering, 2026-06-03](https://engineering.atspotify.com/2026/6/code-with-claude-coding-is-no-longer-the-constraint)
- **Lead only (search summary; primary source Unreachable).** OpenAI AgentKit (October 2025) includes an Agent Builder and a Connector Registry for central admin of connectors. The announcement returned 403. — [OpenAI: Introducing AgentKit](https://openai.com/index/introducing-agentkit/) (Unreachable)

### Inferences
- **Inference.** The core stays unchanged because extension is data, not code: manifests, Markdown instructions and MCP endpoints. In practice the "plugin API" of an agent harness is a file layout plus a protocol (MCP). That explains why teams can add capabilities without a core release.
- **Inference.** Three distribution layers are converging: per-asset formats (`SKILL.md`, agent profile `.md`, MCP server), bundles (plugins), and catalogs (marketplaces, MCP registry and sub-registries). A multi-team framework needs all three.
- **Proposed.** Treat the internal developer portal or tool catalog as the source of the agent tool catalog (the Spotify pattern), rather than keeping a separate MCP inventory.

## Layering: what stays central vs. per team or topic; inheritance and override

### Takeaway
Claude Code documents an explicit layered configuration: managed (org) > command line > project-local > shared project > user. Lists such as permission rules **merge** across layers, while managed keys **lock**. Admin-only switches can restrict lower layers to centrally provided hooks, permission rules, MCP servers and plugins. This maps onto a "central guardrails, team-owned content" split. Model gateway, identity, audit and cost controls sit above the harness. Agent-specific evidence for them is thinner and comes mostly from vendor docs.

### Cited Findings
- **Established.** Precedence, highest first: managed settings, command line (`--settings`), project local (`.claude/settings.local.json`), shared project (`.claude/settings.json`, committed), user (`~/.claude/settings.json`). "Nothing in your own settings files or `--settings` overrides a managed key." — [Claude Code: Settings files and precedence](https://code.claude.com/docs/en/settings)
- **Established.** "When you set the same list key, such as `permissions.allow`, in more than one file, Claude Code combines the lists instead of picking one." Model lists are an exception: a managed `availableModels` is applied as-is. — [Settings](https://code.claude.com/docs/en/settings)
- **Established.** Some security-sensitive keys honor a *stricter* value from a lower scope even over managed settings, for example `disableClaudeAiConnectors: true` and `blockReadsOutsideWorkingDirectories: true` from any scope, and a lower `maxEffortLevel` cap ("the lowest cap applies"). — [Settings: Exceptions to managed settings precedence](https://code.claude.com/docs/en/settings)
- **Established.** Committed project `permissions.allow`, `extraKnownMarketplaces` and most `env` values apply only after a teammate trusts the folder, while `deny` and `ask` rules apply right away. — [Settings](https://code.claude.com/docs/en/settings)
- **Established.** Managed settings are delivered by server-managed settings (claude.ai admin console, or a self-hosted "Claude apps gateway"), MDM or OS policy, or a `managed-settings.json` with a `managed-settings.d/` drop-in directory for splitting policy across teams. By default only the first managed source applies, and `managedSourcesBehavior: "merge"` composes all of them. — [Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org)
- **Established.** Central lock-down keys include `allowManagedHooksOnly`, `allowManagedPermissionRulesOnly`, `strictPluginOnlyCustomization` (blocks skills, agents, hooks and MCP servers from user and project sources, so customization must arrive via plugins), and `disableSideloadFlags`. MCP is governed by `allowedMcpServers` / managed MCP. — [Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org); [Settings](https://code.claude.com/docs/en/settings)
- **Established.** Per-group policy has no dedicated key: "every plugin key applies to every user who receives the settings". Per-group targeting is done by delivering different settings per group (separate MDM profiles, ordered gateway policies, or Enterprise group configs, which "[don't] merge with the organization-wide one"). — [Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org)
- **Established.** Cowork "uses the same agentic architecture that powers Claude Code". It loads connectors, skills and plugins enabled for the claude.ai account and "doesn't read the Claude Code CLI's `~/.claude` directory". Each surface therefore has its own configuration plane even though the harness is shared. — [Claude Docs: Cowork overview](https://claude.com/docs/cowork/overview)
- **Established (vendor case).** Spotify kept central fleet infrastructure ("targeting repositories, opening pull requests, getting reviews, and merging into production") unchanged and swapped only the transformation step for an agent. A thin internal CLI "allows us to seamlessly switch between different agents and LLMs". Shared tooling such as commit tagging, LLM quota management and trace collection is standardized for all task sources. — [Spotify Engineering, Honk Part 1, 2025-11-06](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1)

### Inferences
- **Synthesized.** The managed > project > user stack mirrors established platform-engineering policy layering (org baseline, team overlay, personal preference). The "lists merge, managed locks, stricter-wins for security keys" rules are a concrete instance of "guardrails central, content federated".
- **Proposed.** Central (platform team): core loop and version pinning, identity/SSO, model allowlist and gateway, deny rules, hook allowlist, marketplace allowlist, telemetry export, sandbox defaults. Per team or topic: skills, subagent definitions, project instructions (CLAUDE.md/AGENTS.md), team plugins in an allowlisted marketplace, and allow rules within the central deny envelope.
- **Inference.** Spotify's design, with a stable orchestration layer and the agent as a swappable component behind an internal CLI, is evidence that keeping the core loop vendor-neutral behind an internal interface reduces redesign when models or harnesses change.

### Gaps
- No primary source compared layering models across vendors (Copilot org/enterprise policy vs. Claude managed settings vs. Cursor/others).
- No primary evidence was found on instruction-file inheritance conflicts (org-level vs. repo-level system prompts or AGENTS.md) at scale.

## Shared, versioned assets: registries, versioning, rollout, deprecation, supply-chain trust

### Takeaway
Rollout tooling is maturing. Claude Code supports git ref/SHA pinning, `sha256`-pinned archives, auto-update policy per marketplace, stable/early-access "release channels" via two marketplaces, seed directories for CI and containers, and allow/block lists checked both before download and at session start. Trust remains review-based, though. Plugins run arbitrary code with user privileges, I found no package-signing scheme for plugins or skills, and the MCP Registry is moderated by denylisting. OWASP's 2026 agentic Top 10 names agentic supply chain as a top risk (ASI04).

### Cited Findings
- **Established.** "A Claude Code plugin you install can execute arbitrary code on your machine with your user privileges." Hooks, monitors, MCP and LSP servers and mod processes run outside the sandbox, and permission rules cover only Claude's tool calls. — [Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- **Established.** With auto-update on, "the files you reviewed can change on disk". The built-in trust warning says Anthropic "cannot verify that they will work as intended or that they won't change". — [Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- **Established.** Integrity controls: reserved official and community marketplace names are accepted only from `github.com/anthropics/`, the community catalog pins nearly every plugin to a commit SHA, and `archive` sources can be pinned to a `sha256` digest. Neither page reviewed describes signatures or provenance attestations. — [Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- **Established.** Org controls: the `strictKnownMarketplaces` allowlist (supports `your-org/*` owner wildcards and `hostPattern` for GHES/GitLab) and the `blockedMarketplaces` blocklist apply "before a download" and "again at session start", so a plugin whose source no longer matches doesn't load. `enabledPlugins: false` blocks one plugin from an allowed marketplace, and `disableCommandPluginSources` blocks plugins built by running a command. — [Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org)
- **Established.** Rollout and versioning: the managed `autoUpdate` per marketplace overrides the user toggle. `DISABLE_AUTOUPDATER` freezes the fleet. Release channels are run by hosting "two marketplaces that point at different refs of the same plugins" and assigning each user group one. Seed directories (`CLAUDE_CODE_PLUGIN_SEED_DIR`) give read-only, pre-built plugin caches for CI and air-gapped fleets, with "`autoUpdate` off". Cached plugin versions are stored at `cache/<marketplace>/<plugin>/<version>/`, and old versions are swept after 14 days. — [Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org); [Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- **Established.** Deprecation and audit: OpenTelemetry events `claude_code.plugin_installed` and `plugin_loaded`, with third-party names redacted unless `OTEL_LOG_TOOL_DETAILS=1`. An Enterprise Analytics API returns per-plugin, per-day install and invocation counts across Claude Code and Cowork, groupable by user or RBAC group. — [Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org)
- **Established.** Agent Skills: "malicious skills may introduce vulnerabilities in the environment where they're used". "We recommend installing skills only from trusted sources." Less-trusted skills should be audited for code dependencies, bundled resources and instructions that connect to external networks. — [Anthropic Engineering: Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- **Established.** MCP Registry moderation: community flags spam, malicious code or impersonation, and maintainers "denylist these entries and retroactively remove them from public access". — [MCP Registry preview](https://blog.modelcontextprotocol.io/posts/2025-09-08-mcp-registry-preview/)
- **Established (date only).** The OWASP Top 10 for Agentic Applications for 2026 was posted 2025-12-09 as a "globally peer-reviewed framework". — [OWASP GenAI](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)
- **Lead only (search summaries).** ASI04 "Agentic Supply Chain Vulnerabilities" covers compromised models, MCP servers, skills, plugins or libraries that agents load dynamically at runtime. Suggested mitigations include a component inventory (AIBOM) and re-review at upgrades. — [Palo Alto Networks blog](https://paloaltonetworks.com/blog/cloud-security/owasp-agentic-ai-security/); [Teleport](https://goteleport.com/blog/owasp-top-10-agentic-applications); the full OWASP PDF text was not read.

### Inferences
- **Synthesized.** Release channels via two refs, SHA pinning, seed caches and allowlists are standard artifact-repository practice: internal mirrors, pinned lockfiles, staged rollout rings. The agent-specific twist is that the "artifact" is partly natural-language instructions, which code scanners cannot vet for prompt-injection or behavioural risk.
- **Proposed.** Run an internal marketplace and MCP sub-registry as the only allowed sources. Require SHA pinning, turn auto-update off for third-party sources, keep the marketplace repo under CODEOWNERS review, and treat `SKILL.md` and agent profiles as reviewable code. Add signing or provenance (e.g. Sigstore-style attestations) as an internal control, because the harness does not natively verify signatures (Inference, from the absence of signing in the docs read).
- **Inference.** Auto-update conflicts with "review before install". Organizations should choose deliberately per marketplace tier.

### Gaps
- No primary evidence of signing or provenance for skills, plugins or MCP servers in any vendor's harness. The MCP Registry's namespace-verification mechanism was not described in the post read.
- The full OWASP ASI04 text is Unreachable in this run (PDF not fetched).
- No documented public incident report of a malicious plugin or skill was verified in this run.

## Onboarding: self-service within guardrails (golden paths, templates, tiered risk)

### Takeaway
The CNCF Platform Engineering Maturity Model gives the vocabulary: golden paths at Level 2, self-serve portals and templates at Level 3, and an ecosystem where users extend the platform at Level 4. Agent-specific onboarding evidence appears in vendor docs as per-repo plugin requirements, project-level settings committed to git, and folder-trust gates. Spotify shows that platform standards ("golden state", Soundcheck) double as agent guardrails. Tiered risk profiles for agents are mostly Synthesized.

### Cited Findings
- **Established.** CNCF maturity aspects are Investment, Adoption, Interfaces, Operations and Measurement. Levels are Provisional, Operationalized, Scalable and Optimizing. Level 2 Interfaces: "'Paved roads' or 'golden paths', in the form of documentation and templates, are provided." Level 3 Adoption: "Self-serve portals, golden-path templates, and other documents enable rapid use." Level 3 Investment: "Product management and user experience are explicitly considered and invested in." Level 4: an enabled ecosystem lets users extend and contribute. The page is © 2025 and labelled v1.0. — [CNCF TAG App Delivery: Platform Engineering Maturity Model](https://tag-app-delivery.cncf.io/whitepapers/platform-eng-maturity-model/)
- **Established.** A repository can require a marketplace and plugins for its contributors via committed `.claude/settings.json`. These apply only after the contributor trusts the folder, and the plugin still needs `claude plugin install … --scope project`. — [Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org)
- **Established.** Recommended rollout order: require plugins, seed containers and CI, restrict, set update policy, audit. — [Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org)
- **Established (vendor case).** At Spotify, Backstage "replaced roughly a hundred internal tools" with one catalog. Soundcheck and "golden state" define recommended practice per component type. Standards act as guardrails, with linting and static analysis giving the agent immediate feedback. "If Claude has a lot of other code to look at, and that code looks roughly consistent, Claude will do a better job." — [Spotify Engineering, 2026-06-03](https://engineering.atspotify.com/2026/6/code-with-claude-coding-is-no-longer-the-constraint)
- **Established (survey).** DORA 2025 (published 2025-09-23; nearly 5,000 respondents): "90% of organizations have adopted at least one platform and there is a direct correlation between a high quality internal platform and an organization's ability to unlock the value of AI." "AI doesn't fix a team; it amplifies what's already there." — [Google Cloud: Announcing the 2025 DORA report](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)
- **Lead only.** Third-party playbooks suggest piloting with 5–10 developers, testing managed settings and spend caps, and holding off on mutating MCP servers until governance is in place. These are vendor and consultant blogs, not experience reports. — [TrueFoundry](https://www.truefoundry.com/blog/claude-code-governance-building-an-enterprise-usage-policy-from-scratch); [claudereadiness.com](https://claudereadiness.com/blog/claude-code-team-deployment/)

### Inferences
- **Synthesized.** Team Topologies maps onto the harness as follows: platform team = harness platform (core, policy, gateway, marketplace); stream-aligned teams = consumers authoring their own skills and agents; enabling team = an "agent enablement" group that seeds templates; complicated-subsystem teams = owners of specialist MCP servers (e.g. data or finance systems). I did not fetch a Team Topologies primary source in this run.
- **Synthesized/Proposed.** Golden path for a new team or topic: a template repo (Backstage software-template style) that scaffolds `.claude/settings.json` requiring the org marketplace, a starter `CLAUDE.md`/`AGENTS.md`, a team plugin skeleton, and a default risk profile. Risk tiers could be (a) read-only/sandboxed, (b) workspace-write with ask rules, (c) autonomous/CI with managed-only hooks and network allowlists. Each tier would be delivered as a managed settings bundle per group, which the vendor docs support as the per-group mechanism.
- **Inference.** DORA's "amplifier" finding plus Spotify's consistency observation imply that platform maturity (standards, catalogs, tests) is a precondition for scaling agents, not a later add-on.

### Gaps
- Backstage software-template docs and Team Topologies were not fetched. Claims about them are Synthesized.
- The seven capabilities of the DORA AI Capabilities Model were not verified, because they appear only in an image on the page read.
- No primary agent-specific "tiered risk profile" standard was found.

## Scaling governance and operations: gateways, policy-as-code, observability, evals, cost attribution

### Takeaway
LLM gateways such as LiteLLM give hierarchical spend and rate controls (key, user, team, team-member, customer, agent, per-model), and these map directly onto per-team cost attribution. Harness-side telemetry (OpenTelemetry events, analytics API) gives fleet observability of plugin and tool use. Spotify's practice adds LLM-as-judge diff evaluation, trace capture and central quota management. Evidence for OPA-based agent policy, and for Kong, Envoy or Portkey AI gateways, was not gathered from primary sources in this run.

### Cited Findings
- **Established.** LiteLLM proxy budgets: virtual keys carry `max_budget` and `budget_duration`. Teams have shared budgets, and keys with a `team_id` draw on them ("only the team (and team-member) budgets are enforced"). There are per-member `max_budget_in_team` limits, user budgets across keys, global per-deployment customer budgets, and agent limits (TPM/RPM, per-session limits, iteration caps, per-session dollar cap). Per-model budgets are an Enterprise feature. Budgets require Postgres, and multi-instance rate limiting uses Redis. Without `fail_closed_rate_limit_enforcement`, instances fall back to local memory during an outage. — [LiteLLM docs: Budgets, rate limits](https://docs.litellm.ai/docs/proxy/users)
- **Established.** Claude Code fleet telemetry includes OpenTelemetry plugin install and load events (with `plugin.scope` such as `org` vs `user-local`) and an Enterprise Analytics API with per-plugin counts groupable by RBAC group. — [Plugin security and trust](https://code.claude.com/docs/en/plugins/security); [Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org)
- **Established.** A self-hosted "Claude apps gateway" can deliver managed settings, with ordered per-group policies where "the gateway applies the first policy whose match rule fits a user". — [Manage plugins for your organization](https://code.claude.com/docs/en/plugins/org)
- **Established (vendor case).** Spotify's internal CLI runs formatting and linting via local MCP, "uses LLMs as judges to evaluate diffs", uploads logs to GCP and captures traces in MLflow. Shared standards for commit tagging, LLM quota management and trace collection benefit every task source. Its stated concerns at scale are long run times, unpredictable output requiring new validation, and "significant computational expense of running LLMs at scale". — [Spotify Honk Part 1](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1)
- **Lead only (search summary of vendor blogs).** MCP gateways are pitched as "one chokepoint for authentication, rate limiting, and audit logging across every agent-tool interaction". Per-developer MCP configs mean "no single point of control". — [TrueFoundry](https://www.truefoundry.com/blog/claude-code-enterprise-mcp-gateway); [Scalekit](https://www.scalekit.com/blog/claude-code-enterprise-mcp-governance) (vendors selling gateways)

### Inferences
- **Synthesized.** Gateway-based chargeback (team budget = cost center) is established FinOps practice. LiteLLM's team-to-key hierarchy is its LLM instance. Map the gateway "team" to the Team Topologies team or catalog owner so that cost and ownership share one key.
- **Proposed.** Policy-as-code: keep managed settings (permissions, MCP allowlists, marketplace allowlists) in a git repo with review and CI validation, and render them per group. OPA/Rego could centralize gateway and MCP-gateway decisions. That would be an inference from general practice, not shown here for agents.
- **Proposed.** Evaluation pipeline: per-skill and per-plugin eval suites run in marketplace CI before promotion from the early-access to the stable channel (combining Spotify's LLM-judge practice with the two-marketplace channel mechanism).

### Gaps
- Kong AI Gateway, Envoy AI Gateway, Portkey and cloud API gateways were not fetched.
- OPA applied to agent tool calls: no primary evidence collected.
- No published per-team cost-overrun incident with figures was verified.

## Case studies and failure modes when scaling across many teams

### Takeaway
The strongest primary case is Spotify: from Fleet Management (about half of PRs automated since mid-2024) to Honk on the Claude Agent SDK, with 1,500+ merged agent PRs by November 2025 and, by June 2026, over 2.5 million automated maintenance PRs. Reported problems are fragmentation degrading agent quality, review becoming the bottleneck, cost, and unpredictability. Anthropic's internal report shows the same harness used by legal, marketing and design. Primary experience reports of failure modes such as config sprawl, MCP sprawl and shadow AI are scarce. Most of that material is vendor marketing.

### Cited Findings
- **Established (Spotify self-report).** The Fleet Management Maven updater script grew to "over 20,000 lines" before agents. Spotify reports "around half of Spotify's pull requests have been automated by Fleet Management since mid-2024", 1,500+ agent PRs merged, "hundreds of developers" using the agent, and "60–90%" time savings on migrations. Ad hoc tasks are exposed via MCP from Slack and GitHub Enterprise. — [Spotify Honk Part 1, 2025-11-06](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1)
- **Established (Spotify self-report).** Spotify reports that over 99% of engineers use AI coding tools weekly and PR frequency is up 76%. Over 2.5 million automated maintenance PRs have been merged, mostly auto-merged. Honk runs Claude via the Agent SDK in a custom harness on Kubernetes. The post's lessons: fragmentation hurts agents ("The fewer technologies we are world-leading in, the faster we go"), review becomes the bottleneck, and the constraint has moved to decision-making. — [Spotify Engineering, 2026-06-03](https://engineering.atspotify.com/2026/6/code-with-claude-coding-is-no-longer-the-constraint)
- **Established (vendor claim).** Anthropic's customer story cites 650+ agent PRs merged per month and up to 90% time savings. These are vendor-published figures. — search lead pointing to [claude.com/customers/spotify](https://claude.com/customers/spotify) (not fetched)
- **Established (survey).** DORA 2025: "90% of survey respondents report using AI at work". "30% report little or no trust in the code generated by AI." AI adoption "does continue to have a negative relationship with software delivery stability". Without "strong automated testing, mature version control practices, and fast feedback loops, an increase in change volume leads to instability". — [DORA 2025 announcement](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)
- **Lead only.** "At around 100 engineers, inconsistent configurations mean inconsistent security policies, fragmented MCP integrations, and highly variable onboarding experiences." This is a playbook claim, not an experience report. — search summary of [Claude Code Adoption Guide](https://gmanch94.github.io/claude-platform-playbook/artifacts/claude-code-adoption-guide.html)

### Inferences
- **Inference.** Spotify scaled without redesign by putting the agent behind an existing orchestration platform and catalog. The documented failure modes are organizational (heterogeneous stacks, review capacity) more than technical.
- **Synthesized.** The failure modes in the brief (config sprawl, MCP sprawl, shadow AI, cost overruns, inconsistent instructions) correspond to known platform anti-patterns: snowflake config, unmanaged dependencies, shadow IT, and missing chargeback. The Claude Code control matrix (allowlists, managed-only hooks and MCP, telemetry) exists specifically to counter them. That is evidence the vendor anticipates them, not evidence of incidents.

### Gaps
- No primary engineering-blog post describing a failed or rolled-back multi-team agent rollout was found. Search results were dominated by gateway vendors.
- Large-company Copilot rollout reports (e.g. Accenture, ANZ, Microsoft internal) and the Stack Overflow 2025 survey were not fetched.

## Cross-discipline: coding-specific vs. discipline-agnostic harness concepts; non-coding use

### Takeaway
The loop, tools via MCP, skills, plugins, subagents, permissions, sandboxing and managed policy are discipline-agnostic. Anthropic ships the same agent architecture to non-developers as Cowork (documents, spreadsheets, research) with the same skills, connectors and plugins model, and its official marketplace tier includes legal, financial-services, life-sciences and "knowledge-work" plugin catalogs. Coding-specific parts are repo context, test and lint feedback loops, git checkpoints and PR-based review. Spotify's evidence shows those verification loops drive quality, so non-coding disciplines need a substitute verifier.

### Inferences
- **Inference/Proposed.** Concept transfer table:
  - **Discipline-agnostic, transfers as-is:** agent loop; tools via MCP; skills (progressive disclosure); plugins and marketplaces; subagents; permission modes and allow/deny rules; sandboxing; managed policy layering; hooks as policy enforcement points; telemetry and cost attribution; memory/instruction files.
  - **Transfers with a substitute:** git checkpoints become document versioning or snapshot/undo of workspace files; test and lint feedback becomes domain validators (schema checks, spreadsheet formula checks, citation checks, compliance rule checks) or LLM-as-judge rubrics; PR review becomes a human approval step in the business system (draft, then approve).
  - **Coding-specific:** repo-wide code search, build systems, CI integration, language servers (LSP), diff-based change sets.
- **Inference.** Because Cowork and Claude Code share architecture but keep separate config planes (Cowork reads claude.ai-enabled assets, not `~/.claude`), a multi-discipline framework needs a cross-surface catalog. Anthropic's "roll out one plugin to claude.ai, Cowork, and Claude Code together" path is that bridge.
- **Inference.** The weakest point for non-coding transfer is verification. Coding has cheap, objective oracles (tests, compilers), and most knowledge work does not. This is the main reason to classify the feedback loop as coding-specific.

### Gaps
