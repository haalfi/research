## Q1. Do the claims in § 3.9 and § 4 survive the full texts?

### Takeaway
Most of it holds. Four claims need correcting. (1) The C quote is right, but it comes from ISO C (N1570 § 3.4.1), not from WG23 N0245. (2) The SQL rule that "a stronger level may be substituted" is not in Berenson et al. It is in the SQL-92 text itself (SET TRANSACTION, General Rule 5), and Berenson shows the levels form a partial order, not a chain. (3) HADOOP-13501 was closed as Won't Fix, and `is-blobstore` was kept as an informational flag. It was not deprecated or removed. (4) The current Python docs no longer support the PEP 3116 rule that buffered reads come back short only at EOF or when non-blocking. Two new primary sources make the narrow-only rule stronger: WebAssembly 3.0's Profiles appendix and SQL-92 GR 5.

### Inferences
- *Inference:* The narrow-only rule (§ 4 composite rule 3) no longer rests only on Liskov & Wing / A/G refinement by analogy. Two normative texts state it outright. WebAssembly 3.0: profiles "do not add syntax or alter behaviour". SQL-92 GR 5: the actual level "will not exhibit any of the phenomena" the requested level would not exhibit. Both are B.
- *Inference:* Berenson's incomparability result (RR »« SI) limits "take values from a published lattice". The order is partial, so "narrower" is only defined between comparable values. The standard judges substitution against its own listed phenomena, not against every anomaly. PostgreSQL's SI-based REPEATABLE READ passes the SQL rule even though Berenson calls RR and SI incomparable under the broad reading. A profile's narrowing check has to name the reference set of excluded behaviours it is judged against.
- *Inference:* WebAssembly is a counter-pattern to runtime-queried profiles (POSIX value 0, JDBC, OGC /conformance, Hadoop PathCapabilities). It fixes the profile statically and discourages runtime conditioning. The report's rule should say which style applies: a static per-reality record, or a runtime probe as well. Hadoop shows the probe's asymmetry: True is a promise, False may mean unknown.

### Gaps
- The OGC Modular Specification Policy (08-131r3) full text was unreachable (T4-19).
- The ISO/IEC 9075 current text is paywalled. Only the SQL-92 draft on an unofficial mirror was read, so whether GR 5 survives verbatim in SQL:2016/2023 is unverified.
- The Benveniste book edition (nowpublishers) was not opened. The 2012 INRIA report was used instead.

## Q2. Python `io`: may buffered `read` return `None` in non-blocking mode, or must it raise `BlockingIOError`? RawIOBase `read` → `None`?

### Takeaway
The current docs, the class docstrings and the implementation disagree. The docs settle it by declaring a variation point: "implementations may either raise BlockingIOError or return None … io implementations return None." CPython's BufferedReader in fact returns `None`, while the `BufferedIOBase` class docstring (C and `_pyio`) still says "will never return None". RawIOBase returning `None` is confirmed everywhere.

### Cited Findings
- RawIOBase.read (docs 3.15.1): "If 0 bytes are returned, and size was not 0, this indicates end of file. If the object is in non-blocking mode and no bytes are available, None is returned." Also: "fewer than size bytes may be returned if the operating system call returns fewer than size bytes." — [io docs](https://docs.python.org/3/library/io.html)
- BufferedIOBase class text (docs): "if the underlying raw stream is in non-blocking mode, when the system returns would block write() will raise BlockingIOError … and read() will return data read so far or None if no data is available." — [io docs](https://docs.python.org/3/library/io.html)
- BufferedIOBase.read and read1 notes (docs): "When the underlying raw stream is non-blocking, implementations may either raise BlockingIOError or return None if no data is available. io implementations return None." Also: "Fewer bytes may be returned than requested. … Less than size bytes being returned does not imply that EOF is imminent." — [io docs](https://docs.python.org/3/library/io.html)
- BufferedReader.peek: "If the underlying raw stream is non-blocking and the operation would block, returns empty bytes." BufferedWriter.write: "When in non-blocking mode, a BlockingIOError with BlockingIOError.characters_written set is raised if the buffer needs to be written out but the raw stream blocks." — [io docs](https://docs.python.org/3/library/io.html)
- The CPython C class docstring (`bufferediobase_doc`) is the opposite: "read(), readinto() and write() may raise BlockingIOError if the underlying raw stream is in non-blocking mode and not ready; unlike their raw counterparts, they will never return None." In the same file, the clinic docstring of `_io._BufferedIOBase.read` says "Return None if the underlying raw stream was open in non-blocking mode and no data is available at the moment." The implementation (`_bufferedreader_read_generic`) returns `Py_RETURN_NONE` when the raw read "would block" (raw `readinto` returned None, mapped to code −2) and nothing was read yet. — [bufferedio.c (main)](https://raw.githubusercontent.com/python/cpython/main/Modules/_io/bufferedio.c)
- `_pyio` has the same split. The `BufferedIOBase` docstring says "will never return None" and `read` "Raises BlockingIOError if the underlying raw stream has no data at the moment". `BufferedReader.read` says "Returns exactly size bytes of data unless the underlying raw IO stream reaches EOF or if the call would block in non-blocking mode", and `_read_unlocked` returns `nodata_val`, which is `None` when the raw read returned `None`. `RawIOBase.read`: "Returns an empty bytes object on EOF, or None if the object is set not to block and has no data to read." — [_pyio.py (main)](https://raw.githubusercontent.com/python/cpython/main/Lib/_pyio.py)
- PEP 3116 (2007): RawIOBase.read "If the object is in non-blocking mode and no bytes are available, the call returns None"; buffered short reads only at EOF (see T4-05). — [PEP 3116](https://peps.python.org/pep-3116/)

### Inferences
- *Inference:* This is a clean, primary-source instance of the report's pattern. The contract ("BufferedIOBase") names a variation point with two allowed outcomes, and a declared value says what one implementation does ("io implementations return None"). It is also an instance of drift (P2 failure). Three statements of one rule (class docstring, method docstring, reference docs) live in one repository and disagree. The reference docs settled it by widening the base contract, not by forking it.
- *Inference:* The report's § 4 claim that "PEP 3116 already works this way" (raw weaker, buffered stronger) should be restated. The current base `BufferedIOBase.read` contract allows short reads not caused by EOF. The strengthening now lives in `BufferedReader.read` (`_pyio`: "Returns exactly size bytes … unless … EOF or … would block"), which is again the per-implementation layer.

### Gaps
- I did not check when the "may either raise … or return None" note was added to the docs (needs `Doc/library/io.rst` history).

## Q3. PEP 3151: errno → exception subclass mapping

### Takeaway
PEP 3151 (Final, Python 3.3) maps chosen errno values onto a fixed set of OSError subclasses. It deliberately does not cover every errno, and several errnos map to one class, with `errno` kept as an attribute.

### Cited Findings
- "define additional subclasses which will be raised, rather than their parent, for specific errno values … Trying to map all errno mnemonics, indeed, seems foolish, pointless, and would pollute the root namespace." — [PEP 3151](https://peps.python.org/pep-3151/)
- "EAGAIN, EALREADY, EWOULDBLOCK and EINPROGRESS are all used to signal that an operation on a non-blocking socket would block … They could therefore all raise an identical subclass and let the user examine the errno attribute". — [PEP 3151](https://peps.python.org/pep-3151/)
- Mapping table: BlockingIOError (EAGAIN, EALREADY, EWOULDBLOCK, EINPROGRESS); ChildProcessError (ECHILD); ConnectionError → BrokenPipeError (EPIPE, ESHUTDOWN), ConnectionAbortedError (ECONNABORTED), ConnectionRefusedError (ECONNREFUSED), ConnectionResetError (ECONNRESET); FileExistsError (EEXIST); FileNotFoundError (ENOENT); InterruptedError (EINTR); IsADirectoryError (EISDIR); NotADirectoryError (ENOTDIR); PermissionError (EACCES, EPERM); ProcessLookupError (ESRCH); TimeoutError (ETIMEDOUT). — [PEP 3151](https://peps.python.org/pep-3151/)
- "these subclasses should still set adequate values for the various exception attributes defined on the superclass (for example errno, filename, and optionally winerror)". "Since it is proposed that the subclasses are raised based purely on the value of errno, little or no changes should be required in extension modules". The mechanism: adapt `OSError.__new__` "to instantiate the appropriate subclass". Status Final, Created 21-Jul-2010, Python-Version 3.3. — [PEP 3151](https://peps.python.org/pep-3151/)

### Inferences
- *Inference:* PEP 3151 is a precedent for an error classification as a bounded, many-to-one mapping from backend codes onto a small set of caller-visible classes, with the raw code kept as data. The class is the contract; the code is profile-level detail.

### Gaps
- None for the PEP itself. I did not check the current builtins docs for later changes to the mapping.

## Q4. POSIX `read()` idiom

### Takeaway
POSIX.1-2024 `read()` states short reads as an enumerated set of allowed causes. It splits errors into "shall fail" (every implementation must detect) and "may fail" (optional detection, documented in the conformance document). EAGAIN is tied to O_NONBLOCK.

### Cited Findings
- Short reads: "This number shall never be greater than nbyte. The value returned may be less than nbyte if the number of bytes left in the file is less than nbyte, if the read() request was interrupted by a signal, or if the file is a pipe or FIFO or special file and has fewer than nbyte bytes immediately available for reading." — [read() Issue 8](https://pubs.opengroup.org/onlinepubs/9799919799/functions/read.html)
- EINTR and partial data: "If a read() is interrupted by a signal before it reads any data, it shall return -1 with errno set to [EINTR]. If … after it has successfully read some data, it shall return the number of bytes read." — same
- EAGAIN: "If O_NONBLOCK is set, read() shall return -1 and set errno to [EAGAIN]." In ERRORS, "These functions shall fail if: [EAGAIN] The file is neither a pipe, nor a FIFO, nor a socket, the O_NONBLOCK flag is set …". Sockets: "[EAGAIN] or [EWOULDBLOCK]". "These functions may fail if: [EIO] A physical I/O error has occurred. [ENOBUFS] … [ENOMEM] … [ENXIO] …". — same
- Built-in unspecified/implementation-defined points: "The behavior of multiple concurrent reads on the same pipe, FIFO, or terminal device is unspecified." "If the value of nbyte is greater than {SSIZE_MAX}, the result is implementation-defined." Rationale: "This volume of POSIX.1-2024 does not specify the value of the file offset after an error is returned; there are too many cases." — same
- Definition of the idiom (XSH 2.3): "The ERRORS section on each reference page specifies which error conditions shall be detected by all implementations ('shall fail') and which may be optionally detected by an implementation ('may fail'). If no error condition is detected, the action requested shall be successful. If an error condition is detected, the action requested may have been partially performed, unless otherwise stated." "If more than one error occurs … any one of the possible errors may be returned, as the order of detection is undefined." "Implementations shall not generate a different error number from one required by this volume … but may generate additional errors unless explicitly disallowed". "Each implementation shall document, in the conformance document, situations in which each of the optional conditions … is detected." — [XSH chap. 2](https://pubs.opengroup.org/onlinepubs/9799919799/functions/V2_chap02.html)

### Inferences
- *Inference:* POSIX has three variation mechanisms inside one page: "may fail" with a documented-detection duty (a per-implementation profile entry), "implementation-defined", and "unspecified". It also states that error order is unspecified and that partial effects on error are allowed. Each maps onto a § 4 rule: the variation point sits in the contract, and the choice lives in the conformance document.

### Gaps
- None.

## Q5. Go error and reader conventions

### Takeaway
Go's `io.Reader` contract allows data and an error from the same call and two EOF behaviours, and tells callers to handle n > 0 first. `errors.Is`/`As` match on a tree of wrapped errors. `io/fs` defines sentinel errors meant to be tested with `errors.Is`.

### Cited Findings
- "When Read encounters an error or end-of-file condition after successfully reading n > 0 bytes, it returns the number of bytes read. It may return the (non-nil) error from the same call or return the error (and n == 0) from a subsequent call. … a Reader returning a non-zero number of bytes at the end of the input stream may return either err == EOF or err == nil. The next Read should return 0, EOF." "Callers should always process the n > 0 bytes returned before considering the error err." "If some data is available but not len(p) bytes, Read conventionally returns what is available instead of waiting for more." "Implementations of Read are discouraged from returning a zero byte count with a nil error … Callers should treat a return of 0 and nil as indicating that nothing happened". "Implementations must not retain p." — [io.go (master)](https://raw.githubusercontent.com/golang/go/master/src/io/io.go)
- EOF: "EOF is the error returned by Read when no more input is available. (Read must return EOF itself, not an error wrapping EOF, because callers will test for EOF using ==.) Functions should return EOF only to signal a graceful end of input." Otherwise use `ErrUnexpectedEOF` "or some other error giving more detail". — same
- errors.Is: "Is reports whether any error in err's tree matches target. … The tree consists of err itself, followed by the errors obtained by repeatedly calling its Unwrap() error or Unwrap() []error method. … An error is considered to match a target if it is equal to that target or if it implements a method Is(error) bool such that Is(target) returns true." Example: `func (m MyError) Is(target error) bool { return target == fs.ErrExist }`. errors.As finds "the first error in err's tree that matches target"; the current source says "For most uses, prefer [AsType]". — [wrap.go (master)](https://raw.githubusercontent.com/golang/go/master/src/errors/wrap.go)
- io/fs: "Generic file system errors. Errors returned by file systems can be tested against these errors using [errors.Is]." `ErrInvalid`, `ErrPermission`, `ErrExist`, `ErrNotExist` ("file does not exist"), `ErrClosed` ("returned when operations are attempted on a file that has already been closed, including when Close is called more than once"). `FS.Open`: "When Open returns an error, it should be of type *PathError with the Op field set to "open", the Path field set to name, and the Err field describing the problem." — [fs.go (master)](https://raw.githubusercontent.com/golang/go/master/src/io/fs/fs.go)

### Inferences
- *Inference:* Go's `io.Reader` names two allowed EOF behaviours plus a caller obligation that makes both safe. That is "unspecified within a bounded set", stated together with the client rule that makes the variation harmless. `errors.Is` with sentinels is a classification-by-predicate mechanism: one predicate per error class, and backend errors opt in through an `Is` method. It plays the same role as PEP 3151's subclasses.

### Gaps
- I read source comments on master, not pkg.go.dev. The two carry the same text by construction, but I did not render pkg.go.dev. The `AsType` addition is recent; its version was not checked.

## Q6. Google AIP-193 (errors) and AIP-194 (automatic retry)

### Takeaway
AIP-193 requires canonical `google.rpc.Code` values plus a machine-readable `ErrorInfo` (reason, domain), with stability rules, and fixes the PERMISSION_DENIED vs NOT_FOUND order. AIP-194 classifies codes as retryable (only UNAVAILABLE) or not, and limits automatic retry to idempotent, non-transactional, unary calls.

### Cited Findings
- AIP-193 (Approved; page shows "Updated 2019-07-26" with a 2022-11-04 changelog entry): "Services must return a google.rpc.Status message when an API error occurs, and must use the canonical error codes defined in google.rpc.Code." "All error responses must include an ErrorInfo within details." "The (reason, domain) pair form a machine-readable way of identifying a particular error. Services must use the same (reason, domain) pair for the same error, and must not use the same (reason, domain) pair for logically different errors." Metadata: "All keys that have been included must continue to be included (but may have empty values)". "APIs should not support partial errors." — [AIP-193](https://google.aip.dev/193)
- AIP-193 Permission Denied: "If the user does not have permission to access the resource or parent, regardless of whether or not it exists, the service must error with PERMISSION_DENIED (HTTP 403). Permission must be checked prior to checking if the resource or parent exists. If the user does have proper permission, but the requested resource or parent does not exist, the service must error with NOT_FOUND (HTTP 404)." — [AIP-193](https://google.aip.dev/193)
- AIP-194 (Approved, 2019-08-16): "Clients should automatically retry requests for which repeated runs would not cause unintended state changes, which are non-transactional, and which are unary." Retryable: "UNAVAILABLE: This code generally results from network hiccups, and is generally transient." Non-retryable: OK, CANCELLED, DEADLINE_EXCEEDED, INVALID_ARGUMENT, DATA_LOSS. Generally non-retryable: RESOURCE_EXHAUSTED, INTERNAL, UNKNOWN, ABORTED ("should be retried at a level higher (the entire transaction, for example)"). Also NOT_FOUND ("A client should not retry until a resource is created"), ALREADY_EXISTS, PERMISSION_DENIED, UNAUTHENTICATED, FAILED_PRECONDITION, OUT_OF_RANGE, UNIMPLEMENTED. "This AIP does not cover client streaming or bi-directional streaming." — [AIP-194](https://google.aip.dev/194)

### Inferences
- *Inference:* AIP-193's ordering rule (permission before existence) is a cross-backend observable guarantee written once in the contract. It is exactly the kind of rule that differs per backend if left unstated. AIP-194 attaches a derived property (retryability) to each error class, so classification and retry policy share one table.

### Gaps
- AIP-194 excludes streaming explicitly, so it says nothing about failures in the middle of a stream, which is the running example's hard case.

## Q7. AWS S3 consistency model (brief; a parallel track also checks it)

### Takeaway
S3 promises strong read-after-write for PUT/DELETE, single-key atomicity ("old data or the new data, but never partial or corrupt"), and last-writer-wins for concurrent PUTs, with no object locking. The user guide says nothing explicit about an object overwritten while a GET is being streamed.

### Cited Findings
- "Amazon S3 provides strong read-after-write consistency for PUT and DELETE requests of objects in your Amazon S3 bucket in all AWS Regions. This behavior applies to both writes to new objects as well as PUT requests that overwrite existing objects and DELETE requests." "Updates to a single key are atomic. For example, if you make a PUT request to an existing key from one thread and perform a GET request on the same key from a second thread concurrently, you will get either the old data or the new data, but never partial or corrupt data." — [S3 User Guide, data consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)
- "Amazon S3 does not support object locking for concurrent writers. If two PUT requests are simultaneously made to the same key, the request with the latest timestamp wins." "Updates are key-based. There is no way to make atomic updates across keys." Concurrent case: "Amazon S3 internally uses last-writer-wins semantics … the order in which Amazon S3 receives the requests and the order in which applications receive acknowledgments cannot be predicted". Bucket configurations are eventually consistent; after enabling versioning "wait for 15 minutes". — same

### Inferences
- *Inference:* S3's "old or new, never partial" for a concurrent GET is a stronger per-reality value than Hadoop's base contract, which allows changes to be "partially visible" (Q8). That is a ready example of a profile value that narrows the base. Whether it holds for a long ranged or streamed GET is not stated (gap).

### Gaps
- Behaviour of a long-running or multi-range GET across an overwrite is not stated on this page.

## Q8. Hadoop: what replaced `is-blobstore`; current `open()`/`openFile()` wording, especially change or delete during a read

### Takeaway
`is-blobstore` was replaced, for test gating, by `create-overwrites-directory` and `create-visibility-delayed`, and kept as an informational flag. `open()` MUST check existence at open time but promises nothing about data after that. The FSDataInputStream spec lists the allowed outcomes when data changes or is deleted during a read. `openFile()` MAY open lazily and MUST NOT check file preconditions in the `openFile()` call.

### Cited Findings
- Replacement flags (HADOOP-13502, patch 001, kept through patch 004): "Introduced 2 new specific contract options: create-overwrites-directory and create-visibility-delayed." "S3A adds create-visibility-delayed, but does not add create-overwrites-directory. That's because HADOOP-13188 recently changed the implementation to avoid overwriting directories." Final: "retains is-blobstore as an informational flag. It is not deprecated. The tests no longer need to check for is-blobstore". Reviewer note on skip messages: "remove the assumption of *object store* in the comments and the skip message to match the description of the new flag, which should be applicable to all HCFS". — [HADOOP-13502](https://issues.apache.org/jira/rest/api/2/issue/HADOOP-13502) (C)
- Current option list (trunk `ContractOptions.java`): create-overwrites-directory ("a newly created file may overwrite a pre-existing directory"), create-visibility-delayed ("a newly created file is not made visible in the namespace immediately. Instead, the file becomes visible at a later point … such as when the client closes it"), create-file-under-file-allowed, is-case-sensitive, is-blobstore, rename-creates-dest-dirs, rename-overwrites-dest, rename-returns-false-if-dest-exists, rename-returns-false-if-source-missing, rename-remove-dest-if-empty-dir, supports-append, supports-settimes, supports-getfilestatus, supports-atomic-rename, supports-atomic-directory-delete, supports-block-locality, supports-concat, supports-seek, rejects-seek-past-eof, supports-seek-on-closed-file ("Some filesystems only raise an exception later, when trying to read"), supports-available-on-closed-file, supports-strict-exceptions, supports-unix-permissions, supports-positioned-readable, supports-file-reference, supports-content-check, supports-unbuffer, max-path, max-filesize, test.root-tests-enabled, test.random-seek-count, supports-hflush, supports-hsync, metadata_updated_on_hsync, vector-io-early-eof-check, vector-io-overlapping-ranges. `CONTRACT_OPTIONS_RESOURCE = "contract-test-options.xml"` is the bindings file. — [ContractOptions.java (trunk)](https://raw.githubusercontent.com/apache/hadoop/trunk/hadoop-common-project/hadoop-common/src/test/java/org/apache/hadoop/fs/contract/ContractOptions.java) (B, source)
- `open(Path f, int bufferSize)` precondition: "if not isFile(FS, p)) : raise {FileNotFoundException, IOException}". "This is a critical precondition. Implementations of some FileSystems (e.g. Object stores) could shortcut one round trip by postponing their HTTP GET operation until the first read() on the returned FSDataInputStream. However, much client code does depend on the existence check being performed at the time of the open() operation. Implementations MUST check for the presence of the file at the time of creation. This does not imply that the file and its data is still at the time of the following read() or any successors." Postcondition: "whether that access is to the contents at the time the open() operation was invoked, or whether and how it may pick up changes to that data in later states of FS is an implementation detail. The result MUST be the same for local and remote callers of the operation." — [filesystem.html 3.5.0](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-common/filesystem/filesystem.html)
- FSDataInputStream Consistency: "All readers, local and remote, of a data stream FSDIS provided from a FileSystem.open(p) are expected to receive access to the data of FS.Files[p] at the time of opening. If the underlying data is changed during the read process, these changes MAY or MAY NOT be visible. Such changes that are visible MAY be partially visible." Formally, from t ≥ t1 "the value of FSDIS0 is undefined". "It may be unchanged" / "It may pick up the new data" / "It may be inconsistent, such that a read of an offset returns data from either of the datasets" / "It may also be inconsistent on repeated reads of same offset … r3 != r2". "Similarly, if the data at the path p, is deleted, this change MAY or MAY not be visible during read operations performed on FSDIS0." Lazy seek: "The fact that a file has been deleted or truncated may not surface until that read() call." readVectored: "If a file is changed while the readVectored() operation is in progress, the output is undefined." — [fsdatainputstream.html 3.5.0](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-common/filesystem/fsdatainputstream.html)
- `openFile()`: "the chain FileSystem.openFile(path).build().get() has the same preconditions and postconditions as FileSystem.open(Path p, int bufferSize). However, there is one difference …: The returned stream MAY implement a lazy open where file non-existence or access permission failures may not surface until the first read() of the actual data." "this file-specific preconditions (file exists, file is readable, etc) MUST NOT be checked here." — [openfile.html 3.5.0](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-common/filesystem/openfile.html)
- Builder `build()`: "MAY perform the validation of the file's existence … Alternatively … MAY be performed asynchronously within the returned CompletableFuture<> … MAY be postponed until the first byte is read". "if even when file does not exist, or is a directory rather than a file, the following call MUST succeed". "The inability to access/read a file MUST raise an IOException or subclass in either the future's get() call, or, for late binding operations, when an operation to read data is invoked." "permission failures MUST be delayed until the get() call and MAY be delayed into subsequent operations." — [fsdatainputstreambuilder.html 3.5.0](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-common/filesystem/fsdatainputstreambuilder.html)
- PathHandle (caller-requested guarantee): "By default, any modification results in an error. The caller MAY specify relaxations …" "An implementation MUST throw UnsupportedOperationException if it cannot support the semantics specified by the caller." "a PathHandle created with CONTENT constraints MAY return a stream that ignores updates to the file after it is opened". "Object stores that implement rename by copying objects MUST NOT claim to support CONTENT and REFERENCE unless the lineage of the object is resolved." — [filesystem.html 3.5.0](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-common/filesystem/filesystem.html)

### Inferences
- *Inference:* For the running example, Hadoop states "consistency under a concurrent writer" as a weakest base contract with the allowed outcomes listed formally. It has no profile flag for snapshot reads. The stronger guarantee is reached through a caller request (PathHandle CONTENT) that MUST be refused if unsupported. That pattern, request a level and get at least that level or an explicit refusal, also appears in SQL-92 GR 5 and JDBC (`supportsTransactionIsolationLevel` with `setTransactionIsolation`). It is a fourth variation mechanism next to declared profile, runtime probe and emulation flag. The report's § 4 does not list it.
- *Inference:* Error timing is handled by a separate entry point with a wider contract (`openFile`: lazy failure allowed). `open()` itself does not vary per backend. The notes said this; the full text confirms it.

### Gaps
- I did not find a contract-XML option that gates the FSDataInputStream consistency outcomes. The suite does not seem to test them, consistent with testing.html: "Core areas not covered are concurrency and aspects of failure across a distributed system." This is inference from the option list, not a statement.

## Q9. fsspec `spec.py` and Apache Arrow FileSystem

### Takeaway
fsspec's `AbstractFileSystem` raises builtin `FileNotFoundError`/`FileExistsError`/`NotImplementedError`/`ValueError`. ## Q10. Findings that would change the Kernsatz, the form rule, the scorecard or the shortlist

### Takeaway
Nothing here overturns the § 4 composite answer. Three findings change its content: the narrow-only rule gets direct normative precedent, a request/refusal mechanism is missing from the list, and the "published lattice" wording needs "partial order, with a stated reference set". The rest are citation fixes and restyling.

### Cited Findings
- **Changes substance (§ 4 composite rules; possibly the shortlist row "g" at l. 435):**
  1. Narrow-only: WebAssembly 3.0 "do not add syntax or alter behaviour" and SQL-92 GR 5 turn rule 3 from inference into documented normative practice (B) — [Wasm profiles](https://webassembly.github.io/spec/core/appendix/profiles.html); [SQL-92 mirror](http://www.contrib.andrew.cmu.edu/~shadow/sql/sql1992.txt)
  2. Partial order with incomparable values: Berenson "Remark 9. REPEATABLE READ »« Snapshot Isolation". Rule 1 ("taken from a published lattice") should read "partial order", and the narrowing check must name its reference set of excluded behaviours — [Berenson et al.](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-95-51.pdf)
  3. Static versus runtime profile: Wasm says "Runtime conditioning on the 'current' profile is not intended". Hadoop PathCapabilities is a promise-or-unknown probe. The composite rule should say whether profiles are static records, runtime-probed, or both, and that a probe's False may mean unknown — [Wasm](https://webassembly.github.io/spec/core/appendix/profiles.html); [pathcapabilities.html](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-common/filesystem/pathcapabilities.html)
  4. Missing mechanism: caller-requested guarantee with mandatory refusal (Hadoop PathHandle "MUST throw UnsupportedOperationException if it cannot support the semantics specified by the caller"; SQL SET TRANSACTION; JDBC) — [filesystem.html](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-common/filesystem/filesystem.html)
  5. Rule 4 ("never kinds of backend") is confirmed but should be phrased as "a kind label may exist as description but must gate no test". HADOOP-13502 kept `is-blobstore` as informational and moved gating to two guarantee flags. This aligns with rule 7's meta-check — [HADOOP-13502](https://issues.apache.org/jira/rest/api/2/issue/HADOOP-13502)
- **Changes evidence for "Unspecified is a statement" (§ 3.2 / brief § 3.2), not the Kernsatz:** Hadoop FSDataInputStream lists the allowed outcomes under a concurrent writer and a delete formally, and POSIX splits "shall fail" from "may fail" with a duty to document. Both are primary examples of deliberate non-promise stated as a set — [fsdatainputstream.html](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-common/filesystem/fsdatainputstream.html); [XSH 2.3](https://pubs.opengroup.org/onlinepubs/9799919799/functions/V2_chap02.html)
- **Changes an example (§ 4 l. 302):** PEP 3116's buffered strengthening is superseded. Current io docs declare the variation point "may either raise BlockingIOError or return None … io implementations return None", which fits the report's pattern better, and the CPython docstrings show drift — [io docs](https://docs.python.org/3/library/io.html); [bufferedio.c](https://raw.githubusercontent.com/python/cpython/main/Modules/_io/bufferedio.c)
- **Merely restyled / citation fixes (no change in argument):** T4-01 (re-cite C quote to N1570); T4-02 (cite POSIX Issue 8); T4-09 (attribute the rule to SQL-92 GR 5 and PostgreSQL, keep Berenson for the order); T4-13, T4-18 (remove †); T4-14 ("two properties", 13501 Won't Fix); T4-17 (RFC 6707 motivation is service config toggles); T4-20 (JDBC count 175/68, `SQLFeatureNotSupportedException` lives on Connection etc.).
- **§ 8.1 l. 546 "not researched at all" list:** Go `errors.Is` and AIP-193 are now sourced (Q5, Q6). PyFilesystem2 was not covered here.

### Inferences
- *Inference:* None of the above touches the Kernsatz's core claim (one contract, declared profile, narrow-only, checked by one suite). It adds precedent and two refinements: partial-order reference set, and the request/refusal mechanism.
