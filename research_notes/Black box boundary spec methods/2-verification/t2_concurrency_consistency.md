### Gap 2: AWS S3 consistency wording (official User Guide)

#### Takeaway
The official User Guide **does** address a GET concurrent with an overwrite: the reader gets old or new data, never partial or corrupt. It also explicitly frames reads and writes as intervals (start/finish). This contradicts the notes' inference that "none of the vendor statements found addresses an object being overwritten *while a GET is streaming*". The guide does not say whether "concurrently" covers a long download whose body is still streaming. That is not stated.

#### Cited findings ([S3 User Guide, "Amazon S3 data consistency model", fetched 2026-10-22](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html); grade B)
- "Amazon S3 provides strong read-after-write consistency for PUT and DELETE requests of objects in your Amazon S3 bucket in all AWS Regions."
- "Updates to a single key are atomic. For example, if you make a PUT request to an existing key from one thread and perform a GET request on the same key from a second thread concurrently, you will get either the old data or the new data, but never partial or corrupt data."
- "Any read (GET or LIST request) that is initiated following the receipt of a successful PUT response will return the data written by the PUT request."
- Concurrent writers: "Amazon S3 does not support object locking for concurrent writers. If two PUT requests are simultaneously made to the same key, the request with the latest timestamp wins. If this is an issue, you must build an object-locking mechanism into your application."
- "Concurrent applications": "W2 does not finish before the start of R1. Therefore, R1 might return color = ruby or color = garnet." When "W2 begins before W1 has received an acknowledgment … these writes are considered concurrent. Amazon S3 internally uses last-writer-wins semantics … the order in which Amazon S3 receives the requests and the order in which applications receive acknowledgments cannot be predicted".
- "Bucket configurations have an eventual consistency model". The guide recommends waiting "15 minutes after enabling versioning".
- The same page lists S3 Lifecycle ("expire objects that reach the end of their lifetimes") and Replication as features, but the consistency section says nothing about them as writers.

#### Inferences
- *Inference:* S3's prose is the regular-register shape: a read overlapping a write returns old or new, judged by interval overlap (start of read versus finish of write). It is a B-grade vendor precedent for stating H1 with intervals.
- *Inference:* O3 actors (lifecycle expiry, replication) are listed as features but absent from the consistency statement. That is the exact silence the report's O3 point is about.

## 3. Disconfirming search (c)

### Takeaway
Both "no method" claims in § 3.4 are too strong.
- **Operations with an extent** are standard. Every history model read here gives operations an invocation–response interval. Interval-linearizability goes further and lets an operation's effect span states along its interval. Lamport's safe, regular and atomic registers define what an overlapping read may return. Hadoop's FileSystem spec states the visibility of changes during a long-lived stream read.
- **An environment distinct from clients** is native to rely–guarantee and TLA+. There the environment is state change, not sessions. Jepsen separates the nemesis process from client processes.

What survives is narrower: there is no ready-made object type for a chunked stream, and no published method separates "second API caller" from "out-of-band mutator" as two kinds of environment.

### Cited findings: stream or operation with an extent
- **Interval-linearizability** (Castañeda, Rajsbaum, Raynal). It introduces "interval-sequential objects" whose "transitions are labeled with sets of invocations and responses, allowing operations to span several consecutive transitions". Interval-linearizability "allows to associate states along the interval of execution of an operation", and "remains local and non-blocking". Source: [arXiv 1507.00073](https://arxiv.org/pdf/1507.00073). Grade: A-pre as read. A later J. ACM version exists according to my bibliographic knowledge, not verified this session.
- **Substep linearizability** (Hackett, Wrench, Beschastnikh, Wei, Oct 2026). Its abstract says interval linearizability "requires an interval-sequential specification … which we show is challenging to correctly generate or understand, even for simple operations on a single concurrent register". It proposes substep linearizability, "equivalent to interval linearizability", whose sequential specs are "comparable in complexity to linearizability's", and it models "snapshot isolation between database transactions". Source: [arXiv 2610.16099](https://arxiv.org/pdf/2610.16099). Grade A-pre.
- **Lamport, "On Interprocess Communication"** (author copy dated Dec 1985; published in Distributed Computing 1986 according to bibliographic knowledge).
  - Operation executions are nonatomic. "Nonatomicity introduces the possibility that an operation execution A can influence an operation execution B without preceding it". It adds a "can affect" relation beside "precedes".
  - Safe register: "a read that overlaps a write … must obtain one of the possible values".
  - Regular register: "a read that overlaps a write obtains either the old or new value".
  - Atomic register: overlapping operations behave "as if the operations had been performed in that order, with no overlapping".
  - Part II implements atomic higher-level operations from lower-level reads, "as in a database".
  - Source: [lamport.azurewebsites.net/pubs/interprocess.pdf](https://lamport.azurewebsites.net/pubs/interprocess.pdf). Grade A.
- **Viotti & Vukolić** give operations explicit `stime`/`rtime`, with `Ω` for non-returning operations, and a "Concur" set of writes concurrent with an operation. They also treat Lamport's safe, regular and atomic registers as consistency predicates. Source: [arXiv 1512.00168](https://arxiv.org/pdf/1512.00168). Grade A.
- **Jepsen/Knossos history model**: "an invoke, when the op begins, and a completion: either ok …, fail …, or info if you're not sure what happened". A process that times out "is said to be crashed and cannot perform another operation ever again". Source: [Knossos README](https://raw.githubusercontent.com/jepsen-io/knossos/master/README.md). Grade C.
- **Hadoop FileSystem spec, FSDataInputStream "Consistency"**. Readers of a stream from `open(p)` "are expected to receive access to the data of FS.Files[p] at the time of opening. If the underlying data is changed during the read process, these changes MAY or MAY NOT be visible. Such changes that are visible MAY be partially visible." It is formalised as "At time t0 FSDIS0 = FS'read(p) … At time t1 FS' … From time t >= t1, the value of FSDIS0 is undefined". For `readVectored()`: "If a file is changed while the readVectored() operation is in progress, the output is undefined. Some ranges may have old data, some may have new". It also covers failure after return: under lazy seek, "the fact that a file has been deleted or truncated may not surface until that read() call". Source: [hadoop.apache.org fsdatainputstream.html](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-common/filesystem/fsdatainputstream.html). Grade B.
- **S3 User Guide**: see Gap 2. Concurrent GET/PUT returns old or new, never partial; ordering is judged by read start versus write finish. Grade B.
- **Adya-style long-running transactions**: the Adya thesis covers predicate-based reads and multi-operation transactions. A transaction is the classic many-operation unit with extent, and Elle checks such histories. I did not find a passage treating a single long read as a transaction. *Inference:* a stream modelled as a read-only transaction of per-chunk reads would make Adya/Elle's snapshot-style predicates directly usable.

### Cited findings: environment or out-of-band actor distinct from a client
- **Rely–guarantee**: interference is "any state changes made by other processes", as a predicate on state pairs, not a set of API calls. Source: [Jones 1983](https://ilyasergey.net/CS6213/_static/05-owicki/rg.pdf). Grade A.
- **TLA+**:
  - `Next = SysNext ∨ EnvNext` separates environment steps, though Lamport adds that this split "has no formal significance". Open-system specs "are sometimes called rely-guarantee or assume-guarantee specifications".
  - Lamport also writes: "we almost always write closed-system specifications … in practice, there's seldom any reason to do so" (that is, to turn them into open-system specs).
  - Source: [Specifying Systems § 4, § 10.7](https://lamport.azurewebsites.net/tla/book-02-08-08.pdf). Grade A (book by the method's author; treat as authoritative documentation).
- **Abadi–Lamport**: "we must state what we are assuming about its environment". The environment is a separate formula E. Source: [Conjoining](https://lamport.azurewebsites.net/pubs/abadi-conjoining.pdf). Grade A.
- **Benveniste et al.**: a contract is a pair of sets, implementations and "legal environments". Source: [FME review](https://fmeurope.org/2020/10/30/book-review-contracts-for-system-design/), C; monograph not read.
- **Jepsen nemesis**: "The nemesis is a special client, not bound to any particular node, which introduces failures across the cluster", and it draws operations from its own generator. Sources: [Jepsen tutorial ch. 5](https://raw.githubusercontent.com/jepsen-io/jepsen/main/doc/tutorial/05-nemesis.md), C; [Jepsen README](https://raw.githubusercontent.com/jepsen-io/jepsen/main/README.md), C: "a special *nemesis* process introduces faults into the system".
- **P**: the environment is "ghost machines" distinct from "real machines". Source: [P PLDI 2013](https://ankushdesai.github.io/assets/papers/p.pdf). Grade A.

### Inferences
- *Inference:* the report's "gap" on stream extent is a gap in **its survey**, not in the literature. Three things exist: an A-grade formalism (interval-linearizability), A-grade register semantics for overlapping reads (Lamport; Viotti–Vukolić), and two B-grade boundary specs that state exactly H1 (Hadoop FSDataInputStream, S3). The project still has to *decide* the semantics, but it need not invent the vocabulary.
- *Inference:* the cost warning in the substep-linearizability preprint (A-pre) suggests interval-sequential specs are hard to write correctly. That matters for P5 and for agent authoring.
- *Inference:* on O3, rely–guarantee and TLA+ already model an actor outside the API as raw state change. The open question is whether O2 and O3 need *different* environment clauses: O3 may bypass library conventions, while O2 goes through the API. No source read makes that distinction, so the narrower gap stands.

### Gaps
- I found no published method that gives O2 and O3 separate, typed roles. Jepsen's nemesis is the closest, but it is for faults, not data mutation.
- Interface automata (de Alfaro & Henzinger) were not re-read this session.
