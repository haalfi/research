## Q1. Standards practice: how do standards declare variation without forking the base text?

### Takeaway
Standards use a small, fixed set of variation kinds: implementation-defined (a documented choice), unspecified (any of a bounded set, undocumented), undefined (no contract), optional features with fixed IDs, and named profiles or levels. They keep the base text single by putting the variation point in the contract ("value X is implementation-defined") and putting the choice somewhere else: a conformance statement, a header constant, or a runtime query. POSIX is the closest analogue to "declared profile plus runtime query", since every option has a compile-time constant and a `sysconf`/`pathconf` query.

### Cited Findings
- **POSIX options (B, normative) [search-verified]:** Each option symbol in `<unistd.h>` has the value -1, 0 or greater than 0. "If a symbolic constant is defined with the value -1, the option is not supported." A value greater than 0 means "the option shall always be supported when the application is executed". A value of 0 means only that "all headers, data types, and functions shall be present", and support must be checked at runtime "by calling fpathconf(), pathconf(), or sysconf()". "Unless explicitly specified otherwise, the behavior of functions associated with an unsupported option is unspecified." XSI is an option group. — [Open Group Base Specs Issue 6, unistd.h](https://www.gaertner.de/~neitzel/susv3/basedefs/unistd.h.html); [unistd.h(7posix)](https://sites.uclouvain.be/SystInfo/manpages/man7/unistd.h.7posix.html)
  - `_POSIX_SYNCHRONIZED_IO` (synchronized I/O) and `_POSIX_FSYNC` are examples of guarantee-level options, not just extra APIs. — same sources
  - `pathconf` is per path, so the profile can differ per mounted file system, not only per implementation. — [unistd.h(7posix)](https://sites.uclouvain.be/SystInfo/manpages/man7/unistd.h.7posix.html) [search-verified for the existence of fpathconf/pathconf queries; per-path scoping is background]
- **W3C "Variability in Specifications" (B; W3C Working Group Note, 31 Aug 2005, eds. Hazaël-Massieux and Rosenthal/NIST) [search-verified]:** It names seven dimensions of variability. These are classes of product; **profiles** ("subsets of a technology tailored to a particular application community's functional needs"); **modules** (semantically related features forming a unit of functionality); **levels** ("a hierarchy of nested subsets, from minimal or core functionality up to full functionality"); deprecation; **discretionary items** ("explicit grants of discretion... allowing optional behavior, parameter values, or error handling"); and extensibility. The dimensions are not necessarily orthogonal. — [W3C NOTE spec-variability](https://www.w3.org/TR/spec-variability/); [dated version](https://www.w3.org/TR/2005/NOTE-spec-variability-20050831/)
  - "Discretionary items" explicitly cover error handling. That maps directly onto error timing, such as "error at open vs at first read".
- **C/C++ behaviour categories (B, normative) [background, not re-verified]:** ISO C defines *implementation-defined behaviour* as "unspecified behavior where each implementation documents how the choice is made". *Unspecified behaviour* is defined as two or more possibilities with no further requirement on which is chosen. *Undefined behaviour* has no requirements at all. Annex J lists the implementation-defined items, and C++ requires implementations to document them. — [ISO/IEC 9899 draft N1570 §3.4](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)
- **IETF requirement levels (B) [background, not re-verified]:** RFC 2119 defines MUST/SHOULD/MAY. MAY items are where interoperability variation is allowed, and an implementation that omits one "MUST be prepared to interoperate" with one that includes it. RFC 8174 limits the keywords to their uppercase form. Advancement to Internet Standard requires implementation reports showing that features were implemented interoperably (RFC 6410 replaced the older RFC 2026 rules). — [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119); [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174); [RFC 6410](https://www.rfc-editor.org/rfc/rfc6410)
- **SQL standard (B) [background, not re-verified]:** ISO/IEC 9075 names optional features with stable IDs (for example T121, F311), separate from Core SQL. Products publish conformance tables keyed by those IDs, for example PostgreSQL's "SQL Conformance" appendix. Isolation levels are a named, ordered set (READ UNCOMMITTED < READ COMMITTED < REPEATABLE READ < SERIALIZABLE) defined by excluded phenomena. An implementation may run a weaker requested level at a stronger level, which makes it an explicit "stronger profile satisfies weaker contract" rule. — [PostgreSQL SQL Conformance appendix](https://www.postgresql.org/docs/current/features.html); [Berenson et al., "A Critique of ANSI SQL Isolation Levels", SIGMOD 1995 (A)](https://www.microsoft.com/en-us/research/publication/a-critique-of-ansi-sql-isolation-levels/)
- **JDBC DatabaseMetaData (B) [background, not re-verified]:** One interface (the contract) plus about 150 capability queries, for example `supportsTransactionIsolationLevel(int)`, `supportsTransactions()`, `supportsBatchUpdates()`, `locatorsUpdateCopy()`, `nullsAreSortedHigh()`. Callers query the profile at runtime, and unsupported operations throw `SQLFeatureNotSupportedException`. — [java.sql.DatabaseMetaData](https://docs.oracle.com/en/java/javase/21/docs/api/java.sql/java/sql/DatabaseMetaData.html)
- **Java SE optional operations (B) [background, not re-verified]:** In the Collections Framework, interface methods are marked "optional operation" and implementations may throw `UnsupportedOperationException`. Java SE 8 also defined compact profiles (compact1–3) as nested API subsets. — [java.util.Collection](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Collection.html)
- **WebAssembly (B) [background, not re-verified]:** Features arrive as proposals that move through phases. The Wasm 3.0-era specification work adds "profiles", such as a deterministic profile that fixes otherwise non-deterministic behaviour like NaN bit patterns, as named restrictions of the single spec. Engines expose per-feature flags. — [WebAssembly proposals repo](https://github.com/WebAssembly/proposals); [WebAssembly spec](https://webassembly.github.io/spec/)
- **OGC conformance classes (B) [background, not re-verified]:** OGC's modular specification policy requires every requirement to belong to a requirements class, with a matching conformance class of abstract tests. Implementations declare which classes they conform to, and OGC API servers list them at a `/conformance` endpoint, which is a machine-readable runtime profile. — [OGC Modular Specification Policy 08-131r3](https://docs.ogc.org/is/08-131r3/08-131r3.html); [OGC API – Features Part 1 /conformance](https://docs.ogc.org/is/17-069r4/17-069r4.html)
- I did not find or verify a source for ISO/IEC 10646 profiles or collections in this session.

### Inferences
- **Inference:** The common pattern is that the contract names the variation point and its allowed range, and the profile states the choice. C's implementation-defined behaviour, POSIX option constants, OGC conformance classes and SQL feature IDs all follow it. In each case the base text has one sentence per variation point, so per-implementation detail cannot grow inside the contract.
- **Inference:** "Unspecified with a bounded set" is the right category for things a caller must tolerate without being told, such as whether a read stream sees concurrent writes. "Implementation-defined with a declared value" is the right category for things a caller may branch on.
- **Inference:** OGC is the strongest model for P4 ("every claim names its check"), because requirement → conformance class → abstract test is a policy-mandated chain.

### Gaps
- Exact wording of C/C++, RFC 2119, SQL, OGC and WebAssembly profile texts was not fetched this session. These items carry grade B for the source type, but my quoting of them is unverified.
- ISO/IEC 10646 profiles: no source found.

## Q2. Software-engineering theory: product lines, parameterised specs, refinement, subtyping, consistency lattices

### Takeaway
The academic toolbox gives four complementary devices. Feature models give a declared, constraint-checked profile vocabulary. Parameterised algebraic specs give a single contract with a formal parameter whose axioms are the minimum guarantee. Refinement and behavioural subtyping give the proof obligation that a stronger profile still satisfies the base contract. Consistency hierarchies give a ready-made partial order of guarantee levels.

### Cited Findings
- **Product-line analysis (A) [search-verified metadata]:** Thüm, Apel, Kästner, Schaefer and Saake, "A Classification and Survey of Analysis Strategies for Software Product Lines", ACM Computing Surveys 47(1), 2014, DOI 10.1145/2580950. It classifies more than 100 approaches (the ACM record says 123 articles) for statically analysing product lines, such as type checking and model checking. — [Uni Passau PDF](https://www.infosun.fim.uni-passau.de/publications/docs/TAK14.pdf); [Saarland PDF](https://www.se.cs.uni-saarland.de/publications/docs/TAK+15se.pdf)
  - **[background, not re-verified]** The survey separates *product-based* analysis (check each variant), *family-based* analysis (check the whole family once, using the feature model), and *feature-based* analysis (check each feature in isolation). It also covers specification approaches, including family-wide versus feature-local specifications. This maps onto the choice between checking each backend separately and checking the contract once while parameterising tests by profile.
- **FODA (A/B, SEI technical report) [background, not re-verified]:** Kang et al. 1990, CMU/SEI-90-TR-21, introduced feature models with mandatory, optional and alternative features plus requires/excludes constraints. A backend profile is then a valid configuration of the feature model. — [SEI report](https://insights.sei.cmu.edu/library/feature-oriented-domain-analysis-foda-feasibility-study/)
- **Parameterised algebraic specification (A) [background, not re-verified]:** CASL (Astesiano et al., TCS 2002) and Larch (Guttag and Horning, 1993) support generic specs `spec S[P]` where the formal parameter P has its own axioms, and instantiation requires a "fitting" morphism proving the actual parameter satisfies P. — [CASL overview, TCS 286(2) 2002](https://doi.org/10.1016/S0304-3975(01)00368-1)
- **Event-B refinement (A) [background, not re-verified]:** Abrial's Event-B (CUP 2010) puts refinement proof obligations on every concrete machine to show it preserves the abstract machine's invariants. A stronger backend is then a refinement of the abstract contract. — [Event-B / Rodin](https://www.event-b.org/)
- **Behavioural subtyping (A) [background, not re-verified]:** Liskov and Wing, "A Behavioral Notion of Subtyping", ACM TOPLAS 16(6), 1994. A subtype must have weaker or equal preconditions, stronger or equal postconditions, and preserve invariants and history constraints. — [DOI 10.1145/197320.197383](https://doi.org/10.1145/197320.197383)
- **Consistency hierarchy (A) [search-verified]:** Viotti and Vukolić, "Consistency in Non-Transactional Distributed Storage Systems", ACM Computing Surveys 49(1), 2016, DOI 10.1145/2926965. The survey defines "more than 50 different consistency notions, ranging from linearizability to eventual and weak consistency" and arranges them in a partial order by semantic strength. — [EUREcom record](https://www.eurecom.fr/en/node/4903210); [PDF](https://www.eurecom.fr/publication/4781/download/rs-publi-4781.pdf)

### Inferences
- **Inference:** Behavioural subtyping is what makes "one contract plus profile" sound. The base contract states the weakest guarantee. A profile value may only *strengthen* a postcondition or *narrow* an unspecified range, never weaken it. If a backend needs to weaken it, the base contract was too strong and must widen the allowed range at that variation point (one edit, in one home).
- **Inference:** Profile axes such as consistency or read-isolation should take their values from an existing published lattice like Viotti and Vukolić, rather than inventing per-backend prose. That keeps per-reality detail bounded to "pick a node".
- **Inference:** Family-based checking is the analogue of one contract test suite that reads the profile, while product-based checking is the analogue of separate per-backend test suites. The latter tends to fork the contract.

### Gaps
- No peer-reviewed source found that applies product-line specification specifically to storage or filesystem API contracts.

## Q3. Industrial API practice: how storage abstractions declare, query and test differences

### Takeaway
Apache Hadoop is the most developed precedent. It has a normative spec in set-theoretic, Python-like notation and per-filesystem XML contract-option files that the shared contract test suite reads to skip or adapt tests. It also has a runtime `PathCapabilities` probe and explicit MAY clauses for object-store differences such as lazy open. Its history includes a coarse flag ("is-blobstore") that turned out to hide several distinct properties and had to be split. OpenDAL takes a different route: a typed `Capability` struct, with a native/full split that separates what the backend guarantees from what layers emulate.

### Cited Findings
**Apache Hadoop FileSystem specification (B)**
- The spec states a core model and assumptions, and flags where object stores break them. "Hadoop assumes that directory rename() operations are atomic, as are delete() operations. Object store FileSystem clients implement these as operations on the individual objects whose names match the directory prefix." "Object stores are generally *Eventually Consistent*". [search-verified] — [Hadoop FS spec introduction (stable)](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-common/filesystem/introduction.html); [3.4.2 intro](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-common/filesystem/introduction.html)
- In current versions, object-store caveats appear inline in operation definitions: "for object stores, even with the same enclosing root, there is no guarantee file or directory rename is atomic". The 3.6.0-SNAPSHOT spec adds etag requirements and says "appropriate etag Path Capabilities SHOULD be declared". [search-verified] — [filesystem.html 3.4.2](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-common/filesystem/filesystem.html); [3.6.0-SNAPSHOT](https://apache.github.io/hadoop/hadoop-project-dist/hadoop-common/filesystem/filesystem.html)
- **Running example, open-for-read (directly relevant):** For `open()`, implementations "MUST check for the presence of the file at the time of creation", noting that "much client code does depend on the existence check being performed at the time of the open() operation". For the newer `openFile()` builder, the stream "MAY implement a lazy open where file non-existence or access permission failures may not surface until the first read()". This is motivated by object stores, which "could shortcut one round trip by postponing their HTTP GET operation until the first read()". The builder spec says the inability to read a file "MUST raise an IOException or subclass in either the future's get() call, or, for late binding operations, when an operation to read data is invoked". `openFile()` file-specific preconditions "MUST NOT be checked here". [search-verified] — [openfile.html](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-common/filesystem/openfile.html); [fsdatainputstreambuilder.html](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-common/filesystem/fsdatainputstreambuilder.html); [filesystem.html 3.6.0-SNAPSHOT](https://apache.github.io/hadoop/hadoop-project-dist/hadoop-common/filesystem/filesystem.html)
  - So Hadoop handled error-timing variation by adding a *second API entry point* with a wider contract (a MAY clause), rather than letting `open()` vary per backend.
- **Contract tests driven by declared options:** Each filesystem has an XML contract file (for example `contract/localfs.xml`). The testing doc says "defining all options in that XML makes the listing of FileSystem behaviors immediately visible". Remote filesystems need `contract-test-options.xml` with credentials and are skipped otherwise. [search-verified] — [Testing the Filesystem Contract (3.1.2)](https://hadoop.apache.org/docs/r3.1.2/hadoop-project-dist/hadoop-common/filesystem/testing.html); [3.6.0-SNAPSHOT](http://apache.github.io/hadoop/hadoop-project-dist/hadoop-common/filesystem/testing.html)
- Option names are constants in `ContractOptions.java`, for example `supports-atomic-rename`, `supports-atomic-directory-delete`, `supports-seek` ("is seeking supported at all"), and `supports-seek-on-closed-file` (some filesystems "only fail later when reading"). A third-party filesystem (cephfs-hadoop) adopted the suite by supplying an XML that sets `supports-atomic-rename`=true, `supports-seek`=true and `supports-concat`=false. [search-verified] — [ContractOptions.java mirror](https://github.com/c9n/hadoop/blob/master/hadoop-common-project/hadoop-common/src/test/java/org/apache/hadoop/fs/contract/ContractOptions.java); [cephfs-hadoop commit](https://github.com/ceph/cephfs-hadoop/commit/c4d0d20859fc820f416fa2a4784034f44dd8961a)
- **Drift and coarse flags (C, issue-tracker evidence):** HADOOP-13502 states that `fs.contract.is-blobstore` "guards against execution of several contract tests to account for known limitations with blob stores", but "it's still possible that a file system implemented against a blob store could pass those tests". It proposed renaming the flag or splitting it into narrower flags, and was resolved for 2.8.0 / 3.0.0-alpha2. HADOOP-13501 found that WASB "is still capable of passing these tests, because its implementation matches the semantics of HDFS", and turned the flag off so the tests ran. [search-verified] — [HADOOP-13502](https://jira.apache.org/jira/browse/HADOOP-13502); [HADOOP-13501](https://jira.apache.org/jira/browse/HADOOP-13501)
  - I could not confirm the names of the replacement flags. I recall `create-visibility-delayed` and `create-overwrites-directory`, but they are **unverified**.
- **Runtime probe [background, not re-verified]:** Hadoop 3.3 added `PathCapabilities.hasPathCapability(path, capability)` with string keys in `CommonPathCapabilities` (for example `fs.capability.paths.append`, `fs.capability.etags.available`). Its spec says a `true` result is a promise and `false` may mean "unknown". — [Hadoop pathcapabilities.html](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-common/filesystem/pathcapabilities.html)
- **Spec notation [background, not re-verified]:** The spec models a filesystem as sets and maps (`paths`, `files`, `data`) and states operations as preconditions and postconditions in Python-like pseudocode. It treats HDFS behaviour as the reference, and the introduction notes that HDFS behaviour is what is expected unless stated otherwise. — [Hadoop FS spec model](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-common/filesystem/model.html)

**Apache OpenDAL (B/C)**
- Each `OperatorInfo` exposes two capability sets. `native_capability` holds what the storage backend supports natively. `full_capability` adds what layers emulate (example: blocking via `BlockingLayer`). Users should use `full_capability` to decide what is available and `native_capability` to find optimised operations. The RFC's motivation: users "are unable to determine whether it is a native capability or not, which may result in them unknowingly utilizing this feature in performance-sensitive scenarios". [search-verified] — [RFC 2852 native_capability](https://docs.rs/crate/opendal-core/0.58.1/source/src/docs/rfcs/2852_native_capability.md); [Capability struct](https://opendal.apache.org/docs/rust/opendal/struct.Capability.html)
- `CapabilityOverrideLayer` "updates Capability exposed by OperatorInfo::full_capability without changing the accessor's native capability". The RFC notes that the behaviour test harness already edited `full_capability` by hand (`core/tests/behavior/async_delete.rs`). [search-verified] — [RFC 6707](https://docs.rs/crate/opendal-core/0.58.1/source/src/docs/rfcs/6707_capability_override_layer.md); [CapabilityOverrideLayer](https://opendal.apache.org/docs/rust/opendal/layers/struct.CapabilityOverrideLayer.html)
- A `capability_check` layer enforces declared capabilities at call time. [search-verified existence] — [capability_check.rs](https://opendal.apache.org/docs/rust/src/opendal/layers/capability_check.rs.html)
- An RFC dated 2026-06-05 (PR #7700) proposes collapsing native/full into one user-facing `Capability`, keeping the service-declared state internal. Its acceptance status is unconfirmed. [search-verified] — [RFC 7700](https://docs.rs/crate/opendal-core/latest/source/src/docs/rfcs/7700_capability_api.md)
- **[background, not re-verified]** OpenDAL behaviour tests are one suite run against every service, and each test is gated on the service's declared capability (for example, skip if `!cap.write_can_append`).

**fsspec (C)**
- `AbstractFileSystem` declares class-level flags such as `cachable`, `async_impl` and `mirror_sync_methods`, plus a newer `transaction_type`. These are mostly implementation and plumbing flags, not semantic guarantees. The only atomicity-like mechanism is a transaction context where files "are committed together upon exit", which requires the file class to implement `.commit()`/`.discard()`. [search-verified] — [fsspec.spec source](https://filesystem-spec.readthedocs.io/en/latest/_modules/fsspec/spec.html)
- No declared semantic profile (consistency, atomicity, error timing) was found for fsspec.

**Not verified this session:** Apache Arrow FileSystem docs, jclouds/libcloud capability flags, and S3-compatibility matrices (for example Ceph RGW or MinIO feature tables). I recall that libcloud publishes provider feature matrices and Arrow documents per-filesystem caveats in prose, but I have no citation from this session. Treat these as a **gap**.

### Inferences
- **Inference:** Hadoop shows the three parts of a working profile system, kept apart. (1) The normative contract with explicit MUST/MAY points. (2) A declared profile (contract XML for tests, `PathCapabilities` at runtime). (3) A single contract test suite that reads the profile. The weak spot is that (2) is split between a test-only XML and a runtime probe with a different vocabulary, so the two can drift.
- **Inference:** HADOOP-13502 shows that coarse "kind of backend" flags ("is-blobstore") fail. Profiles should name individual guarantees, never backend categories.
- **Inference:** OpenDAL's native/full split is a useful lesson. A profile must say whether a guarantee is intrinsic or emulated by a wrapper. For the running example, a stream's isolation from concurrent writes could be native (snapshot/version read) or emulated (buffer-on-open), with different cost but the same observable contract.

- Arrow, jclouds, libcloud and S3-compat matrices: no verified citations.
- No measured data on how often Hadoop contract-XML options disagree with `hasPathCapability` answers.

## Q4. How is a profile checked, and what evidence of drift exists when per-backend notes live in the main contract?

### Takeaway
The verified mechanism is a single shared test suite that reads a per-backend declared-options file and skips or adapts tests (Hadoop, OpenDAL). The verified drift evidence is limited to issue-tracker reports (C grade). Hadoop's `is-blobstore` flag both suppressed tests that a backend could actually pass and blurred several distinct properties. I found no measured study of drift.

### Cited Findings
- Hadoop's shared contract tests read per-filesystem XML options and skip tests whose options are false, or skip whole suites when no endpoint is configured. — [Testing the Filesystem Contract](https://hadoop.apache.org/docs/r3.1.2/hadoop-project-dist/hadoop-common/filesystem/testing.html) [search-verified]
- Coarse declared options hid real capability: WASB passed the guarded tests once `is-blobstore` was turned off. — [HADOOP-13501](https://jira.apache.org/jira/browse/HADOOP-13501); [HADOOP-13502](https://jira.apache.org/jira/browse/HADOOP-13502) [search-verified, C]
- OpenDAL's test harness manipulated `full_capability` by hand, which led to a dedicated override layer. That suggests tests need to *set* profiles, not only read them. — [RFC 6707](https://docs.rs/crate/opendal-core/0.58.1/source/src/docs/rfcs/6707_capability_override_layer.md) [search-verified, C]
- Hadoop's per-store caveats live inside operation definitions ("for object stores ... no guarantee rename is atomic"), and newer versions add SHOULD-declare-capability clauses. This reads as a move from prose caveats toward declared capabilities over time. — [filesystem.html 3.6.0-SNAPSHOT](https://apache.github.io/hadoop/hadoop-project-dist/hadoop-common/filesystem/filesystem.html) [search-verified for the clauses; the trend reading is **Inference**]
- POSIX makes an unchecked use of an unsupported option behave in an "unspecified" way. The contract keeps the conditional; it does not fork. — [unistd.h Issue 6](https://www.gaertner.de/~neitzel/susv3/basedefs/unistd.h.html) [search-verified]

### Inferences
- **Inference:** Tests should be written against the variation point, not against the backend. For the running example, one test might assert "a missing key raises NotFound at open OR at first read, per profile field `open_error_timing ∈ {eager, lazy}`". The test reads the profile and asserts the declared branch. It never skips the check entirely.
- **Inference:** Add a meta-check that every profile field is read by at least one test and every test-gating flag is a profile field. That catches the Hadoop failure mode where a flag guards more tests than its name implies.
- **Inference:** Per-backend notes inside the main contract grow with each backend. Hadoop's spec has accumulated object-store caveats across versions (2.7 → 3.6). I have not measured this, so the growth claim is an inference and should not be presented as data.

### Gaps
- No peer-reviewed or measured study of spec/test drift across storage backends found.
- Could not open the HADOOP JIRA history beyond search snippets. The replacement flag names and the S3A-specific contract XML contents are unverified.

## Q5. Fit to principles P1–P4

### Takeaway
The mechanisms that fit all four principles together combine: a single contract whose variation points are named, typed fields with bounded value sets (C implementation-defined / W3C discretionary item / POSIX option); a separate machine-readable profile per backend (Hadoop XML, OpenDAL Capability, OGC /conformance, JDBC metadata); a stronger-only refinement rule (Liskov and Wing); and one test suite that reads the profile, with a conformance class per requirement (OGC).

### Cited Findings
- P1 (what, not how): POSIX options and SQL isolation levels define observable behaviour or excluded phenomena, not mechanisms. — [unistd.h](https://www.gaertner.de/~neitzel/susv3/basedefs/unistd.h.html) [search-verified]; [Berenson et al. 1995](https://www.microsoft.com/en-us/research/publication/a-critique-of-ansi-sql-isolation-levels/) [background]. OpenDAL's native/full split shows that "how" (native vs emulated) can be declared separately from "what". — [RFC 2852](https://docs.rs/crate/opendal-core/0.58.1/source/src/docs/rfcs/2852_native_capability.md) [search-verified]
- P2 (one home per rule): W3C's variability note treats each variability dimension as a deliberate design choice of the single spec. — [W3C NOTE](https://www.w3.org/TR/spec-variability/) [search-verified]
- P3 (bounded per-reality detail, kept apart): The Hadoop contract XML keeps per-filesystem declarations outside the spec and makes "the listing of FileSystem behaviors immediately visible". — [testing.html](https://hadoop.apache.org/docs/r3.1.2/hadoop-project-dist/hadoop-common/filesystem/testing.html) [search-verified]. Counterexample: Hadoop's inline object-store caveats. — [filesystem.html](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-common/filesystem/filesystem.html) [search-verified]
- P4 (every claim names its check): OGC requirement → conformance class → abstract test. — [OGC 08-131r3](https://docs.ogc.org/is/08-131r3/08-131r3.html) [background]. In Hadoop, contract options are tied to specific contract test classes. — [ContractOptions.java](https://github.com/c9n/hadoop/blob/master/hadoop-common-project/hadoop-common/src/test/java/org/apache/hadoop/fs/contract/ContractOptions.java) [search-verified]

### Inferences
- **Inference: fit summary per mechanism**

| Mechanism | Base contract stays single? | What becomes checkable | P1 | P2 | P3 | P4 | Evidence grade |
