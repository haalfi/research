## Q1 (A2): Per state kind: storage location, read/export path, rebuild path, verdict if Dagster is replaced

### Takeaway
All seven state kinds live in Dagster's own SQL tables. In Postgres the run, event-log and schedule storages are usually one database. Most of the values are Dagster-serialized blobs (`run_body`, `event`, `instigator_body`, `tick_body`, `bulk_actions.body`), not plain columns. Reading is well served by documented-but-"internal" `DagsterInstance` methods, GraphQL, and direct SQL. A faithful import into another Dagster instance exists only per run, through `dagster debug export`/`import`, which is a debugging tool. Any other rebuild re-reports events, which gives them new timestamps and an empty run_id. Another orchestrator such as Databricks Lakeflow can read none of this natively. If Dagster is removed, every state kind is lost unless it is copied out first (**inference**).

**Direct SQL on Postgres**
- All the tables above can be queried directly. Most payload columns, however, are Dagster-serialized documents (`run_body`, `event`, `instigator_body`, `tick_body`, `body`). The serialization format (Dagster serdes JSON with class markers) is **inference**: I did not read `_serdes` in this run. Decoding outside Python Dagster means re-implementing that format. Dagster docs describe storage subclasses as things "Users should not directly instantiate" (live Internals page). The schema changes between minors, as the many `dagster instance migrate` steps in CHANGES 1.9.0–1.12.9 show.

### Inferences
- Because Lakeflow and Dagster would share "the same storage", any pipeline decision based on Dagster state needs either a Dagster-API reader or direct SQL against tables that Dagster migrates on upgrade. Neither is designed as a cross-orchestrator contract.
- Gate verdicts (item 1) are the most tightly coupled to Dagster. Re-execution semantics come from the engine walking run ancestry and event logs. Removing even one ancestor run with `delete_run` breaks `from-failure` re-execution with `DagsterRunNotFoundError`.
- State that is small and exact (sensor cursors, dynamic partition keys, pool limits, schedule on/off) can be exported and replayed losslessly. Event-shaped history (materialisations, check results, ticks, backfills) cannot be replayed faithfully through public paths, because public writers stamp events with the current time.

### Gaps
- I did not verify whether `instance.store_event` on a runless re-insert keeps the `asset_check_executions` index and the partition status cache consistent for imported events. The debug-import path relies on it.
- I did not trace exactly how `selector_id` is derived (code location, repository and instigator name). Renaming the code location or repository probably orphans instigator state (**inference**, unverified).
- I did not check Postgres-specific storage (`dagster-postgres`) for differences from the generic SQL storage (for example `wipe_asset_partitions`, see Q3).

## Q2: Which APIs are public and stable versus internal, preview or deprecated, and what changed from 1.9 to 1.13

### Takeaway
On `DagsterInstance` (1.13.27), the methods marked `@public` and listed on the docs "Internals" page are listed below in the findings. The Internals page also warns that APIs from submodules "are not considered stable". All storage-level readers are internal: tick, backfill and instigator-state readers, asset-check history, `get_materialized_partitions`, `store_event` and the cursor KV. `get_event_records` and `fetch_planned_materializations` are deprecated with removal at 2.0. GraphQL is explicitly "subject to breaking changes". The 1.9–1.13 changes touching this state are schema migrations, pool naming and enforcement, check wipe semantics, and a 1000-row GraphQL log default limit. None of them removes a public instance method.

## Q3: Supported export/import of materialisation history, practitioner migration reports, retention

### Takeaway
Dagster's official answer for moving history is a **sample job, not a feature**. The OSS→Dagster+ guide says Dagster+ metadata "will be empty". You either start fresh at cutover or follow the `oss-metadata-to-plus` example, which reads `fetch_materializations` and POSTs each record to `/report_asset_materialization/`. The only round-trip that keeps timestamps and run IDs is the per-run `dagster debug export/import`. OSS retention covers schedule, sensor and auto-materialize ticks only. Runs and events are never purged automatically. `dagster asset wipe` is a logical wipe of the asset index plus a delete of the check executions. I obtained no first-hand practitioner reports.

### Cited Findings

### Inferences
- Moving the whole instance (Postgres to Postgres, same Dagster version) through `pg_dump`/restore keeps everything, because all state is in those tables and `dagster.yaml`. I found no Dagster doc stating this, so it is inference.
- Because OSS never auto-purges runs or events, "read state back" logic can rely on full history by default. Tick-based reasoning is limited by `purge_after_days`. Skipped sensor ticks disappear after 7 days by default.
- Re-reporting history through `report_runless_asset_event` or REST makes every imported event look like it happened at import time and outside any run (`run_id=""`). Any downstream "latest" or "lateness" logic would read it wrongly unless it uses an event time stored in metadata.
