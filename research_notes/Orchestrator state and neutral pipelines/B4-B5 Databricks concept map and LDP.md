# B4-B5 Databricks concept map and LDP

Scope: the Databricks side of the concept map (B4) and the cost of running pipelines on Databricks with or without Declarative Pipelines (B5). Dagster terms only describe the concept. Retrieved 2026-10-27. All docs.databricks.com pages below were fetched in full with curl (HTTP 200) and converted to text. Each carries the page's own "Last updated" date. Grades: **[doc <date>]** = vendor doc with date; **[first-hand]** = practitioner report with an outcome; **[inferred]** = my inference; **[lead]** = search snippet only, not verified.

## Q0. Current product names and status (this frames every row)

### Takeaway
As of Oct 2026 the Databricks docs call DLT "**Lakeflow pipelines**", and the full title is "Spark Declarative Pipelines on Lakeflow". The name "Lakeflow Declarative Pipelines" (2025) has been dropped from the doc titles. Databricks Asset Bundles are now "**Declarative Automation Bundles**", and Workflows is "**Lakeflow Jobs**". The open-source core is Apache Spark Declarative Pipelines (SDP), which ships from Spark 4.1 (Spark 4.2.0 docs are current). Expectations, AUTO CDC, the event log and continuous mode are Databricks-only.

### Cited Findings
- The LDP landing page is titled "Spark Declarative Pipelines on Lakeflow": "Lakeflow pipelines are built on Apache Spark Declarative Pipelines and are interoperable with it. They extend it with additional functionality and run on the performance-optimized Databricks Runtime" [doc Oct 22, 2026] — [Spark Declarative Pipelines on Lakeflow](https://docs.databricks.com/aws/en/ldp/)
- "The product formerly known as Delta Live Tables (DLT) has been updated to Lakeflow pipelines… no migration required… your code will still work". `import dlt` becomes `from pyspark import pipelines as dp`, `@table` now creates streaming tables, the new `@materialized_view` creates MVs, and `@view` becomes `@temporary_view`. "The classic SKUs for Lakeflow pipelines still begin with DLT, and event log schemas with dlt in the name have not changed" [doc Sep 11, 2026] — [What happened to DLT?](https://docs.databricks.com/aws/en/ldp/where-is-dlt)
- "Declarative Automation Bundles (formerly known as Databricks Asset Bundles)" [doc Sep 11, 2026] — [Bundles](https://docs.databricks.com/aws/en/dev-tools/bundles/)
- "Apache Spark includes declarative pipelines beginning in Spark 4.1, available through the pyspark.pipelines module… Code written with the open-source pipelines module runs without modification on Databricks." The differences table marks these as **not** in Apache Spark: event log, Apply Changes/AUTO CDC (`dp.create_auto_cdc_flow`), expectations (`dp.expect`), continuous mode, `@dp.update_flow`, `@dp.foreach_batch_sink`, `@dp.foreach_sink`. These **are** in Apache Spark: imports, `@dp.table`, `@dp.materialized_view`, `@dp.temporary_view`, `@dp.append_flow`, SQL `CREATE STREAMING TABLE / MATERIALIZED VIEW / FLOW`, `dp.create_sink` [doc Oct 25, 2026] — [Python reference](https://docs.databricks.com/aws/en/ldp/developer/python-ref)
- The open-source SDP guide (Spark 4.2.0 docs) covers flows, datasets (streaming table, materialized view, temporary view), a `spark-pipeline.yml` spec with `storage` (checkpoints, required), `catalog` and `libraries`, and the `spark-pipelines init|run|dry-run` CLI built on spark-submit. Run options are `--full-refresh`, `--full-refresh-all` and `--refresh`, and the default is "incremental update". The guide never mentions expectations [doc, Spark 4.2.0, no date on page] — [SDP Programming Guide](https://spark.apache.org/docs/latest/declarative-pipelines-programming-guide.html)
- A Databricks blog (Feb 23, 2026; Aslam, Zhu, Zaharia) lists the Spark 4.1 SDP features as Python/SQL APIs, batch and streaming, automatic dependency tracking with parallel updates, and a CLI. In its example `@dp.expect_or_drop` is commented out because Databricks is "working with the community to open source it". Continuous execution, "more efficient incremental processing" and CDC are roadmap items [doc Feb 23, 2026; vendor blog, read via fetch summary] — [Databricks blog](https://www.databricks.com/blog/spark-declarative-pipelines-why-data-engineering-needs-become-end-end-declarative)
- Spark 4.1.0 was released in January 2026 [lead: conference abstract] — [Berlin Buzzwords 2026](https://2026.berlinbuzzwords.de/session/apache-spark-declarative-pipelines-in-action/)

## Q1 (B4). Concept-by-concept Databricks equivalents

### Takeaway
Databricks has strong equivalents for event triggers, retries, per-task compute, notifications, run history in system tables, and lineage. It has **no equivalent** for partitions as a first-class concept, partition mappings, named cross-job concurrency pools, manually recorded check results, code-version staleness, or a static freshness SLA on an arbitrary table. Assets are split across products: datasets inside pipelines (LDP), tasks (Jobs) and tables (UC). No single object plays the role of a Dagster asset.

### Cited Findings (row per concept; **NO-EQ** = no equivalent, **DIFF** = different semantics)

1. **Asset as unit of definition, with dependencies.** DIFF. In LDP the units are datasets (streaming table, materialized view, temporary view) written by flows, and "the pipeline… analyzes the dependencies of your defined objects and orchestrates their order". In Jobs the unit is the task, and dependencies are declared between tasks, not tables. In UC the unit is the table, which is a governed object with lineage but no definition of how it is built [doc Oct 13, 2026] — [Pipeline concepts](https://docs.databricks.com/aws/en/ldp/concepts); [SDP guide](https://spark.apache.org/docs/latest/declarative-pipelines-programming-guide.html). Limits: 1,000 datasets per pipeline, 1,000 concurrent pipeline updates per workspace, 12,000 saved pipelines [doc Oct 21–22, 2026] — [Pipeline limitations](https://docs.databricks.com/aws/en/ldp/limitations); [Resource limits](https://docs.databricks.com/aws/en/resources/limits)
2. **One step producing several assets.** DIFF. One pipeline update produces many datasets. "Pipeline datasets can be defined only once… the target of only a single operation across all pipelines". The exception is append flows, where several flows write one streaming table [doc Oct 22, 2026] — [Pipeline limitations](https://docs.databricks.com/aws/en/ldp/limitations). In Jobs one task can write any number of tables, but the platform does not track them as outputs (only UC lineage records them after the fact) [inferred].
3. **Observed external source not produced by the platform.** Partial or DIFF. UC "external metadata" objects let you register sources such as Salesforce or MySQL and add them to the lineage graph, created through the UI or the External Metadata/External Lineage APIs. They are lineage nodes, not observed or versioned sources [doc Oct 7, 2026] — [External lineage](https://docs.databricks.com/aws/en/data-governance/unity-catalog/external-lineage). File-arrival and table-update triggers watch UC volumes, external locations and UC tables. Table-update triggers also cover OpenSharing objects and system tables, which is GA per release notes [doc Oct 2, 2026] — [Table update triggers](https://docs.databricks.com/aws/en/jobs/trigger-table-update). A vendor's job state (for example an API status) has **NO-EQ** short of a custom polling task [inferred].
4. **Data-quality checks attached to an asset; blocking checks.** LDP expectations come with actions `warn` (default), `drop` (`expect_or_drop` / `ON VIOLATION DROP ROW`) and `fail` (`expect_or_fail` / `ON VIOLATION FAIL UPDATE`, which "atomically rolls back the transaction"). "In a triggered pipeline, the failure of a single flow does not cause other parallel flows to fail"; in continuous mode it stops the flow and its dependents. With `fail`, "metrics are not recorded". For control over downstream work, the doc says to "split the validation and downstream work into separate pipelines and coordinate them with control flow between the pipeline tasks". Expectations are row-level SQL booleans; aggregate checks need patterns such as validation tables [doc Oct 26, 2026] — [Expectations](https://docs.databricks.com/aws/en/ldp/expectations). Expectations require the **Advanced** product edition (Core = streaming ingest, Pro = adds CDC), and serverless pipelines require Advanced [doc Oct 12, 2026] — [Configure pipelines](https://docs.databricks.com/aws/en/ldp/configure-pipeline). In Jobs, the If/else condition task compares a task value or parameter with `==, !=, >, >=, <, <=` and branches true/false. `==` is a string comparison (`12.0 == 12` is false) [doc Sep 11, 2026] — [If/else](https://docs.databricks.com/aws/en/jobs/if-else). UC "Data quality monitoring" consists of anomaly detection (freshness and completeness, **Public Preview**, with Beta sub-features) and data profiling, which was "formerly known as Lakehouse Monitoring". It runs on serverless, billed under `DATA_QUALITY_MONITORING`, and does not block writers: "Anomaly detection does not modify any tables it monitors, nor does it add overhead to any jobs" [doc Sep 11 / Oct 23, 2026] — [DQ monitoring](https://docs.databricks.com/aws/en/data-quality-monitoring/); [Anomaly detection](https://docs.databricks.com/aws/en/data-quality-monitoring/anomaly-detection/). A blocking check outside LDP = a check task that fails, or an If/else on its task value [inferred].
5. **Manual check result recorded by a human.** **NO-EQ**. The closest is in anomaly-detection incidents: "Assign to me" or "Not an issue", which dismisses a false positive, and "The dismissal persists for 7 days" [doc Oct 23, 2026] — [Anomaly detection](https://docs.databricks.com/aws/en/data-quality-monitoring/anomaly-detection/). This is an incident triage state, not a recorded check result on an asset [inferred].
6. **Partitions (daily, time-window, static, 2-D, mappings).** **NO-EQ** as an orchestration concept. Jobs have parameters and the For-each task. For-each takes a JSON array input, has a Concurrency value (default 1), does not allow a nested For-each, and its inputs are capped at 5,000 characters in the UI, 48 KB via task values and 10,000 characters for job parameters [doc Sep 22, 2026] — [For each](https://docs.databricks.com/aws/en/jobs/for-each). Table partitioning and liquid clustering are storage layout, not run units [inferred; storage pages not fetched]. A nested For-each is not allowed, so a 2-D grid has to be flattened into one array [inferred from doc].
7. **Backfills.** DIFF. "Run backfill" in the Jobs UI splits a date range by an interval into runs, for example 48 hourly runs. Each run gets value references such as `{{backfill.iso_datetime}}`. More than 100 runs are blocked, so the range must be split. Runs are named "Backfill", and parallelism follows the job's max concurrent runs. Limitations: "Backfills always run completely. You can't run a subset of tasks or tables"; pipeline tasks are not parameterized and run sequentially; for LDP the doc recommends "append once" flows. Creation is documented as UI only, and the page shows no preview label [doc Sep 11, 2026] — [Backfill jobs](https://docs.databricks.com/aws/en/jobs/backfill-jobs). There is one-run-per-interval but **no single-run-over-a-range** mode, other than one manual run with range parameters [inferred]. No GA date was found.
8. **Cron schedules over partitions.** DIFF. Scheduled triggers exist, but a tick is not bound to a partition key; the job reads the trigger time from a parameter [inferred from backfill doc]. "Multiple triggers in Lakeflow Jobs is in **Beta**": several triggers of mixed types per job, each paused independently, configured through the `triggers` array (Jobs API 2.1). A continuous trigger cannot be combined with others. A workspace can have at most 12,000 active triggers [doc Oct 23, 2026] — [Triggers](https://docs.databricks.com/aws/en/jobs/triggers)
9. **Event-driven triggers vs polling sensors with a cursor.** Trigger types: Scheduled, Table update, File arrival, Model update, Continuous [doc Oct 23, 2026] — [Triggers](https://docs.databricks.com/aws/en/jobs/triggers). Table update has "Minimum time between triggers" and "Wait after last change" (debounce) settings. It exposes `commit_timestamp` and `version` dynamic values per table, which act as a platform-held cursor. Limits: at most 1,000 jobs with table-update triggers without file events, 10 tables per trigger, 10 dependent views per monitored view, and views using `read_files` are unsupported [doc Oct 2, 2026] — [Table update triggers](https://docs.databricks.com/aws/en/jobs/trigger-table-update). There is **NO-EQ** for a user-coded sensor with a custom cursor [inferred].
10. **Declarative "run when upstream changes OR cron tick".** Partial. With multiple triggers (Beta), "you can use a table update trigger to start a job run when data is ready, and add an additional scheduled trigger as a backup" [doc Oct 23, 2026] — [Triggers](https://docs.databricks.com/aws/en/jobs/triggers). Conditions are per job, not per asset, and there is no AND or "missing partition" logic [inferred].
11. **Freshness expectations and breach alerting.** DIFF. UC anomaly detection freshness is learned: it "builds a per-table model to predict the time of the next commit. If a commit is unusually late, the table is marked as stale". Schema-level alerts can be configured. "Event freshness… was available only to users of the data quality monitoring beta… In the current version, event freshness is not supported". Status is **Public Preview** [doc Oct 23, 2026] — [Anomaly detection](https://docs.databricks.com/aws/en/data-quality-monitoring/anomaly-detection/). Jobs offer run-duration and streaming-backlog thresholds ("Streaming observability for Lakeflow Jobs is in **Public Preview**"); backlog thresholds are not supported for pipeline tasks [doc Sep 11 / Oct 21, 2026] — [Configure job](https://docs.databricks.com/aws/en/jobs/configure-job); [Configure task](https://docs.databricks.com/aws/en/jobs/configure-task). A static "table must be no older than N hours" SLA has **NO-EQ** short of a SQL alert on table history [inferred].
12. **Named concurrency pools and per-group run limits.** **NO-EQ** for a named cross-job pool (verified absent on these pages). Max concurrent runs per job defaults to 1, and runs beyond it are skipped unless queueing is on. "Queueing is a job-level property that queues runs only for that job". Queued runs wait up to 48 hours when the workspace's concurrent active runs, its concurrent Run Job task runs or the job's own maximum is reached. Queueing has been the default for UI-created jobs since April 15, 2024 [doc Sep 11, 2026] — [Configure job](https://docs.databricks.com/aws/en/jobs/configure-job). For-each has a per-loop Concurrency [doc] — [For each](https://docs.databricks.com/aws/en/jobs/for-each). Workspace caps: 2,000 tasks running simultaneously, 750 parent tasks, 12,000 saved jobs [doc Oct 21, 2026] — [Resource limits](https://docs.databricks.com/aws/en/resources/limits).
13. **Per-run isolation, per-vendor secrets per step.** Each task has its own compute: serverless, classic jobs compute or all-purpose [doc Sep 11 / Oct 21, 2026] — [Configure job](https://docs.databricks.com/aws/en/jobs/configure-job); [Configure task](https://docs.databricks.com/aws/en/jobs/configure-task). Serverless jobs support notebook, Python script, dbt, Python wheel and JAR tasks, and require UC and standard access mode. A "Performance optimized" toggle (Public Preview) is offered; standard mode has "4 to 6 minutes" startup latency and consumes fewer DBUs on the same SKU [doc Oct 9, 2026] — [Serverless jobs](https://docs.databricks.com/aws/en/jobs/run-serverless-jobs). Serverless offers no init scripts, compute policies or Databricks Container Services (no custom images) [doc Oct 22, 2026] — [Serverless limitations](https://docs.databricks.com/aws/en/compute/serverless/limitations); [Serverless environment](https://docs.databricks.com/aws/en/compute/serverless/dependencies). Secret scopes are named collections and can be used in Spark config or environment variables. Databricks recommends aligning scopes to roles or applications [doc Sep 11, 2026] — [Secrets](https://docs.databricks.com/aws/en/security/secrets/). UC service credentials are governed cloud-service credentials; on serverless they need environment version 3+ for some uses [doc Oct 6, 2026] — [Service credentials](https://docs.databricks.com/aws/en/connect/unity-catalog/cloud-services/use-service-credentials). The release notes also list "External secrets in Unity Catalog (Beta)" (headline only) — [Release notes](https://docs.databricks.com/aws/en/release-notes/product/). A container per run is DIFF: compute is a Databricks cluster or serverless session, not your own image [inferred].
14. **Retries with policy, per step.** Retries are per task, with count and interval in ms measured from the failed run's start. Timeout applies to each retry. "For most configurations, the default setting does not retry", whereas "serverless jobs auto-optimize retries by default". Continuous jobs use exponential backoff [doc Oct 21, 2026] — [Configure task](https://docs.databricks.com/aws/en/jobs/configure-task). The notifications page instead says "By default, tasks are retried three times before failing fully" [doc Oct 9, 2026] — [Notifications](https://docs.databricks.com/aws/en/jobs/notifications). **The two docs conflict on the default.**
15. **Code/data versions deciding staleness.** DIFF. An MV refresh is data-driven. It "detects changes in the source data and recomputes only the affected results". "Databricks runs a cost analysis to choose the cheaper option between an incremental refresh and a full recompute", and a refresh policy can fail instead of fully recomputing. "Only materialized views updated using serverless pipelines can use incremental refresh. Materialized views that do not use serverless pipelines are always fully recomputed". Incremental sources are Delta (including UC managed and external) and UC managed Iceberg v2/v3. Foreign Iceberg is readable but not incremental. Some operations need row tracking [doc Oct 12, 2026] — [Incremental refresh](https://docs.databricks.com/aws/en/optimizations/incremental-refresh). There is **NO-EQ** for a user-set code version [inferred; how a definition change triggers a refresh was not verified].
16. **Lineage source → SQL (dbt) as one graph.** UC lineage spans tables, views, jobs, notebooks, pipelines, queries, dashboards, models and external assets in "a single graph". Lineage from before Sep 1, 2024 is unavailable; later data is "retained indefinitely". Lineage is lost on renames and with Spark SQL dataset checkpointing. Runs via runs submit or spark-submit lose the job link. LDP column lineage needs DBR 13.3+ [doc Oct 26, 2026] — [Data lineage](https://docs.databricks.com/aws/en/data-governance/unity-catalog/data-lineage). The dbt task runs dbt Core commands (default `deps`, `seed`, `run`) with a SQL warehouse (serverless or pro) and dbt CLI compute. `DBT_ACCESS_TOKEN` is injected for the run-as principal, and Databricks recommends pinning dbt-databricks ≥1.6.0 [doc Sep 11, 2026] — [dbt task](https://docs.databricks.com/aws/en/jobs/dbt). The task-type list also shows "dbt platform (Public Preview)" [doc Oct 21, 2026] — [Configure task](https://docs.databricks.com/aws/en/jobs/configure-task). [inferred] Because dbt SQL runs on a UC warehouse, UC captures table lineage for dbt models. dbt model, test and exposure semantics are not modelled in UC.
17. **Run metadata per materialisation, read back later.** The LDP event log `flow_progress` events carry `num_output_rows`, `num_upserted_rows`, `num_deleted_rows`, expectation pass/fail counts, dropped records, `backlog_bytes` and incrementalization-issue details. The `pipeline_events` system table is in **Beta**. "Do not delete the event log", or the pipeline may fail [doc Oct 22, 2026] — [Event log](https://docs.databricks.com/aws/en/ldp/monitor-event-logs). The release notes say "Lakeflow pipelines system tables are now generally available (GA)" (headline only) — [Release notes](https://docs.databricks.com/aws/en/release-notes/product/). **Possible conflict, or different tables.** For Jobs, task values must be valid JSON of at most 48 KiB, and aggregated references are limited to ~48 KB and 3 per parameter [doc Oct 8, 2026] — [Task values](https://docs.databricks.com/aws/en/jobs/task-values). `system.lakeflow` holds jobs, job_tasks, job_run_timeline, job_task_run_timeline, pipelines and pipeline_update_timeline, with 365-day free retention, the latest SCD2 record kept beyond that, and records "typically available within one hour" [doc Oct 16, 2026] — [Jobs system tables](https://docs.databricks.com/aws/en/admin/system-tables/jobs). These tables hold run metadata, not row counts. In plain jobs, row counts come from Delta history (not fetched; [inferred]).
18. **One alerting stream.** Partial. Job and task notifications fire on Start, Success, Failure, Duration warning and Streaming backlog. Destinations are email or admin-configured system destinations (Slack, Teams, PagerDuty, HTTP webhooks, with documented payloads such as `jobs.on_duration_warning_threshold_exceeded`). "Mute notifications until the last retry" is available. Slack/Teams message content "might change" [doc Oct 9, 2026] — [Notifications](https://docs.databricks.com/aws/en/jobs/notifications). Anomaly detection has its own alerts. The SQL alert task in Jobs is GA, and "Alert system tables are in Public Preview" (release-note headlines) — [Release notes](https://docs.databricks.com/aws/en/release-notes/product/). [inferred] One stream would need a webhook receiver that merges job, pipeline, DQM and SQL alerts. No single native stream covers trigger failures.
19. **Step logs to object storage.** Classic compute: "Compute log delivery" sends driver, worker and event logs to a chosen destination, for example S3 with an instance profile, "every five minutes and archived hourly" [doc Oct 16, 2026] — [Compute configuration](https://docs.databricks.com/aws/en/compute/configure). Serverless: "The Spark UI is not available… Spark logs are not available. Users only have access to client-side application logs" [doc Oct 22, 2026] — [Serverless limitations](https://docs.databricks.com/aws/en/compute/serverless/limitations). On serverless, log shipping is **NO-EQ** beyond what the job code writes itself [inferred].

### Inferences
- [inferred] The partition, backfill and freshness row group is where the mapping is weakest. Backfills over date ranges exist, but nothing persists partition status, so "which days are missing or stale" has to be computed by the team.
- [inferred] The "run history 60 days" figure from the other track is not contradicted here. The 365-day `system.lakeflow` retention was confirmed on the Oct 16, 2026 page.

## Q2 (B5a). Cost of running on Databricks WITHOUT Declarative Pipelines (plain Jobs + wheel/script + dbt tasks)

### Takeaway
You give up expectations and their metrics, the event log, AUTO CDC, managed dependency ordering inside a pipeline, and incremental MV refresh. Per the doc, incremental refresh is available only on serverless pipelines or SQL warehouses, which dbt tasks can use. You keep Jobs features, UC lineage, serverless jobs compute and portability of library code.

### Cited Findings
- **Expectations**: LDP-only, row-level, with warn/drop/fail and metrics in the event log [doc Oct 26, 2026] — [Expectations](https://docs.databricks.com/aws/en/ldp/expectations). They are not in Apache Spark SDP [doc Oct 25, 2026] — [Python reference](https://docs.databricks.com/aws/en/ldp/developer/python-ref)
- **Incremental MVs**: refreshes always run on serverless pipelines, standalone ones included. "Only materialized views updated using serverless pipelines can use incremental refresh"; MVs created with a SQL warehouse are refreshed incrementally if their queries are supported [doc Oct 12, 2026] — [Incremental refresh](https://docs.databricks.com/aws/en/optimizations/incremental-refresh). A release-note headline says "Performance mode now applies to materialized view and streaming table refreshes from dbt tasks", so dbt can create MVs and streaming tables that are themselves pipeline-backed — [Release notes](https://docs.databricks.com/aws/en/release-notes/product/). [inferred] So "no LDP" still lets you use standalone MVs and STs from dbt or SQL, which pulls those tables back into the Databricks-managed refresh engine.
- **Event log and per-flow row metrics** exist only for pipelines [doc Oct 22, 2026] — [Event log](https://docs.databricks.com/aws/en/ldp/monitor-event-logs). Plain jobs get `system.lakeflow` run and task timelines (365 days) and task values of at most 48 KiB [doc Oct 16 / Oct 8, 2026] — [Jobs system tables](https://docs.databricks.com/aws/en/admin/system-tables/jobs); [Task values](https://docs.databricks.com/aws/en/jobs/task-values)
- **Lineage**: UC captures table and column lineage for jobs and notebooks as well as pipelines. What is lost is the in-pipeline dataset graph, not UC lineage. Exception: runs-submit and spark-submit runs lose the job link [doc Oct 26, 2026] — [Data lineage](https://docs.databricks.com/aws/en/data-governance/unity-catalog/data-lineage)
- **Declarative benefits claimed by the vendor**: "In contrast to… manual orchestration via Lakeflow Jobs", pipelines give declarative processing, AUTO CDC for SCD1/2, and incremental processing [doc Oct 13, 2026; vendor framing] — [Pipeline concepts](https://docs.databricks.com/aws/en/ldp/concepts)
- **Pricing tiers**: pipelines come in Core, Pro (adds CDC) and Advanced (adds expectations) editions; serverless pipelines require Advanced. "The classic SKUs… still begin with DLT" [doc Oct 12 / Sep 11, 2026] — [Configure pipelines](https://docs.databricks.com/aws/en/ldp/configure-pipeline); [What happened to DLT?](https://docs.databricks.com/aws/en/ldp/where-is-dlt). Serverless jobs standard vs performance-optimized mode uses "the same SKU, but standard performance mode consumes fewer DBUs" [doc Oct 9, 2026] — [Serverless jobs](https://docs.databricks.com/aws/en/jobs/run-serverless-jobs). The pricing page fetched (HTTP 200) but listed no rates in its static HTML — [LDP pricing](https://www.databricks.com/product/pricing/lakeflow-declarative-pipelines). **Gap**: DBU rates were not captured.
- **Streaming in plain jobs**: compute autoscaling "has limitations scaling down cluster size for Structured Streaming workloads. Databricks recommends using Spark Declarative Pipelines on Lakeflow with enhanced autoscaling for streaming" [doc Oct 16, 2026] — [Compute configuration](https://docs.databricks.com/aws/en/compute/configure)
- **Backfill fit**: plain jobs are parameterized and can run backfill runs in parallel, whereas pipeline tasks are "not parameterized" and run sequentially in backfills [doc Sep 11, 2026] — [Backfill jobs](https://docs.databricks.com/aws/en/jobs/backfill-jobs)

### Inferences
- [inferred] For a ~12 to 30-feed batch estate, the decisive loss is expectations plus the event log metrics. Both can be rebuilt in library code (dbt tests, custom checks writing a results table), at a cost in team effort.
- [inferred] Auto Loader (`cloudFiles`) is a Structured Streaming source on Databricks Runtime, so it is not exclusive to LDP. What LDP adds is managed checkpoints and the streaming-table wrapper. Not verified against the Auto Loader page.
- [inferred] Plain jobs keep the per-partition backfill story (parameters, parallel runs), which LDP tasks lack.

### Gaps
- No vendor or independent TCO comparison of LDP and jobs with numbers was found.

## Q3 (B5b). Cost of adopting Declarative Pipelines (lock-in, portability, limits)

### Takeaway
The portable subset (decorators, MV and ST definitions, flows, sinks) runs on open-source Spark 4.1+. The features that make LDP attractive are Databricks-only: expectations, AUTO CDC, the event log, continuous mode, update and foreach sinks, and incremental MV refresh, which in OSS has no documented engine; the OSS CLI simply defaults to an "incremental update". LDP also has hard platform limits: serverless needs UC, one writer per dataset, MV and ST access by external engines only through extra features, no time travel on MVs, no `pivot()`.

### Cited Findings
- **OSS subset vs Databricks-only**: see the Q0 differences table [doc Oct 25, 2026] — [Python reference](https://docs.databricks.com/aws/en/ldp/developer/python-ref). The OSS SDP target `catalog` is optional, and storage is a checkpoint directory [doc Spark 4.2.0] — [SDP guide](https://spark.apache.org/docs/latest/declarative-pipelines-programming-guide.html)
- **UC-only**: "Serverless pipelines always use Unity Catalog"; legacy Hive metastore is possible on classic only [doc Oct 12, 2026] — [Serverless pipeline](https://docs.databricks.com/aws/en/ldp/serverless); [Configure pipelines](https://docs.databricks.com/aws/en/ldp/configure-pipeline)
- **One-pipeline-per-table ownership**: "Pipeline datasets can be defined only once… the target of only a single operation across all pipelines" (append flows excepted) [doc Oct 22, 2026] — [Pipeline limitations](https://docs.databricks.com/aws/en/ldp/limitations). Release notes list moving tables between pipelines and "Managed tables in Lakeflow pipelines (Beta)" as headlines; a moving-tables preview was seen only as a search lead — [Release notes](https://docs.databricks.com/aws/en/release-notes/product/)
- **Other limits**: no `pivot()`; Delta time travel only on streaming tables, not MVs; identity columns unsupported on AUTO CDC targets; a run-as group must be an account group; event details are shortened past 2,500 columns or 1,000 expectations; at most 100 source files (or 50 entries/1,000 files with folders) per pipeline [doc Oct 22, 2026] — [Pipeline limitations](https://docs.databricks.com/aws/en/ldp/limitations). The OSS guide also forbids `collect()`, `count()`, `toPandas()`, `save()` and `saveAsTable()` in dataset code, and its for-loop list "is always additive" [doc Spark 4.2.0] — [SDP guide](https://spark.apache.org/docs/latest/declarative-pipelines-programming-guide.html)
- **Non-Delta targets / sinks**: sinks are Python-only. They write to Delta (UC managed and external tables, or a path), Kafka, Azure Event Hubs, or custom Python data sources, and are fed by append or update flows. Custom targets go through ForEachBatch or ForEach sinks (Databricks-only) [doc Oct 25, 2026] — [Sinks](https://docs.databricks.com/aws/en/ldp/ldp-sinks). [inferred] DuckLake as a target would need a custom Python data source or foreachBatch. No documented DuckLake sink exists.
- **External readers of MVs and STs**: "By default, materialized views and streaming tables are not available to access from external systems". There are two opt-ins. "External data access" works via the UC/Iceberg REST APIs and needs Delta 4.0+ catalog APIs or Iceberg v3 with deletion vectors. "Compatibility mode" writes a read-only copy at a chosen location and costs "generally under 1%" of refresh [doc Oct 19, 2026] — [External access](https://docs.databricks.com/aws/en/ldp/external-access)
- **DuckDB interop with UC (not DuckLake)**: DuckDB's Delta and Unity Catalog extensions "shed their experimental tags — now with writes, Unity Catalog and time travel support" [doc May 7, 2026; DuckDB blog] — [DuckDB](https://duckdb.org/2026/05/07/delta-uc-updates.html). Databricks (Jul 16, 2026) says "external access to Unity Catalog (UC) managed Delta tables is now in **Public Preview**", with Spark, Flink, Starburst, DuckDB and Streamnative able to create, read and write through catalog commits and credential vending — [Databricks blog](https://www.databricks.com/blog/how-unity-catalog-managed-tables-bring-interoperability-performance-and-unified-governance). An analyst piece describes the write capability as **Beta** [lead, conflicts] — [Futurum](https://futurumgroup.com/insights/databricks-expands-unity-catalog-interoperability-is-true-open-lakehouse-finally-here/). No source found linking DuckLake (Postgres-catalog format) to UC or Delta. A Xebia post's "DuckLake" is an unrelated earlier project [lead] — [Xebia](https://xebia.com/blog/ducklake-a-journey-to-integrate-duckdb-with-unity-catalog/)
- **Testability**: OSS `spark-pipelines dry-run` and `run` work on any spark-submit cluster manager or a remote Spark Connect server [doc Spark 4.2.0] — [SDP guide](https://spark.apache.org/docs/latest/declarative-pipelines-programming-guide.html). [inferred] Code that uses `dp.expect*` or AUTO CDC will not run on OSS Spark, so local tests must stub them or exclude those datasets.
- **Backfill/parameters**: pipeline tasks are not parameterized in Jobs backfills [doc Sep 11, 2026] — [Backfill jobs](https://docs.databricks.com/aws/en/jobs/backfill-jobs). "Parameters for Lakeflow pipelines are now generally available" (release-note headline; semantics not verified) — [Release notes](https://docs.databricks.com/aws/en/release-notes/product/)

### Inferences
- [inferred] Exit cost scales with how much of the pipeline relies on the Databricks-only list. A pipeline of plain `@dp.materialized_view` and `@dp.table` with sinks is close to portable to OSS Spark 4.1+. One relying on expectations, AUTO CDC and incremental MVs is not, and its incremental behaviour on OSS is undocumented.
- [inferred] With DuckLake as the system of record, LDP pushes toward Delta/UC as the primary store, because MV and ST outputs are UC-managed Delta. Keeping DuckLake would mean sinks or dual writes.

### Gaps
- No OSS documentation was found on whether SDP materialized views refresh incrementally on Apache Spark, or which table formats an OSS SDP pipeline supports.
- Spark 4.1 GA date confirmed only via a conference abstract (lead).

## Q4 (B5). Options catalogue and practitioner reports

### Takeaway
There are four options. Practitioner evidence is thin: only one dated, first-hand DLT incident report with an outcome was found, its root cause was not LDP-specific, and the rest is vendor material or forum Q&A.

### Cited Findings
- **Option A: plain Jobs + wheel/script tasks + dbt task** (orchestrator-neutral library code). *Mechanism*: tasks call library functions, dbt runs on a SQL warehouse. *Requires*: UC for serverless jobs [doc Oct 9, 2026] — [Serverless jobs](https://docs.databricks.com/aws/en/jobs/run-serverless-jobs). *Gives*: parameterized parallel backfills, For-each, triggers, UC lineage. *Costs*: no expectations or event log; incremental MV refresh only through dbt or standalone MVs on serverless (see Q2). *Failure mode / early warning* [inferred]: homegrown check and metadata tables drift between feeds, and the warning sign is checks that differ feed by feed. *Exit cost* [inferred]: low for code, medium for the triggers, notifications and bundle YAML.
- **Option B: LDP for ingestion/bronze (Auto Loader, AUTO CDC), plain jobs or dbt downstream.** Forum lead: an author used DLT "for exactly one pipeline, not for Silver/Gold" [lead, not fetched] — [Databricks community](https://community.databricks.com/t5/forums/filteredbylabelpage/board-id/Knowledge-Sharing-Hub/label-name/dlt%20pipeline). *Costs*: Pro or Advanced edition, and the ingestion layer becomes Databricks-only [doc] — [Configure pipelines](https://docs.databricks.com/aws/en/ldp/configure-pipeline)
- **Option C: full LDP with expectations and MVs.** *Requires*: UC, Advanced edition for serverless, and Delta/UC targets. *Gives*: expectations, event log, incremental MVs. *Failure modes*: an expectation with `fail` does not stop parallel flows in triggered mode, and no metrics are recorded on fail [doc Oct 26, 2026] — [Expectations](https://docs.databricks.com/aws/en/ldp/expectations). Unexpected full recomputes raise cost, and the early warning sign is `incrementalization_issues` in the event log [doc Oct 22 / Oct 12, 2026] — [Event log](https://docs.databricks.com/aws/en/ldp/monitor-event-logs); [Incremental refresh](https://docs.databricks.com/aws/en/optimizations/incremental-refresh). *Exit cost*: high for the Databricks-only features (Q3).
- **Option D: write to the OSS SDP subset only (no `dp.expect`, no AUTO CDC), run on Lakeflow, keep the ability to run on OSS Spark.** *Gives*: portability, as Databricks says OSS code "runs without modification" [doc Oct 25, 2026] — [Python reference](https://docs.databricks.com/aws/en/ldp/developer/python-ref). *Costs*: none of the Databricks-only features, and OSS SDP needs a Spark 4.1+ runtime the team would operate. *Failure mode / early warning* [inferred]: a developer imports a Databricks-only API; a CI run on OSS `spark-pipelines dry-run` would catch it.
- **Practitioner report [first-hand, partially verifiable]**: a senior data engineer (Cognizant, regulated healthcare context) describes a production DLT pipeline incident. A library conflict in a custom Python UDF caused silent drift in gold aggregations, which reached three hospital systems. They cite "$4,000 in wasted DBU consumption during the retry storm" and two weeks of manual reconciliation, and report autoscaling spinning up an `r6id.4xlarge` for a tiny backfill. The post is dated "July 25" with no year shown, the root cause was a UDF dependency rather than DLT itself, and it is opinion-heavy (it compares DLT with Snowflake Dynamic Tables) — [dev.to](https://dev.to/aniketsoni/why-i-chose-snowflake-dynamic-tables-over-databricks-dlt-and-when-i-regret-it-468i)
- **Forum [lead]**: a serverless DLT SCD2 silver layer cost more than expected; a Databricks employee suggested incremental loads and temporary views — [Databricks community](https://community.databricks.com/t5/data-engineering/cost-optimization-for-serverless-delta-live-table-implementation/m-p/98714)
- **Vendor claim (not practitioner)**: "one billion records… for less than $1" with DLT (2023 blog, more than 2 years old) [lead] — [Databricks blog 2023](https://www.databricks.com/fr/blog/2023/04/14/how-we-performed-etl-one-billion-records-under-1-delta-live-tables.html)

### Inferences
- [inferred] Option D's portability claim depends on Databricks keeping the OSS subset aligned. The Feb 2026 blog's plan to open-source expectations could widen that subset later. That is a roadmap item, not a fact.

### Gaps
- No first-hand report found of a team abandoning LDP/DLT for plain jobs, or of running OSS SDP in production outside Databricks, with outcomes. Searches returned only Databricks forum Q&A and vendor content.
- No report found on DuckLake with Databricks.
