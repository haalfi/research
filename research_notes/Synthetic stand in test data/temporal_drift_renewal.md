## Temporal generation: how do existing generators model churn, I/U/D, corrections, delays, duplicates, gaps, schema change? Can they be parameterised from aggregates?

### Takeaway
No surveyed open tool generates "delivery-process realism" (corrections or restatements, re-deliveries, late or out-of-order arrival, missing drops) as a first-class, parameterised feature. Two kinds of tool exist. (1) **Benchmark generators** (TPC-DI DIGen/PDGF, TPC-DS dsdgen, LDBC SNB Datagen) model snapshots and change batches deterministically: an initial or historical load plus I/U/D increments, SCD2 dimensions and lifespans with deletions. Their rates are fixed by the spec and scale factor, so they cannot be fitted to a source. (2) **Learned sequential models** (SDV PARSynthesizer, MOSTLY AI TabularARGN for time series, DoppelGANger) learn per-entity sequences from row-level real data. They know nothing about deliveries, versions or transaction time. Agent-based simulators (PaySim, AMLSim/AMLworld, Synthea) evolve entities over simulated time from parameter files. PaySim's second version was explicitly calibrated from *aggregated* transaction logs, the closest precedent for "parameterise from aggregates computed inside". The practical design is therefore inferred: generate the entity state history with a seeded generator, then apply a separate delivery-process layer parameterised by aggregates measured inside (daily counts, I/U/D ratios, lateness distribution, duplicate and gap rates).

### Cited Findings

**TPC-DI (benchmark spec; Version 1.1.0, Nov 2014) [documented]**
- Models a historical load plus incremental updates. "Daily updates are common, and are the model for the TPC-DI benchmark." A run requires a Historical Load and **two** Incremental Update phases, each required to complete in 30–60 minutes. Two increments are required "to ensure repeatability" — [TPC-DI v1.1.0 spec §1.2.2](https://www.tpc.org/tpc_documents_current_versions/pdf/tpc-di_v1.1.0.pdf)
- Historical-load files are full extracts. Incremental files are CDC extracts carrying leading `CDC_FLAG` (I/U/D) and `CDC_DSN` columns. "For updates there is no indication as to what in the row has been changed. Rows that have not changed since the last extract will not appear… A row may change multiple times in the course of a day." CDC_DSN is monotonically increasing and rows are ordered by it, "which also reflects the time order in which the changes were applied" — [TPC-DI §1.3.2](https://www.tpc.org/tpc_documents_current_versions/pdf/tpc-di_v1.1.0.pdf)
- Multiple heterogeneous sources: OLTP CDC extracts, an HR CSV full extract, a purchased "Prospects" CSV for which "The DI process must determine what changes have occurred since the last update", FINWIRE variable-format newswire records, and an XML Customer Management System extract — [TPC-DI §1.2](https://www.tpc.org/tpc_documents_current_versions/pdf/tpc-di_v1.1.0.pdf)
- Staging layout: one directory per batch. `Batch1` holds the Historical Load, `Batch2` Incremental Update 1 and `Batch3` Incremental Update 2 — [TPC-DI §2.3](https://www.tpc.org/tpc_documents_current_versions/pdf/tpc-di_v1.1.0.pdf)
- SCD Type 2 dimensions use `IsCurrent`, `EffectiveDate` and `EndDate`, with `EndDate` = 9999-12-31 for current rows (not NULL), so that `EffectiveDate <= t < EndDate` works for all records. The DImessages table records "Status", "Alert" and "Reject" messages (e.g. Alert "Invalid SPRating") — [TPC-DI §3.2, §4.4.1](https://www.tpc.org/tpc_documents_current_versions/pdf/tpc-di_v1.1.0.pdf)
- DIGen "is a specific implementation built on top of the Parallel Data Generation Framework (PDGF), which is provided and maintained by Bankmark". Modifications to DIGen are not allowed, its version must match the spec, and it writes a `digen_report.txt` of generation statistics — [TPC-DI Clause 6](https://www.tpc.org/tpc_documents_current_versions/pdf/tpc-di_v1.1.0.pdf)

**TPC-DS (Version 4.0.0, Nov 2024) [documented]**
- "Data Maintenance (DM) or Data Refresh": refresh data sets numbered 1..n, each generated by `dsdgen` and applied in generated order. The refresh "consists of new, deleted and changed data". Refresh run n must finish before run n+1 — [TPC-DS v4.0.0 §1.5, §5.1–5.2](https://www.tpc.org/tpc_documents_current_versions/pdf/tpc-ds_v4.0.0.pdf)
- In the current spec, DM is only Method 1 (fact insert via views over source-schema flat files), Method 2 (sales and returns delete by date range) and Method 3 (inventory delete by date range). The revision history records that dimension (SCD) maintenance was removed in v2.0: Clause 5.3.6 now reads "intentionally left blank" since "we don't have any DM functions on dimension tables" (FogBugz 2199). Many `s_*` source tables were removed (FogBugz 2178) — [TPC-DS v4.0.0 revision history and §5.3](https://www.tpc.org/tpc_documents_current_versions/pdf/tpc-ds_v4.0.0.pdf)

**LDBC SNB (spec v2.2.4; arXiv 2001.02299v11, 7 Sep 2024) [documented]**
- Datagen output is an initial bulk data set plus update streams. Interactive uses 90% initial and 10% update streams. BI uses a 97% initial snapshot plus "daily inserts and deletes". "Update streams in version 1 only contain inserts, while in version 2, they contain both inserts and deletes" — [LDBC SNB spec §3.4](https://arxiv.org/pdf/2001.02299v11)
- Dynamic entities carry `creationDate` and `deletionDate` (lifespans) and `explicitlyDeleted` (explicit vs cascading delete). Datagen was extended so that deletes "follow a logic order" (e.g. a `knows` edge is deleted only after both persons joined and before either left) — [LDBC SNB spec §3.5–3.6](https://arxiv.org/pdf/2001.02299v11)
- "Datagen is deterministic regardless of the number of cores/machines used", which makes results reproducible — [LDBC SNB spec §2](https://arxiv.org/pdf/2001.02299v11)
- Spark Datagen (BI) is in `ldbc/ldbc_snb_datagen_spark`, with CSV and Parquet output and `--mode bi`. The Hadoop Datagen produces the Interactive SF1–1000 sets — [ldbc_snb_datagen_spark README](https://raw.githubusercontent.com/ldbc/ldbc_snb_datagen_spark/main/README.md)

**SDV PARSynthesizer (sequential) [documented]**
- Needs multi-sequence data with a `sequence_key`. It "creates brand new entities and brand new sequences" and is not suited to a single sequence. `context_columns` hold values that do not vary within a sequence. The default is 128 epochs, and `segment_size` cuts long sequences. "PAR is a Probabilistic Auto-Regressive model that is based in neural networks" — [SDV docs: PARSynthesizer](https://docs.sdv.dev/sdv/sequential-data/modeling/parsynthesizer) (accessed 2026-11-26)
- The model is described in "Sequential Models in the Synthetic Data Vault" (Zhang, Patki, Veeramachaneni; arXiv 2207.14406, 28 Jul 2022) as a conditional probabilistic auto-regressive (CPAR) model, compared against CTGAN — [arXiv 2207.14406](https://arxiv.org/abs/2207.14406)
- License: Business Source License 1.1 (DataCebo). Use is permitted except for providing a "Synthetic Data Service" to third parties. Each release converts to MIT four years after release — [SDV LICENSE](https://raw.githubusercontent.com/sdv-dev/SDV/main/LICENSE). Latest release sdv 2.2.0 on 2026-11-06 (PyPI)

**MOSTLY AI Synthetic Data SDK (open source) [documented README; capabilities = vendor marketing]**
- Supports "Single-table, multi-table, and time-series" data, the TabularARGN model, Differential Privacy, conditional simulation and "fully permissive open-source license". LOCAL mode trains and generates on your own compute (the default) — [mostlyai README](https://raw.githubusercontent.com/mostly-ai/mostlyai/main/README.md). Latest mostlyai 6.2.1 on 2026-10-29, first release 2023-12-29 (PyPI)

**DoppelGANger [documented]**
- GAN for time series with metadata (IMC 2020, arXiv 1909.13403, v1 30 Sep 2019). Claims "up to 43% better fidelity than baseline models" and says "we do not resolve the privacy problem" — [arXiv 1909.13403](https://arxiv.org/abs/1909.13403)
- Reference code "tested under Python 2.7.5 and Python 3.5.2, TensorFlow 1.4.0 (…1.4.0 – 1.15)". The README points to Gretel's later reimplementation — [DoppelGANger README](https://raw.githubusercontent.com/fjxmlzn/DoppelGANger/master/README.md)

**Agent-based and event simulators [documented]**
- PaySim (mobile-money multi-agent simulator, EMSS 2016): in the second phase the authors "got access to transactional financial logs of the system and developed a new version of the simulator which uses aggregated transactional data to generate financial information more alike the original source" — [PaySim README](https://raw.githubusercontent.com/EdgarLopezPhD/PaySim/master/README.md)
- AMLSim (IBM): a multi-agent simulator on Java 8, MASON and Python 3.7 with pinned old deps (networkx 1.11, matplotlib 2.2.3). Input is parameter files: account lists, alert patterns and an output schema JSON — [AMLSim README](https://raw.githubusercontent.com/IBM/AMLSim/master/README.md)
- AMLworld (Altman et al., arXiv 2306.16424, v1 22 Jun 2023, NeurIPS 2023 D&B): an agent-based generator "calibrated… to match real transactions as closely as possible". Its labels are complete, unlike real data — [arXiv 2306.16424](https://arxiv.org/abs/2306.16424)
- Synthea: CLI with `-s seed`, `-cs clinicianSeed`, `-r referenceDate`, `-i initialPopulationSnapshotPath`, `-u updatedPopulationSnapshotPath` and `-t updateTimePeriodInDays`. These let a saved population be advanced in time and re-exported, a native "advance the stand-in by N days" mechanism — [Synthea README](https://raw.githubusercontent.com/synthetichealth/synthea/master/README.md). `generate.timestep = 604800000` ms (one week). `exporter.years_of_history = 10`. `exporter.csv.append_mode` adds each run's data to existing CSVs — [synthea.properties](https://raw.githubusercontent.com/synthetichealth/synthea/master/src/main/resources/synthea.properties)

**Longitudinal statistical synthesis**
- SynLBD: a partially synthetic version of the Census Longitudinal Business Database (an annual establishment panel since 1976). Synthesised fields include employment, payroll, birth and death years and industry; industry and geography are partly left unsynthesised. Kinney et al., International Statistical Review 2011, and SynLBD 2.0 (2014) — [lead: Census methodology page](https://www.census.gov/programs-surveys/ces/data/public-use-data/synthetic-longitudinal-business-database/methodology.html) (page fetched; body rendered only links and "Page Last Revised February 12, 2025", so model details remain **[lead]**); [lead: IDEAS record](https://ideas.repec.org/a/bla/istatr/v79y2011i3p362-384.html)
- synthpop (R, CRAN): version 1.9-3 published 2026-09-10, GPL-2|GPL-3, maintainer B. Nowok — [CRAN synthpop](https://cran.r-project.org/web/packages/synthpop/index.html) [documented]. I did not verify a dedicated longitudinal or panel mode this run.

**CDC test tooling [documented]**
- Debezium documents integration testing with Testcontainers: `DebeziumContainer` plus Kafka and a Postgres container. Change events are produced by real DML against a containerised database, so it tests the CDC path and does not generate synthetic change patterns — [Debezium docs: Testcontainers](https://debezium.io/documentation/reference/stable/integrations/testcontainers.html)

### Inferences
- **[inferred]** The constraints (only aggregates may leave; several sources per entity; delays) fit a two-layer generator best. Layer 1 is a seeded entity and state-history generator (PDGF/LDBC-style determinism, Synthea-style "advance by N days", SCD2 or bitemporal validity intervals). Layer 2 is a delivery simulator per source: daily batch size, I/U/D mix as in TPC-DI's CDC_FLAG, lateness distribution, duplicate re-delivery rate, gap (missing-drop) probability, correction and restatement rate, schema-change events. Every Layer-2 parameter is an aggregate that can be computed inside and exported (counts per day, ratios, quantiles of arrival_time − event_time).
- **[inferred]** Learned sequential models (PAR, TabularARGN, DoppelGANger) need row-level training data, so they would have to be trained *inside*. Only the trained model or its outputs would leave, and that needs a disclosure review because a model is not "aggregates". Benchmark and agent-based generators parameterised by exported aggregates avoid this.
- **[inferred]** Valid time vs transaction time: TPC-DI's SCD2 (`EffectiveDate`/`EndDate`) is valid-time only. CDC_DSN gives an apply order but no correction semantics. None of the surveyed generators emits *restatements* of past valid-time periods. They must be added in Layer 2, for example by re-emitting a past key with a new transaction time and changed values at a measured restatement rate.
- **[inferred]** Maintenance risk: DoppelGANger (TF 1.x) and AMLSim (Python 3.7, Java 8, pinned 2018-era libs) are effectively legacy. TPC-DI DIGen dates from 2014 and is frozen by the spec.

### Gaps
- TPCx-IoT, PDGF's own papers (Rabl et al.), and synthpop/SynLBD longitudinal model equations were not read in full this run (the PDGF arXiv query returned no hit).
- GitHub repository activity (last commit, archived flag) could not be checked because the GitHub API was blocked in this session.
- I found no open generator that natively models late, duplicate, missing or partial *deliveries* with fitted rates. This is an absence finding from searches, not proof that none exists.

## Delivery-process simulation and data chaos engineering

### Takeaway
"Data chaos engineering" exists as a practice but not as an established framework. The documented open examples are lakeFS's isolated "chaos branches" (delete a partition, run the job, observe) and small hobby-scale configs (Odibi's duplicate_rate, outlier_rate and batch labels for late arrival, plus a schema-evolution pattern). Infrastructure chaos tools (LitmusChaos, Chaos Mesh, Toxiproxy) inject faults into systems, not into data content or delivery schedules.

### Cited Findings
- lakeFS blog "Chaos Data Engineering" (published 2020-11-17, modified 2026-02-05; engineering blog / vendor): create a zero-copy branch (`lakectl branch create lakefs://my-lake@chaos-empty-events --source lakefs://my-lake@main`), delete an arbitrary date partition through the S3 API, then run the Spark job against the branch to see how dependents behave — [lakeFS blog](https://lakefs.io/blog/chaos-data-engineering/) [documented]
- The same lakeFS page carries a banner "lakeFS Acquires DVC, Uniting Data Version Control Pioneers" — [lakeFS blog](https://lakefs.io/blog/chaos-data-engineering/) [documented banner; deal terms not read]. DVC latest release 3.67.1 on 2026-03-31. lakeFS Python SDK `lakefs` 0.17.0 on 2026-11-19 (PyPI).
- Odibi (single-author open-source docs) Pattern 36 "Late-Arriving & Duplicate Data" uses a chaos config with `duplicate_rate` for retransmissions and `outlier_rate` for corrupt values. Its suggested tests check dedup accuracy against the known injected duplicate count ("3% of 1,440 = ~43") and simulate late arrival by splitting on `batch_label` and processing batches sequentially. Pattern 37 "Schema Evolution Test" adds, removes and renames bronze columns to see whether silver crashes or validation catches it — [Odibi docs](https://henryodibi11.github.io/Odibi/simulation/patterns/data_engineering) [documented; small project, maturity unknown]
- Infrastructure-level tools named in search results: LitmusChaos (Kubernetes, Kafka broker partitions causing out-of-order events), Chaos Mesh, Toxiproxy and k6/xk6-disruptor — [lead: dev.to](https://dev.to/gowthampotureddi/chaos-engineering-for-data-pipelines-fault-injection-with-litmuschaos-gremlin-336n); [lead: The New Stack](https://thenewstack.io/a-guide-to-stress-testing-your-ml-data-pipelines/)
- TPC-DI's audit and visibility machinery is the closest standardised "correctness under incremental load" harness. A batch validation query writes into DImessages after each phase, data-visibility queries run at most five minutes apart during increments, and an automated audit must report "OK" for every test — [TPC-DI §7.2–7.4](https://www.tpc.org/tpc_documents_current_versions/pdf/tpc-di_v1.1.0.pdf) [documented]

### Inferences
- **[inferred]** A delivery-fault library is cheap to build in-house as pure functions over a seeded batch stream: `drop(batch)`, `duplicate(batch, k)`, `delay(batch, d)`, `reorder(window)`, `truncate(batch, frac)` (partial delivery), `restate(keys, period)` and `schema_mutate(op)`. Each fault takes its own seed and is logged, so every injected fault is enumerable and a test can assert exact expected counts, as Odibi does for duplicates.
- **[inferred]** lakeFS-style branches (or Iceberg branches and tags, below) give an isolated, reproducible "faulted" copy of a synthetic lake per scenario.

- I found no maintained, general-purpose OSS "data chaos" framework. Gremlin is commercial and infrastructure-focused (not researched). The 2025 St. Cloud State thesis on chaos engineering for ETL ([lead](https://repository.stcloudstate.edu/msia_etds/151)) was not read.
- The Great Expectations and Soda scenario-testing features were not verified. The Soda docs pages (`docs.soda.io/soda-cl/schema.html`, `anomaly-detection.html`) returned a JS shell with no content **[unreachable]**. ## Drift detection between real data and its stand-in (profile diffs, tools, tests, schema drift)

### Takeaway
The best fit for "only aggregates leave" is to compute a **profile or characterisation inside** on a schedule and diff profiles outside. Several tools support this: whylogs profiles (mergeable sketches), TFDV statistics protos with skew/drift comparators (L-infinity, Jensen–Shannon), Deequ's MetricsRepository with anomaly strategies over metric time series, and NannyML's binned KS/Wasserstein mode for large references. Default test thresholds differ by tool, and p-value tests (KS, chi-square) become oversensitive at large n. Evidently switches from p-value tests to distances above 1,000 reference rows. whylogs is open source but its sponsor shut down in 2025, and its last PyPI release was 2024-12-03.

### Cited Findings
- **Evidently** (latest 0.7.23, 2026-09-11). Default data-drift logic: with ≤1000 reference rows it uses two-sample KS for numeric columns with n_unique > 5, chi-squared for categorical or low-cardinality columns, and a Z-test for binary columns, all at 0.95 confidence (drift if p ≤ 0.05). With >1000 rows it uses Wasserstein distance for numeric and Jensen–Shannon for categorical columns, with threshold 0.1 (drift if ≥ 0.1). PSI, K-L, JS, Wasserstein or custom tests are selectable — [Evidently docs: data drift explainer](https://docs.evidentlyai.com/metrics/explainer_drift) [documented]
- **NannyML** (latest 0.13.1, 2025-07-12, roughly 16 months without a release, so maintenance is questionable; [inferred]). Univariate methods: KS, Jensen–Shannon, Wasserstein and Hellinger for continuous columns; chi-squared, JS, Hellinger and L-infinity for categorical. KS and Wasserstein can run either on raw reference data or on **quantile or equal-width bins with stored bin edges and frequencies**. Raw is used by default only if the reference has fewer than 10,000 rows. JS binning uses Doane's formula, and out-of-range chunk values get a new bin with reference frequency 0. Data is analysed in time-, size- or number-based chunks with constant or standard-deviation thresholds — [NannyML docs: univariate drift](https://nannyml.readthedocs.io/en/stable/how_it_works/univariate_drift_detection.html) [documented]
- **TFDV** (latest 1.21.0, 2026-06-11). Detects "skew between training and serving data" and "drift between different days of training data" by comparing *statistics* of datasets using comparators in the schema. An `infinity_norm` threshold (e.g. 0.01) detects skew for categorical features only, and a `jensen_shannon_divergence` threshold works for numeric and categorical features. Results come back as an Anomalies protobuf — [TFDV get started](https://www.tensorflow.org/tfx/data_validation/get_started) [documented]
- **Deequ** (Scala; PyDeequ latest 1.7.0, 2026-09-14). Anomaly detection runs on metrics stored in a `MetricsRepository` under time-stamped `ResultKey`s. The example `RelativeRateOfChangeStrategy(maxRateIncrease = Some(2.0))` on `Size()` flags a row count that more than doubles day over day — [Deequ anomaly detection example](https://raw.githubusercontent.com/awslabs/deequ/master/src/main/scala/com/amazon/deequ/examples/anomaly_detection_example.md). `OnlineNormalStrategy` defaults to lower and upper deviation factors of 3.0 standard deviations and `ignoreStartPercentage = 0.1` — [OnlineNormalStrategy.scala](https://raw.githubusercontent.com/awslabs/deequ/master/src/main/scala/com/amazon/deequ/anomalydetection/OnlineNormalStrategy.scala). Seasonal `HoltWinters` supports Daily, Weekly or Yearly seasonality on Hourly, Daily or Monthly metric intervals — [HoltWinters.scala](https://raw.githubusercontent.com/awslabs/deequ/master/src/main/scala/com/amazon/deequ/anomalydetection/seasonal/HoltWinters.scala) [documented]
- **whylogs / WhyLabs status.** whylogs is Apache-2.0 ("The open standard for data logging") — [whylogs python README](https://raw.githubusercontent.com/whylabs/whylogs/mainline/python/README.md). Its last PyPI release is 1.6.4 (2024-12-03). GeekWire (Taylor Soper, 2025-09-15) reports that Apple absorbed WhyLabs' founders after a "secretive deal" and that "The WhyLabs website is now updated with information about the company 'discontinuing operations' and open-sourcing its platform". The deal appears on a European Commission DMA acquisitions page — [GeekWire](https://www.geekwire.com/2025/founders-at-seattle-startup-whylabs-join-apple-following-under-the-radar-acquisition) [documented]. The platform code is published as `whylabs-oss` ("WhyLabs AI Control Center"; WhyLabs Observe "processes standardized telemetry signals from the whylogs library") — [whylabs-oss README](https://raw.githubusercontent.com/whylabs/whylabs-oss/main/README.md) [documented]. Search extracts say the platform repo is Apache 2.0, some visualisation depends on Highcharts licensing, and it accepts no community contributions **[lead]**.
- **alibi-detect** latest 0.13.0 (2025-12-11). **deepchecks** latest 0.19.1 (2024-12-15). **ydata-profiling** latest 4.18.4 (2026-04-22) (PyPI) [documented dates; features not read this run].

### Inferences
- **[inferred]** For aggregates-only egress, prefer tools that diff **statistics artifacts** rather than raw rows: TFDV statistics protos, whylogs profiles, NannyML binned references (bin edges plus frequencies), and Deequ metric time series. Evidently's default presets take two DataFrames (reference and current). In this setting the "current" side would be the stand-in outside and the "reference" side would have to be a profile, so Evidently fits less naturally unless it runs inside on real vs synthetic and only the report leaves.
- **[inferred]** Two different drifts must be tracked. (a) **Real-vs-real over time**: does today's inside profile differ from the profile the stand-in was built from? Deequ-style metric repositories and HoltWinters or OnlineNormal fit this, applied to daily row counts, I/U/D ratios, lateness quantiles, null rates and distinct counts. (b) **Real-vs-stand-in fidelity**: distance between the current inside profile and the stand-in's profile. JS and Wasserstein distances on shared bins (TFDV, NannyML) are suitable because both sides can be binned identically and only bins leave.
- **[inferred]** Pitfalls at scale. With 10^6+ rows, KS and chi-square p-values are near 0 for practically irrelevant differences, which is why Evidently switches to distance thresholds above 1,000 rows and NannyML bins above 10,000. Distances depend on binning: NannyML's new-bin-at-zero-frequency rule makes JS/PSI sensitive to unseen categories, and PSI is undefined on empty bins without smoothing. Testing many columns daily produces false alarms unless thresholds are tuned or alerts require persistence across chunks.
- **[inferred]** Schema drift is best detected deterministically, not statistically: export the column set, types, nullability and enum domains as part of the characterisation and diff them (TFDV schema anomalies, Deequ or GE column-set constraints). Odibi Pattern 37 illustrates the failure modes (added, removed or renamed columns).

### Gaps
- Commercial Monte Carlo and Bigeye were not researched (reference only by brief).
- Great Expectations and Soda schema, anomaly and freshness checks were not verified from full text (Soda docs unreachable via curl).
- I read no primary paper on PSI or KS behaviour at large sample sizes this run. The pitfalls above are inference, consistent with the tool defaults documented above.

## Renewal and reproducibility (scheduled or drift-triggered regeneration; versioning characterisation, model and seed; fixtures; failing-test reproducibility)

### Takeaway
Reproducibility after renewal comes from treating **(characterisation version, generator version, seed)** as the identity of a stand-in, and from storing failing cases independently of the generator. Deterministic, seed-addressed generators (LDBC Datagen, PDGF/DIGen, Synthea `-s`, Hypothesis `@seed`) make that identity sufficient for regeneration. Table-format time travel (Iceberg snapshot IDs, branches and tags) or lakeFS/DVC commits pin the materialised dataset when regeneration is costly or the generator changes. Hypothesis documents an important caveat: its example database and `@reproduce_failure` blobs are tied to the Hypothesis version and test code. Durable regression cases should therefore be promoted to explicit `@example`s or pinned fixture files.

### Cited Findings
- **Hypothesis** (latest 6.170.17, 2026-11-20). "Hypothesis automatically saves failures to the database… The next time the test is run, Hypothesis will replay any failures" (Phase.reuse). "The database is best thought of as a cache that you never need to invalidate. Entries may be transparently dropped when upgrading your Hypothesis version or changing your test. Do not rely on the database for correctness; to ensure Hypothesis always tries an input, use `@example`" — [Hypothesis API reference](https://hypothesis.readthedocs.io/en/latest/reference/api.html) [documented]
- `@reproduce_failure(version, blob)` runs exactly one case. It is "not intended to be a permanent addition… no compatibility guarantees are made across Hypothesis versions, and @reproduce_failure will error if used on a different Hypothesis version". `@seed(seed)`: "for a fixed seed value Hypothesis will produce the same test cases (assuming… no other sources of nondeterminism…)". `derandomize` is "designed to enable deterministic CI tests rather than reproducing observed failures" — [Hypothesis API reference](https://hypothesis.readthedocs.io/en/latest/reference/api.html) [documented]
- `@example(...)` runs before generation, does not shrink and does not count toward `max_examples`. It "can also be used to easily reproduce a failure", e.g. `@example(n=[0, math.nan])` — [Hypothesis API reference](https://hypothesis.readthedocs.io/en/latest/reference/api.html) [documented]
- `DirectoryBasedExampleDatabase` can be committed to version control (ignore `.hypothesis/*` except `!.hypothesis/examples/`), but "this only makes sense if you also pin to an exact version of Hypothesis". `GitHubArtifactDatabase` with `ReadOnlyDatabase` and `MultiplexedDatabase` lets CI publish failures as an artifact and developers replay them locally read-only, which the docs recommend for continuous fuzzing — [Hypothesis API reference](https://hypothesis.readthedocs.io/en/latest/reference/api.html) [documented]
- **Deterministic generators.** "Datagen is deterministic regardless of the number of cores/machines", and the workload driver is deterministic because "the same random number generator seed is used across executions" — [LDBC SNB spec](https://arxiv.org/pdf/2001.02299v11). TPC-DI requires that the DIGen version match the spec and forbids modifications to DIGen or its bundled PDGF — [TPC-DI Clause 6](https://www.tpc.org/tpc_documents_current_versions/pdf/tpc-di_v1.1.0.pdf). TPC-DS refresh sets "must be used in the order generated by dsdgen" — [TPC-DS §5.1](https://www.tpc.org/tpc_documents_current_versions/pdf/tpc-ds_v4.0.0.pdf). Synthea takes `-s seed` and `-cs clinicianSeed` plus population snapshots (`-i`/`-u`) — [Synthea README](https://raw.githubusercontent.com/synthetichealth/synthea/master/README.md) [documented]
- **Iceberg time travel.** Spark SQL supports `TIMESTAMP AS OF` and `VERSION AS OF`, where VERSION can be a snapshot ID or a **branch or tag name**. A snapshot ID takes precedence over an identically named tag — [Iceberg Spark queries docs](https://iceberg.apache.org/docs/latest/spark-queries/) [documented]
- **lakeFS** branches are metadata-only, zero-copy snapshots of a lake taking "a few milliseconds" — [lakeFS blog](https://lakefs.io/blog/chaos-data-engineering/) [documented, vendor engineering blog]
- **Snapshot-testing libraries**: syrupy latest 7.0.3 (2026-11-21, active). pytest-snapshot latest 0.9.0 (2022-04-23, stale) (PyPI) [documented dates].

### Inferences
- **[inferred]** Recommended identity tuple for every stand-in build: `{characterisation_id (hash of exported aggregate profile), generator_name+version (container digest), config hash, master seed, per-source sub-seeds, delivery-fault plan}`. Store it in the stand-in's metadata (e.g. an Iceberg snapshot summary or tag name, or a lakeFS commit message) so any failing test report can name it.
- **[inferred]** Renewal loop:
  1. A scheduled job inside computes the profile and diffs it against the profile of the current stand-in's characterisation (Deequ or TFDV-style).
  2. On breach (or on a calendar schedule), the new profile is exported after disclosure checks and versioned (DVC/lakeFS/git).
  3. The generator rebuilds outside with a new characterisation ID and the same or new seed.
  4. The new build is published as a new Iceberg tag or lakeFS commit; the old tags are kept.
- **[inferred]** Keep failing tests reproducible across renewals using three layers, ordered by durability:
  1. Minimal failing example extracted as an explicit fixture (`@example` or a small pinned CSV/Parquet), which survives generator and library upgrades.
  2. The identity tuple (characterisation, generator version, seed), which regenerates the full dataset only while the old generator version remains runnable.
  3. A pinned materialised dataset (Iceberg tag, lakeFS commit or DVC hash), which survives generator changes but costs storage and must stay outside-safe.
  Hypothesis-style databases and blobs are a convenience cache, not a guarantee (per the Hypothesis docs).
- **[inferred]** Determinism caveats: parallel generation must use per-entity or counter-based seeding (PDGF/LDBC style) to be independent of worker count. Learned models (PAR, GANs) are reproducible only with fixed framework versions and deterministic kernels, so pin the trained artifact rather than relying on retraining from a seed.
- **[inferred]** Egress: what must leave the protected environment is the aggregate profile (counts, ratios, bins, quantiles, schema) and, for learned generators, possibly a trained model. The latter needs a separate disclosure decision. Seeds, generator code, fault plans and the stand-in itself never involve real data.
