# Track 1: Failure analysis: Tesseract/OCRmyPDF on degraded tabular scans

Round 1 of the deep-research workflow, 2026-11-21. One reader agent per source extracted up to five claims with a supporting quote; the 25 highest-ranked claims across all tracks then went to three adversarial verifiers each (two refutations kill a claim).
Claims marked "not voted" are leads until verified; see the round 2 notes.

Search query: `Tesseract LSTM errors table ruling lines decimal comma period dropped punctuation digits page segmentation mode psm 6 vs 4 vs 11 OCRmyPDF preprocessing deskew binarization DPI "ImproveQuality" tessdoc`

Rationale: Primary docs and issue reports on known Tesseract failure mechanisms (line removal, binarization, DPI/x-height, PSM choice, small punctuation loss, legacy vs LSTM, whitelist behaviour) to separate image loss, preprocessing artifacts, segmentation, recognition, and coordinate errors and to identify diagnostic experiments.

## S0: https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html

Source quality (reader's rating): primary. Date: not stated.

- **S0.0** (central; voted 3-0, confirmed): The official Tesseract documentation states that Tesseract is known to have problems recognising text/data in tables unless custom segmentation or layout analysis is supplied, i.e. the default page segmentation is a documented failure source for tabular documents such as statements (the page gives no quantitative measurement).
  - Quote: "It is known tesseract has a problem to recognize text/data from tables (see [issues tracker](https://github.com/tesseract-ocr/tesseract/issues)) without custom segmentation/layout analysis."
- **S0.1** (central; voted 3-0, confirmed): For non-prose content (receipts, price lists, codes), the Tesseract docs say that disabling both dictionaries (load_system_dawg and load_freq_dawg = false) should increase recognition, and that user word lists, user character patterns and tessedit_char_whitelist (e.g. digits only) can further constrain recognition. The page asserts this as guidance without benchmark numbers, and does not state whether the whitelist is honoured by the LSTM engine in every 4.x/5.x version.
  - Quote: "Disabling the dictionaries Tesseract uses should increase recognition if most of your text isn't dictionary words. They can be disabled by setting both of the [configuration variables `load_system_dawg` and `load_freq_dawg`](tess3/ControlParams.md) to `false`."
- **S0.2** (central; voted 3-0, confirmed): Tesseract's default internal binarisation is global Otsu, which the docs say can be suboptimal when page background darkness is uneven; Tesseract 5.0.0 added two Leptonica-based alternatives (Adaptive Otsu and Sauvola) selectable via thresholding_* parameters, and the intermediate binarised image can be dumped with tessedit_write_images (tessinput.tif) to diagnose whether preprocessing is the failure cause.
  - Quote: "Tesseract does this internally (Otsu algorithm), but the result can be suboptimal, particularly if the page background is of uneven darkness.  Tesseract 5.0.0 added two new Leptonica based binarization methods: Adaptive Otsu and Sauvola. Use `tesseract --print-parameters | grep thresholding_` to see the relevant configurable parameters."
- **S0.3** (supporting; extracted from the source by a reader agent; not voted in round 1): When OCRing a small cropped region (e.g. a single field or cell) rather than a full page, the docs recommend a non-default page segmentation mode (such as PSM 7 single line, 8 single word, 13 raw line; default is 3) and a small white border of about 10 px: crops with no border and crops with very large borders both cause problems, the latter including 'empty page' results.
  - Quote: "By default Tesseract expects a page of text when it segments an image. If you're just seeking to OCR a small region, try a different segmentation mode, using the `--psm` argument. Note that adding a white border to text which is too tightly cropped may also help"
- **S0.4** (supporting; extracted from the source by a reader agent; not voted in round 1): The docs state Tesseract works best at an input resolution of at least 300 dpi, and that page skew significantly degrades line segmentation and thereby OCR quality, so rescaling and deskewing before OCR are recommended. The page also says retraining is unlikely to help unless the font is very unusual or the language is new.
  - Quote: "Tesseract works best on images which have a DPI of at least 300 dpi, so it may be beneficial to resize images. [...] The quality of Tesseract's line segmentation reduces significantly if a page is too skewed, which severely impacts the quality of the OCR."

## S1: https://ocrmypdf.readthedocs.io/en/latest/advanced.html

Source quality (reader's rating): primary. Date: Undated; live "latest" documentation for ocrmypdf 17.14.2 as fetched 2026-11-21 (page text itself references "As of June 2024" for the PSM table and "Added in version 17.13.0").

- **S1.0** (central; voted 3-0, confirmed): OCRmyPDF forwards a Tesseract page segmentation mode via --tesseract-pagesegmode (default 3, fully automatic); the docs state that non-default modes help only when the page structure is known in advance (e.g. single-line pages) and usually make results worse. PSM 4, 6, 7, 11 and 13 are available, but OSD modes 0, 1, 2 and 12 are incompatible with OCRmyPDF.
  - Quote: "The directive --tesseract-pagesegmode Nmode forwards the desired page segmentation mode to Tesseract OCR. The default is 3. Page segmentation can improve OCR results when you know that a PDF ought to be analyzed a particular way, such as PDFs whose pages contain only a single line of text. For the vast majority of users, changing the page segmentation mode will only make things worse. [...] Modes 0, 1, 2, and 12 (all of those that enable orientation and script detection) are not compatible with OCRmyPDF, which performs OSD in a separate step from OCR."
- **S1.1** (central; voted 3-0, confirmed): Tesseract control parameters can be overridden through OCRmyPDF with --tesseract-config; the documented example disables the language dictionary (load_system_dawg 0 and zeroed non-dictionary-word penalties) because the dictionary can interfere with OCR on documents with few real words, such as lists of part numbers. Some parameter combinations break Tesseract or OCRmyPDF's assumptions about its output.
  - Quote: "As an example, this configuration will disable Tesseract’s dictionary for current language. Normally the dictionary is helpful for interpolating words that are unclear, but it may interfere with OCR if the document does not contain many words (for example, a list of part numbers). [...] load_system_dawg 0 / language_model_penalty_non_dict_word 0 / language_model_penalty_non_freq_dict_word 0 [...] Warning: Some combinations of control parameters will break Tesseract or break assumptions that OCRmyPDF makes about Tesseract’s output."
- **S1.2** (supporting; extracted from the source by a reader agent; not voted in round 1): Advanced Tesseract features cannot be reached through OCRmyPDF, which implies that per-field or per-region targeted recognition (custom crops, per-line PSM, direct access to richer Tesseract outputs) requires calling Tesseract directly rather than through the OCRmyPDF wrapper. The implication is inference; the page states only the limitation.
  - Quote: "It is currently not possible to use advanced Tesseract OCR features, such as creating OCR information, when using Tesseract through OCRmyPDF."
- **S1.3** (supporting; extracted from the source by a reader agent; not voted in round 1): Since OCRmyPDF 17.0.0 the default text-layer renderer is fpdf2, described as positioning text aligned with OCR bounding boxes; the hocr/hocrdebug renderers are deprecated and redirect to fpdf2, and the sandwich renderer is retained only for testing and can run words together in some viewers. A positional parser reading the PDF text layer therefore sees renderer-dependent coordinates and word segmentation that can change across OCRmyPDF versions (the last point is inference).
  - Quote: "Changed in version 17.0.0: The fpdf2 renderer is now the default, replacing the legacy hOCR renderer. [...] Accurate text positioning aligned with OCR bounding boxes [...] The sandwich renderer uses Tesseract’s text-only PDF feature, which produces a PDF page that lays out the OCR in invisible text. Currently some problematic PDF viewers like Mozilla PDF.js and macOS Preview have problems with segmenting its text output, and mightrunseveralwordstogether. [...] The hocr and hocrdebug renderer options are deprecated and automatically redirect to fpdf2."
- **S1.4** (supporting; extracted from the source by a reader agent; not voted in round 1): Preprocessing in OCRmyPDF can change geometry and is not fully lossless: some unpaper features reposition text within the image (so --clean without --clean-final can desynchronise OCR coordinates from the output page image), preprocessing such as --deskew causes the page to be re-rendered as a full-page image, and PDF/A conversion and optimization may apply lossy transformations unless disabled.
  - Quote: "Warning: Some unpaper features will reposition text within the image. --clean-final is recommended to avoid this issue. [...] When image preprocessing features like --deskew are used, the original PDF will be rendered as a full page and the OCR layer will be placed on top. [...] In this way, loss of PDF information is generally avoided. (You may need to disable PDF/A conversion and optimization to eliminate all lossy transformations.)"

## S2: https://groups.google.com/g/tesseract-ocr/c/MbFSNPtXt84/m/XjMN9KDhAAAJ

Source quality (reader's rating): forum. Date: 2018-07-06 (thread start; last mirrored reply 2019-01-02; the "2022" in the supplied title could not be confirmed).

- **S2.0** (central; extracted from the source by a reader agent; not voted in round 1): On Tesseract 4.0.0-beta.1 (LSTM engine, --oem 1 --psm 1), a clean, synthetic screenshot of short decimal numbers (no scan degradation at all) was transcribed with decimal points silently dropped: the user reports outputs such as '15', '25', '225', '2235' in a list of decimals, i.e. the error is a deletion that yields a still-plausible number rather than an obviously garbled token. (Provenance caveat: the Google Groups URL returned 'Content unavailable' to unauthenticated fetches; text was read in full from the mail-archive.com mirror of the same list thread, msg16255. The mirror shows the thread dated 2018-2019, not 2022; the specific message XjMN9KDhAAAJ could be a later reply not on the mirror and was not verified.)
  - Quote: "I'm having problems with the simplest image possible. It's a screenshot from GEdit(Ubuntu's text editor), with numbers and points. This is what I get, 23.78 15 1.6 17.6 25 225 2235 0.5 [...] version: tesseract 4.0.0-beta.1-285-g8d3f run from command line like this, tesseract test_image2.png outputbase --oem 1 --psm 1"
- **S2.1** (central; extracted from the source by a reader agent; not voted in round 1): Switching page segmentation mode to --psm 6 (single uniform block), as suggested by a Tesseract maintainer-level contributor (Shree Devi Kumar), did not fix the dropped decimal point; the failure was token-specific: '1.5' failed while visually similar '1.6', '1.7', '1.2', '1.3', '1.4', '1.8', '1.9' were recognized correctly. This is anecdotal evidence (single user, single image) that the failure is in recognition rather than page segmentation and is not predictable from glyph similarity alone.
  - Quote: "tried it with same results, also, all other cases work well. 23.78 15 1.6 1.7 1.2 1.3 1.4 1.8 1.9 The only that won't come out well is "1.5". That's pretty crazy."
- **S2.2** (central; extracted from the source by a reader agent; not voted in round 1): A list respondent (Lorenzo Bolzani) attributes the dropped decimal points to insufficient glyph resolution: with ~20 px character height the dot is only ~3 px and is likely treated as noise; he states upscaling matters more than contrast enhancement. This is an unverified hypothesis offered in the thread (worded 'probably'), with no measurement posted.
  - Quote: "upscale and enhance contrast, but upscale is what really matters: each letter is 20px, a dot is about three pixel, it's probably "seen" as noise."
- **S2.3** (central; extracted from the source by a reader agent; not voted in round 1): A second user reported about six months later (Jan 2019) that upscaling, gamma and contrast changes did NOT eliminate missing decimal points, even on images judged to be good quality; the thread ends without a confirmed fix (the only reply asks for sample images). So the thread itself provides counter-evidence to the 'upscale fixes it' hypothesis and no resolved remedy.
  - Quote: "did anybody get this "solved". I played a lot with upscaling, gamma changes, contrast etc. but I keep on getting errors, in particular missing decimal points even though the point seem to be very well and the image of good quality. Is any param change of help?"
- **S2.4** (tangential; extracted from the source by a reader agent; not voted in round 1): Another respondent suggested cropping surrounding whitespace down to a thin (~8 px) border as a remedy for the dropped decimal points; no outcome of this suggestion was reported in the thread, so its effectiveness is untested there.
  - Quote: "Have you tried removing all surrounding whitespace from the image except for a thin border (say 8px thick)?"

## S3: https://github.com/tesseract-ocr/tesseract/issues/751

Source quality (reader's rating): forum. Date: 2017-03-08.

- **S3.0** (central; extracted from the source by a reader agent; not voted in round 1): In Tesseract 4.00 alpha, tessedit_char_whitelist / tessedit_char_blacklist stopped having any effect, although they worked in 3.04 (issue opened 2017-03-08 by nguyenq). A character whitelist is therefore not a reliable constraint for numeric/date fields on any pipeline pinned to Tesseract 4.0.x.
  - Quote: "Blacklist and whitelist no longer work in 4.00alpha. They used to work in 3.04."
- **S3.1** (central; extracted from the source by a reader agent; not voted in round 1): A Tesseract maintainer (amitdo, 2017-04-13) confirmed that in 4.0 the whitelist/blacklist was not implemented for the LSTM recognizer, i.e. the settings were silently ignored rather than failing with an error.
  - Quote: "It's currently not supported for LSTM."
- **S3.2** (supporting; extracted from the source by a reader agent; not voted in round 1): The failure was specific to engine modes that involve LSTM (--oem 1, 2, 3); the legacy engine (--oem 0) still honoured the whitelist in 4.0 (user report by atefm, 2017-03-28). Using the whitelist on 4.0 therefore required legacy traineddata and the legacy engine.
  - Quote: "I encountered the same issue today when using --oem 1,2,3. It works fine for --oem 0 (Original Tesseract)."
- **S3.3** (central; extracted from the source by a reader agent; not voted in round 1): Users reported that whitelist/blacklist works with the LSTM engine after upgrading from 4.0 to 4.1, and the issue was closed as completed on 2019-08-17; the thread itself names no fix commit. Minimum version for LSTM whitelisting is therefore 4.1 (user reports, not a maintainer statement in this thread).
  - Quote: "This appears to be working for me, just upgraded my 4.0 version to 4.1."
- **S3.4** (supporting; extracted from the source by a reader agent; not voted in round 1): Filtering unwanted characters out of the OCR output after recognition is not equivalent to constraining recognition to a character set (user objection by v3ss0n, 2022-06-28, to a suggested wrapper-level workaround); for 4.0 the maintainer-suggested alternative was to fine-tune a digits-type traineddata ('plus-minus' training).
  - Quote: "It is not detection of numbers only , it is filtering out text AFTER being detected."

## S4: https://ocrmypdf.readthedocs.io/en/latest/cookbook.html

Source quality (reader's rating): primary. Date: Undated living documentation; page footer reads "Copyright 2026, James R. Barlow"; fetched 2026-11-21 as ocrmypdf 17.14.2 docs (RapidOCR section marked "Added in version 17.14.0").

- **S4.0** (central; voted 3-0, confirmed): Since OCRmyPDF 17.14.0, an alternative local OCR engine (RapidOCR, running PaddleOCR PP-OCR detection and recognition models on ONNX Runtime, CPU-only) can be selected inside the existing OCRmyPDF pipeline with --ocr-engine rapidocr, without Tesseract installed. The bundled PP-OCRv6 model covers English and about 45 Latin-script languages with no download, so it can run offline; however the official Docker images do not include it (a custom image must be built), the extra adds about 340 MB, and only the fpdf2 renderer is supported (--pdf-renderer sandwich is rejected).
  - Quote: "RapidOCR runs PaddleOCR’s PP-OCR text detection and recognition models on ONNX Runtime, on the CPU. It is an optional engine, installed with OCRmyPDF’s rapidocr extra and selected with --ocr-engine rapidocr. Tesseract need not be installed. [...] All told, the extra adds about 340 MB to an installation. [...] The Docker images do not include RapidOCR, but you can build one that does."
- **S4.1** (central; voted 3-0, confirmed): The OCRmyPDF documentation asserts (without any benchmark, dataset or number) that RapidOCR often reads numbers, codes and short table cells more accurately than Tesseract, and recommends trying it on tables and forms. This is an unquantified maintainer assertion, not a measured result, and says nothing about exact-field accuracy on degraded statements.
  - Quote: "RapidOCR often reads numbers, codes and short table cells more accurately than Tesseract, so it is worth trying on tables, forms and lab reports. Tables are read row by row in the sidecar text, and prose in columns."
- **S4.2** (central; voted 3-0, confirmed): By default the RapidOCR engine in OCRmyPDF downscales any page whose longer side exceeds 2000 pixels (about 180 dpi for a Letter page scanned at 300 dpi) before text detection, which can hurt very small print unless --rapidocr-max-side-len is raised; it also costs roughly four times Tesseract's CPU time per page and about 1.2 GB of memory per worker (about 2 GB at 4000 px).
  - Quote: "Pages whose longer side exceeds --rapidocr-max-side-len pixels (default 2000, about 180 dpi for a Letter page scanned at 300 dpi) are downscaled before RapidOCR finds text, with a Lanczos filter so that thin strokes survive. Raising it may help with very small print, at the cost of speed and memory. [...] RapidOCR uses much more CPU and memory than Tesseract: roughly four times the CPU time per page, and about 1.2 GB of memory per worker at the default --rapidocr-max-side-len (about 2 GB at 4000)."
- **S4.3** (central; voted 3-0, confirmed): OCRmyPDF's own documentation warns that its image-processing options (--remove-background, --deskew, --clean, --clean-final via unpaper) can remove desirable content, especially on poor-quality scans, and that output should be visually reviewed; --clean applies unpaper only to the image fed to OCR (not the output), so preprocessing can delete marks from the OCR input without any visible change in the output PDF.
  - Quote: "It is suggested that the user review files after image processing as these commands might remove desirable content, especially from poor quality scans. [...] --clean uses unpaper to clean up pages before OCR, but does not alter the final output. This makes it less likely that OCR will try to find text in background noise. --clean-final uses unpaper to clean up pages before OCR and inserts the page into the final output. You will want to review each page to ensure that unpaper did not remove something important."
- **S4.4** (supporting; extracted from the source by a reader agent; not voted in round 1): OCRmyPDF states that incorrect input image resolution metadata degrades OCR quality (because the range of candidate font pixel sizes is derived from it), that --oversample DPI resampling to a higher resolution before OCR 'can improve results', and that --redo-ocr cannot be combined with image-processing options; --force-ocr rasterizes all pages, potentially reducing quality.
  - Quote: "The --oversample DPI argument can be specified to resample images to higher resolution before attempting OCR; this can improve results as well. OCR quality will suffer if the resolution of input images is not correct (since the range of pixel sizes that will be checked for possible fonts will also be incorrect)."

## S5: https://tesseract-ocr.github.io/tessdoc/tess3/FAQ-Old.html

Source quality (reader's rating): primary. Date: 2018-05-01 (archive snapshot date stated on page: "as of May 1, 2018"; content covers Tesseract 2.0x, 3.0x and 4.00.00alpha, with some entries dating to 2008).

- **S5.0** (central; voted 3-0, confirmed): Tesseract's official (legacy-era) FAQ states that accuracy degrades below 10pt at 300 dpi and rapidly below 8pt at 300 dpi; the practical check is x-height in pixels: about 20 px is typical for 10pt at 300 dpi, below 10 px x-height accurate results are unlikely, and below about 8 px most text is discarded by noise removal. (Quote verified against the raw page text. Guidance was written for Tesseract 2.x/3.x legacy engine; applicability to LSTM is partly an inference.)
  - Quote: "Accuracy drops off below 10pt x 300dpi, rapidly below 8pt x 300dpi. A quick check is to count the pixels of the x-height of your characters. (X-height is the height of the lower case x.) At 10pt x 300dpi x-heights are typically about 20 pixels, although this can vary dramatically from font to font. Below an x-height of 10 pixels, you have very little chance of accurate results, and below about 8 pixels, most of the text will be “noise removed”."
- **S5.1** (central; voted 2-1, confirmed): For the LSTM engine there is also an upper bound: x-heights above roughly 30 px reportedly degrade accuracy, whereas the legacy engine is less affected. The FAQ's own wording is hedged ('seems') and its evidence is a linked mailing-list thread, so this is an anecdotal observation, not a measured result; it implies that over-upscaling a scan can hurt LSTM recognition.
  - Quote: "Using LSTM there seems also to be a maximum x-height somewhere around 30 px. Above that, Tesseract doesn’t produce accurate results. The legacy engine seems to be less prone to this"
- **S5.2** (supporting; extracted from the source by a reader agent; not voted in round 1): Increasing the dictionary's influence in Tesseract (legacy language-model penalties language_model_penalty_non_freq_dict_word / language_model_penalty_non_dict_word, defaults 0.1 and 0.15) also increases the tendency to hallucinate dictionary words; the dictionary can be turned off by removing dawgs from the traineddata or setting load_<type>_dawg false via a config file at init time (not via SetVariable). Relevant to merchant descriptions and non-dictionary tokens; these parameters are documented for Tesseract >= 3.01 legacy, not confirmed here for LSTM.
  - Quote: "Of course any changes that up the power of the dictionary also up the ability to hallucinate dictionary words. [...] To go the opposite way and turn off the dictionary, you can either delete the appropriate dawg(s) from the traineddata file using combine_tessdata, or set the appropriate load_type_dawg parameter to false, but this must be done with a config file and the version of Init that takes a configs argument. It cannot be done by SetVariable, because the parameter is controlling initialization."
- **S5.3** (supporting; extracted from the source by a reader agent; not voted in round 1): In the legacy engine, word-level confidence is defined as the minimum of the character certainties (character certainty = -20 * distance to a training sample), and word rating is the sum of character ratings; per-word coordinates and confidence are obtainable through hOCR output or the API. This describes the Tesseract 2.x/3.x classifier, so it does not establish how LSTM-mode confidences are computed or whether they are calibrated.
  - Quote: "Character - Compute a distance measure between 0 and 1 of the character from a training sample: certainty = -20 * distance; rating = distance * outline length. Word: certainty = min over word of character certainty. rating = sum over word of character rating."
- **S5.4** (supporting; extracted from the source by a reader agent; not voted in round 1): Digits-only recognition is supported via the bundled 'digits' config, which sets tessedit_char_whitelist to 0123456789 (must be set before Init when using the API). This is documented for Tesseract 2.x/3.x; the page does not say whether the whitelist works under the 4.x LSTM engine, and a pure-digit whitelist would exclude decimal separators, signs and currency symbols needed for amount fields.
  - Quote: "Use the digits config file like this: tesseract imagename outputbase digits [...] TessBaseAPI::SetVariable("tessedit_char_whitelist", "0123456789"); BEFORE calling an Init function or put this in a text file called tessdata/configs/digits: tessedit_char_whitelist 0123456789"
