## OP-01: read whole / streamed

1. **Streamed reads open a snapshot only if the library pins one.** Hadoop: a stream from `open(p)` "MAY or MAY NOT" see later changes. Changes that are seen "MAY be partially visible", and repeated reads of the same offset may differ. [documented, HADOOP-FSDIS "Consistency"]. s3fs changed this in 2026.3.0: "check for file expiry with ETag if server doesn't support If-Match (#1008)" [documented, S3FS-CL]. *Change*: s3fs detects replacement during a read. The Hadoop spec leaves the result undefined.
2. **The writer's mtime does not equal the reader's view.** S3 `Last-Modified` for multipart uploads is "the date of initiation of the multipart upload" [documented, AWS UsingMetadata]. Relevant when "read if unchanged since" is keyed on time. See also OP-09.
3. **Closing or exiting must reach the transport layer.** smart_open 7.0.0 (#786, fixes #684) made `open().__exit__`/`close()` propagate to the underlying stream. Before that, the compression layer swallowed `__exit__` [documented, SMART-MIG §v7.0.0]. The write-side effect is under OP-03. On the read side, smart_open 8.0.x closed streamed HTTP responses on close or seek (#966) [documented, SMART-CL 8.0.2].
4. **Default read-ahead policy changes performance and memory, not results.** s3fs 2023.1.0: "default cache to be readahead (#678)" [documented, S3FS-CL]. gcsfs 2026.7.0 enabled an "adaptive" prefetcher by default, raising peak memory from ~170 MB to 600 MB on single-stream reads [documented, GCSFS-CL]. gcsfs 2026.8.1 then defaulted `cat_file` concurrency back to 1 (#1051) to restore "single-request sequential reads without range headers" for small objects [documented, GCSFS-CL]. *Change*: whole-object read (`cat_file`) and streamed read (`open` + cache) were tuned separately.
5. **The read API split by access pattern.** pyarrow keeps `open_input_stream` ("sequential reading") apart from `open_input_file` ("random access reading") [documented, PYARROW FileSystem]. Hadoop added `openFile()` with `fs.option.openfile.read.policy` (sequential / random / whole-file) because "optimizing reads for sequential reads may impair random performance -and vice versa" [documented, HADOOP-OPENFILE]. The same builder's `withFileStatus()` lets stores with etag/version "guarantee that the file they opened is exactly the one returned in the listing" [documented].
6. **Missing object versus directory.** object_store 0.6.0 changed `head`/`get` on a directory path: they had returned a "Directory" result for LocalFileSystem and hierarchical Azure, and now return NotFound (#4230/#4231) [documented, OS-CL]. See OP-09.

## OP-02: read at offsets (seekable / range)

1. **Range semantics past EOF differ between backends and changed in libraries.** object_store `GetRange::Bounded` returns an error if the range "is zero-length or starts after the end of the object". If it "ends after the end", the remainder is returned [documented, OS-DOCS GetRange]. Before 0.12.0, LocalFileSystem errored on a satisfiable range that ended beyond EOF. This was fixed by #6751 (issue #6749) [documented, OS-CL]. fsspec 2026.7.0: "Clamp read end to file size in BlockCache and BackgroundBlockCache (#2081)" [documented, FSSPEC-CL]. adlfs v0.7.7: "Fixed bug in fetch_range that caused attempted reads beyond end of file" [documented, ADLFS-CL]. smart_open 7.4.0: "Improve handling of InvalidRange and seek on empty file (#889)". smart_open 3.x/4.x fixed "seeking past end of file for s3" (#549) [documented, SMART-CL]. s3fs Unreleased: "Return empty `cat_file` slices without issuing an S3 range request (#1064)" [documented, S3FS-CL]. Hadoop: a failed `seek` past EOF "may move the read position to the end of the file, as well as raising an EOFException". Object-store connectors use "lazy-seek" [documented, HADOOP-FSDIS].
2. **Range shapes vary by service.** object_store grew from a plain `Range` to `GetRange::{Bounded, Offset, Suffix}` (0.9.0: "full HTTP range support" #5222, "range request with suffix" #4611) [documented, OS-CL / OS-DOCS]. Azure accepts only `bytes=start-` and `bytes=start-end` (no suffix form). It also needs `x-ms-range` for >4 GiB with some clients [documented, AZ range header]. S3 "doesn't support retrieving multiple ranges of data per GET request" [documented, AWS GetObject]. object_store errors "if Remote Ignores HTTP Range Header" (0.7.1, #4841) [documented, OS-CL]. smart_open 8.0.3: "Raise from seek() when the server rejects a range request (#980)" [documented, SMART-CL].
3. **Multi-range reads split out as their own operation with coalescing.** Several libraries made this a separate operation: object_store `get_ranges` "will automatically coalesce adjacent ranges" (`OBJECT_STORE_COALESCE_DEFAULT`). LocalFileSystem got coalescing only in 0.14.1 (#777/#778) [documented, OS-DOCS / OS-CL]. OpenDAL `Reader::fetch` merges ranges with a configurable gap ("Set gap to 0 to avoid merging…") [documented, OPENDAL Reader]. fsspec has `cat_ranges(..., max_gap=...)` [documented, FSSPEC-API]. fsspec 2026 dev made `merge_offset_ranges` O(n log n) and kept merged blocks within `max_block` (#2091) [documented]. Hadoop added `readVectored` with `minSeekForVectorReads` / `maxReadSizeForVectorReads` [documented, HADOOP-FSDIS]. paramiko has `SFTPFile.readv(chunks)` [documented, PARAMIKO].
4. **Consistency across several range reads needs version or ETag pinning.** Hadoop `readVectored`: "If a file is changed while the readVectored() operation is in progress, the output is undefined. Some ranges may have old data, some may have new" [documented, HADOOP-FSDIS]. object_store's docs say: "To retrieve ranges from a versioned object, use ObjectStore::get_opts by specifying the range in the GetOptions". `GetOptions` carries `if_match`, `version`, `if_unmodified_since` [documented, OS-DOCS]. `get_ranges` itself takes no options [documented, signature]. *Split*: pinned range reads go through `get_opts`, coalesced ones through `get_ranges`. OpenDAL exposes `read_with_if_match` / `read_with_if_version_match` as capabilities [documented, OPENDAL Capability]. Caveat: S3's If-Unmodified-Since/NotModified uses exact timestamp matching in some cases ("Some stores, such as S3, will only return NotModified for exact timestamp matches") [documented, OS-DOCS GetOptions].
5. **Block caches return wrong or duplicate data at edges.** fsspec 2026.2.0: "remove prefetching loop in block-cache causing double read (#1984)". 2026.7.0: `FirstChunkCache` end=None handling (#2082). Dev: `cat_ranges` on whole-file caches fixed (#2163), `simplecache.cat_ranges` downloads uncached files (#2154) [documented, FSSPEC-CL]. fsspec cache types (`BlockCache`, `BytesCache`, `ReadAheadCache`, `FirstChunkCache`, `BackgroundBlockCache`, `MMapCache`) are selected through `cache_type` [documented, FSSPEC-API]. [inference] Cache choice affects request count and memory. The bug history shows it can also affect correctness.

## OP-03: write whole / streamed

1. **Streamed object-store writes become visible only on close, and close can fail.** Hadoop: object-store streams "MAY buffer the entire stream's output until the final close()"; close "may take a time proportional to the quantity of data" and "may also fail —a failure that is better escalated than ignored" [documented, HADOOP-INTRO "Durability", HADOOP-OUT "Object Stores"]. gocloud: "The write operation is not guaranteed to have succeeded until Close returns with no error"; "until then, any previous blob will still be readable" [documented, GOCLOUD Writer.Close / NewWriter]. paramiko's pipelined writes mean "an exception might be thrown from within close instead of write" [documented, PARAMIKO set_pipelined].
2. **Abort is a separate, explicit operation, and not all stores clean up on drop.** gocloud: "To abort a write, cancel ctx … The caller must call Close on the returned Writer, even if the write is aborted" [documented, GOCLOUD]. object_store: "some stores, such as S3 and GCS, cannot perform cleanup on drop … MultipartUpload::abort can be invoked", and lifecycle rules are recommended because abort is not always possible [documented, OS-DOCS MultipartUpload]. object_store 0.10.2 also changed `WriteMultipart` to abort on `complete` error (#5974) and to allow abort after completion (#5977) [documented, OS-CL]. OpenDAL `Writer`: "make sure either close or abort has been called before dropping the writer otherwise the data could be lost" [documented, OPENDAL Writer]. smart_open 7.0.0: before #786 "an interrupted S3 multipart upload was never aborted, leaving billable orphan parts behind" [documented, SMART-MIG]. smart_open 8.0.4 aborts uploads when closing a compressed stream fails (#969) [documented, SMART-CL]. AWS recommends a lifecycle `AbortIncompleteMultipartUpload` rule [documented, AWS mpu-abort].
3. **Part-size floors force buffering and a single-vs-multipart split.** S3 part size is "5 MiB to 5 GiB", with no minimum for the last part and at most 10,000 parts [documented, AWS qfacts]. object_store: "Most stores require that all parts excluding the last are at least 5 MiB, and some further require that all parts excluding the last be the same size, e.g. R2"; `WriteMultipart::new` uses 5 MB chunks [documented, OS-DOCS]. OpenDAL makes `write_multi_min_size` / `write_multi_max_size` / `write_can_multi` / `write_can_empty` capabilities [documented, OPENDAL Capability]. smart_open lets callers pick `multipart_upload: False` (single PUT, "allows seek() before upload") [documented, smart_open README]. smart_open 7.3.0 made `SinglepartWriter` seekable (#854) [documented, SMART-CL]. s3fs added R2 multipart support (#888) [documented, S3FS-CL].
4. **Empty files are an edge case.** OpenDAL has a separate `write_can_empty` capability [documented]. s3fs Unreleased: "Preserve exclusive-create conditions and file options when committing empty files" [documented, S3FS-CL]. [inference] The zero-byte write path is often a separate code path (no multipart) and has lost options before.
5. **Local writes need a durability step that object-store PUT already implies.** object_store 0.14.0 added `LocalFileSystem::with_fsync` (#643), which fsyncs files and "the affected parent directories". It also added explicit close-error checking (#676, issue #661 "Reliable file writes") [documented, OS-DOCS LocalFileSystem / OS-CL]. *Change*: local durability became opt-in, to match "the implicit durability contract of remote object stores".
6. **Parent creation is implicit on object stores and explicit on filesystems.** fsspec 2023.9.2 reverted `auto_mkdir` in `open()` (#1365, reverting #1358) [documented, FSSPEC-CL]. fsspec 2026.7.0 creates parent dirs for "x" and "a" modes under `auto_mkdir` (#2079) [documented]. object_store 0.7.1: "LocalFileSystem Copy and Rename Don't Create Intermediate Directories" (#4760), fixed by #4759 [documented, OS-CL].

## OP-04: replace atomically

1. **Object-store PUT replaces atomically; filesystem rename is the local substitute.** S3: "Updates to a single key are atomic … you will get either the old data or the new data, but never partial or corrupt data" [documented, AWS consistency]. object_store `put_opts` "is guaranteed to be atomic … No clients should be able to observe a partially written object" [documented, OS-DOCS]. On local disk, object_store implements this by writing temp files named `…#<n>`. Such names "are not supported by LocalFileSystem … will be ignored for listing operations" [documented, OS-DOCS LocalFileSystem]. object_store 0.7.1 auto-cleaned these temp files (#4778) [documented, OS-CL]. *Change*: a reserved name pattern leaked into the key space.
2. **Rename-overwrite differs by OS and protocol, and the APIs split because of it.** Python `os.rename`: "On Windows, if dst exists a FileExistsError is always raised". `os.replace` (added 3.3) replaces silently, and "the renaming will be an atomic operation (this is a POSIX requirement)" [documented, PY-OS]. SFTP: paramiko `rename` follows "'standard' SFTP RENAME behavior" where newpath "must not exist already". `posix_rename` (added 2.2) overwrites and raises if "posix-rename is not supported by the server" [documented, PARAMIKO]. OpenSSH defines the `posix-rename@openssh.com` extension because POSIX semantics "are different to those provided by the standard SSH_FXP_RENAME" [documented, OPENSSH-PROTO §4.3]. Hadoop lists "action when attempting to rename a file atop another file" as a local-FS quirk [documented, HADOOP-INTRO].
3. **Rename on object stores is copy+delete: not atomic, and timestamps change.** object_store `rename_opts`: "By default, this is implemented as a copy and then delete source. It may not check when deleting source that it was the same object" [documented, OS-DOCS]. Hadoop: rename timestamps "may become that of the time the rename … was started" [documented, HADOOP-INTRO]. object_store 0.13.0 merged `rename` and `rename_if_not_exists` into `rename_opts` (#555), and `copy` and `copy_if_not_exists` into `copy_opts` (#548) [documented, OS-CL]. *Change*: conditional variants were folded into option structs.
4. **Durability of local replace needs a directory fsync.** object_store `with_fsync` fsyncs "affected parent directories" for put/copy/rename. 0.14.x fixed "fsync create-mode rename source delete" (#758) [documented, OS-DOCS / OS-CL]. [inference] Without the directory fsync, a crash can lose the rename even after the data was fsynced.
5. **Local copy was not atomic until fixed.** object_store 0.7.1: "LocalFileSystem Copy is not Atomic" (#4758) → "Make ObjectStore::copy Atomic…" (#4759). The current LocalFileSystem copy uses `hard_link` and "does not support copying across filesystem boundaries" [documented, OS-CL / OS-DOCS].
6. **Multi-file "atomic" commit is only semi-atomic.** fsspec transactions finalise "in a semi-atomic way". Synchronising across instances "is a harder problem" [documented, FSSPEC-FEAT]. fsspec 2026 dev ensured the transaction ends even when commit/discard raises (#2108) [documented, FSSPEC-CL].

## OP-05: conditional write (if absent / if unchanged)

1. **Native conditional PUT arrived late on S3, so libraries carried workarounds and then removed them.** S3 now supports `If-None-Match: *` and `If-Match` on PutObject, CopyObject and CompleteMultipartUpload [documented, AWS conditional-writes]. object_store's history: DynamoDB-lock-based `copy_if_not_exists` (0.8.0, #4880/#4918), conditional put (`put_opts`, 0.8.0, #4879/#4984), "Support native S3 conditional writes" (0.11.2, #6682), removal of `S3ConditionalPut::ETagPutIfNotExists` (#6802), and "enable conditional put by default for S3" (0.12.0, #7181) [documented, OS-CL].
2. **Conflict signalling differs: 412 versus 409, and a 404 race.** S3: a mismatch yields 412. "You can also receive a 409 Conflict response in the case of concurrent requests", and a 404 if a concurrent delete wins. For 409 the docs say uploads "may be retried" [documented, AWS conditional-writes]. Azure: `If-None-Match: *` means "only if the resource doesn't exist"; failures are 412 [documented, AZ conditional headers]. GCS uses generation numbers, and `ifGenerationMatch=0` is a special case. It "only proceeds if no object with the specified name exists … or if there are only noncurrent versions" [documented, GCS-PRECOND]. object_store maps these to `Error::AlreadyExists` (Create) versus `Error::Precondition` (Update) [documented, OS-DOCS PutMode]. *Split*: "if absent" and "if unchanged" have distinct error kinds.
3. **When the check runs is undefined for streamed writes.** fsspec "Exclusive write" (mode `create` / `xb`, added 2024.12.0 #1762) says: "the timing of when the check is done is not defined - it may be at the start or at the completion … This feature is currently included on a trial basis". `open()` docs add: "whether it is checked up front or on commit, and whether it is atomic is implementation-dependent" [documented, FSSPEC-FEAT / FSSPEC-API / FSSPEC-CL]. Hadoop: S3A's no-overwrite `create()` "allows >1 client to create a file with overwrite=false … using create() to acquire an exclusive lock … may not not a safe algorithm" [documented, HADOOP-FS create; HADOOP-OUT]. s3fs: "exclusive write" (2024.12.0, #917), "fix exclusive write for small files" (2025.7.0, #974) [documented, S3FS-CL]. adlfs 2024.12.0 added "exclusive" mode to put/pipe/open [documented, ADLFS-CL].
4. **Local filesystems support "if absent" but not "if unchanged".** object_store issue #423 asked for `PutMode::Update` on LocalFileSystem. The maintainer said it could not be added "without introducing some sort of locking setup … Most systems only support advisory locking … Locking would add non-trivial overheads even to read operations". The issue was closed 2025-07-04 [observed, OS-423 via WebFetch]. A later duplicate is arrow-rs #6535 "PutMode::Update is not supported for LocalFileSystem" [observed]. "If absent" maps to `O_EXCL`: paramiko's `'x'` flag "is commonly known as the O_EXCL flag in posix" (since 1.5.2) [documented, PARAMIKO]. Python exposes `os.O_EXCL` [documented, PY-OS]. [inference] SFTP gives "if absent" through O_EXCL, but no compare-and-swap.
5. **Capabilities are reported per backend.** OpenDAL splits `write_with_if_not_exists`, `write_with_if_none_match`, `write_with_if_match`, `write_with_if_version_match` and `copy_with_if_not_exists` into separate flags [documented, OPENDAL Capability]. gocloud has a single `WriterOptions.IfNotExist`, which returns `PreconditionFailed` "by Write or Close" [documented, GOCLOUD].

## OP-06: list a folder's children

1. **Directories are implicit, and marker objects create ambiguity.** S3 console folders are "a 0-byte object … key … plus a trailing forward slash" [documented, AWS using-folders]. Hadoop S3A: the old s3n used `_$folder$` markers. Marker deletion on every file create caused throttling (one write op per listed key, 3,500 writes/s, tombstones in versioned buckets). 3.3.1 added a `keep` retention policy that "is not backwards compatible": older clients "will mistake directories containing data for empty directories" [documented, HADOOP-MARKERS]. cloudpathlib v0.6.5: "directories created on AWS S3 were reported as files" (#148) [documented, CLOUDPATH-CL]. object_store 0.10.0: "MicrosoftAzure store list result omits empty objects" (#5451), and #5452 uses `ResourceType` to filter directories on HNS [documented, OS-CL]. adlfs 2024.12.0 handles mixed-case `hdi_isfolder` metadata [documented, ADLFS-CL].
2. **Listing a missing prefix: error or empty, depending on the library.** Hadoop `listStatus` raises FileNotFoundException if the path does not exist [documented, HADOOP-FS]. pyarrow `FileSelector(allow_not_found=False)` errors by default; with True "an empty selection is returned" [documented, PYARROW]. OpenDAL `list` "does not require the parent directory to exist". It returns the path itself if it exists, plus prefixed children [documented, OPENDAL Operator::list]. object_store lists by "path segment" prefix: `foo/bar` is not a prefix of `foo/bar_baz/x` (docs clarified in 0.11.1, #6520) [documented, OS-DOCS / OS-CL]. adlfs fixed `ls()` when "a file shares the same prefix as other files" (#409) [documented, ADLFS-CL]. cloudpathlib fixed `iterdir` including self (v0.7.0, #15) and `S3Path.exists()` "returns True on partial matches" (v0.10.0, #208) [documented, CLOUDPATH-CL].
3. **Ordering is not guaranteed in general, and a store-level guarantee can break.** Hadoop: "there is no guarantee of ordering of the listed entries" [documented, HADOOP-FS]. object_store `list`: "the order of returned ObjectMeta is not guaranteed" [documented, OS-DOCS]. S3 ListObjectsV2 is lexicographic, except "Directory buckets … ListObjectsV2 does not return objects in lexicographical order" [documented, AWS ListObjectsV2]. Azure List Blobs is "alphabetical … upper-case letters listed first"; on HNS accounts "/ is treated as the lowest sort order" in recursive listings [documented, AZ list-blobs]. gocloud promises lexicographical order of UTF-8 keys [documented, GOCLOUD]. paramiko `listdir` is "in arbitrary order" [documented, PARAMIKO]. object_store issue #388 (listed in 0.12.4) is titled "LocalFileSystem: offset for list_with_offset can't be identified / List results *must* be sorted" [documented title, OS-CL]. *Change*: offset-based listing assumes an order that the local backend did not provide.
4. **Pages can be short or empty, and page tokens are not cursors over a snapshot.** Azure "might return fewer results than specified by maxresults, and also return a continuation token" (max 5,000) [documented, AZ list-blobs]. S3 returns up to 1,000 per page [documented, AWS ListObjectsV2]. gocloud `ListPage` "might have 0 results … if the last item was deleted" and "is not guaranteed to include all recently-written blobs" [documented, GOCLOUD]. s3fs 2026.9.0 now retries transient errors per page "instead of failing or truncating it" (#982, 1042) [documented, S3FS-CL]. gcsfs 2023.12.0: "use same version when paginating list (#591)" [documented, GCSFS-CL]. object_store `list_with_offset` was added per backend over time: GCS pushdown (0.8.0, #4993), LocalFileSystem custom impl (0.12.0, #7019, after "very slow over network file system" #7018), Azure (#623) with a OneLake regression (#695, 0.14.0) [documented, OS-CL]. object_store added `PaginatedListStore` (0.12.2, #371) [documented].
5. **Listing caches go stale.** fsspec `DirCache` with `listings_expiry_time` / `max_paths`; use `use_listings_cache=False` "when the target location is known to be volatile because it is being written to from other sources". Writes call `invalidate_cache` [documented, FSSPEC-FEAT]. s3fs bug history includes a "directory cache race condition (#655)", "Fix repeated find corrupting cache (#730)", "invalidate cache in rm_file (#762)", and (2026.7.0) "don't cache prefix-filtered listings as complete directory entries (#1034)" [documented, S3FS-CL].
6. **Concurrent mutation during listing.** object_store 0.10.2: "Potential race condition in list_with_delimiter on Local" (#5800) → "Handle missing files in list_with_delimiter" (#5803) [documented, OS-CL]. fsspec 2024.12.0: "race condition in local ls() (#1744)" [documented, FSSPEC-CL]. Hadoop `listStatusIterator` "does not guarantee atomicity if other callers are adding/deleting" [documented, HADOOP-FS].

## OP-07: walk subtree, depth-limited

1. **Flat recursive listing versus per-level listing is a real split.** object_store keeps `list` ("recursive") apart from `list_with_delimiter` ("not recursive"). 0.10.2 updated docs "to delineate which ObjectStore lists are recursive" (#5794) [documented, OS-DOCS / OS-CL]. Hadoop added `listFiles(path, recursive)` so that "large recursive directory scans" are handled "by reducing the amount of data which must be collected in a single RPC call" [documented, HADOOP-FS]. OpenDAL `list_with(...).recursive(true)` is a capability (`list_with_recursive`) [documented, OPENDAL]. cloudpathlib v0.25.0 added `walk(lazy=True)`. The default "whole subtree is fetched up front with a single recursive listing", while lazy lists per directory so `top_down` pruning of `dirnames` saves API calls (#518, #574) [documented, CLOUDPATH-CL]. *Change*: pruning only works with per-level listing.
2. **Depth limits do not map to object-store listing.** fsspec `find(path, maxdepth, withdirs)` and `walk(path, maxdepth, topdown, on_error)`; `maxdepth=None` is "limitless, but not recommended on link-based file-systems" [documented, FSSPEC-API]. fsspec history: `topdown` added to `walk` (2022.11.0, #1081), "allow dir modification during walk()" (2023.6.0, #1263), `on_error` in walk (2023.9.0, #1303), topdown in async walk (2026.7.0, #2052), `maxdepth` passed through in async `_rm` (dev, #2106) [documented, FSSPEC-CL]. gcsfs 2023.9.0 "maxdepth in find() (#566)". s3fs: "dircache usage with depth (#791)" [documented, GCSFS-CL / S3FS-CL]. Arrow C++ `FileSelector` has `max_recursion`, but pyarrow's `FileSelector(base_dir, allow_not_found, recursive)` does not expose it [documented, PYARROW; the gap is observed from the two signatures].
3. **Whether directories are emitted varies.** fsspec `find` `withdirs` defaults False, "True when used by glob" [documented, FSSPEC-API]. s3fs 2026.3.0 "allow _find with both prefix/withdirs" (#1014) [documented]. pyarrow selector results exclude the base dir ("The selector's base directory will not be part of the results") [documented, PYARROW].
4. **Cost is O(entries), and walk on object stores was slow enough that libraries rewrote it.** Hadoop: directory operations on object stores are "more likely to be O(child-entries)" [documented, HADOOP-INTRO]. fsspec 2026.7.0 "Single-pass MemoryFileSystem.find() to avoid O(n_dirs * n_entries)" (#2055) [documented]. gcsfs 2026.x reduced CPU in recursive `find()` "(also used by glob(), du(), and recursive rm()/get()/copy())" [documented, GCSFS-CL].
5. **Hierarchical-namespace stores behave differently from flat ones.** Azure List Blobs on HNS errors "where the name of a file appears in the middle of the prefix path" [documented, AZ list-blobs]. gcsfs: "add support for partial prefixes in find method for HNS buckets (#831)" (2026.5.0) [documented, GCSFS-CL].

## OP-08: match keys by pattern

1. **Glob semantics changed in the libraries.** adlfs 2023.9.0: "Compatability with new glob behavior in fsspec 2023.9.0" [documented, ADLFS-CL]. That fsspec 2023.9.0 change is **not itemised** in the fsspec changelog [unverified: what exactly changed]. s3fs 2023.9.0: "better ** support in bulk ops/glob (#769)" [documented, S3FS-CL]. Later fsspec changes: glob docstring corrected "to reflect reality" (2025.5.0, #1825) and for `[!]` (2026.7.0, #2084); `withdirs` in glob (2026.3.0, #1998; async 2025.12.0, #1953); "Fix infinite recursion in expand_path with glob magic characters" (2026.6.0, #2038); "Use / as the only glob separator on every platform" (dev, #2112) [documented, FSSPEC-CL]. gcsfs 2023.12.0 "fix double asterisk glob test (#589)" [documented].
2. **Current fsspec rules (2026.9) worth noting** [documented, FSSPEC-API glob]: `**` "must be an entire path component"; `maxdepth` "Applied on the first '**' found"; a trailing `/` returns folders only; `[]` / `[!]` never match; no brace expansion, no extglob.
3. **The reference behaviour (pathlib) also changed.** Python 3.13: "Globbing with a pattern that ends with '**' returns both files and directories. In previous versions, only directories were returned". 3.11: a trailing separator returns only directories [documented, PY-PATHLIB]. Python also split matching: `PurePath.match` (recursive `**` "acts like non-recursive '*'", matches from the right) versus `full_match` (added 3.13) [documented, PY-PATHLIB]. cloudpathlib v0.7.0 switched glob/rglob to "pathlib's globbing logic rather than fnmatch" (#154) [documented, CLOUDPATH-CL].
4. **Keys can contain metacharacters.** pathlib: "For a literal match, wrap the meta-characters in brackets" (e.g. `[?]`) [documented, PY-PATHLIB]. gcsfs: "fix issue with special characters in rm method (#831)" [documented, GCSFS-CL]. Older fsspec added "support for hat dollar lbrace rbrace regex character escapes in glob" [documented, FSSPEC-CL pre-2021]. [inference] A key such as `a[1].txt` is a pattern unless it is escaped. Any operation that silently expands globs (fsspec `expand_path`, `open_files(expand=…)`) can misread a literal key.
5. **Bucket or root-level globbing has been restricted.** s3fs: "raise for glob("*")" [documented, S3FS-CL 2021.x]. cloudpathlib v0.12.1: "add error on globbing all buckets" (#311/#312) [documented].

## OP-09: inspect (exists, kind, size, time)

1. **Kind is ambiguous on object stores, and libraries changed their answer.** object_store 0.6.0: "ObjectStore::head Returns Directory for LocalFileSystem and Hierarchical Azure" (#4230) → "Return NotFound for directories in Head and Get" (#4231) [documented, OS-CL]. gocloud `ListObject.IsDir`: "Fields other than Key and IsDir will not be set if IsDir is true" [documented, GOCLOUD]. Hadoop: on object stores "the timestamps of directories may be artificially generated" [documented, HADOOP-INTRO]. fsspec `info`: "Some file systems might not be able to measure the file's size, in which case … 'size': None" [documented, FSSPEC-API].
2. **Directory detection costs extra calls, and libraries kept tuning it.** s3fs 2021.05.0: "short listing to determine directory (#472, 471)"; 2022.x: "don't lsbuckets for isdir(bucket) (#856)"; Unreleased: "Recognize readable directories with prefix-scoped S3 permissions (#1049)" and "Preserve missing-version errors instead of falling back to a directory (#886)" [documented, S3FS-CL]. adlfs: isdir/isfile made direct calls instead of `ls` (2021.09.1); `exists()` "now also checks whether a directory with that name exists … Previously this was only checked from the cache" (v0.7.6); `info()` reordered to search the parent "only after searching for the specified item directly" (2022.11.2) [documented, ADLFS-CL]. cloudpathlib v0.25.0 moved S3 metadata from `GetObject` to `HeadObject` [documented].
3. **A missing key can report 403, not 404.** S3 HeadObject: without `s3:ListBucket` permission, a missing key returns "403 Forbidden"; with it, 404 [documented, AWS HeadObject]. [inference] Mapping 403 to "not found" or to "permission denied" cannot be decided without knowing the caller's permissions.
4. **mtime meaning and granularity differ.** S3 `Last-Modified`: for multipart uploads, "the date of initiation of the multipart upload" [documented, AWS UsingMetadata]. Hadoop: object-store timestamp granularity is "likely to be 1 second"; mtime "MAY be that of the create() call, or the actual time which the PUT request was initiated … some period in between"; rename via COPY may reset it; timezone may differ [documented, HADOOP-INTRO "Timestamps"]. cloudpathlib v0.26.0 fixed a spurious `OverwriteNewerCloudError` on "filesystem with coarse modified-time resolution (such as FAT/exFAT…)" (#586) [documented]. fsspec 2025.7.0 "use st_birthtime in localFS, if available (#1883)"; fsspec dev added `created`/`modified` for SFTP (#2104) [documented, FSSPEC-CL]. paramiko `stat` exposes only `st_mode, st_size, st_uid, st_gid, st_atime, st_mtime`, and "An SFTP server may return as much or as little info as it wants" [documented, PARAMIKO].
5. **ETag format inconsistencies.** object_store 0.14.1: "InMemory and LocalFileSystem return unquoted ETags, violating RFC 9110" (#769/#770) [documented, OS-CL]. adlfs: `ls(detail=True)` returned Etag without quotes (#544) [documented]. cloudpathlib v0.25.0: gateways that omit `ETag` from HeadObject (#582) [documented]. s3fs: "deal with missing ETag (#557)", "empty ETag (#605)" [documented]. Hadoop requires etags to be consistent across list and getFileStatus [documented, HADOOP-FS EtagSource].
6. **Exists is not a separate primitive everywhere.** gocloud `Exists` is "a shortcut for calling ListPage and checking" NotFound [documented, GOCLOUD]. Hadoop deprecated single-attribute probes "to encourage users to make a single call to getFileStatus(p)" [documented, HADOOP-FS getBlockSize]. pyarrow `get_file_info` returns `FileType.NotFound` rather than raising [documented, PYARROW].

## OP-10: delete item

1. **Deleting a missing key: success or error, depending on the library.** S3: "If the Timestamp matches or if the object doesn't exist, the operation returns a 204" (stated in the conditional-delete context) [documented, AWS DeleteObject]. object_store `delete_stream`: "local filesystems, GCP, and Azure return an error, while S3 and in-memory will return Ok … Error::NotFound" [documented, OS-DOCS]. OpenDAL: "Deleting a file that does not exist is a successful no-op" [documented, OPENDAL]. gocloud `Delete`: missing → `gcerrors.NotFound` [documented, GOCLOUD]. fsspec dev changed `MemoryFileSystem.rm` to raise FileNotFoundError for a missing path "as rm_file and the other filesystems do" (#2140) [documented, FSSPEC-CL]. cloudpathlib v0.9.0 `unlink(missing_ok=True)` by default, which "diverges from pathlib" [documented]. Hadoop: delete of a nonexistent path returns False, and callers "SHOULD just call delete … and assume the destination is no longer present" [documented, HADOOP-FS].
2. **Bulk delete split from single delete, with per-store batch limits.** S3 DeleteObjects takes up to 1,000 keys and needs Content-MD5 or a checksum header [documented, AWS DeleteObjects]. Azure Blob Batch takes up to 256 subrequests [documented, AZ blob-batch]. object_store 0.13.0 moved `delete` to `ObjectStoreExt` and made `delete_stream` the trait method (#549) [documented, OS-DOCS / OS-CL]. Per-backend use: S3 batches of 1,000, Azure 256, GCP/HTTP/Local 10 concurrent single deletes [documented]. Regressions: MinIO needed Content-MD5 (#5414/#5415); "S3: delete() now requires DeleteObjects … breaks S3-compatible providers (Alibaba Cloud OSS)" (#731) → option to disable bulk delete (#734), 0.14.0 [documented, OS-CL]. OpenDAL has the `delete_max_size` capability and a `Deleter` that "leverages batch deletion capabilities" [documented]. cloudpathlib v0.21.1: "rmtree fail on Azure with no hns and more than 256 blobs" (#509) [documented].
3. **Partial failure in a batch.** object_store: "some errors will be from an overall call to a bulk delete operation, and not from a specific location" [documented]. s3fs Unreleased: "Raise translated errors when S3 reports per-object failures for bulk deletes (#838)"; earlier "_bulk_delete must return list (#866)", "return list of deleted keys (#726)" [documented, S3FS-CL]. gcsfs: `rm()` "now raises the original error when a whole delete batch fails" [documented, GCSFS-CL].
4. **On versioned buckets, delete creates a delete marker.** S3 DeleteObject on a versioning-enabled bucket "inserts a delete marker"; permanent deletion requires the versionId [documented, AWS DeleteObject / DeleteMarker]. s3fs Unreleased: "Delete the requested object version in rm_file when the path includes one" [documented]. OpenDAL: `delete_with_version` capability [documented]. GCS `ifGenerationMatch=0` treats "only noncurrent versions" as absent [documented, GCS-PRECOND]. [inference] Delete-then-"create if absent" on a versioned bucket depends on whether the store counts noncurrent versions.
5. **File-only and folder-only deletes are separate on filesystems.** paramiko `remove` "only works on files; for removing folders … use rmdir" [documented]. fsspec 2026.6.0: "LocalFS: remove directory symlinks without requiring recursive mode (#1299)" [documented]. object_store LocalFileSystem: "Deleting a path that resolves to a symlink will only delete the symlink"; `with_automatic_cleanup` removes empty parent dirs (0.10.2, #5978) [documented].

## OP-11: delete folder tree

1. **Not atomic and O(n) on object stores; the spec acknowledges it.** Hadoop: "Recursive directory deletion MAY be atomic … none of the other Hadoop FileSystems offer such a guarantee (including local FileSystems)"; object stores "implement delete() as recursive listing and entry-by-entry delete", so "the state of the object store reflects the partially completed operation" [documented, HADOOP-INTRO / HADOOP-FS]. Azure HNS was introduced to give "atomic directory manipulation" by "updating a single entry" [documented, AZ HNS]. gcsfs: "merge HNS and flat bucket deletion routing in rm (#858)" [documented].
2. **Root deletion is special-cased.** Hadoop: some object-store implementations "always return false when deleting the root". A client "MAY reject calls to delete("/", true)" [documented, HADOOP-FS]. pyarrow `delete_dir_contents(accept_root_dir=False, missing_dir_ok=False)`; C++ disallows the empty path, and `DeleteRootDirContents` is "EXPERIMENTAL" [documented, PYARROW]. pyarrow S3 `allow_bucket_deletion=False` by default [documented].
3. **Directory markers must be deleted too.** s3fs 2026.2.0: "do delete placeholders with rm(recursive=True) (#1005)" [documented, S3FS-CL]. Hadoop S3A marker policies (see OP-06) [documented, HADOOP-MARKERS]. cloudpathlib v0.6.3: `rmtree` on nested dirs on GCS and Azure (#184) [documented].
4. **The API shape changed: recursive became a flag on delete.** OpenDAL deprecated `remove_all` in 0.55.0: "Use delete_with with recursive(true)" [documented, OPENDAL]. fsspec `rm(path, recursive=False, maxdepth=None)`; docs "Clarify that rm handles directories (#2096)"; async `_rm` did not pass `maxdepth` until dev (#2106); "async rm in reverse order (#1014)" (2022.x) [documented, FSSPEC-API / FSSPEC-CL]. cloudpathlib UNRELEASED: `rmtree(ignore_errors, onerror, onexc)` (#270) [documented].
5. **Concurrent writers and listing lag.** gocloud and Hadoop note that listings may not include recently written blobs on eventually-consistent services [documented, GOCLOUD / HADOOP-INTRO]. [inference] A tree delete that lists and then deletes can leave objects written during the operation. The S3 strong-consistency note covers single-key list-after-write only [documented, AWS consistency].
