## Q1. Serverless compute: NCC, private endpoints, egress IPs, egress control, quotas, GA status

### Takeaway
Serverless compute has no VNet of its own, so it cannot use VNet peering. It reaches private Azure resources only through account-level **network connectivity configurations (NCCs)**. An NCC holds private endpoint rules that Databricks creates in its own network and you approve on the resource side. **Azure Database for PostgreSQL Flexible Server is a documented, directly supported NCC private endpoint target, but only if the server uses the "public access" networking mode.** Microsoft says private endpoints are not supported on VNet-integrated servers (delegated subnet). For a VNet-integrated server, or for Postgres on a VM or in AKS, the documented path is NCC → Private Link Service → internal Standard Load Balancer (GA 2025-08-04). Two alternatives exist: allowlisting published serverless egress IPs (Public Preview), and the new Private network gateway (Preview/Beta, billing from 2026-12-01).

### Cited Findings

**Option S1: NCC private endpoint rule straight to Azure Database for PostgreSQL Flexible Server**
- Mechanism **[doc]**: NCCs are "account-level regional constructs that manage private endpoint creation". When you add a private endpoint rule, Databricks sends a private endpoint request to your resource. Once it is approved, serverless uses it, and the endpoint is "dedicated to your Azure Databricks account and accessible only from authorized workspaces". — [Serverless private link, 2026-10-16](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/serverless-private-link)
- Supported products **[doc]**: NCC private endpoints work from "SQL warehouses, jobs, notebooks, Lakeflow pipelines, and model serving endpoints". — [same page](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/serverless-private-link)
- Postgres support **[doc]**: the Azure "Supported resources" list includes "Azure Database for PostgreSQL - Flexible server", "Azure Database for PostgreSQL - Single server" and "Resources behind a Standard Load Balancer". — [Manage private endpoint rules, 2026-10-09](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/manage-private-endpoint-rules)
- **Azure-side hard prerequisite [doc]**: "You must configure the networking mode to not use virtual network integration but public access." "The use of private endpoints isn't currently supported on servers created with virtual network integration." Also: "You can't configure private endpoints for servers that you created before that date [Private Link support]". — [PG Flexible Server Private Link, 2026-07-13](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-networking-private-link)
- Converting a VNet-integrated server **[doc, PREVIEW]**: "Migrate from virtual network to a private endpoint capable network configuration … (Preview)". It "typically takes about 20 minutes"; "For about 10 minutes, the server is inaccessible"; "When migration finishes, the server is inaccessible until you configure a private endpoint or establish appropriate firewall rules." — [PG migrate VNet→PE-capable, 2026-09-15](https://learn.microsoft.com/en-us/azure/postgresql/network/how-to-migrate-vnet-private-endpoint-capable-server)
- Same page, logical replication **[doc]**: "Private endpoint connectivity is inbound-only. PostgreSQL logical replication subscribers initiate outbound connections to the publisher". This matters only if the Flexible Server is itself a subscriber. Lakeflow Connect connects inbound to the publisher **[inferred]**. — [same](https://learn.microsoft.com/en-us/azure/postgresql/network/how-to-migrate-vnet-private-endpoint-capable-server)
- DNS on the Postgres side **[doc]**: on public-access servers the FQDN is a CNAME to `server_name.privatelink.postgres.database.azure.com` when a private endpoint with the default zone exists. — [PG Private Link, 2026-07-13](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-networking-private-link)
- Databricks-side steps **[doc]**: account admin, Premium plan. Create the NCC in the workspace region, attach it to the workspace ("Wait 10 minutes … Restart any running serverless services"), add the rule (resource ID + subresource), approve it in Azure under Networking → Private endpoint connections, and wait for ESTABLISHED. Optionally set the resource's public network access to Disabled. — [Serverless private link](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/serverless-private-link)
- Classic side effect **[doc]**: "If you configure your Azure resource to only accept connections from private endpoints, any connection to the resource from your classic Databricks compute resources also must use private endpoints." — [same](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/serverless-private-link)
- Rule states / failure signals **[doc]**: CREATING, PENDING, ESTABLISHED, REJECTED, DISCONNECTED, EXPIRED ("expires after being in the REJECTED, DISCONNECTED, or PENDING state for 14 days"), CREATE_FAILED. "Most changes … propagate … within 10 minutes, but can take up to 24 hours". — [Manage PE rules](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/manage-private-endpoint-rules)
- Costs **[doc]**: "Private endpoint rules are billed by Azure for each hour they exist, regardless of connection state." Charges: Private Connectivity /GB "Waived until further notice"; Private Connectivity /hour billed; Public Connectivity /GB (NAT Gateway pricing) billed; Data Transfer /GB billed. — [Manage PE rules](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/manage-private-endpoint-rules); [Networking costs, 2026-09-11](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/cost-management)
- Exit **[doc]**: delete the rule. Databricks "might retain the private endpoint on your cloud resource for 1 day before permanently deleting it." — [Manage PE rules](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/manage-private-endpoint-rules)
- GA status: Azure Private Link for serverless was announced GA in a Databricks blog. The search snippet gives "As of April 2024 … DBSQL Serverless … generally available". I did not fetch the blog itself, so this is **lead only**. — [Databricks blog (snippet)](https://www.databricks.com/blog/announcing-general-availability-azure-private-link-and-azure-storage-firewall-support). The NCC pages carry no preview banner **[doc]**.
- Documentation conflict (Lakehouse Federation): the federation networking page says "From the serverless compute plane, Azure Private Link for the SQL Server connector is supported" and names no PostgreSQL. The supported-resources list does include PG Flexible Server. — [Federation networking, 2026-10-13](https://learn.microsoft.com/en-us/azure/databricks/query-federation/networking) vs [Manage PE rules, 2026-10-09](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/manage-private-endpoint-rules). Shown, not resolved.

**Option S2: NCC → Private Link Service → internal Standard Load Balancer (for VNet-integrated Flexible Server, a VM, or AKS Postgres)**
- Mechanism **[doc]**: "configure Private Link connections from serverless compute to resources in your virtual network (VNet) through an Azure load balancer". On the Azure side: an internal LB (frontend IP, backend pool, health probe, rules) and a Private Link service in the same region. On the Databricks side: a private endpoint rule with the PLS resource ID plus **domain names**, then approval on the PLS and ESTABLISHED status. — [pl-to-internal-network, 2026-10-16](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/pl-to-internal-network)
- Constraints **[doc]**: "Each private endpoint rule … supports up to 100 domain names." "DNS chasing and DNS redirect are not supported. All domain names must resolve directly to the backend resources." "Enter the DNS name of the specific resource instance … not a service-level or wildcard domain. Domains using private-use TLDs (such as .internal, .localhost, or .test) are not supported." "Domains added as Private Link entries are implicitly allowlisted in network policies." — [same](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/pl-to-internal-network)
- GA dates **[doc]**: Public Preview 2025-06-04, "now generally available" 2025-08-04. — [Release notes Jun 2025](https://learn.microsoft.com/en-us/azure/databricks/release-notes/product/2025/june); [Aug 2025](https://learn.microsoft.com/en-us/azure/databricks/release-notes/product/2025/august)
- Azure PLS facts **[doc]**: PLS needs a Standard (not Basic) LB. The provider side sees the PLS NAT IP as the source ("the NAT IP address displays as source IP for all packets received by your service"). It allows up to eight NAT IPs and has an optional TCP Proxy v2. "Private Link Service Direct Connect" (no LB) is **public preview**. — [Private Link service overview, 2026-08-10](https://learn.microsoft.com/en-us/azure/private-link/private-link-service-overview)
- Inference: putting an SLB+PLS in front of a VNet-integrated Flexible Server means the backend pool targets the server's private IP. The docs allow IP-based backend pools, but Flexible Server IPs can change on failover or maintenance. I found no Microsoft or Databricks doc that blesses SLB-in-front-of-Flexible-Server, so treat it as **unverified**.
- First-hand (Azure, Databricks staff authors, no outcome metric): a technical blog (2025-10-16, Kiran Anand / Suraj Karuvel) walks through SLB → PLS → NCC rule. Caveats: use the PLS resource ID, not the LB's. The PLS subnet needs "private link service network policies disabled". "If the target service isn't running on the VM, an IP forwarder is needed". It covers no Postgres and no failure modes. — [Community tech blog](https://community.databricks.com/t5/technical-blog/azure-databricks-serverless-private-connectivity-to-customer-s/ba-p/134411)
- First-hand (AWS analogue, outcome = solved): the NCC endpoint showed ESTABLISHED and nslookup returned private IPs, yet traffic left via eth0 and the connection was refused. A Databricks employee blamed "DNS interception not engaging" because the LB's own hostname was used in place of a custom FQDN, and noted "an ESTABLISHED status only proves the PrivateLink tunnel exists". The poster marked an NLB-settings fix as the solution: disable "enforce inbound rules on PrivateLink traffic" and enable cross-zone LB. Thread dates 2026-06-03 to 2026-06-19. — [Community thread](https://community.databricks.com/t5/administration-architecture/serverless-ncc-private-endpoint-established-but-traffic-routes/td-p/158275)

**Option S3: Allowlist serverless public egress IPs on the Postgres firewall**
- **[doc, PUBLIC PREVIEW]**: "For resources other than Azure storage accounts … serverless compute uses public IP addresses". "The legacy list of stable IPs was decommissioned. If you use legacy IPs, migrate". You get the IPs from `ip-ranges.json` (service Databricks, type outbound, region, platform azure). "You must automate updates … Updates publish as often as once every 30 days, new IPs become active as soon as 60 days after publication". "It can't connect to resources that are reachable only over IPv6." — [Serverless firewall, 2026-10-23](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/serverless-firewall)
- Implication **[inferred]**: this only works if the Postgres server has a public endpoint, which contradicts a "Postgres inside a private network" posture. The ranges are shared, region-wide Databricks ranges, not tenant-dedicated.
- Service tag / NSP **[doc]**: the `AzureDatabricksServerless` service tag via a Network Security Perimeter "is supported only for NSP inbound rules targeting Azure Storage". It does not apply to Postgres. — [same](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/serverless-firewall)
- First-hand (no outcome): an Azure user (2025-01-28 to 2025-02-06) reported that a classic cluster reached a VNet Postgres via peering but serverless could not. Terraform said the database "must be recreated with the endpoint enabled" (consistent with the VNet-integration restriction). The thread was never resolved. — [Community thread](https://community.databricks.com/t5/data-engineering/allows-to-serveless-compute-to-connect-to-postgres-db/m-p/107922)

**Option S4: Private network gateway (subnet delegated to Databricks; reaches anything the subnet can reach)**
- **[doc, PREVIEW]**: "This feature is in Public Preview." "Billing … begins on or after December 1, 2026." You delegate a subnet to `Microsoft.Databricks/workspaces`, and serverless can then "reach the resources that subnet can, including networks transitively connected … over ExpressRoute or a VPN". It lives inside the existing NCC. Route priority: PE rules > service endpoints > gateway > default egress. Modes are SPECIFIC_DESTINATIONS (destinations auto-allowed in egress policy) or ALL_TRAFFIC (through your firewall, stable own IPs). Limits: same region as NCC; 10/30/50/100 Gbps tiers; "An NCC supports at most two gateways. A gateway supports at most two DNS resolvers and at most 100 destinations." — [Private network gateway, 2026-09-03](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/private-network-gateway)
- Status conflict **[doc]**: the release notes say "Private network gateway is in Private Preview" (2026-08-24) and then "is in Beta" (2026-09-03), while the feature page says "Public Preview". — [RN Aug 2026](https://learn.microsoft.com/en-us/azure/databricks/release-notes/product/2026/august); [RN Sep 2026](https://learn.microsoft.com/en-us/azure/databricks/release-notes/product/2026/september)
- Inference: this is the only documented serverless path that resembles VNet routing, so it would reach a VNet-integrated Flexible Server or AKS Postgres without PLS. It is less than two months old and pre-GA.

**Serverless egress control (network policies)**
- **[doc]**: there are two modes, Full Access and Restricted Access. Restricted allows only UC external locations, listed FQDNs and storage accounts, and the workspace's own APIs. "Outbound access through private endpoints is also subject to the rules defined in the network policy. The destination must be listed either in Unity Catalog or within the policy." The policy is account-level, one per workspace, and has a dry-run mode. — [Network policies, 2026-10-23](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/network-policies)
- Dates **[doc]**: introduced 2024-12-11. "Manage network policies for serverless egress control (Generally Available)" on 2025-06-09, with denial logs in Unity Catalog. "Block specific internet destinations" is Public Preview (2026-06-23). — [RN Dec 2024](https://learn.microsoft.com/en-us/azure/databricks/release-notes/product/2024/december); [RN Jun 2025](https://learn.microsoft.com/en-us/azure/databricks/release-notes/product/2025/june); [RN Jun 2026](https://learn.microsoft.com/en-us/azure/databricks/release-notes/product/2026/june)
- Failure mode **[inferred from doc]**: in Restricted mode, a Postgres FQDN reached through an S1 private endpoint rule that is not listed in the policy (or in a UC connection) gets blocked even though the endpoint is ESTABLISHED. S2 domains are implicitly allowlisted (pl-to-internal-network page). Early warning: denials appear in the network access events system table (Public Preview since 2024-12-11). — [RN Dec 2024](https://learn.microsoft.com/en-us/azure/databricks/release-notes/product/2024/december)

**Quotas [doc]**
- 20 NCCs per region per account; 100 private endpoints per region (shared across 1-20 NCCs); 50 workspaces per NCC; 100 domain names per PLS rule. — [Resource limits, 2026-10-21](https://learn.microsoft.com/en-us/azure/databricks/resources/limits); [Serverless private link](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/serverless-private-link)
- An NCC is regional and only attaches to same-region workspaces. — [pl-to-internal-network](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/pl-to-internal-network)

### Inferences
- For the stated context (Postgres "inside a private Azure network"), S1 needs a public-access-mode Flexible Server with public access disabled. A VNet-integrated server first needs the Preview in-place conversion (about 10 minutes offline) or a rebuild. If the existing server is VNet-integrated, that decision costs the most to reverse.
- Early warning signs, by option: S1/S2 rule stuck in PENDING (expires at 14 days); ESTABLISHED but connection refused or timing out (DNS/domain mismatch or LB rule/probe); a Restricted-mode network policy denial; S3 connection failures 30-60 days after an ip-ranges.json change.
- Exit costs: S1/S2 are account-console objects, deleted in minutes (PE retained up to 1 day), but Azure-side PLS/LB and server networking-mode changes stay. S3 leaves a public endpoint on Postgres to close. S4 has an unknown cost model before 2026-12-01.

- I found no doc date for "NCC private endpoints to PG Flexible Server" becoming GA. The April 2024 serverless Private Link GA blog was not fetched; I only have the search snippet.
- I did not fetch the NCC Terraform/API reference, so domain_names behaviour for direct PaaS rules is unverified.

## Q2. Classic compute: VNet injection, peering/hub-spoke, private DNS, NSGs, UDRs/firewall, SCC, back-end Private Link

### Takeaway
Classic compute runs in a customer VNet (VNet injection). Reaching Postgres uses ordinary Azure networking: peering, either directly or through a hub, to the Postgres VNet, plus a private DNS zone link. A private endpoint for a public-access-mode Flexible Server can also sit inside the workspace VNet or hub. These features are long-established. The pages carry no preview banners, and the dates relevant now are operational: default outbound access retired for new VNets after 2026-03-31, and subnet CIDRs are immutable.

### Cited Findings
- VNet injection requirements **[doc]**: VNet in the same region **and same subscription** as the workspace; /16-/24; two dedicated subnets (container/host), recommended at least /26, not shareable across workspaces; "Subnet CIDR ranges cannot be changed after deployment"; NSG rules and delegation to `Microsoft.Databricks/workspaces` auto-configured; network contributor role needed. "Databricks recommends using an Azure NAT gateway … After March 31, 2026, new VNets require explicit outbound connectivity methods." Features listed: on-prem access via UDRs, custom DNS, egress control via extra NSG rules. — [VNet inject, 2026-10-09](https://learn.microsoft.com/en-us/azure/databricks/security/network/classic/vnet-inject)
- The same page's verification checklist says "Virtual network peering is disabled (this is expected for VNet injection)". **Inference**: this refers to the workspace's built-in "VNet peering" setting (used for the managed-VNet deployment), not to user-created peerings on the injected VNet. The on-prem page below peers the injected VNet explicitly.
- Hub/transit **[doc]**: "Your Azure Databricks workspace must be deployed in your own virtual network". Peer it to a transit VNet with "Allow Gateway Transit" and "Use Remote Gateways", and possibly "Allow Forwarded Traffic". Add UDRs for the return route to the control plane (SCC relay IP if SCC is on), metastore, artifact/log storage and Event Hubs. "In some cases, BGP route propagation causes failures when validating". — [On-prem network, 2026-09-21](https://learn.microsoft.com/en-us/azure/databricks/security/network/classic/on-prem-network)
- UDRs **[doc]**: "You need a UDR for every type of outbound connection from the VNet". Prefer the service tags AzureDatabricks/Storage/EventHub (region-scoped possible; some regions have secondary storage in another region). Port 3306 egress for the legacy Hive metastore. — [UDR, 2026-09-11](https://learn.microsoft.com/en-us/azure/databricks/security/network/classic/udr)
- SCC / No Public IP **[doc]**: "customer virtual networks have no open ports and compute resources … have no public IP addresses". It defaults to Yes in the portal. With the default VNet, Databricks creates a NAT gateway in the managed RG ("incurs additional cost"). "Always allowlist the provided domain names (FQDNs) for SCC relay endpoints instead of individual IP addresses." Default outbound access retires for new VNets after 2026-03-31 and does not affect existing workspaces. — [SCC, 2026-10-08](https://learn.microsoft.com/en-us/azure/databricks/security/network/classic/secure-cluster-connectivity)
- Back-end Private Link **[doc]**: requires Premium plan, a dedicated PE subnet, Azure-managed private DNS, a "Microsoft-recommended hub-spoke architecture", and SCC = Yes with Required NSG rules = NoAzureDatabricksRules. Compute must resolve the workspace URL to the PE IP. — [Private Link standard, 2026-10-09](https://learn.microsoft.com/en-us/azure/databricks/security/network/classic/private-link-standard). Relevance **[inferred]**: back-end Private Link secures compute↔control plane traffic and is not on the Postgres data path.
- Federation from classic **[doc]**: "All network traffic for federated queries is directly between Azure Databricks clusters (or SQL warehouses) and the external database system." Options: a stable egress IP (NAT gateway) or Private Link between the DB network and the compute network. With custom DNS, "add the database system's hostname to your custom DNS server". — [Federation networking, 2026-10-13](https://learn.microsoft.com/en-us/azure/databricks/query-federation/networking)
- Postgres-side DNS for VNet-integrated servers **[doc]**: "Private DNS zone settings and virtual network peering are independent". To reach the server from another VNet, link the private DNS zone to that VNet. "You can only link Private DNS zone names that end with postgres.database.azure.com." With custom DNS, forward to 168.63.129.16. "We no longer validate virtual network link presence on server creation". A catch-all 0.0.0.0/0 → NVA route on the delegated subnet "is not supported". — [PG private access, 2026-07-13](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-networking-private)
- Postgres-side for public-access + private endpoint **[doc]**: private endpoints support NSGs/UDRs/ASGs (network policies) and are reachable from peered VNets and over ExpressRoute/VPN. The zone name `privatelink.postgres.database.azure.com` is needed for auto-config. — [PG Private Link, 2026-07-13](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-networking-private-link)
- First-hand (Azure, outcome = solved, not Postgres-specific): a cluster failed to start until a VNet link was added to the private DNS zone. Some clusters started before the fix, so the symptom was inconsistent. I saw this only via a search summary and did not fetch it, so it is a **lead**. — [Community thread](https://community.databricks.com/t5/administration-architecture/databricks-cluster-failed-to-start-add-nodes-failed-solution/td-p/92911)
- First-hand (Azure, outcome = working, thin): in the Postgres thread above, the poster's personal (classic) cluster reached the VNet Postgres "through VNet peering" while serverless did not. — [Community thread, 2025-01-28](https://community.databricks.com/t5/data-engineering/allows-to-serveless-compute-to-connect-to-postgres-db/m-p/107922)

### Inferences
- Classic option C1 (peering/hub to a VNet-integrated Flexible Server): the Azure side needs a peering, a link from the PG private DNS zone to the Databricks VNet (or a resolver chain), and NSG allowance on 5432. The Databricks side needs nothing beyond VNet injection. It yields the private path with no Databricks-specific objects. Cost: IP planning (non-overlapping CIDRs, immutable subnets) and peering data charges. Failure mode: DNS resolves to nothing or a public name (zone not linked), or an asymmetric route through a hub NVA. Early warning: `nslookup <server>.postgres.database.azure.com` from a cluster init script or notebook. Exit: remove the peering and zone link.
- Classic option C2 (private endpoint for a public-access-mode server inside the Databricks VNet/hub): the same server could serve serverless S1 and classic C2 at once. The documented statement that a PE-only server forces classic to use private endpoints (serverless private link page) makes C2 the counterpart of S1.
- If Databricks becomes the orchestrator alongside Dagster on AKS, both would read the same Postgres. Classic peering lets the Databricks VNet see the AKS/Postgres VNet at L3, a wider blast radius than a per-resource private endpoint.

### Gaps
- No page states GA dates for VNet injection or SCC. They are long-established features, and the docs carry no preview label.
- Federation docs give no Postgres-specific networking guidance (only BigQuery/Snowflake connector notes).

## Q3. Lakehouse Federation and Lakeflow Connect for Postgres: which compute, networking implications

### Takeaway
**Lakehouse Federation** queries run on the compute that issues them: classic clusters (DBR ≥ 13.3 LTS, Standard/Dedicated) or pro/serverless SQL warehouses. Its network path is therefore the classic path (Q2) or the serverless path (Q1). **Lakeflow Connect PostgreSQL is Public Preview** (since 2025-12-16, enrolment via the account team). Its **ingestion gateway must run on classic compute** and continuously, while the ingestion pipeline runs on serverless. So the gateway's classic VNet needs the network path to Postgres, and the source must have logical replication enabled.

### Cited Findings
- Federation compute **[doc]**: "Azure Databricks compute must use Databricks Runtime 13.3 LTS or above and Standard or Dedicated access mode." "SQL warehouses must be pro or serverless and must use 2023.40 or above." TLS is always on, with `userProvidedServerCertificate` for an internal CA; hostname verification applies with verify-full. Join pushdown is Public Preview (DBR 17.2+ / SQL warehouse). — [Federation PostgreSQL, 2026-10-06](https://learn.microsoft.com/en-us/azure/databricks/query-federation/postgresql)
- Federation path **[doc]**: neither Unity Catalog nor the control plane is on the data path. OAuth token exchange runs from the control plane, so the control plane must reach the OAuth endpoint (password auth for Postgres avoids this, **[inferred]**). — [Federation networking, 2026-10-13](https://learn.microsoft.com/en-us/azure/databricks/query-federation/networking)
- LFC status **[doc, PUBLIC PREVIEW]**: "The PostgreSQL connector is in Public Preview. Contact your Azure Databricks account team to request access." Release note dated 2025-12-16. — [LFC PostgreSQL, 2026-10-09](https://learn.microsoft.com/en-us/azure/databricks/ingestion/lakeflow-connect/postgresql); [RN Dec 2025](https://learn.microsoft.com/en-us/azure/databricks/release-notes/product/2025/december)
- LFC compute **[doc]**: "Although the ingestion pipeline runs on serverless compute, the ingestion gateway must run on classic compute." "The ingestion gateway must run in continuous mode to prevent Write-Ahead Log (WAL) bloat and replication slot accumulation." Gateway policy: Job Compute family, minimum 8 cores. Serverless must be enabled. — [LFC limitations, 2026-09-11](https://learn.microsoft.com/en-us/azure/databricks/ingestion/lakeflow-connect/postgresql-limits); [LFC pipeline, 2026-10-06](https://learn.microsoft.com/en-us/azure/databricks/ingestion/lakeflow-connect/postgresql-pipeline)
- LFC source requirements and failure modes **[doc]**: PG ≥ 13 with `wal_level=logical` ("typically requires a database restart"), a replication user, publications and slots per database, and replica identity FULL/DEFAULT. "Logical replication is only supported on primary instances". "Replication slots are not automatically removed when you delete pipelines." "If the primary PostgreSQL node is demoted or replaced (for example, during a failover), the replication slot information is lost … requires a full refresh of all tables". Recommendation of at most 250 tables per pipeline; one gateway per pipeline. Supported sources include "Azure Database for PostgreSQL, Azure virtual machines". Flexible Server supports logical replication on all tiers. — [LFC limitations](https://learn.microsoft.com/en-us/azure/databricks/ingestion/lakeflow-connect/postgresql-limits); [LFC source setup, 2026-09-11](https://learn.microsoft.com/en-us/azure/databricks/ingestion/lakeflow-connect/postgresql-source-setup)

### Inferences
- Because the LFC gateway is classic, a fully serverless estate still needs a VNet-injected workspace (or a classic path) for Postgres CDC. The serverless NCC path covers federation and plain JDBC reads from serverless, not the LFC gateway.
- The failover slot-loss rule interacts with any HA Postgres (Flexible Server HA failover, or a Kubernetes operator promoting a replica). Early warning: "slot not found" errors and growing `pg_replication_slots` retained WAL. Exit cost: drop slots and publications manually, and revert `wal_level` (restart).

## Q4. Postgres in Kubernetes (operator in AKS) versus Flexible Server

### Takeaway
A Postgres running in AKS is not an Azure PaaS private-link resource, so serverless can reach it only via NCC → **Private Link Service in front of an AKS internal Standard Load Balancer** (S2, GA 2025-08-04), or via the Preview private network gateway (S4). AKS can create the PLS from Service annotations. Classic compute reaches it by peering or hub routing to the AKS VNet and an internal LB IP or DNS name.

### Cited Findings
- AKS PLS **[doc]**: a Service of type LoadBalancer with `azure-load-balancer-internal` and `service.beta.kubernetes.io/azure-pls-create: "true"` creates an internal LB in the node RG and a PLS on its frontend IP. It requires a Standard LB with the `nodeIPConfiguration` backend pool type ("doesn't support Basic Load Balancer or the IP-based nodeIP backend pool type"), IPv4 and TCP/UDP only. "If the service uses externalTrafficPolicy: Local, the Private Link Service subnet must be different from the pod subnet." — [AKS internal LB + PLS, 2026-07-31](https://learn.microsoft.com/en-us/azure/aks/internal-lb)
- Databricks constraints that bite for in-cluster names **[doc]**: domain names must "resolve directly to the backend resources"; DNS chasing/redirect is not supported; private-use TLDs like `.internal` are not supported; no wildcards. — [pl-to-internal-network, 2026-10-16](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/pl-to-internal-network)
- Source IP seen by Postgres **[doc]**: PLS NATs consumer traffic, so the provider sees the PLS NAT IP. TCP Proxy v2 is optional. — [PLS overview, 2026-08-10](https://learn.microsoft.com/en-us/azure/private-link/private-link-service-overview)
- LFC on operator-managed HA **[doc]**: slot information is lost on primary demotion or replacement, which forces a full refresh. — [LFC limitations](https://learn.microsoft.com/en-us/azure/databricks/ingestion/lakeflow-connect/postgresql-limits)

### Inferences
- The Azure side needs a dedicated K8s Service (the operator's read-write service, exposed as an internal LB with the PLS annotations) managed in GitOps, a PLS NAT subnet, and `pg_hba` rules that admit the PLS NAT range rather than Databricks IPs. The Databricks side needs an NCC PLS rule whose domain name is a public-style custom FQDN (for example under a corporate domain) that also matches the Postgres TLS certificate if verify-full is used.
- Gains: a per-service, approval-gated path. AKS owns the LB lifecycle, so the PLS can be recreated if the Service is deleted or recreated (e.g., namespace teardown), which is a GitOps-specific failure mode. Early warning: the NCC rule moves to DISCONNECTED or REJECTED.
- Failover behaviour depends on the operator's primary service following the leader. A health probe on the LB gives one layer of protection. Logical slots for LFC need operator support for slot failover. I did not verify this for any operator.
- Compared with Flexible Server: there is no Microsoft-managed private DNS zone or direct PaaS private endpoint. You own LB, PLS, DNS name and certificate. The S1 networking-mode restriction does not apply.

### Gaps
- No first-hand report found of Databricks serverless → PLS → AKS-hosted Postgres (CloudNativePG, Zalando, Crunchy).
- I found no doc on PLS behaviour when the AKS-managed LB frontend changes.
