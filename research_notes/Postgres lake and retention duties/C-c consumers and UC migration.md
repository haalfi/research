# C-c: Consumer unawareness with two orchestrators on plain Postgres (C4), and Postgres to Delta/UC migration paths (C5)

Scope: a lake made of plain Postgres tables in one database (raw, standardized, curated), consumers reading Postgres views, Dagster OSS today and Databricks (Azure) possibly later, with feeds migrated one at a time while both orchestrators write the same Postgres tables. Options study: no recommendation and no ranking.

Grading legend: **[documented]** = vendor doc or spec, version and date given; **[first-hand]** = practitioner report with an outcome; **[inferred]** = my inference, labelled; **[lead]** = search snippet only, full text not fetched or unreachable.

## C4.1 Postgres-native mechanisms that let consumers stay unaware of the producer (views, view swaps, renames, partitions, transactional DDL)

### Takeaway
Postgres views are a workable "published name" layer (C1), but they bind tightly to the tables underneath. `CREATE OR REPLACE VIEW` can only append columns: it cannot rename, reorder, retype or drop them. Dropping or replacing a table that a view depends on requires `CASCADE`, and `CASCADE` drops the view. Swaps therefore have to be done by redefining the view, or by `ATTACH`/`DETACH PARTITION`, not by drop-and-recreate. Any pipeline step that drops tables (dbt `table` materializations, Spark JDBC overwrite without `truncate`) interacts badly with consumer views.

### Cited Findings
- **[documented, PG17]** `CREATE OR REPLACE VIEW`: "The new query must generate the same columns that were generated by the existing view query (that is, the same column names in the same order and with the same data types), but it may add additional columns to the end of the list. The calculations giving rise to the output columns may be completely different." So the producer can repoint a view to a different table (for example `feed_x_v2`) in one statement, as long as the column signature is unchanged or only extended at the end. — [PostgreSQL 17: CREATE VIEW](https://www.postgresql.org/docs/17/sql-createview.html)
- **[documented, PG17]** On replace, "only the view's defining SELECT rule, plus any WITH ( ... ) parameters and its CHECK OPTION are changed. Other view properties, including ownership, permissions, and non-SELECT rules, remain unchanged. You must own the view to replace it." Consumer grants survive a repoint. Both orchestrators' roles would need to be members of the owning role to perform the swap. — [PostgreSQL 17: CREATE VIEW](https://www.postgresql.org/docs/17/sql-createview.html)
- **[documented, PG17]** `DROP TABLE`: "to drop a table that is referenced by a view ... CASCADE must be specified. (CASCADE will remove a dependent view entirely ...)". — [PostgreSQL 17: DROP TABLE](https://www.postgresql.org/docs/17/sql-droptable.html)
- **[documented, PG17]** `ALTER TABLE ... RENAME` changes the name of a table, view or similar object, "There is no effect on the stored data". RENAME, SET SCHEMA, ATTACH PARTITION and DETACH PARTITION cannot be combined into a multi-action ALTER TABLE list. — [PostgreSQL 17: ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html)
- **[inferred]** Postgres views store references to the underlying relation by OID, not by name. A rename-swap (`ALTER TABLE t RENAME TO t_old; ALTER TABLE t_new RENAME TO t;`) therefore leaves existing views pointing at `t_old`, not at the new `t`. The dbt forum thread below is consistent with this: views follow the table they were bound to, and are dropped with it. This contradicts the DuckLake-era C1 idea that "the producer swaps the table behind the name". On Postgres, the thing that gets swapped has to be the view definition, or a partition. I did not fetch a PG doc page that states the OID binding explicitly, so this is inference.
- **[documented, PG17]** Partition swap: an existing table can be loaded, checked and transformed and then attached with `ALTER TABLE ... ATTACH PARTITION`. This "requires only a SHARE UPDATE EXCLUSIVE lock on the partitioned table rather than the ACCESS EXCLUSIVE lock required by CREATE TABLE ... PARTITION OF". The attached table is scanned under ACCESS EXCLUSIVE on that partition unless a matching CHECK constraint exists beforehand. `DETACH PARTITION` needs ACCESS EXCLUSIVE on the parent; `DETACH PARTITION ... CONCURRENTLY` needs only SHARE UPDATE EXCLUSIVE. Partitions must have exactly the parent's columns. — [PostgreSQL 17: Table Partitioning](https://www.postgresql.org/docs/17/ddl-partitioning.html)
- **[documented, PG17]** `TRUNCATE` takes ACCESS EXCLUSIVE, "is not MVCC-safe" (after a truncate, concurrent transactions that took their snapshot before it see the table as empty), but "is transaction-safe with respect to the data ... rolled back if the surrounding transaction does not commit". — [PostgreSQL 17: TRUNCATE](https://www.postgresql.org/docs/17/sql-truncate.html)
- **[first-hand, 2019, older than 2 years]** dbt forum, Nov 2019: a user found views that `ref` a model disappearing when the model was rebuilt. The dbt maintainer explained that Postgres refuses `drop table` while dependents exist, so "dbt is forced to use the cascade qualifier ... This has the result of dropping my_view as well". Redshift late-binding views avoid this, but "on Postgres, there's no equivalent feature". The maintainer also said incremental models are updated in place (delete+insert) and do not cascade-drop. The outcome: guidance to materialise BI-facing models as tables. — [dbt Community Forum: Why are my views being dropped…](https://discourse.getdbt.com/t/why-are-my-views-being-dropped-when-the-incremental-model-it-refs-is-being-updated/689)

### Inferences
- **[inferred]** Postgres patterns that keep consumers unaware:
  - (a) Consumer view `published.<feed>` and producer-owned physical tables; swap with `CREATE OR REPLACE VIEW` inside a transaction. Column-compatible changes only; incompatible changes need `DROP VIEW` + `CREATE VIEW`, which consumers can see, and grants must be reissued.
  - (b) A partitioned table per feed, with one partition per delivery or period, swapped with DETACH/ATTACH.
  - (c) A rename-swap only for objects that no view depends on.
- **[inferred]** Postgres DDL is transactional (TRUNCATE is shown above; CREATE OR REPLACE VIEW and RENAME run inside a transaction). A "stage, then repoint view, then commit" step is therefore atomic for readers whose snapshot starts after the commit. I did not fetch a general "transactional DDL" doc page.

### Gaps
- No PG doc page fetched that states the OID binding of views explicitly, or covers lock levels for `CREATE OR REPLACE VIEW` (it takes a lock on the view; the level is not verified here).
- Behaviour with `security_invoker` views across two writer roles was not examined.

## C4.2 Single-writer safety across two orchestrators: advisory locks, ownership tables, idempotent upserts

### Takeaway
Postgres offers primitives that both Dagster (Python) and Databricks (JDBC or psycopg) can use against the same database: advisory locks as a lease, a feed-ownership row in the ops schema, and keyed upserts (`ON CONFLICT`, `MERGE`). Advisory locks are only cooperative. They protect nothing against a writer that does not take them, and session-level locks do not follow transaction semantics.

### Cited Findings
- **[documented, PG17]** Advisory locks "have application-defined meanings ... the system does not enforce their use — it is up to the application to use them correctly."
  - **Session level:** held "until explicitly released or the session ends"; they "do not honor transaction semantics", so a lock taken in a rolled-back transaction is still held.
  - **Transaction level:** "automatically released at the end of the transaction, and there is no explicit unlock operation".
  - **Re-entrancy:** a session already holding a lock always succeeds on a further request.
  - **Visibility:** current holders appear in `pg_locks`.
  - **Capacity:** locks share the lock pool sized by `max_locks_per_transaction` and `max_connections`.
  - — [PostgreSQL 17: Explicit Locking §13.3.5](https://www.postgresql.org/docs/17/explicit-locking.html)
- **[documented, PG17]** Keys are one 64-bit value or two 32-bit values ("these two key spaces do not overlap"). `pg_try_advisory_xact_lock(key bigint) → boolean` "will either obtain the lock immediately and return true, or return false without waiting". Multiple session-level requests stack and each needs its own unlock. — [PostgreSQL 17: System Administration Functions §9.28.10](https://www.postgresql.org/docs/17/functions-admin.html)
- **[documented, PG17]** `INSERT ... ON CONFLICT DO UPDATE` "guarantees an atomic INSERT or UPDATE outcome; provided there is no independent error, one of those two outcomes is guaranteed, even under high concurrency". Caveat: "While CREATE INDEX CONCURRENTLY or REINDEX CONCURRENTLY is running on a unique index, INSERT ... ON CONFLICT statements on the same table may unexpectedly fail with a unique violation." — [PostgreSQL 17: INSERT](https://www.postgresql.org/docs/17/sql-insert.html)
- **[documented, PG17]** `MERGE` with concurrent modifiers follows the usual isolation rules. The docs suggest `INSERT ... ON CONFLICT` "as an alternative statement which offers the ability to run an UPDATE if a concurrent INSERT occurs", note the two "are not interchangeable", and say source ordering may be needed "to avoid deadlocks between concurrent transactions". — [PostgreSQL 17: MERGE](https://www.postgresql.org/docs/17/sql-merge.html). (That MERGE first appeared in PG15 is from the supported-versions list on that page, not from release notes.)

### Inferences
- **[inferred]** A cross-orchestrator lease could be either:
  - `pg_try_advisory_xact_lock(hash(feed_id))` taken in the same transaction that writes the feed. The lock is released at commit or rollback, so a crashed job does not leave a stuck lease.
  - A session-level lock for multi-transaction loads. This risks a stuck lease while the session stays up, for example in pooled connections.
  Both need every writer path to cooperate. A Spark JDBC `df.write` opens its own connections per partition and takes no advisory lock, so Spark-side writes would need a staging table plus a final SQL step (run from a driver-side connection) that takes the lock and merges.
- **[inferred]** An ownership table in the ops schema (`feed_owner(feed_id, orchestrator, valid_from)`) checked inside the write transaction, ideally `SELECT ... FOR UPDATE` on the row, is enforced only by convention. Making it a hard guard would take a trigger on the target table that compares `current_user` or `application_name` to the owner row, or separate DB roles per orchestrator with GRANTs switched per feed. Per-role GRANTs are the only mechanism of these that Postgres itself enforces.
- **[inferred]** Idempotency keyed by delivery id (a unique index on `(delivery_id, natural_key)` plus `ON CONFLICT`) makes double-runs by the two orchestrators converge rather than duplicate. It does not prevent last-writer-wins on differing content.
- **[inferred]** Early warning signs: `pg_locks` showing advisory locks held by unexpected `application_name`s, rows in the run log from two orchestrators for the same delivery id, lock-wait or deadlock errors on feed tables, and `ON CONFLICT DO UPDATE` row counts > 0 where inserts were expected.

### Gaps
- I found no practitioner report (with outcome) of advisory locks used as a lease between Dagster and Databricks specifically.

## C4.3 dbt-postgres materializations, contracts, and whether dbt can target Postgres from a Databricks job

### Takeaway
dbt-postgres supports append, merge, delete+insert and microbatch. Its `table` materialization builds a temp relation, renames, commits, then drops the backup **with CASCADE**, which removes consumer views bound to the old table. The Databricks **dbt task** is documented only with a SQL warehouse and the dbt-databricks adapter. Running dbt-postgres from Databricks is not documented, and would mean running dbt Core yourself on job compute (inference).

### Cited Findings
- **[documented, dbt docs, versionless, fetched 2026-10-27]** "In dbt-postgres, the following incremental materialization strategies are supported: append, merge, delete+insert (default when unique_key is defined), microbatch." Indexes configured on a model are created "within the same transaction as its main create statement". `unlogged=True` is available ("considerably less safe"). — [dbt: Postgres configurations](https://docs.getdbt.com/reference/resource-configs/postgres-configs)
- **[documented, dbt docs]** Strategy matrix: dbt-postgres supports append, merge, delete+insert, microbatch (no insert_overwrite). dbt-databricks supports all five. — [dbt: About incremental strategy](https://docs.getdbt.com/docs/build/incremental-strategy)
- **[documented, dbt docs]** Microbatch is "Available for dbt v1 Latest and dbt v1.9 or higher". dbt-postgres implements microbatch with the merge strategy and requires `unique_key`. dbt-databricks uses `replace_where`. Batches can run concurrently and be retried independently. — [dbt: Incremental microbatch](https://docs.getdbt.com/docs/build/incremental-microbatch)
- **[documented, dbt-adapters main, 2026-10-27]** Global `table` materialization:
  1. Create the `intermediate_relation`.
  2. `adapter.rename_relation(existing_relation, backup_relation)`.
  3. `adapter.rename_relation(intermediate_relation, target_relation)`.
  4. `adapter.commit()`.
  5. "finally, drop the existing/backup relation after the commit".
  The default drop macro renders `drop {{ relation.type }} if exists {{ relation.render() }} cascade`.
  — [dbt-adapters table.sql](https://raw.githubusercontent.com/dbt-labs/dbt-adapters/main/dbt-adapters/src/dbt/include/global_project/macros/materializations/models/table.sql); [dbt-adapters relations/drop.sql](https://raw.githubusercontent.com/dbt-labs/dbt-adapters/main/dbt-adapters/src/dbt/include/global_project/macros/relations/drop.sql)
- **[documented, dbt docs]** Contracts (`contract: enforced: true`) apply to table and incremental models (incremental requires `on_schema_change: append_new_columns` or `fail`). Views get only column names and types. dbt runs a "preflight" check of names and types and puts columns and constraints in DDL. On **Postgres**: not_null, primary_key, foreign_key and unique are definable and enforced, check is definable and enforced. On **Databricks**: only not_null and check are enforced; primary and foreign keys are definable but not enforced. — [dbt: Model contracts](https://docs.getdbt.com/docs/mesh/govern/model-contracts). The per-platform matrix was read from the rendered tabs. Its tab-to-row mapping is ambiguous in my text extraction, so re-check the Postgres versus Databricks rows before quoting them.
- **[documented, Azure Databricks, ms.date 2026-09-11]** dbt task requirements:
  - The Run As principal needs "CAN USE on the SQL warehouse that runs the SQL generated by dbt" plus UC privileges.
  - "The SQL warehouse drop-down menu shows only serverless and pro SQL warehouses".
  - The dependent library defaults to `dbt-databricks>=1.0.0,<2.0.0`.
  - Databricks "injects the DBT_ACCESS_TOKEN".
  - No Postgres profile option is described.
  — [Azure Databricks: dbt task for jobs](https://learn.microsoft.com/en-us/azure/databricks/jobs/dbt)

### Inferences
- **[inferred]** C2 ("same dbt project on both runners") on Postgres means the same dbt-postgres project run by Dagster (dagster-dbt) and by a Databricks job. The Databricks job would have to be a Python/shell task that installs `dbt-postgres` and supplies its own `profiles.yml` and secrets, not the native dbt task, which is built around a SQL warehouse and dbt-databricks. Network reach from Databricks compute to Azure Postgres is also needed. This is undocumented by Databricks, so it is inference.
- **[inferred]** For consumer unawareness, models that back `published.*` views would avoid the `table` materialization's backup-drop-cascade. The alternatives are incremental models (in-place delete+insert or merge), or post-hooks that recreate consumer views (a visible gap during the run). Running the same project from two runners at once on the same model would race on the `__dbt_tmp`/`__dbt_backup` names. The table macro drops any "preexisting" intermediate or backup relation first, so a concurrent second run could drop the first run's temp table.

### Gaps
- No Databricks doc found on running dbt-postgres from Lakeflow Jobs. No practitioner report found.
- dbt-postgres's own `rename_relation` and `drop_relation` overrides were not checked. The global macros shown are what dbt-postgres inherits unless overridden. I only saw `drop schema ... cascade` in dbt-postgres adapters.sql.

## C4.4 A Databricks Spark JDBC write and a Dagster Python loader writing the same Postgres table: semantics, failure modes, early warnings

### Takeaway
A Spark JDBC write is not one transaction. Each DataFrame partition commits separately, so a failed or retried job can leave partial or duplicate rows. Overwrite mode **drops and recreates** the table unless `truncate=true`, and dropping fails or cascades when views depend on the table. Overwrite also discards the indexes, grants and constraints a Dagster/dbt producer created. The Spark 4.2.0 docs say `truncate` is not supported for PostgresDialect, but the v4.0.1 source does truncate for Postgres. The doc and the code conflict here. The JDBC writer has no upsert or MERGE save mode, so keyed upserts need a staging table plus SQL.

### Cited Findings
- **[documented, Spark 4.2.0 docs]** `truncate` (default false): "When SaveMode.Overwrite is enabled, this option causes Spark to truncate an existing table instead of dropping and recreating it ... prevents the table metadata (e.g., indices) from being removed ... MySQLDialect, DB2Dialect, MsSqlServerDialect, DerbyDialect, and OracleDialect supports this while PostgresDialect and default JDBCDialect doesn't. For unknown and unsupported JDBCDialect, the user option truncate is ignored." `cascadeTruncate`: for PostgreSQL it runs `TRUNCATE TABLE ONLY t CASCADE`, which "will affect other tables". `isolationLevel` default `READ_UNCOMMITTED`. `batchsize` default 1000. `numPartitions` "also determines the maximum number of concurrent JDBC connections". — [Spark 4.2.0: JDBC To Other Databases](https://spark.apache.org/docs/latest/sql-data-sources-jdbc.html)
- **[documented, Spark source v4.0.1; contradicts the doc above]** `JdbcRelationProvider`, `SaveMode.Overwrite`: `if (options.isTruncate && isCascadingTruncateTable(options.url) == Some(false)) { truncateTable(...) ; saveTable(...) } else { dropTable(...); createTable(...); saveTable(...) }`. `PostgresDialect.isCascadingTruncateTable()` returns `Some(false)`, and `getTruncateQuery` returns `TRUNCATE TABLE ONLY $table`. So in v4.0.1 code, `truncate=true` is honoured for Postgres. — [JdbcRelationProvider.scala v4.0.1](https://raw.githubusercontent.com/apache/spark/v4.0.1/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/jdbc/JdbcRelationProvider.scala); [PostgresDialect.scala v4.0.1](https://raw.githubusercontent.com/apache/spark/v4.0.1/sql/core/src/main/scala/org/apache/spark/sql/jdbc/PostgresDialect.scala). I did not check the Spark 4.2 source or the Databricks Runtime fork.
- **[documented, Spark source v4.0.1]** `JdbcUtils.savePartition` sets `conn.setAutoCommit(false) // Everything in the same db transaction.` per partition, then `conn.commit()`, or `conn.rollback()` on failure. The truncate or drop runs earlier on a separate driver connection. — [JdbcUtils.scala v4.0.1](https://raw.githubusercontent.com/apache/spark/v4.0.1/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/jdbc/JdbcUtils.scala)
- **[documented, Databricks KB, published 2022-05-24, older than 2 years]** "one partition of the DataFrame is written to a SQL table. This is generally done as a single JDBC transaction ... However, if the transaction fails after the commit occurs, but before the final stage completes, it is possible for duplicate data to be copied". The documented fix: "use a temporary table to buffer the write", check it for duplicates, then "Merge the temporary table with the target table". — [Databricks KB: JDBC write fails with a PrimaryKeyViolation error](https://kb.databricks.com/sql/jdbc-write-fails-primarykeyviolation)
- **[lead, unreachable: community.databricks.com returned 403]** Search snippet: a Databricks employee says JDBC write atomicity "is ensured at a task level and not at a stage level", so stage retries can duplicate rows. — [Databricks Community: Can Spark JDBC create duplicate records](https://community.databricks.com/t5/data-engineering/can-spark-jdbc-create-duplicate-records/m-p/19147)

### Inferences
- **[inferred]** Collision matrix for the same table:
  - **Spark overwrite without truncate, table has dependent views:** `DROP TABLE` fails (no CASCADE), and the job errors before writing. If the views were dropped earlier, the drop succeeds and Spark recreates the table with Spark-mapped types and none of the dbt contract constraints or indexes.
  - **Spark overwrite with truncate:** ACCESS EXCLUSIVE on the target blocks concurrent Dagster inserts and consumer reads. TRUNCATE is not MVCC-safe for older snapshots. The truncate commits on its own connection before partitions load, so readers can see an empty or partially loaded table between the truncate commit and the last partition commit.
  - **Spark append and a Dagster upsert concurrently:** with a unique index, the two block on row locks or Spark fails on PK violations. Without one, duplicates appear.
  - **Default isolation `READ_UNCOMMITTED`:** Postgres treats this as READ COMMITTED (general PG knowledge, not fetched).
- **[inferred]** One pattern consistent with the KB fix and with C3 (write-audit-publish): Spark writes only to a per-delivery staging table, then one SQL transaction (from Databricks via a JDBC/psycopg connection, or handed back to a Postgres-side procedure) takes the advisory lock, reconciles, MERGEs or `ON CONFLICT`-upserts into the target, writes the audit and run-log row, and commits.
- **[inferred]** Early warning signs:
  - target tables whose OID changed (drop/recreate happened);
  - missing indexes or constraints after a run;
  - row counts per delivery id not matching the manifest;
  - more than one `application_name` writing a feed table in `pg_stat_activity` or `pg_stat_statements`;
  - lock waits on ACCESS EXCLUSIVE.

### Gaps
- No first-hand report (with outcome) of mixed Spark-JDBC and Python-loader writers on one Postgres table.
- Spark 4.2 source and DBR-specific JDBC behaviour were not checked. The doc-versus-code conflict on `truncate` remains open for 4.2.

## C4.5 Re-running C1–C5 for the Postgres premise: what breaks, what still applies, what is new

### Takeaway
C1–C3 carry over with Postgres-specific constraints. C4 and C5 change meaning, because UC can only see Postgres through read-only federation. A UC "single writer" means storage moves out of Postgres, which is C5 (migration), not a consumer-unawareness trick.

### Cited Findings
- **C1 stable views:** applies. Constraints: column-append-only replace, cascade-drop of dependents. — [PG17 CREATE VIEW](https://www.postgresql.org/docs/17/sql-createview.html); [PG17 DROP TABLE](https://www.postgresql.org/docs/17/sql-droptable.html)
- **C2 same dbt project on both runners:** applies only if both runners execute dbt-postgres. The Databricks-native dbt task targets SQL warehouses with dbt-databricks. — [Azure Databricks dbt task, 2026-09-11](https://learn.microsoft.com/en-us/azure/databricks/jobs/dbt)
- **C3 write-audit-publish:** maps to staging table, then reconcile, then view repoint or partition ATTACH in one transaction. It matches Databricks' own JDBC duplicate fix. — [PG17 partitioning](https://www.postgresql.org/docs/17/ddl-partitioning.html); [Databricks KB](https://kb.databricks.com/sql/jdbc-write-fails-primarykeyviolation)
- **C4 catalog indirection into UC:** with Postgres storage this is Lakehouse Federation. Query federation is "Not supported (read-only)" for writes, and queries are pushed down to Postgres over JDBC. It lets Databricks *read* the lake and does not change what Postgres consumers see. — [Azure Databricks: Connect to external databases and catalogs, ms.date 2026-09-29](https://learn.microsoft.com/en-us/azure/databricks/query-federation/)

### Inferences
- **[inferred] Breaks:** DuckLake-style "swap the table pointer behind the name" (Postgres views bind to the table, not the name); C4 as written ("foreign tables read-only, refresh lag"), since PG federation is live pushdown, not a refreshed copy.
- **[inferred] New on Postgres:**
  - per-orchestrator DB roles and GRANT switching as an enforced single-writer mechanism;
  - advisory-lock leases;
  - partition-per-delivery publish;
  - delivery-id keyed `ON CONFLICT`;
  - the Spark JDBC overwrite hazard;
  - dbt table-materialization cascade.
- **[inferred]** C5 "UC as the single writer" under Postgres storage only makes sense as one of two things. Either a feed whose master moves to Delta, with Postgres fed by reverse sync (see C5.2). Or Databricks as the sole Postgres writer via JDBC/SQL, in which case "UC" governs nothing on the Postgres side.

### Gaps
- None beyond those listed in the other sections.

## C5.1 Documented migration paths Postgres → Delta / Unity Catalog

### Takeaway
There are four documented routes:
- **Lakeflow Connect PostgreSQL**, logical-replication CDC. **Public Preview** on Azure as of 2026-09/10.
- **Lakehouse Federation** (GA, read-only) followed by CTAS. Databricks itself names "Lakehouse Federation + CTAS" as a data-move pattern.
- **Plain Spark JDBC read** into Delta.
- **Repointing the dbt project** from one adapter to dbt-databricks, model by model, with old and new targets side by side.

There is no Postgres-specific dbt migration guide. Databricks' repoint guide assumes the data is already in UC.

### Cited Findings
- **[documented, Azure Databricks, ms.date 2026-09-11 / 2026-10-06]** "The PostgreSQL connector for Lakeflow Connect is in **Public Preview**. Reach out to your Databricks account team to enroll." Details from the limits page:
  - **Sources and versions:** PostgreSQL 13+ with `wal_level=logical`; replication from primary instances only; Azure Database for PostgreSQL is supported (Flexible Server on all tiers).
  - **Access and compute:** username/password authentication only; "the ingestion gateway must run in continuous mode to prevent WAL bloat"; the gateway runs on classic compute.
  - **Table requirements:** each table needs replica identity FULL or DEFAULT.
  - **Replication slots:** slots are "not automatically removed when you delete pipelines"; a failover loses the slot and "requires a full refresh of all tables".
  - **DDL handling:** column type change, column rename, PK change, logged/unlogged conversion, and adding or removing partitions all require a full refresh; each partition is treated as a separate table.
  - **Data types:** TIMESTAMP without time zone and TIME are ingested as strings; MONEY is a string; NUMERIC with precision over 38 is a string.
  - **Scale:** "250 or fewer tables per pipeline"; no two same-named tables across schemas in one pipeline.
  - — [Lakeflow Connect: PostgreSQL limitations](https://learn.microsoft.com/en-us/azure/databricks/ingestion/lakeflow-connect/postgresql-limits); [Ingest data from PostgreSQL](https://learn.microsoft.com/en-us/azure/databricks/ingestion/lakeflow-connect/postgresql-pipeline); [PostgreSQL FAQ](https://learn.microsoft.com/en-us/azure/databricks/ingestion/lakeflow-connect/postgresql-faq)
- **[documented, Azure Databricks, ms.date 2026-09-29]** Query federation pushes queries "down to the foreign database using JDBC". Its use case is "ad hoc reporting or proof-of-concept access", and writes are not supported. "When your source supports both Lakehouse Federation and Lakeflow Connect, Azure Databricks recommends Lakeflow Connect if performance on higher data volumes and lower latency are priorities." Catalog federation (object-storage catalogs) is the one described for "migrating to Unity Catalog incrementally"; it does not apply to Postgres. — [Connect to external databases and catalogs](https://learn.microsoft.com/en-us/azure/databricks/query-federation/)
- **[documented, Azure Databricks, ms.date 2026-10-06]** PostgreSQL federation requirements: DBR 13.3 LTS+ (Standard or Dedicated access mode), or pro/serverless SQL warehouse 2023.40+. Join pushdown is Public Preview (DBR 17.2+). — [Run federated queries on PostgreSQL](https://learn.microsoft.com/en-us/azure/databricks/query-federation/postgresql)
- **[documented, Databricks blog, published 2026-10-06; vendor]** "How to repoint dbt ETL pipelines to Databricks":

## C5.2 Two-store period: Postgres consumers while some tables are mastered in UC (federation, reverse sync, dual-write) and audit consequences

### Takeaway
Databricks documents the reverse direction (UC/Delta into Postgres) only into **Lakebase** Postgres, via synced tables (GA; LTAP Direct Writes in Beta), not into an arbitrary Azure Database for PostgreSQL. For the existing Postgres lake, the documented reverse paths are Spark JDBC writes from Databricks, with the per-partition-commit caveats above. Federation goes UC to Postgres for reads by Databricks users, not Postgres to UC, so Postgres-view consumers cannot read Delta-mastered tables through it. I found no Databricks-documented way for a Postgres view to read Delta directly.

### Cited Findings
- **[documented, Azure Databricks, ms.date 2026-10-22]** Lakebase synced tables:
  - Sync works one way, from Unity Catalog into Lakebase Postgres ("reverse ETL"), and creates "A Postgres table in Lakebase (read-only, queryable by your applications)".
  - "Synced tables are generally available." "LTAP Direct Writes is in Beta."
  - Modes: Snapshot (full copy on each run), Triggered, and Continuous (incremental via change data feed; the source must have CDF or Automatic CDF).
  - Up to 16 connections per sync.
  - "Only additive schema changes ... are supported for Triggered and Continuous". To change the PK or make a non-additive change, delete and recreate.
  - "If two rows have the same primary key in the source table, the sync pipeline fails unless you configure deduplication using a timeseries key".
  - `databricks_superuser` can write to synced tables "in case you need to make urgent changes", but "Azure Databricks recommends making fixes in your source table instead".
  - The target is a Lakebase project, branch and database ("Set Database type to Autoscaling").
  - — [Azure Databricks: Synced tables (Lakebase)](https://learn.microsoft.com/en-us/azure/databricks/oltp/projects/sync-tables)
- **[documented]** Lakehouse Federation is read-only. Query federation suits "ad hoc reporting or proof-of-concept access to operational data". — [Connect to external databases and catalogs, ms.date 2026-09-29](https://learn.microsoft.com/en-us/azure/databricks/query-federation/)
- **[documented, Spark 4.2.0 / KB 2022]** JDBC write semantics for a reverse sync into the existing Postgres: per-partition transactions, overwrite drops or truncates, and duplicates on retry. Fix: a staging table, then MERGE. — [Spark JDBC](https://spark.apache.org/docs/latest/sql-data-sources-jdbc.html); [Databricks KB](https://kb.databricks.com/sql/jdbc-write-fails-primarykeyviolation)
- **[documented, Azure Databricks, page ms.date 2024-06-18 (updated_at 2026-09-11)]** A separate "Query PostgreSQL with Azure Databricks" (JDBC) page exists. Its content date is older than 2 years. — [Azure Databricks: PostgreSQL JDBC](https://learn.microsoft.com/en-us/azure/databricks/connect/external-systems/postgresql)

### Inferences
- **[inferred]** Two-store options (not ranked):
  - **(a) Delta master with a JDBC reverse write** into the same Postgres table behind the consumer view: staging, then MERGE, then view stays. Consumers stay unaware. There are two copies, and the Postgres copy is derived.
  - **(b) Move consumers to Lakebase**, with synced tables as the reverse path. Consumers switch database endpoint, so they are not unaware. It is also a different Postgres service from the current one.
  - **(c) Dual-write** from the producer to both Postgres and Delta. No cross-store transaction exists, so divergence must be caught by reconciliation.
  - **(d) Postgres stays master** and Databricks reads it via federation or Lakeflow Connect; Delta is derived. This reverses the master direction.
- **[inferred] Audit consequences** (for a regulated asset manager):
  - For each feed, the ops schema must record which store is master and which copy is derived, and the run log must carry both the producing run (Databricks job run id or Dagster run id) and the sync run.
  - Reconciliation must compare Delta and Postgres per delivery id: row counts, hashes, and type-mapping losses such as TIMESTAMP to string and NUMERIC over 38 to string.
  - Reverse-sync lag means the publication calendar must reference when the Postgres copy is ready, not when Delta is ready.
  - Lakebase superuser write access to synced tables is an integrity exception to log.
  - Delta time travel or history and Postgres row history are separate trails.
