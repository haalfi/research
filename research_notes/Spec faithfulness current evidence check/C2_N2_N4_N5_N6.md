## N2: Zhao, Zhou, Cohen, LLM-generated suites replication (ISSTA 2026)

### Takeaway
The lead exists as cited and is graded **A** (ISSTA 2026, PACMSE). For LLM-written Java unit tests sized naturally per method, suite size correlates only weakly with mutation score and with real-bug detection, and fixing the size changes the correlations little. It does **not** contradict Papadakis et al. in a way that touches G8. Inside one model and in the pooled view, mutation score stays a weak predictor of real-bug detection, whether or not size is controlled. The paper's own explanation is that the size effect comes from sampling sub-suites out of a pool, and that is exactly how [TD] H3 builds equal counts. **The equal-count comparison stays valid.** At most it needs a one-clause scope note (proposed wording below).

### Cited Findings
- **Citation, corrected and confirmed.** Junda Zhao, Shurui Zhou, Eldan Cohen, "Do Coverage and Mutation Scores of LLM-Generated Test Suites Correlate with Their Effectiveness? (Replicability Study)", *Proc. ACM Softw. Eng.* 3 (ISSTA), Article ISSTA002, Oct 2026, DOI 10.1145/3832093. The arXiv comment reads "Accepted at ISSTA 2026"; Crossref gives the container "Proceedings of the ACM on Software Engineering", vol. 3, issue ISSTA, published 2026-10-01; every page footer of the PDF carries "Proc. ACM Softw. Eng., Vol. 3, No. ISSTA, Article ISSTA002". **Grade A; full text read: y (24 pp.).** — [arXiv API](https://export.arxiv.org/api/query?id_list=2607.22880); [Crossref](https://api.crossref.org/works/10.1145/3832093); [PDF](https://arxiv.org/pdf/2607.22880v1)
- **Setting.**
  - Benchmark: Defects4J v3.0, restricted to **318 buggy focal methods** across all 17 projects. Each method exists in both the buggy and the fixed version and triggers at least one failing developer test.
  - Models: **11 LLMs from 6 developers, 13 settings** (Gemini 2.5 Pro/Flash, Claude 4 Sonnet with and without reasoning, Grok-4/3, GPT-4.1, o4-mini, DeepSeek-V3/R1, Qwen3-Coder-Plus/Qwen3-Plus), temperature 0.
  - Output: **8,268 suites with 101,123 tests**, generated **white-box**: the prompt holds the focal-method body plus surrounding code context. — [PDF §3.2–3.4, §8](https://arxiv.org/pdf/2607.22880v1)
- **Suite construction.**
  - 1,000 draws, each of 100 focal-method suites.
  - "Unconstrained" keeps each LLM suite at its natural size.
  - "Size-controlled" keeps **k ∈ {3, 5, 10}** tests chosen uniformly at random from each suite. The paper notes "most models generate roughly 10 tests per suite on average".
  - Tools: coverage with CodeCover, mutation with PIT.
  - A bug counts as detected if the suite holds a test that passes on the fixed version and fails on the buggy one.
  - Three views: combined, intra-model, and inter-model (one point per model, so n = 13). — [PDF §3.5–3.7](https://arxiv.org/pdf/2607.22880v1)
- **Size vs mutation score.** In the combined view (Table 3) Pearson r is 0.031 (raw, average aggregation), 0.029 (raw, accumulated), 0.098 and −0.112 (normalized). The text says the correlation is "weak to negligible … across combined, intra-model, and inter-model analyses", and the inter-model coefficients are "weak and not statistically significant". — [PDF §4.1, Table 3](https://arxiv.org/pdf/2607.22880v1)
- **Size vs real-bug detection.** Weak in the combined and intra-model views. The inter-model value is "around 0.4 … not statistically significant". — [PDF §5.1](https://arxiv.org/pdf/2607.22880v1)
- **Mutation score vs real-bug detection (the Papadakis replication).**
  - Combined view, average aggregation: Pearson 0.475–0.511. Accumulated: 0.146–0.196.
  - Intra-model: "weak across all models".
  - Inter-model, raw score: r = 0.863 (average) and 0.622 (accumulated).
  - At fixed k, the combined and intra-model views "remain weak". The inter-model raw r is 0.695–0.833 under average aggregation.
  - Summary sentence: "at most moderate in the combined view and weak in the intra-model view, regardless of whether test suite size is controlled". — [PDF §6.1–6.3, Tables 12–14](https://arxiv.org/pdf/2607.22880v1)
- **The authors' size claim.** "While both Inozemtseva et al. and Papadakis et al. argue that test suite size is a strong confounder … our results for LLM-generated tests provide little support for this conclusion … moving from the size-unconstrained to the fixed-size setting yields only a small drop in correlations". — [PDF §7 ④](https://arxiv.org/pdf/2607.22880v1)
- **The authors' mechanism for the difference.** "prior studies construct suites by sampling a specified number of tests from a project-wide test pool. Under that setup … larger sampled suites mechanically aggregate more of these partial contributions … creating a stronger size-driven confounding effect", whereas in their set-up each size "arises naturally from the testing needs of the focal method". — [PDF §7 ⑤](https://arxiv.org/pdf/2607.22880v1)
- **Scope limits stated by the authors.**
  - Java/Defects4J only, and a single prompting workflow [§8].
  - The inter-model view has "a relatively small number of data points (one per model)".
  - Future work names "black-box or specification-based settings" as untested [§9].
  - Mutation analysis is "not applicable" when the code under test may be buggy, because it presupposes a green suite [§3.3 fn. 1; §7 ①]. — [PDF](https://arxiv.org/pdf/2607.22880v1)
- **A side finding relevant to [TD].** Tests generated from buggy code assert the buggy behaviour. In the Lang-14 `StringUtils.equals` example, the buggy input produced `assertFalse` where the intended behaviour needs `assertTrue`. Coverage on buggy code was uninformative about bug detection in all three views. — [PDF §5.4](https://arxiv.org/pdf/2607.22880v1)
- **Own-tool flag:** none. This is a replication with no tool of the authors under test.
- **Old text, verbatim.**
  - [V] Part 2 (the verified recommendation): "**Compare families at equal test counts** (or report kills per test), because suite size alone drives much of the apparent association (Papadakis, below) [V3-04]."
  - [V] header: "Papadakis et al. show that mutation kills must be compared at equal suite size."
  - [S §4]: "Kills must be compared at equal test counts (Papadakis: r ≈ 0.05–0.20 with suite size controlled)."
  - [TD] H3: "p10(expectation tests vs spec-enforcing tests, Pipeline A) at **equal test counts**: 200 random subsamples to the smaller suite's size, with per-seed catch probability averaged."

### Inferences
- *Inference*, §5(b), first half. N2 finds a **weaker** size confounder for LLM suites, but does not overturn Papadakis for G8's use.
  - The design differs. Papadakis's sub-suites are sampled from a pool; N2's sizes are natural per-method sizes.
  - The two agree on the point the branch relies on: within one generator, mutation score tracks real-bug detection only weakly with size controlled (Papadakis 0.05–0.20; N2 intra-model "weak").
  - N2's claim that mutation is informative holds **between models**, and that rests on n = 13.
- *Inference*, §5(b), second half. **The equal-count comparison stays valid.**
  - G8/H3 compares two families of different provenance and equalises them by random subsampling to the smaller family's size. That is the pool-sampling construction which N2 itself names as the source of mechanical size effects, so there a size control is appropriate by N2's own reasoning.
  - N2 gives no reason to think the control is harmful, only that it changed little in its own set-up.
  - The two G8 families are spec- or record-derived, black-box with respect to R. N2 is white-box and code-derived, and its authors list "specification-based settings" as untested. Transfer is therefore *analogous* at best.
- *Inference*. N2 strengthens an existing qualification rather than adding a new one. [V] S7 already says "Kills guide gap-finding but do not measure real-fault detection". N2's weak intra-model mutation–bug correlation, with or without size control, fits this.
- *Inference*. The §5.4 result is an analogue of the [TD] §2.0 reframing that "spec tests regenerated from a misread spec catch it almost never". In both, LLM tests derived from a faulty artefact encode the fault. Transfer is *analogous* (code, not specs). Not a change, only a corroborating citation option.
- **Transfer:** *analogous*: Java unit tests vs API-behaviour reference-model tests; white-box vs spec- or record-derived.
- **Delta:** confirms R17/G8 as worded; it qualifies only the *strength* of the Papadakis rationale for LLM suites. Proposed optional wording for [V] G8/R17, to be added after the existing sentence: "Compare families at equal test counts (subsample the larger family) and also report raw kills. For LLM-generated suites the size confounder may be weaker (Zhao, Zhou & Cohen, ISSTA 2026, A: size vs mutation score |r| ≤ 0.11 for naturally sized per-method Java suites). That study is white-box and Defects4J-only, its within-model mutation-vs-real-bug correlations stay weak with or without size control, and subsampling reintroduces the mechanical size effect it describes, so the equal-count control is kept."

### Gaps
- Papadakis's and N2's coefficients are not directly comparable: suite sampling, aggregation and the unit (project vs focal method) all differ. No study measures the size effect for spec-derived, black-box LLM suites against a reference model.

## N5: Nee, Zhong, Ni, "Wavering Oracles" (arXiv 2609.11428)

### Takeaway
The lead exists as cited (an arXiv preprint, no venue) and is graded **A-pre**. The setting is **multiple-choice**: SycoBench-600, four-option questions. 0.285 is the mean pairwise Pearson correlation of baseline 0/1 error indicators over 7 published models on 555 aligned questions. 2.58 is the equal-correlation heuristic N/(1+(N−1)ρ̄) and is not independently measured. It adds **nothing beyond Kim et al. (ICML 2025)** for this branch: the same MCQ setting, with far fewer models.

### Cited Findings
- **Citation, corrected.** Authors as listed on arXiv: "Xiaoshn Nee", Haobo Zhong, Xiaomin Ni. Title: "Wavering Oracles: Selective Updating and Correlated Failures in LLMs and Their Implications for Scientific Workflows", arXiv 2609.11428v1, 10 Sep 2026. No journal reference, no comment, no DOI. "Xiaoshn" is spelled that way in the arXiv metadata. **Grade A-pre; full text read: y (11 pp.).** — [arXiv API](https://export.arxiv.org/api/query?id_list=2609.11428); [PDF](https://arxiv.org/pdf/2609.11428v1)
- **Setting.**
  - Benchmark: "SycoBench-600 contains 600 English four option questions formed from 272 normalized stems across eight domains and three difficulty levels". The baseline prompt "requests exactly one option letter".
  - SycoBench-600 is by D. Sinha [ref 7], not by these authors. — [PDF §4.1, refs](https://arxiv.org/pdf/2609.11428v1)
- **Published arm (source of 0.285 and 2.58).**
  - The authors "reanalyze the released raw logs" for GPT-4o-mini, GPT-4o, Claude 3.5 Haiku, Claude Sonnet 4, Gemini 2.5 Flash, Llama 4 Maverick and Mistral 7B.
  - Forty-five repaired items were excluded, leaving **555 questions**.
  - The ensemble analyses use phrasing variant zero [Table 4 caption]. — [PDF §4.2, Table 4](https://arxiv.org/pdf/2609.11428v1)
- **Computation.**
  - "For model m, define baseline error e_im = I{ŷ⁰_im ≠ y_i}. We calculate the mean Pearson correlation of e_im across model pairs, denoted ρ̄e".
  - "A compact equal correlation heuristic translates dependence into an effective independent count, N_eff = N / (1 + (N − 1) ρ̄e)" (Eq. 6).
  - Check: 7 / (1 + 6 × 0.285) = 2.58.
  - The local arm (Qwen3-4B, Gemma3-4B, SmolLM3-3B) gives ρ̄e = 0.340 and N_eff = 1.79. — [PDF §3.3, Eq. 6; §5, Table 4](https://arxiv.org/pdf/2609.11428v1)
- **Other ensemble figures.** Best single model 95.3 %; plurality 88.6 %; oracle ceiling 99.8 %. The authors' leave-one-stem-family-out reliability selector reaches 96.2 % and recovers 67.7 % of the plurality-to-oracle gap. Answer agreement is 70.5 %. — [PDF §5, Table 4](https://arxiv.org/pdf/2609.11428v1)
- **The authors' own scope statement.** "The controlled multiple choice setting isolates answer transitions with exact gold labels"; implications for workflows rest on "the structure shared by both settings". The authors cite Kim et al. [22] for "broad evidence of correlated model errors". — [PDF §6.1, §7.1](https://arxiv.org/pdf/2609.11428v1)
- **Own-tool flag:** partial TA, for the selector only. The correlation figures are a reanalysis of a third-party benchmark's logs.
- **Old text, verbatim.**
  - [V] §2.5: "Kim et al. ICML 2025 (A): **multiple-choice** answers of 349 LLMs on 12,032 questions and 71 LLMs on 14,042 (HELM), plus a résumé-screening case. When both models are wrong they pick the same wrong answer 0.423 (chance 0.127) and 0.60 (chance 1/3) of the time".
  - [S §4]: "LLM error correlation is measured only on multiple-choice tasks."

### Inferences
- *Inference*, §5(d). **The setting is multiple-choice.** N5 does **not** add to Kim et al. as the branch uses them: 7 models vs 349, the same task type, and an A-pre grade vs A. The "only measured on multiple-choice tasks" caveat in [S §4] stays true.

- *Inference*. N5's proposed remedy is independent generation plus a *learned, calibrated selector* using gold-labelled calibration items. It does not test different derivation paths or deterministic adjudication, so it cannot back those claims.
- **Transfer:** *inference*: MCQ answer errors vs spec-misreading errors.
- **Delta:** no change. At most an optional extra citation beside Kim et al. for "correlation persists in 2026 models (GPT-4o, Claude Sonnet 4, Gemini 2.5 Flash)", labelled MCQ and A-pre.

## N6: 30-LLM NL → TLA+ evaluation (ICSOFT 2026, SciTePress)

### Takeaway
The DOI resolves to Bisharat et al., "Can LLMs Write Correct TLA+ Specifications? Evaluating Natural-Language-to-TLA+ Generation", ICSOFT 2026 (SciTePress), pp. 39–50. This is **the same paper the branch already cites as arXiv 2606.05792** (A-pre, abstract only). **Grade A-pre → A; full text now read.** The full text corrects how the headline figures should be read:
- 205 is the size of the dataset, but **only 26 test specs** were evaluated.
- "Semantic correctness" means **TLC runs without error using the reference .cfg**. It is not faithfulness to the NL.
- 26.6 % and 8.6 % are **pooled pass rates over 25 open-weight models** for one strategy each, not best-model rates.
- The 0 % TLC rates for three strategies are **97–99 % infrastructure failures** by the authors' own Table 4.

It reinforces the "weak and grading-sensitive" baseline; on grading sensitivity it is a stronger example than the branch's earlier sources.

### Cited Findings
