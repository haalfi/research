## Q1. Detecting test gaps against code change (test gap analysis, change impact / regression test selection, diff coverage, incremental mutation testing)

### Takeaway
There is solid industrial evidence that changed-but-untested code is where field defects concentrate. In a Munich Re system, only about 44–45% of changed methods were tested, and changed-untested methods had the highest bug probability. Two mature tool families are documented. Diff/patch coverage and test gap analysis say whether a change was executed. Google's diff-based mutation testing says whether the tests would notice a change. The mutation work only became usable after heavy filtering: developers first rated 85% of the mutants they were shown as unproductive, and arid-node suppression raised the productive share to 89%. Regression test selection (Ekstazi, Meta's predictive selection) is the inverse tool. It reduces what runs; it does not find gaps.

### Cited Findings
**Test gap analysis (TGA), from CQSE / TUM / Munich Re**
- Eder, Hauptmann, Junker, Juergens, Vaas, Prommer, "Did We Test Our Changes? Assessing Alignment between Tests and Development in Practice", AST 2013 workshop at ICSE. (The brief says ICSM 2013; the paper itself says AST'13.) The approach finds methods that were changed but never executed during testing. Methods are tracked across releases with "method genealogies". The case study is a C# business information system at Munich Re: 14 months of development changes, test activity and field faults. [documented] — [TUM PDF](https://wwwbroy.in.tum.de/publ/papers/AST13Hauptmann.pdf)
- Results: 34% of methods were untested in both releases and 15% were changed. 8% / 9% of all methods were changed-untested. Of the changed methods, only 44% (release 1) and 45% (release 2) were tested. Bug fixes: 23 in release 1 and 10 in release 2. Changed-untested methods held 43% and 40% of all bugs. Bug probability per method was highest in the changed-untested group: 0.53% in release 1, 0.21% in release 2. The authors themselves say "the number of bugs we found is too small to derive generalizable results". [documented] — [TUM PDF](https://wwwbroy.in.tum.de/publ/papers/AST13Hauptmann.pdf)
- Juergens & Pagano, "Did We Test the Right Thing? Experiences with Test Gap Analysis in Practice" (2016 whitepaper, CQSE/Teamscale; **vendor-authored**). It restates the study: about 15% of code was modified per release, "approximately half the changes went into production untested", and changed-untested code was "five times more error-prone than unchanged code". TGA combines static analysis (what changed, with refactorings and moves filtered out) and dynamic analysis (coverage from both automated and manual tests). Stated limits: (1) changes made at the configuration level without code changes are invisible to it; (2) "green" only means executed, not thoroughly tested, and this gets worse as coverage granularity gets coarser. On the other hand, red/orange (unexecuted) code is certain not to have been tested. Issue trackers were found unreliable for finding which changes to test. [documented][vendor] — [Teamscale PDF](https://teamscale.com/hubfs/26978363/Publications/2016-did-we-test-the-right-thing-experiences-with-test-gap-analysis-in-practice.pdf?hsLang=en)
- The same whitepaper describes applying TGA-style recording in production ("feature profiling"). In one enterprise system, 28% of features were never used in production, which led to deleting about a quarter of the source code. [documented][vendor] — [Teamscale PDF](https://teamscale.com/hubfs/26978363/Publications/2016-did-we-test-the-right-thing-experiences-with-test-gap-analysis-in-practice.pdf?hsLang=en)
- Rott, Niedermayr, Juergens et al., "Ticket Coverage: Putting Test Coverage into Context" (arXiv 1804.07599, 2018). Ticket coverage is the share of methods changed for a ticket that automated or manual tests covered. Study object: a 650 kLOC Java industrial system. Developers rated the 110 test gaps found: 18.2% critical, 50.9% uncritical, 25.5% "not interesting" (toString, simple getters, too trivial). 35.5% were judged worth testing within the ticket's scope. The method separates coverage recorded during system startup from coverage recorded during tests: only 9.2% of the changed-and-tested methods had been executed during startup. [documented] — [arXiv](https://arxiv.org/pdf/1804.07599)
- Haas, Sailer, Joblin, Juergens, Apel, "Prioritizing Test Gaps by Risk in Industrial Practice", IEEE TSE 2025. Data: 31 historical test-gap reviews from 8 industrial systems (Munich Re, LV 1871) and interviews with 6 quality engineers. An automated risk ranking (code criticality, complexity) placed gaps that experts had labelled risky at the 30th percentile on average, which is "equivalent to expert assessments". [documented-abstract] — [Saarland PDF](https://www.se.cs.uni-saarland.de/publications/docs/HSJ+25.pdf)

**Diff / patch coverage tools**
- diff-cover (Python CLI). It compares a coverage report with `git diff` (by default against `origin/main`). Input formats: Cobertura, Clover, JaCoCo XML or LCov. It has a companion `diff-quality` for linter violations on the diff. Licence Apache-2.0. Latest 11.0.4, released 2026-11-19; first release 2013-06-28. [documented] — [README (raw)](https://raw.githubusercontent.com/Bachmann1234/diff_cover/main/README.rst); [PyPI JSON](https://pypi.org/pypi/diff-cover/json)
- Codecov `codecov/patch` status "only measures lines adjusted in the pull request or single commit". It can gate PRs with `threshold`, or run in `informational` mode, which never fails. Codecov is a hosted commercial service, cited here as a capability reference. [documented][vendor] — [Codecov docs](https://docs.codecov.com/docs/commit-status)
- At Google, both absolute and incremental coverage (covered added/modified lines ÷ all added/modified lines) are shown at code review. [documented] — [Petrović & Ivanković ICSE-SEIP 2018](https://research.google.com/pubs/archive/46584.pdf)
- coverage.py "dynamic contexts" (`[run] dynamic_context = test_function`) record which test function executed each line. This gives a per-test "who tests what" map, so a line covered only by an incidental test can be told apart from a line covered by a targeted test. coverage.py 7.17.5 docs. [documented] — [coverage.py contexts](https://coverage.readthedocs.io/en/latest/contexts.html)

**Incremental / diff-based mutation testing**
- Petrović & Ivanković, "State of Mutation Testing at Google", ICSE-SEIP 2018. The approach is diff-based and probabilistic. It mutates only lines that the diff changed, that are covered, and that are not "arid" (logging, memory reservation, and similar). It surfaces surviving mutants as code-review findings with "Please fix" / "Not useful" buttons. Evaluation: more than 70,000 diffs, 1.1M mutants and 150,000 actionable findings. Reported usefulness rose from 20% to 80% through the developer-feedback loop. About 30% of diffs that have coverage were processed. [documented] — [Google PDF](https://research.google.com/pubs/archive/46584.pdf)
- Petrović, Ivanković, Fraser, Just, "Practical Mutation Testing at Scale: A view from Google", arXiv 2102.11378 (Feb 2021; later in TSE). Context: 2 billion LOC and more than 500M tests per day. The system covers more than 24,000 developers and more than 1,000 projects. **Unsuccessful-first result:** developers initially classified 85% of reported mutants as unproductive. Feedback from more than 20,000 developers over six years produced suppression heuristics that raised the productive share from 15% to 89%. Arid-node suppression plus one mutant per line gives a median of 7 mutants per changelist, against 820 for traditional mutagenesis. Mutation operators are selected using their historical performance. [documented] — [arXiv](https://arxiv.org/pdf/2102.11378)
- PIT (Java) incremental analysis is labelled **"experimental"**. It reuses earlier results, for example "if a mutation was killed in the last run and neither the class under test or the killing test has changed", and relies on the assumption that dependency changes rarely flip a mutant's status: "this assumption seems reasonable, it is currently unproven". Controlled by `withHistory` / `historyInputLocation` / `historyOutputLocation`. pitest 1.30.2; Maven metadata lastUpdated 2026-11-05. [documented] — [PIT incremental analysis](https://pitest.org/quickstart/incremental_analysis/); [Maven Central metadata](https://repo1.maven.org/maven2/org/pitest/pitest/maven-metadata.xml)
- StrykerJS `--incremental` stores `reports/stryker-incremental.json`, diffs code and test files against it, and re-tests only changed mutants. **Documented limitations:** it does not detect changes in files other than mutated files and test files, nor changes to dependencies, environment variables, `.snap` files and similar. Detecting test changes depends on the test-runner plugin (full support for Jest and Cucumber; partial for Mocha, Jasmine, Karma). `--force` forces reruns. @stryker-mutator/core 10.1.1 (2026-10-23), Apache-2.0. [documented] — [Stryker docs](https://stryker-mutator.io/docs/stryker-js/incremental/); [npm registry](https://registry.npmjs.org/@stryker-mutator/core)
- mutmut 3.x (Python, BSD-3-Clause, 3.8.1 released 2026-10-28). It "remembers work that has been done, so you can work incrementally". It mutates only functions that are called, with an option to restrict to lines covered according to coverage.py. The README I read documents no git-diff-scoped mode. cosmic-ray (MIT, 8.9.0 released 2026-11-10) is an alternative. [documented] — [mutmut README](https://raw.githubusercontent.com/boxed/mutmut/main/README.rst); [PyPI JSON](https://pypi.org/pypi/mutmut/json); [cosmic-ray PyPI](https://pypi.org/pypi/cosmic-ray/json)

**Regression test selection (RTS): the inverse problem**
- Ekstazi (Gligoric, Eloussi, Marinov, ISSTA 2015) tracks dynamic test-to-file dependencies and needs no version-control integration. Evaluation: 615 revisions of 32 projects (about 5M LOC). End-to-end test time fell 32% on average and 54% for longer-running suites. Adopted by Apache Camel, Commons Math and CXF. [documented-abstract] — [author abstract](https://users.ece.utexas.edu/~gligoric/papers/abstracts/GligoricETAL15Ekstazi.txt). Gligoric's dissertation reports that **manual** RTS by developers was "not safe 74% of the time and not precise 73% of the time". [documented-abstract] — [PhD thesis](https://users.ece.utexas.edu/~gligoric/papers/Gligoric15PhD.pdf). Maintenance: org.ekstazi.core 5.3.0, Maven metadata lastUpdated 2018-03-20 (dormant). [documented] — [Maven Central](https://repo1.maven.org/maven2/org/ekstazi/org.ekstazi.core/maven-metadata.xml). STARTS (static RTS): starts-maven-plugin 1.4, dated 2023-01-21. [documented] — [Maven search](https://search.maven.org/solrsearch/select?q=g:edu.illinois+AND+a:starts-maven-plugin&core=gav&rows=1&wt=json)
- Machalica et al., "Predictive Test Selection" (Facebook, ICSE-SEIP 2019, arXiv 1810.05286). A model trained on historical test outcomes halves the infrastructure cost of testing changes while "over 95% of individual test failures and over 99.9% of faulty changes are still reported". It accounts for flakiness. [documented-abstract] — [arXiv](https://arxiv.org/pdf/1810.05286)
- dbt "state:modified" selection plus `--defer` ("slim CI") compares the project to a production manifest and builds only changed models and everything downstream. This is RTS for a SQL DAG. The docs say state selection "rel[ies] on your models being idempotent". dbt-core 1.12.7 (2026-11-12), Apache-2.0. [documented] — [dbt state selection](https://docs.getdbt.com/reference/node-selection/state-selection); [PyPI](https://pypi.org/pypi/dbt-core/json)

### Inferences
- [inferred] For a data platform, the TGA evidence carries over best to transformation, entity-resolution and reconciliation code. Its documented blind spot, "configuration-level changes", matches matching thresholds, mapping tables and SQL in config, which often live outside the coverage tools' view.
- [inferred] Diff coverage and TGA answer "was the change executed?". Diff mutation testing answers "would the tests notice?". Only the second checks fixture *values* (whether a hand-written fixture is rich enough to tell a mutant apart). Google's 85%→89% history shows that raw mutant output is unusable without arid-line suppression and per-diff limits.
- [inferred] Incremental mutation caches (PIT, Stryker) assume that only code and test files matter. Fixture or data changes are explicitly *not* tracked (Stryker lists `.snap` and other files). So replacing a fixture needs `--force` or a full run.

### Gaps
- No empirical comparison of diff-coverage gating against TGA against diff mutation testing on the same systems was found.
- Neither the Memon et al. 2017 Google TAP paper nor the Legunsen et al. FSE 2016 STARTS paper was read (not fetched). I found no empirical study of dbt state:modified safety (missed downstream breakages).

## Q2. Detecting test gaps against changing *data* (production/field coverage vs test coverage, schema co-evolution, new value categories, data-contract changes)

### Takeaway
Measured field-vs-test gaps exist even for well-tested libraries. In Wang, Brun & Orso (ICST 2017), tests missed 6.2% of the statements and 7.7% of the methods executed in the field, and 52.6% of field behavioural invariants. EvoSuite-generated tests closed little of that gap. Google's Productive Coverage (ICSE-SEIP 2024) is the clearest documented industrial practice that feeds aggregated production execution data (CPU-seconds per AST node) back into test-gap prioritisation. No documented practice was found that exports rule-firing or branch-hit diffs from a protected data environment specifically to flag fixture gaps. The closest are a 2021 defensive publication that compares production inputs against integration-test inputs "in a privacy-compliant manner" [lead] and Teamscale-style production feature profiling [vendor]. Schema co-evolution studies show that schema changes are frequent and concentrated, and that they force code changes; I found no study measuring the effect of schema change on test fixtures.

### Cited Findings
**Field vs in-house behaviour**
- Wang, Brun, Orso, "Behavioral Execution Comparison: Are Tests Representative of Field Behavior?", ICST 2017. Subjects: JetUML used by 83 human subjects, plus Commons IO, Commons Lang and Log4j traced through their use in real GitHub client projects. Behaviour was compared with four models: statement coverage, method coverage, mutation score and kTails temporal invariants. Results: tests missed 6.2% of field statements and 7.7% of field methods. Field-only behaviour kills an extra 8.6% of mutants. Tests miss 52.6% of field invariants. **Unsuccessful approach:** adding EvoSuite tests aimed at high coverage "only marginally improves" representativeness. [documented-abstract] — [UMass PDF](https://people.cs.umass.edu/~brun/pubs/pubs/Wang17icst.pdf)
- Gazzola, Mariani, Pastore, Pezzè, "An Exploratory Study of Field Failures" (arXiv 1708.09494, 2017). From bug reports of 5 applications in 3 ecosystems, 70% of field faults are "intrinsically hard to detect at design-time". Taxonomy: Irreproducible Execution Condition, Unknown Application Condition, Unknown Environment Condition, Combinatorial Explosion (the most frequent), and Bad Testing, which is not field-intrinsic. Example of an Unknown Application Condition: a folder name ending in a blank. Only 18% of combinatorial-explosion cases came from specific inputs. [documented] — [arXiv](https://arxiv.org/pdf/1708.09494)
- Ivanković, Petrović, Kulizhskaya, Lewko, Kalinovčić, Just, Fraser, "Productive Coverage: Improving the Actionability of Code Coverage", ICSE-SEIP 2024 (Google). It ranks uncovered code by similarity to well-tested code and by production execution frequency. "Google samples all code running in production". Each AST node is scored log2(1+CPU-seconds) with a 0.01 CPU-s floor, and the score is propagated up the AST. Never-before-seen n-grams are treated conservatively as maximally important. A 3-month randomised experiment covered 29,149 experiment and 28,577 control changelists. Reported results: strongly positive developer sentiment, a "meaningful" rise in test quality over a strong baseline, no effect on authoring efficiency, modestly better review efficiency, and fewer defects introduced. Median starting changelist coverage was above 90%. [documented] — [UW PDF](https://homes.cs.washington.edu/~rjust/publ/productive_coverage_icse_2024.pdf)
- Gao, Rafferty, Sampson, Kubik, "Test Coverage Analysis by Diffing Production Logs", Technical Disclosure Commons #4113, 2021-03-01 (defensive publication, not empirical). It compares production input and configuration usage with integration-test data, done "in a privacy-compliant manner", to find untested input subspaces ("test-gaps") and to rank them by production frequency. It is aimed at "highly complex input schemas or schemas that change over time". [lead — landing page summary only; PDF at core.ac.uk returned 403] — [TDCommons](https://www.tdcommons.org/dpubs_series/4113)
- Qiu, Di Grazia, Mariani, Pezzè, "E-Test" (arXiv 2510.19860, Oct 2025). It uses an LLM to find production execution scenarios not yet tested and generates tests for them. On 1,975 scenarios, F1 was 0.55, against at most 0.34 for regression/field-testing baselines and 0.39 for vanilla LLMs. [documented-abstract] — [arXiv](https://arxiv.org/pdf/2510.19860)
- CQSE production feature profiling: 28% of features unused (see Q1). [documented][vendor] — [Teamscale PDF](https://teamscale.com/hubfs/26978363/Publications/2016-did-we-test-the-right-thing-experiences-with-test-gap-analysis-in-practice.pdf?hsLang=en)

**Schema evolution**
- Qiu, Li, Su, "An Empirical Analysis of the Co-evolution of Schema and Code in Database Applications", ESEC/FSE 2013. The study covers 10 open-source database applications and more than 160K revisions, with 24 atomic schema-change types. Schemas evolve frequently. Schema changes "induce significant code-level modifications", and some change types have more impact on code than others. Co-change analysis "can be viable to automate or assist" evolution. 80% of schema changes fell in 20–30% of tables and about 40% of tables never changed. Referential-integrity constraints and stored procedures were rarely used. The paper studies code co-change, not test co-change. [documented-abstract] — [UC Davis PDF](https://www.cs.ucdavis.edu/~su/publications/fse13-db-study.pdf)

**Data-pipeline tooling relevant to data-driven gaps**
- dbt unit tests use static `given`/`expect` fixtures (inline dict, CSV or SQL, or files under `tests/fixtures/`). dbt Labs "strongly recommends only running unit tests in development or CI", since their inputs are static. Local DuckDB execution is experimental and opt-in. [documented] — [dbt unit tests](https://docs.getdbt.com/docs/build/unit-tests)
- SQLMesh `create_test` generates a complete unit test for a model "as long as the tables of its upstream models exist in the project's data warehouse and are already populated". It runs a user-supplied query against the warehouse (for example `SELECT … LIMIT 3`) for the input rows, then computes the expected output by running the current model. The docs warn that macro date variables must be pinned "to make the generated test deterministic". sqlmesh 0.236.4 (2026-10-22), Apache-2.0. [documented] — [SQLMesh tests docs](https://sqlmesh.readthedocs.io/en/stable/concepts/tests/); [PyPI](https://pypi.org/pypi/sqlmesh/json)

### Inferences
- [inferred] For the protected-environment constraint: per-test or per-run coverage produced inside the environment (coverage.py contexts, JaCoCo/LCov) holds file paths, line numbers and counts, not data values. That makes it a plausible candidate for "approved derived information": a production-run coverage or branch-hit vector diffed against the outside test suite's coverage, in the manner of Productive Coverage and TDCommons #4113. Rule-firing counts per reconciliation or validation rule would be the data-platform analogue. This is not documented for data platforms; it is an extrapolation.
- [inferred] Risk: even hit counts can leak information, for example that a rare category exists, or the count of a small cohort. The TDCommons disclosure's "privacy-compliant" wording is unexplained in what I could read.
- [inferred] SQLMesh `create_test` is a characterization/snapshot generator. Its oracle is the *current* implementation, so it pins existing behaviour (bugs included). Its fixture rows are copied verbatim from the warehouse, so tests generated inside the protected environment would contain real (possibly personal or licensed) rows and could not leave without review or transformation.
- [inferred] Gazzola's "Unknown Application Condition" class (inputs whose relevance nobody foresaw) is the software-testing name for "new value categories seen only in production". The Wang result suggests coverage metrics understate the gap; invariants or behaviour models expose more.

### Gaps
- No published study found that measures how schema or data-contract changes break test fixtures, or that automates fixture updates driven by schema changes. This is absence of evidence. Qiu et al. study application-code co-change only.
- No documented practice found that exports rule-hit or branch-hit diffs from a protected data environment to flag fixture gaps (absence of evidence; the nearest are Productive Coverage and TDCommons #4113).
- The TDCommons PDF was not readable (403), so its method details are unverified. Meta and Microsoft production-vs-test coverage reports were not found in this run.

## Q3. Automated renewal and repair of fixtures and generated tests (test repair, regenerating generated tests, snapshot/golden/approval workflows, oracle-update risk)

### Takeaway
Renewal tooling falls into three families. (1) Snapshot, golden and approval tools regenerate expected outputs on a flag (`--snapshot-update`, `--force-regen`, `--inline-snapshot=fix`, `jest -u`) and rely on human diff review as the oracle check. (2) Test-repair research has moved from ReAssert (2009; repaired 78% of failures in one case study, per a search extract) to LLM repair (TaRGET, 66.1% exact match on 45,373 repairs). (3) Generated suites (Randoop at ABB) can be kept maintainable, needing 4 edits over 2 years and 3 versions. The risk all three share is that the update step rewrites the oracle to match current behaviour. Practitioner studies report false positives on intentional changes and the burden of reviewing large result sets. Only Jest documents a hard guard against silent oracle writes in CI.

### Cited Findings
**Test repair / maintenance research**
- ReAssert (Daniel, Jagannath, Dig, Marinov, ASE 2009) suggests edits to failing *tests*, such as literal replacement, changing the assertion method, or splitting assertions. In a case study, 78% of failures (29 of 37) were repaired. The ICSE 2011 tool paper notes that it fails on complex control flow or on operations over expected values. [lead — IDEALS PDF returned 403] — [IDEALS](https://www.ideals.illinois.edu/items/13598/bitstreams/49074/data.pdf); [ICSE 2011 tool page](https://2011.icse-conferences.org/content/reassert-tool-repairing-broken-unit-tests.html)
- Pinto, Sinha, Orso, "Understanding Myths and Realities of Test-Suite Evolution", FSE 2012. Repairing broken tests is only a small part of test evolution; deletions and additions dominate. [lead; the Georgia Tech PDF failed to connect (TLS error)] — [Orso PDF link](https://faculty.cc.gatech.edu/~orso/papers/pinto.sinha.orso.ICSE12.pdf); [IBM page](https://research.ibm.com/publications/understanding-myths-and-realities-of-test-suite-evolution)
- Yaraghi, Holden, Kahani, Briand, "Automated Test Case Repair Using Language Models" (TaRGET), arXiv 2401.06765 (Jan 2024). It fine-tunes code LMs and introduces the TaRBench benchmark (45,373 broken-test repairs across 59 projects). 66.1% exact-match accuracy. The paper includes a guide to predicting when repairs are unreliable. [documented-abstract] — [arXiv](https://arxiv.org/pdf/2401.06765v1)
- Liu, Lemner, Wahlgren, Gay, Mohammadiha, Wennerberg, "Exploring the Integration of LLMs in Industrial Test Maintenance Processes" (Ericsson, arXiv 2409.06416v2, Jul 2025). Industrial case study of maintenance triggers, plus a multi-agent prototype that predicts which tests need maintenance. [documented-abstract] — [arXiv](https://arxiv.org/pdf/2409.06416)
- Levin & Yehudai, "The Co-Evolution of Test Maintenance and Code Maintenance through the lens of Fine-Grained Semantic Changes" (arXiv 1709.09029, Sep 2017; 61 projects, more than 240,000 commits): "more often than not, developers perform code fixes without performing complementary test maintenance in the same commit". [documented-abstract] — [arXiv](https://arxiv.org/pdf/1709.09029)

**Regenerating generated tests**
- Robinson, Ernst, Perkins, Augustine, Li, "Scaling up automated test generation: automatically generating maintainable regression unit tests for programs", ASE 2011 (ABB + Randoop). Earlier generators produced brittle, hard-to-read suites. With the enhancements, the generated tests had good coverage and mutation score, were readable by product developers, and needed "just 4 edits to accommodate 2 years and 3 public versions of changes". When a generated test fails on generation, "Randoop assumes the failing test is nondeterministic and … disables each failing assertion" (a flakiness filter that also weakens the oracle). The paper also notes the incentive problem: if updating a failing test is tedious, "the temptation to remove it becomes too great to resist". [documented] — [UW PDF](https://homes.cs.washington.edu/~mernst/pubs/maintainable-tests-ase2011.pdf)
- Shamshiri, Rojas, Galeotti, Walkinshaw, Fraser, ICST 2018 (75 participants, 150 data points). Maintenance takes longer with generated tests, but developers were equally effective at fixing failures with generated or manual tests. [lead] — [Leicester figshare](https://figshare.le.ac.uk/articles/conference_contribution/How_Do_Automatically_Generated_Unit_Tests_Influence_Software_Maintenance_/10224710)
- Pynguin (Python test generator, MIT): 0.48.0 is the latest stable; 0.49.0.dev0 was uploaded 2026-10-16; first release 2020-07-25. [documented] — [PyPI JSON](https://pypi.org/pypi/pynguin/json). EvoSuite: Maven Central `evosuite-standalone-runtime` 1.0.6, metadata lastUpdated 2018-04-05. GitHub releases were not checked because the GitHub API was not available in this session. **Empirical evidence on snapshot maintenance and oracle-update risk**
- "On the Effectiveness of Snapshot Testing: An Empirical Study", arXiv 2610.29549 (submitted 2026-10-21). 340 GitHub repositories and a survey of 60 practitioners. Median statement coverage of snapshot plus non-snapshot tests was 86.7%; the two kinds exercise distinct code regions. Suites with snapshots killed 1.3× more mutants. Reported hurdles: "reviewing large result sets and managing false positives". [documented-abstract] — [arXiv](https://arxiv.org/abs/2610.29549)
- UFMG master's dissertation (2024, Jest). A grey-literature review of 50 documents plus 380 sampled tests from 569 projects. Snapshot drawbacks are "fragility and lack of context [that] can lead to false positives". It frames intended changes as false positives where "developers should update the snapshot, introducing a new golden standard based on the current state". Two snapshot test smells were identified. [documented-abstract] — [UFMG PDF](https://homepages.dcc.ufmg.br/~mtov/diss/2024-victor.pdf)
- Fujita, Kashiwa, Lin, Iida, "An Empirical Study on the Use of Snapshot Testing", ICSME 2023, pp. 335–340. [unreachable — bibliographic record only] — [researchr](https://researchr.org/publication/FujitaK0I23)
- LLMShot (arXiv 2507.10062v2, Jul 2025) uses vision-language models to classify UI snapshot failures as regressions or intentional changes; above 84% recall with a 12B model. UI-only. [documented-abstract] — [arXiv](https://arxiv.org/pdf/2507.10062v2)
- Practitioner claim that developers "simply press the button to update the snapshots without looking". Anecdotal blog. [lead] — [LogRocket](https://blog.logrocket.com/refactoring-legacy-code-with-jest-snapshots-e290ceccccc3)

**Record/replay fixture renewal**
- vcrpy (MIT, 9.4.2 released 2026-11-02) has four record modes. `once` (default) records only if there is no cassette and errors on new requests. `new_episodes` records new interactions. `none` replays only and errors on any new request. `all` always re-records. ### Inferences
- [inferred] Every regenerate flag (`--snapshot-update`, `--force-regen`, `create_test`, `jest -u`, cassette `all`) turns "current behaviour" into "expected behaviour". When the fixture input is *refreshed real data*, as opposed to a changed implementation, a regeneration diff mixes data change with logic change. Practices that separate them: regenerate under the old code and under the new code against the same pinned input; review diffs; forbid writes in CI (Jest's rule); use syrupy-style "new-only" modes; and fail on unused snapshots, so that a deleted scenario is noticed rather than silently dropped.
- [inferred] For protected data, golden outputs produced from real inputs are themselves derived data. Whether a snapshot diff (rather than the snapshot) can leave the environment is a policy question; no tool documents this distinction.
- [inferred] Randoop's "disable failing assertions on generation" and the arid-mutant filtering at Google are the same trade-off: they cut false alarms by discarding oracle strength.

### Gaps
- No empirical measurement found of how often snapshot updates in real projects hide real regressions (blind acceptance). Only survey and practitioner reports were found. Fujita et al. 2023 was unreachable.
- No study found on regenerating EvoSuite/Pynguin suites across versions (regeneration churn) beyond Randoop/ABB 2011 and Shamshiri 2018 (lead).
- No test-repair work found that targets data fixtures (as opposed to test code).

## Q4. Keeping historical failures reproducible (regression-test-per-bug, fuzzing corpora, pinned seeds/generators, bisecting, data-dependent flakiness)

### Takeaway
Fuzzing ecosystems hold the most complete documented practice. Go writes each failing input into `testdata/fuzz/…`, which `go test` then runs as a regression test. libFuzzer treats the corpus as a regression check and offers `-merge=1` minimisation and crash minimisation. ClusterFuzz/OSS-Fuzz deduplicate crashes, minimise testcases, bisect regression ranges and recheck fixed testcases automatically. Outside fuzzing, adding a regression test with each bug fix is the norm, but it is not what happens: most fix commits carry no test change (61-project study). The flaky-test literature shows that order dependence, randomness, unordered collections, time and platform make "historical failures" unreproducible unless seeds and environment are pinned. Order dependency causes 59% of Python flaky tests, and 170 reruns are needed for 95% confidence that a passing test is not flaky.

### Cited Findings
**Fuzzing regression corpora**
- Go native fuzzing: "The fuzzing engine wrote this failing input to the seed corpus for that fuzz test, and it will now be run by default with go test, serving as a regression test once the bug has been fixed … submit the patch with the new testdata file acting as your regression test." Seed corpus entries come from `(*testing.F).Add` and from files under `testdata/fuzz`, and must match the fuzz argument types. [documented] — [go.dev fuzzing](https://go.dev/doc/security/fuzz/)
- libFuzzer: "The corpus can also act as a sanity/regression check". In this mode the fuzzer binary can be used as a regression test, running the corpus inputs without fuzzing. `-merge=1` minimises a corpus while keeping coverage, and `-merge_control_file` makes merges resumable. Crashes are saved as `crash-<sha1>` / `leak-<sha1>`. `-minimize_crash` shrinks reproducers; `-exact_artifact_path` sets the artifact path. [documented] — [LLVM LibFuzzer docs](https://llvm.org/docs/LibFuzzer.html)
- ClusterFuzz features: accurate crash deduplication, testcase minimization, and "regression finding through bisection". [documented] — [ClusterFuzz docs index (raw)](https://raw.githubusercontent.com/google/clusterfuzz/master/docs/index.md)
- OSS-Fuzz: every issue has an attached reproducer ("testcase") file, run with `./fuzz_target_binary <testcase_path>` or `infra/helper.py reproduce`. After a fix, ClusterFuzz will "automatically pick up the changes, recheck the testcase, and close" the issue. Corpora are kept on GCS with **daily zipped corpus backups**, and access is limited to contacts listed in `project.yaml`. [documented] — [OSS-Fuzz reproducing](https://raw.githubusercontent.com/google/oss-fuzz/master/docs/advanced-topics/reproducing.md); [OSS-Fuzz corpora](https://raw.githubusercontent.com/google/oss-fuzz/master/docs/advanced-topics/corpora.md)

**Regression test per bug: practice vs reality**
- 61 projects, more than 240K commits: "more often than not, developers perform code fixes without performing complementary test maintenance in the same commit". [documented-abstract] — [arXiv 1709.09029](https://arxiv.org/pdf/1709.09029)
- Covrig (Marinescu, Hosek, Cadar, ISSTA 2014) studied whether code patches come with test changes, and the coverage of bug-fix revisions, in Memcached, Redis and ØMQ. I did not extract the specific proportions. [documented-abstract] — [Imperial PDF](https://srg.doc.ic.ac.uk/files/papers/covrig-issta-14.pdf)
- Jest's determinism rule and SQLMesh's "pin date macro variables to make the generated test deterministic" are documented determinism requirements for golden artefacts. [documented] — [Jest](https://jestjs.io/docs/snapshot-testing); [SQLMesh](https://sqlmesh.readthedocs.io/en/stable/concepts/tests/)

**Flakiness and data-dependent nondeterminism**
- Luo, Hariri, Eloussi, Marinov, "An Empirical Analysis of Flaky Tests", FSE 2014. 201 flaky-fix commits in 51 projects; of the 161 classified, Async Wait accounted for 45%, Concurrency 20% and Test Order Dependency 12%. 47% of order-dependency flaky tests depend on external resources, and 74% were fixed by cleaning shared state between runs. Concurrency fixes: 31% locks, 25% "making code deterministic". [documented] — [PDF copy (Vanderbilt course site)](https://huang.isis.vanderbilt.edu/cs8395/paper/flakytest.pdf)
- Gruber, Lukasczyk, Kroiß, Fraser, "An Empirical Study of Flaky Tests in Python", ICST 2021 (arXiv 2101.09077). 22,352 PyPI projects and 876,186 tests yielded 7,571 flaky tests. Order dependency caused 59%, test infrastructure 28% (a newly documented cause), and network/randomness most of the remaining 13%. 95% confidence that a passing test is not flaky "would require 170 reruns". [documented-abstract] — [arXiv](https://arxiv.org/pdf/2101.09077)
- Parry, Kapfhammer, Hilton, McMinn, "A Survey of Flaky Tests", TOSEM 31(1), 2022 (76 papers). Categories include randomness, floating-point, unordered-collection iteration order and platform dependency (for example different Linux kernel versions). "Unsynchronized seeds", where seeds for different libraries' RNGs were set inconsistently, were blamed for two flaky tests. [documented-abstract] — [author PDF](https://o-parry.github.io/papers/2021a.pdf)

### Inferences
- [inferred] The fuzzing pattern of "failing input → minimised → committed to a seed-corpus directory → run by default → auto-recheck on fix" maps directly onto data-fixture regression stores. The blocking issue for a protected environment is that the reproducer *is* the data. Go and OSS-Fuzz commit or store raw inputs, and OSS-Fuzz access-controls them. Real-data reproducers would therefore have to stay inside the environment (a protected corpus, with OSS-Fuzz-style backups and ACLs), or be minimised and transformed before leaving. No source documents the transform step for confidential data.
- [inferred] Reproducing a historical failure deterministically needs the seed, the generator or tool version, input order (order dependence is the top Python flakiness cause) and environment or platform pinned together. Parry's "unsynchronized seeds" case shows that a single recorded seed is not enough when several RNGs are involved.
- [inferred] ClusterFuzz-style bisection presumes the reproducer input is fixed while code varies. Bisecting with *pinned data* is the same discipline applied to fixtures; no non-fuzzing tool documenting it was found in this run (versioned-data tools were out of scope here).

### Gaps
- Exact proportions of bug fixes accompanied by regression tests were not extracted (Covrig and 1709.09029 full numbers not read).
- No study found that measures how long historical data-pipeline failures stay reproducible, or how fixture-store versioning affects this.
- Luo 2014's minor categories (randomness, floating point, unordered collections, time, I/O) were not extracted with counts.
