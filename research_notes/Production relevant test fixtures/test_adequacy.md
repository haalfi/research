# Test adequacy for fictional test data in data-intensive and database-backed software

Scope: adequacy criteria (coverage, mutation, oracle/assertion adequacy, data/combinatorial coverage), the empirical evidence that they predict defect detection, ways to separate weak inputs from weak assertions from faulty implementations, and OSS tools, as they apply to a data platform (ingestion, transformation, entity resolution, reconciliation, validation, incremental processing on Python, SQL and Spark).

Labels: **[documented]** means I downloaded the full text (PDF, README or doc page) and read the cited passage. **[lead]** means the claim comes from a search-result extract only. **[inferred]** means my own engineering inference. **[vendor]** means a project's or vendor's own description, not independently checked. Research date: 2026-11-26. Release dates come from the PyPI JSON API and Maven Central `maven-metadata.xml`. The GitHub API was not reachable from this session (HTTP 403, "access not enabled"), so I could not get repository push dates.

## 1. Coverage criteria for SQL and data logic, and whether coverage predicts defect detection

### Takeaway
SQL-specific criteria exist and are well defined. The best known is SQLFpc, which applies masking MC/DC to SQL: it covers WHERE/HAVING, joins including outer joins, GROUP BY, aggregates, subqueries, CASE and NULLs. Its coverage rules are themselves SQL queries that run against the test database. A dataflow+UDF path criterion exists for Spark-style programs (BigTest's JDU paths). dbt-coverage, by contrast, only counts whether columns have documentation or tests attached. It is not a measure of logic coverage. Across general software, structural coverage correlates only weakly to moderately with fault detection once suite size is controlled for (Inozemtseva & Holmes 2014). A more careful design (Chekam et al. 2017) found little or no effect of statement or branch coverage on fault revelation. Only strong mutation showed a strong link, and only above a threshold.

### Cited Findings
- **SQLFpc definition [documented].** Tuya, Suárez-Cabal and de la Riva, "Full predicate coverage for testing SQL database queries", STVR 20(3):237-288, Sept 2010 (author preprint). SQLFpc "is based on Masking Modified Condition Decision Coverage (MCDC) or Full Predicate Coverage and takes into account a wide range of the syntax and semantics of SQL, including selection, joining, grouping, aggregations, subqueries, case expressions and null values." Test requirements are expressed as "coverage rules that is obtained by applying successive transformations on the query under test", and "the coverage rules are executable and able to determine whether the different situations expressed by the test requirements are covered by the test data." The criterion treats NULLs explicitly: there is a null-check predicate nl(Ai), and nullability is derived from the schema. Outer joins are handled through left and right "outer increments". — [Tuya et al. 2010 preprint](https://giis.uniovi.es/testing/papers/stvr-2010-sqlfpc.pdf)
- **SQLFpc empirical support [documented, weak evidence].** The paper says that "as the test database contains more rows that increase the SQLFpc coverage, they are able to reveal more faults in the query (measured in terms of mutation score)". It also cites an earlier controlled experiment by the same authors in which testers guided by the criterion detected more faults. The evidence comes from a case study measured with mutants, not real faults, by the criterion's own authors. — [Tuya et al. 2010](https://giis.uniovi.es/testing/papers/stvr-2010-sqlfpc.pdf)
- **SQLFpc on deployed applications [documented].** The executed queries "can be collected using vendor specific DBMS tracing tools or using external software like p6spy and then evaluating their coverage". The authors claim "efficient evaluation of the coverage, even for large databases". — [Tuya et al. 2010](https://giis.uniovi.es/testing/papers/stvr-2010-sqlfpc.pdf). The Oviedo group still hosts an "SQL Code Coverage" page (test4data.uniovi.es/sqlcoverage), which explains that conventional condition and decision coverage misses business logic embodied in SQL. I did not determine what the tool behind it is or what state it is in. — [test4data SQL coverage page](https://test4data.uniovi.es/sqlcoverage)
- **Coverage-aware test database reduction [lead].** Tuya, de la Riva, Suárez-Cabal and Blanco, "Coverage-Aware Test Database Reduction", IEEE TSE. It reduces a database with respect to a set of SQL queries and a coverage criterion. The PDF link returned HTML, so I did not read it. — [search result, digibuo.uniovi.es](https://digibuo.uniovi.es/dspace/bitstream/10651/36745/1/07384760.pdf)
- **Criteria for database applications in general [documented, via a related-work section].** Blanco, Tuya and Seco (arXiv 2023) list the main criteria: data-flow criteria by Kapfhammer & Soffa, structural and data-flow criteria by Willmor & Embury, multiple-condition coverage by Suárez-Cabal & Tuya, and SQLFpc. They then apply an MCDC-based criterion to *business rules* (specification-based, not code-based). Their motivation: "test cases that rely on the source code might not expose faults if the implementation does not fulfil the system specification". They report that the approach found "interesting faults which were located in the procedural code". — [Blanco, Tuya, Seco, arXiv:2304.12671](https://arxiv.org/pdf/2304.12671)
- **Kapfhammer & Soffa, "A family of test adequacy criteria for database-driven applications", ESEC/FSE 2003 [lead].** Data-flow criteria that treat relational database entities (database, relation, attribute, record, attribute value) as definitions and uses. I did not reach the full text. A 2007 dissertation PDF exists. — [author page](https://www.cs.allegheny.edu/sites/gkapfham/research/papers/Kapfhammer2003/); [dissertation](https://www.cs.virginia.edu/~soffa/research/dissertations/kapfhammer_dissertation_final_April_2007.pdf)
- **BigTest, Joint Dataflow and UDF (JDU) path coverage for Spark [documented].** Gulzar, Mardani, Musuvathi and Kim, FSE 2019. Their evaluation finds that "despite ultra-large scale input data size, real world DISC applications are often significantly skewed and inadequate in terms of test coverage, leaving 34% of Joint Dataflow and UDF (JDU) paths untested." "Only few of the data records (order of tens) are actually required to achieve the same JDU coverage as the entire production data." BigTest "reveal[s] 2X more manually-injected faults than the previous approach [Sedge]" and saves 194X CPU time on average. The method uses symbolic execution of dataflow operators plus UDFs and solves the path constraints with Z3 or CVC4. The fault benchmark is 31 faulty applications with *manually injected* faults. — [Gulzar et al. 2019](http://web.cs.ucla.edu/~miryung/Publications/fse2019-bigtest.pdf)
- **dbt-coverage [documented / vendor].** "A single CLI tool which checks your dbt project for missing documentation and tests." It computes doc or test coverage from `target/catalog.json` and `target/manifest.json`, and can compare two reports in CI. It measures whether tests or docs are attached. It does not show whether those tests exercise logic or would detect faults. MIT licence, v0.5.0 released 2026-10-07, first release 2021-11-16 (PyPI). — [dbt-coverage README](https://raw.githubusercontent.com/slidoapp/dbt-coverage/main/README.md); [PyPI](https://pypi.org/pypi/dbt-coverage/json)
- **Inozemtseva & Holmes, ICSE 2014 [documented].** They generated "31,000 test suites for five systems consisting of up to 724,000 lines of source code" and measured statement, decision and modified condition coverage. Conclusions: "there is a low to moderate correlation between the coverage of a test suite and its effectiveness when its size is controlled for"; "the strength of the relationship varies between software systems"; "the type of coverage used had little impact on the strength of the correlation"; "using a fixed coverage value as a quality target is unlikely to produce an effective test suite". Effectiveness was measured with *mutants*, not real faults. — [Inozemtseva & Holmes 2014](https://cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf)
- **Chekam, Papadakis, Le Traon and Harman, ICSE 2017 [documented].** Most earlier studies rely on the "Clean Program Assumption", that a test suite gets similar coverage on faulty and fixed versions. The authors "present evidence that the Clean Program Assumption does not always hold". With a design that avoids it, on C programs with real faults: "For statement, branch and weak mutation testing, we found that increased coverage has little or no effect on fault revelation". Strong mutation "has the highest fault revelation of four widely-used criteria" and shows "threshold behaviour, below which improved coverage has little effect on fault revelation". — [Chekam et al. 2017](https://discovery.ucl.ac.uk/10058915/7/Chekam_ICSE17.pdf)
- **Earlier studies summarised by Inozemtseva & Holmes [documented, secondary].** Their related-work table reports these older findings. Frankl & Weiss: all-uses was related to effectiveness independently of size, decision coverage was not. Frankl, Weiss & Hu: "Effectiveness improves with coverage but not until coverage reaches 80%; even then increase is small". Frankl & Iakounenko: effectiveness correlated with all-uses and decision coverage, but the "increase is small until high levels of coverage are reached". — [Inozemtseva & Holmes 2014](https://cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf)
- **NIST combinatorial coverage measurement [documented].** NIST IR 7878 (Kuhn et al., 2012) defines "simple t-way combination coverage" as "the proportion of t-way combinations of n variables for which all variable-values configurations are fully covered". It notes that "many test sets not based on covering arrays may still provide significant t-way coverage". The measure applies to any existing test set viewed as a table of variable values. — [NIST IR 7878](https://nvlpubs.nist.gov/nistpubs/ir/2012/NIST.IR.7878.pdf)

### Inferences
- [inferred] SQLFpc's coverage rules are SQL queries run against a database, and the only output needed is covered or not covered per rule (or a row count). The same rules could therefore be run inside the protected environment on real data, to see which test requirements real data satisfies and the hand-written fixtures do not. Only rule identifiers and covered/uncovered flags would need to leave. The rule text is derived from the query, not from the data. Whether those flags count as "approved derived information" is a governance decision.
- [inferred] The BigTest result (tens of records reach the same JDU coverage as full production data) supports, for Spark-style programs, the idea that small synthetic fixtures can in principle match real-data *path* coverage. The same paper also shows real data leaving 34% of JDU paths unexercised, so real data is not a coverage oracle either.
- [inferred] dbt-coverage-style "test presence" metrics carry no information about fixture adequacy, and should not be confused with logic coverage.
- [inferred] Given Inozemtseva & Holmes and Chekam et al., any coverage target (SQLFpc, JDU, line or branch) is best read as a way to find *unexercised* logic, not as evidence of fault-detection ability. Both papers say this explicitly for code coverage.

### Gaps
- I found no MC/DC-for-SQL work besides SQLFpc in this track. Other SQL coverage work (Suárez-Cabal & Tuya multiple-condition coverage; Willmor & Embury) is cited only through Blanco et al., and its full texts were not read.
- I found no empirical study validating SQLFpc against *real* SQL faults by independent authors. This is absence of evidence found, not evidence of failure.
- I did not find a maintained, packaged OSS SQLFpc tool with a known licence and release date. Whether the GIIS/test4data tools are currently available is unverified.
- I found no coverage criterion for dbt models' SQL logic in OSS.
- I did not check the availability or maintenance state of BigTest's code.
- I did not retrieve later follow-ups to Inozemtseva & Holmes (for example Gopinath et al. ICSE 2014, Gligoric et al. TOSEM 2015, Kochhar et al. SANER 2015, Chen et al. ASE 2020).

## 2. Mutation analysis as an adequacy criterion: SQL, schema, dataflow and Python/JVM tools, validity and cost

### Takeaway
Mutation tools exist for SQL schemas (SchemaAnalyst), Spark RDD programs (TRANSMUT-Spark), Scala in general (Stryker4s), Java (PIT, with the Descartes extreme-mutation engine) and Python (mutmut and cosmic-ray are active; mutatest and MutPy are stale). The evidence that mutants stand in for real faults is mixed:
- Just et al. 2014 found a significant correlation independent of coverage, with 73% of real faults coupled to mutants.
- Papadakis et al. 2018 (lead only) found weak correlations once suite size is controlled, but useful guidance.
- Chekam et al. 2017 found strong mutation to be the best of four criteria.

Equivalent and other ineffective mutants are a measurable cost: up to 24% of schema mutants in McMinn et al.

### Cited Findings
- **Just et al., FSE 2014, "Are mutants a valid substitute for real faults" [documented].** Based on 357 real faults in 5 Java programs (Defects4J), "The results show a statistically significant correlation between mutant detection and real fault detection, independently of code coverage", and that correlation is "stronger than the correlation between statement coverage and real fault detection". A "coupling effect [exists] for 73% of real faults". "10% of real faults require a new or stronger mutation operator" and "17% of real faults are not coupled to mutants". "Conditional operator replacement, relational operator replacement, and statement deletion mutants are more often coupled to real faults than other mutants." — [Just et al. 2014](https://homes.cs.washington.edu/~rjust/publ/mutants_real_faults_fse_2014.pdf)
- **Papadakis, Shin, Yoo and Bae, ICSE 2018 [lead; PDF not retrieved].** Using CoreBench (C) and Defects4J (Java), correlations between mutation score and real fault detection are weak when suite size is controlled. Selecting suites by higher mutation score still significantly improves fault detection compared with random suites of the same size. — [search extract; CORE link returned HTML](https://core.ac.uk/download/154760839.pdf); [IEEE record](https://ieeexplore.ieee.org/document/8453121)
- **Conflict.** Just et al. 2014 report a significant coverage-independent correlation. Papadakis et al. 2018 (lead) report weak correlation controlling for size. Chekam et al. 2017 report a strong link only for strong mutation and only above a threshold. The studies differ in subjects, in how they control for size, and in the Clean Program Assumption. — sources above
- **Google, Petrović, Ivanković, Fraser and Just, ICSE 2021 [documented].** The dataset has "almost 15 million mutants" over six years. "Developers using mutation testing write more tests, and actively improve their test suites with high quality tests such that fewer mutants remain". Analysis of past fixes of high-priority faults gives "evidence that mutants are indeed coupled with real faults". The authors also note that "only few of these [mutants] can be shown to developers" because there are so many. Exhaustive mutation "for a large code base is impracticable". — [Petrović et al. arXiv:2103.07189](https://arxiv.org/pdf/2103.07189)
- **TRANSMUT-Spark, dataflow mutation for Spark [documented].** de Souza Neto et al. (arXiv 2108.02589, Aug 2021; journal version STVR 32(8) e1809, 2022, per a search extract). It defines "15 mutation operators divided into two groups: data flow and transformations". Data-flow operators modify the program's DAG. Transformation operators modify specific operations such as aggregation, set operations, distinct, filter deletion and sortByKey deletion. "Reduction rules" suppress redundant mutants, for example DTIE removes equivalent mutants created by inserting `distinct` after an aggregation. Cost is reduced by selective mutation and Mutant Schema Generation. Equivalent mutants are marked by hand in the described process. — [TRANSMUT-Spark paper](https://arxiv.org/pdf/2108.02589). Tool README: an sbt plugin that requires sbt 1.3+ and Scala 2.12.x and supports "Spark programs using only the RDD (Core) API". It is "not yet been published to a remote repository" (you build it locally). MIT licence (LICENSE, ©2020). — [README](https://raw.githubusercontent.com/jbsneto-ppgsc-ufrn/transmut-spark/master/README.md)
- **SchemaAnalyst, schema mutation [documented].** README: "a test data generation and a mutation testing tool for relational database schemas". Operators change the schema's integrity constraints. Output columns `scorenumerator`/`scoredenominator` give a mutation score in [0,1]. It supports HyperSQL, PostgreSQL and SQLite. GPL licence (LICENSE.txt). I could not get a release or push date because the GitHub API was blocked. — [SchemaAnalyst README](https://raw.githubusercontent.com/schemaanalyst/schemaanalyst/master/README.md)
- **Ineffective schema mutants [documented].** McMinn, Wright, McCurdy, Kapfhammer et al., IEEE TSE 45(5):427-463, 2019. Across 34 schemas on HyperSQL, PostgreSQL and SQLite, automatically removed ineffective mutants (stillborn, equivalent, redundant) "can account for up to 24% of mutants, leading to a change in mutation score for 33 out of 34 schemas". Equivalent mutants carry a "human cost: … testers often have to manually inspect test cases, mutants, and the original schema to determine why a mutant is still alive". Removal also cuts execution cost, especially on heavyweight DBMSs such as PostgreSQL (the last point is a lead from the search extract). — [McMinn et al. 2019](https://eprints.whiterose.ac.uk/126146/1/ineffective-mutants.pdf)
- **PIT (Java) [documented / vendor].** For each mutation PIT reports one of: Killed, Survived, No coverage, Non viable, Timed Out, Memory error, Run error. "Survived means the mutation was not detected by the covering test. No coverage is the same as Survived except there were no tests that exercised the line of code where the mutation was created." Apache-2.0 licence. Latest release 1.30.2, Maven metadata lastUpdated 2026-11-05. — [PIT basic concepts](https://pitest.org/quickstart/basic_concepts/); [Maven metadata](https://repo1.maven.org/maven2/org/pitest/pitest/maven-metadata.xml)
- **Stryker4s (Scala) [documented / vendor].** "A mutation testing framework for Scala". sbt plugin; Apache-2.0. Latest 1.1.1, Maven metadata lastUpdated 2026-07-30. Spark-specific operators are not claimed in its README. — [Stryker4s README](https://raw.githubusercontent.com/stryker-mutator/stryker4s/master/README.md); [Maven metadata](https://repo1.maven.org/maven2/io/stryker-mutator/stryker4s-core_3/maven-metadata.xml)
- **Python mutation tools [documented from PyPI JSON and README].**
  - **mutmut:** 3.8.1, released 2026-10-28, first release 2016-12-01. The LICENSE header reads "Copyright (c) 2016, Anders Hovmöller All rights reserved"; I infer it is BSD-style from that header. The README says it runs in parallel, can restrict mutation to lines that coverage.py marks as executed (honouring `# pragma: no cover`), can drop mutants that the mypy or pyrefly type checkers reject, writes mutants and stats to `mutants/`, and needs WSL on Windows. — [mutmut README](https://raw.githubusercontent.com/boxed/mutmut/main/README.rst); [PyPI](https://pypi.org/pypi/mutmut/json)
  - **cosmic-ray:** 8.9.0, released 2026-11-10, first release 2015-04-24, MIT. — [PyPI](https://pypi.org/pypi/cosmic-ray/json)
  - **mutatest:** 3.1.0, last release 2022-02-20, MIT (stale). — [PyPI](https://pypi.org/pypi/mutatest/json)
  - **MutPy:** 0.6.1, last release 2019-11-17, Apache-2.0 (stale). — [PyPI](https://pypi.org/pypi/MutPy/json)
  - **poodle:** 1.4.0, released 2026-10-31, MIT. — [PyPI](https://pypi.org/pypi/poodle/json)
  - **pytest-gremlins:** 1.15.0, released 2026-11-26, first release 2026-01-27, MIT (very young project). — [PyPI](https://pypi.org/pypi/pytest-gremlins/json)
- **dbt unit tests run on static fixtures [documented / vendor].** "Unit tests allow you to validate your SQL modeling logic on a small set of static inputs before you materialize your full model in production." Limitations: SQL models only; no materialized views, recursive SQL or introspective queries. dbt advises unit-testing logic "for which you had bugs reported before" and "Edge cases not yet seen in your actual data". It advises *against* testing built-ins such as `min()`. — [dbt unit tests docs](https://docs.getdbt.com/docs/build/unit-tests)

### Inferences
- [inferred] "Data mutation" (perturbing input rows) and "code mutation" (perturbing the program or query) answer different questions. Code or SQL mutation measures whether the *fixtures plus assertions* distinguish the program from faulty variants. Data mutation measures whether *checks/validators* detect corrupted data. Only code mutation is the adequacy measure the cited validity studies (Just, Papadakis, Chekam) address. I found no empirical validity study for data mutation as a test-adequacy criterion in this track.
- [inferred] Mutation reports from PIT, mutmut and cosmic-ray describe mutants by source location and operator, plus a killed/survived status. They contain no data rows unless the test logs do. A mutation run inside the protected environment, against tests that read real rows, could plausibly export a report of mutant IDs and statuses without exporting data. One caveat: mutant descriptions in SQL could embed literals that come from the code, not the data.
- [inferred] For SQL-heavy platforms, the operator sets that exist (SQL query mutation à la Tuya, schema mutation à la SchemaAnalyst, Spark RDD dataflow mutation à la TRANSMUT-Spark) do not cover the DataFrame/Dataset/SQL APIs of Spark. TRANSMUT-Spark is RDD-only and Scala 2.12-only. None packages dbt models. Python AST mutators (mutmut, cosmic-ray) mutate Python code but not SQL strings embedded in it.

### Gaps
- I did not read SQLMutation (Tuya, Suárez-Cabal, de la Riva, IST 2007), Chan, Cheung & Tse (QSIC 2005) or Zhou & Frankl JDAMA (ICST 2009). Their operator lists and empirical results are not reported here. Current availability of an SQLMutation tool or service is unverified.
- I did not read the Jia & Harman 2011 and Papadakis et al. 2019 surveys, so cost figures and equivalent-mutant rates from those surveys are not reported.
- I found no mutation tool for PySpark DataFrames, pandas transformations or dbt SQL, and no empirical study of mutation adequacy for ETL or entity-resolution code. This is absence in my search, not proof that none exist.
- I did not measure the computational cost of mutation on a real data pipeline. The Google paper says exhaustive mutation does not scale, and TRANSMUT-Spark uses selective mutation and schemata, but no numbers for data pipelines were found.

## 3. Assertion and oracle adequacy: checked coverage, pseudo-tested methods, assertion counts, vacuous tests

### Takeaway
Coverage says nothing about whether results are checked. Three metrics target oracle adequacy:
- **Checked coverage** (Schuler & Zeller 2011): the dynamic slice from assertions.
- **Pseudo-tested methods** (Niedermayr et al. 2016; Vera-Pérez et al. 2018), detected by extreme mutation (Descartes for PIT): methods that are covered, yet no test fails when the method body is removed.
- **Assertion quantity and assertion coverage** (Zhang & Mesbah 2015), which correlate strongly with mutation-measured effectiveness.

In data tooling, dbt data tests are defined so that "if the test returns zero rows, your assertion passes". A check can therefore pass vacuously when the model under test is empty.

### Cited Findings
- **Schuler & Zeller, checked coverage, ICST 2011 [documented].** "A known problem of traditional coverage metrics is that they do not assess oracle quality—that is, whether the computation result is actually checked against expectations." "Checked coverage [is] the dynamic slice of covered statements that actually influence an oracle." "It is perfectly possible to achieve a 100% coverage and still not have any result checked by even a single oracle." On seven OSS projects, checked coverage is "a sure indicator for oracle quality—and even more sensitive than mutation testing". It needs one run with "constant overhead", compared with mutation's many runs. The implementation uses JavaSlicer (dynamic slicing of Java). The validation removed assert statements and observed the metric drop. — [Schuler & Zeller 2011](https://www.st.cs.uni-saarland.de/publications/files/schuler-icst-2011.pdf)
- **Niedermayr, Juergens and Wagner, "Will my tests tell me if I break this code?", CSED 2016 [documented].** Pseudo-tested methods are found with an "extreme mutation operator in which we eliminated the whole logic from a method". The ratio "ranges between 6% and 72% for the analyzed study objects … (mean: 35.48%, standard deviation: 20.60%)". It "is acceptable for unit tests but not for system tests (that execute large portions of the whole system)". — [Niedermayr et al. arXiv:1611.07163](https://arxiv.org/pdf/1611.07163)
- **Vera-Pérez, Danglot, Monperrus and Baudry, "A comprehensive study of pseudo-tested methods", EMSE 2019 (arXiv 2018) [documented].** The study covers 21 OSS Java projects and confirms "pseudo-tested methods exist in all our subjects". The authors manually analysed 101 pseudo-tested methods: "pseudo-tested methods are significantly less tested than the other methods; yet, for most of them, the developers would not pay the testing price to fix this situation." — [Vera-Pérez et al. arXiv:1807.05030](https://arxiv.org/pdf/1807.05030)
- **Descartes (PIT engine) [documented / vendor].** It "evaluates the capability of your test suite to detect bugs using extreme mutation testing. It is able to find the worst tested methods in a project". It is a PIT mutation-engine plugin and is enabled with `<mutationEngine>descartes</mutationEngine>`. LGPL licence. Latest release 1.3.4, Maven metadata lastUpdated 2025-09-19. — [Descartes README](https://raw.githubusercontent.com/STAMP-project/pitest-descartes/master/README.md); [Maven metadata](https://repo1.maven.org/maven2/eu/stamp-project/descartes/maven-metadata.xml)
- **Zhang & Mesbah, "Assertions are strongly correlated with test suite effectiveness", ESEC/FSE 2015 [documented].** "We find that the number of assertions in a test suite strongly correlates with its effectiveness, and this factor directly influences the relationship between test suite size and effectiveness." Assertion coverage is also strongly correlated with effectiveness. The master suites of the subjects showed statement coverage of 45-93% against assertion coverage of 10-65%. Effectiveness was measured with mutants. — [Zhang & Mesbah 2015](https://people.ece.ubc.ca/amesbah/resources/papers/fse15.pdf)
- **Counterpoint [lead].** A later study by Jie M. Zhang et al., "Do Pseudo Test Suites Lead to Inflated Correlation in Measuring Test Effectiveness?", reportedly found that statement coverage correlates better with overall fault-revealing ability than assertion coverage does. The PDF link returned HTML, so I did not read it. — [UCL record (search extract)](https://discovery-pp.ucl.ac.uk/10075196/7/Zhang_Do%20Pseudo%20Test%20Suites%20Lead%20to%20Inflated%20Correlation%20in%20Measuring%20Test%20Effectiveness_AAM.pdf)
- **Vacuous pass on zero rows in dbt [documented / vendor].** "dbt constructs a select query for each data test … These queries return the rows where your assertion is not true; if the test returns zero rows, your assertion passes." — [dbt data tests docs](https://docs.getdbt.com/docs/build/data-tests)

### Inferences
- [inferred] Because of the dbt semantics, every dbt-style generic test (unique, not_null, accepted_values, relationships) passes on an empty model. The same applies to any check written as "select violating rows", and also to fixtures whose join keys never match. A non-emptiness or row-count assertion, or a mutation that empties an upstream input, is needed to tell "no violations" apart from "nothing tested". The same reasoning applies to other row-wise validators (pandera, Great Expectations); I did not verify their behaviour on empty inputs in this track.
- [inferred] Extreme mutation maps naturally onto data pipelines. Deleting a whole transformation step (an identity transform), dropping a filter, or returning an empty DataFrame are "method-body removal" analogues. TRANSMUT-Spark's transformation-deletion operators (UTD, FTD, DTD, OTD) are already this kind of operator for RDDs.
- [inferred] Checked coverage needs dynamic slicing, which is available for Java (JavaSlicer) but not, as far as I found, for SQL or Spark execution. This makes it hard to apply to SQL-centric logic.

### Gaps
- I found no OSS tool that computes checked coverage or assertion coverage for Python, SQL or Spark.
- I did not survey test-smell detectors (tsDetect, JNose, PyNose) for empty or assertion-less tests, so their capabilities and maintenance are unreported.
- I did not verify pandera, Great Expectations or Soda behaviour on zero-row inputs, or any "row count > 0" defaults.
- I found no assertion-density studies specific to data or ETL tests.

## 4. Telling input inadequacy, assertion inadequacy and implementation errors apart (RIP/PIE, covered-but-not-detected)

### Takeaway
The standard decomposition is Reachability, Infection, Propagation, extended with Revealability (RIPR), and Voas's PIE analysis. Tools make the first cut directly: PIT's "No coverage" versus "Survived" separates unreached code from code that was reached but not detected. Reneri (Vera-Pérez et al. 2019) automatically splits undetected extreme mutations into three causes: no-infection (inputs too weak), no-propagation, and weak-oracle. It found the three roughly balanced, with 63% of cases infected, so most misses were observability or oracle problems. Failed error propagation is negligible at unit level but substantially higher at system level. That matters for end-to-end pipeline tests.

### Cited Findings
- **PIT outcome categories [documented].** "No coverage" means no test exercised the mutated line, which points to reachability or input inadequacy. "Survived" means the line was covered but the mutant was not detected, which points to infection, propagation or oracle inadequacy, or to an equivalent mutant. — [PIT basic concepts](https://pitest.org/quickstart/basic_concepts/)
- **Reneri [documented].** Vera-Pérez, Danglot, Monperrus and Baudry, arXiv 1909.04770 (Sept 2019). It determines whether "the test inputs are not sufficient to infect the state of the program (no-infection)", "the infection does not propagate to the test cases (no-propagation)", or "the test cases have a weak oracle that does not observe the infection (weak-oracle)". "For 63% of the cases, the existing test cases can infect the program state, meaning that undetected transformations are mostly due to observability and weak oracle issues". "There is no dominant root cause … there is balance between no-infection, no-propagation and weak oracle". The generated suggestions led to tests that "detect 77% of the previously undetected extreme transformations". It is a Java dynamic analysis built on the RIP/PIE model. — [Reneri, arXiv:1909.04770](https://arxiv.org/pdf/1909.04770)
- **Strong vs weak mutation [documented].** "Strong mutation does not subsume weak mutation because of potential failed error propagation, which may cause state differences to be over-written by subsequent computation". Their tool checks strong kills only for mutants that are already weakly killed. This makes weak-kill versus strong-kill a practical infection-versus-propagation split. — [Chekam et al. 2017](https://discovery.ucl.ac.uk/10058915/7/Chekam_ICSE17.pdf)
- **Failed error propagation with real faults [documented].** Defects4J, 6 projects, 386 real bugs: "the prevalence of failed error propagation is negligible when testing is performed at the unit level. However, when system-level inputs are provided, the prevalence of failed error propagation increases substantially." — [arXiv:2011.10787](https://arxiv.org/pdf/2011.10787)
- **PIE and RIPR [lead].** Voas, "PIE: A dynamic failure-based technique", IEEE TSE 18(8):717-727, 1992. PIE estimates the probabilities of execution, infection (state change) and propagation to output, and is described as costly. Ammann & Offutt's RIP model is similar. Li & Offutt extended it to RIPR, where the oracle must *reveal* the failure. All of this comes from secondary citations in search extracts. — [search: Springer record](https://link.springer.com/article/10.1023/A:1022190021310); [Reneri paper cites RIP/PIE](https://arxiv.org/pdf/1909.04770)
- **Clean Program Assumption [documented].** Adequacy measured on the fixed program may not hold for the faulty one, and vice versa. That warns against reading adequacy from a single program version. — [Chekam et al. 2017](https://discovery.ucl.ac.uk/10058915/7/Chekam_ICSE17.pdf)

### Inferences
- [inferred] A practical triage for a data platform follows the PIT/Reneri decomposition:
  1. Mutant not covered: the fixture never reaches the branch, join or rule, so the input is inadequate. SQLFpc or JDU requirements name *which* data situation is missing.
  2. Covered, and the intermediate DataFrame or table differs from the original's (infected), but the final asserted output does not differ: propagation or oracle inadequacy. Either assert on intermediate outputs, or add assertions such as full-table equality instead of row counts.
  3. A test fails on the *original* program with fixtures the spec agrees with: an implementation error, or a wrong expected value. Telling these apart needs an independent specification, as in the business-rule MCDC approach of Blanco et al.
  4. A mutant survives every test and no input can tell it apart: equivalent mutant (a cost, not a defect).
- [inferred] For incremental and stateful pipelines, system-level failed error propagation (arXiv 2011.10787) suggests that end-to-end fixtures may mask faults in early stages, for example when a later deduplication or aggregation overwrites a corrupted value. That argues for per-stage assertions.
- [inferred] Running inside the protected environment: comparing "infected" with "propagated" needs state diffs. Those diffs could contain real values, so only aggregate statuses (counts per mutant per stage) would be candidates for export.

### Gaps
- I found no Python, SQL or Spark tool that performs Reneri-style infection and propagation analysis.
- I did not read Voas 1992 or Li & Offutt (RIPR) in full.
- I found no empirical study of how often survived mutants in data pipelines are equivalent rather than oracle gaps.

## 5. Data-specific adequacy: combinatorial and input-space coverage, entity resolution and reconciliation, data-quality rules, ETL

### Takeaway
Combinatorial (t-way) coverage measurement is a well-defined, tool-supported way to score an existing fixture table's input-space coverage (NIST IR 7878; CCM tool). For entity resolution and reconciliation, the only adequacy-oriented work I found is the Oviedo group's model-driven approach: it derives test requirements from business rules, applying MCDC to rules for entity reconciliation (A-TEST 2016) and for user-database interaction (arXiv 2023). I found no validated adequacy criterion specific to ETL, entity-resolution matching logic or incremental processing. ER evaluation literature centres on accuracy against truth sets, which is a different question from test adequacy.

### Cited Findings
- **Combinatorial coverage [documented].** For a test set over n variables, "simple t-way combination coverage is the proportion of t-way combinations of n variables for which all variable-values configurations are fully covered". "If the test set is a covering array, then coverage is 100%, by definition, but many test sets not based on covering arrays may still provide significant t-way coverage." Exhaustive testing of n variables with 10 values each "would require inputs of all 10^n combinations". — [NIST IR 7878](https://nvlpubs.nist.gov/nistpubs/ir/2012/NIST.IR.7878.pdf)
- **Entity reconciliation testing [documented].** Blanco and colleagues, Oviedo, "Towards an MDE-Based Approach to Test Entity Reconciliation Applications", A-TEST 2016. "Testing the applications that implement the entity reconciliation problem is crucial to ensure both the correctness of the reconciliation process and the quality of the reconciled data." They present "a first approach, based on MDE, which allows the creation of test models for the integration testing of entity reconciliation applications". From business rules, "the situations of interest to be tested (test requirements) that guide the generation of the test cases can be automatically derived". It is a position-level paper ("first approach"). — [A-TEST 2016 paper](https://giis.uniovi.es/testing/papers/a-test-2016-testing-entity-reconciliation.pdf)
- **Business-rule MCDC for database applications [documented].** "A MCDC-based criterion is applied over the business rules to automatically derive the situations of interest to be tested (test requirements), which guide the design of the test inputs." It is specification-based, so it can expose faults where "the application does not do what it should do". — [Blanco, Tuya, Seco arXiv:2304.12671](https://arxiv.org/pdf/2304.12671)
- **ER evaluation versus testing [lead].**
  - A UALR ICIQ 2017 paper notes that FP and FN rates from Boolean match rules designed on a truth set "may not necessarily translate well to the full dataset". — [UALR ICIQ 2017](https://ualr.edu/informationquality/p12-iciq2017-the-challenges-of-truth-sets)
  - A 2026 arXiv paper treats sameness rules as auditable artefacts. It describes "divergence witnesses" that identify implementation faults and notes that blocking keys can encode unintended identity distinctions. — [arXiv:2607.20729](https://arxiv.org/pdf/2607.20729)
  - A US patent describes monotonic consistency tests for an ER engine (a 2,880-test grid built from 6 variables). — [USPTO](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12367219)
  - Senzing [vendor] warns that accuracy tests on insufficient data volumes will not match real-world accuracy. — [Senzing](https://senzing.com/evaluating-entity-resolution/)
- **Real data versus fixtures on path coverage [documented].** Production data left 34% of JDU paths untested in real Spark applications, and tens of synthetic records matched production data's JDU coverage. — [BigTest 2019](http://web.cs.ucla.edu/~miryung/Publications/fse2019-bigtest.pdf)
- **dbt guidance on fixtures [documented / vendor].** Unit-test "Edge cases not yet seen in your actual data". Unit-testing warehouse built-ins is not useful: "fixture data in the unit test won't provide valuable information". — [dbt unit tests docs](https://docs.getdbt.com/docs/build/unit-tests)

### Inferences
- [inferred] Combinatorial coverage measurement only needs the categorical or binned values of the chosen variables, for example source × null-pattern × identifier-type × delay bucket. The same t-way measurement could therefore run on real data inside the protected environment and on fixtures outside. Exporting only the *list of t-way combinations present in real data but absent from the fixtures* is a derived, aggregate artefact. It can still leak rare combinations (small cells), so it would need the same disclosure review as any aggregate.
- [inferred] Rule-derived requirements (MCDC over match, merge and reconciliation rules, à la Blanco et al., and SQLFpc over the SQL that implements them) are the closest documented analogue to "coverage of entity-resolution decision paths". I found no empirical validation of fault detection for these criteria on ER code.
- [inferred] For data-quality rules, the documented dbt semantics (a test passes on zero violating rows) imply that "rule coverage" should be at least two-sided. Each rule needs a fixture that violates it (the check fires) and a fixture that satisfies it non-vacuously (non-empty input). This is MC/DC-style reasoning applied to validation rules. It is an engineering inference, not a documented criterion.

### Gaps
- I did not retrieve NIST CCM or ACTS tool details (licence, current release, input formats). NIST IR 7878 is a 2012 report.
- I found no adequacy criterion specific to ETL, incremental or late-arriving data, or reconciliation logic with empirical validation. This is absence of evidence from a limited search, not proof none exists.
- The A-TEST 2016 ER approach has no follow-up empirical evaluation that I found.
- I found no study comparing hand-written fixtures with real data on mutation score for data pipelines.
