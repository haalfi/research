# Alternatives to production-relevant fixtures: assurance approaches for data-intensive software

Labels used on every claim: **[documented]** = full text read by this researcher; **[lead]** = search extract or secondary summary only; **[inferred]** = this researcher's engineering inference; **[unreachable]** = primary source could not be fetched; **[vendor]** = claim by a tool vendor about its own product. "Engineering blog" marks company blog posts. These are documented practice, not controlled studies. Tool maintenance facts come from the PyPI JSON API, fetched 2026-11-26. The GitHub REST API was not reachable from this session (the session has no GitHub access for those repos), so stars, archive flags and issue activity were **not** checked. Archive or deprecation status comes only from the README text on raw.githubusercontent.com.

Context assumed from the brief: real data stays in a protected environment where tests can run. Only approved derived information leaves. Development happens outside, and hand-written fixtures are much simpler than real data. The logic covered is ingestion, transformation, entity resolution (ER), reconciliation, validation and incremental processing.

## 1. Testing on real data inside the protected environment (shadow/parallel runs, write-audit-publish, production data-quality monitoring)

### Takeaway
Large data organisations document two practices: shadow/parallel runs that compare a new and an old implementation on real production inputs, and "audit before publish" gates. Both export only counts, checksums, mismatch flags and sample keys. That fits a "tests run inside, only derived results leave" setting. The published evidence is engineering-blog practice with outcome figures (migrations completed, incident-detection share). It is not controlled defect-detection studies.

### Cited Findings
- **Uber, Hive to Spark SQL migration (engineering blog, 2025-06-12; Kakwani, Acharya, Khandelwal et al.) [documented]**: Hive workflows ran on Spark SQL "in shadow mode" and were validated against production runs. An Automated Migration Service triggered shadow runs and marked a workflow READY_TO_MIGRATE after enough validated runs. The validation chain was: (1) row-count comparison, which short-circuits on a mismatch; (2) row-level checksums with acceptable mismatch thresholds; (3) consistent sampling by hashing key columns, so both sides sample the same rows. Workarounds were needed for floating-point SUM/AVG (rounding plus tolerance, which the post says "wasn't foolproof"), for stringified JSON (a key-sorting UDF before checksumming), and for non-deterministic functions (ROW_NUMBER, RAND, COLLECT_LIST/SET and CURRENT_TIMESTAMP columns excluded manually). Defect classes surfaced included semantic engine differences: boolean-to-string, timestamp-to-numeric casts, CSV header skipping, VARCHAR truncation, and `regexp_like` returning null vs false. Other mismatches came from timing differences with frequently updated inputs and circular dependencies. Scale: ~18,000 workflows and "about 5 million monthly queries" migrated. The post gives no total mismatch count. — [Uber Engineering](https://www.uber.com/us/en/blog/how-uber-migrated-from-hive-to-spark-sql-for-etl-workloads/)
- **Meta, data-ingestion system migration (engineering blog, 2026-05-12; Tao et al.) [documented]**: Shadow jobs read the same source as production and wrote to a separate shadow table. For each landed partition, a data-quality tool compared row count and checksum with the production partition and logged mismatches and example rows hourly to Scuba. In a "reverse shadow" phase the new system wrote to production and the old one became the shadow, which kept comparison signals running and allowed fast rollback. Cleanup happened only after no discrepancies appeared. The scale was "tens of thousands of ingestion jobs", with 100% migrated and the legacy system deprecated. Change data capture propagates bad data downstream, so bad partitions were flagged and halted. There are no mismatch counts or root-cause categories. — [Engineering at Meta](https://engineering.fb.com/2026/05/12/data-infrastructure/migrating-data-ingestion-systems-at-meta-scale/)
- **Uber Data Quality Platform (engineering blog, 2021-08-05; Zou, Yan, Ying) [documented]**: The platform runs freshness, completeness (row completeness vs upstream, and a sampling test that upstream rows appear downstream), duplicate-primary-key, cross-datacenter consistency (row counts; Bloom-filter membership) and user-defined semantic tests. Tests run periodically or when a pipeline finishes. For incremental tables only the latest partition is tested, after the freshness SLA. Figures: "over 2,000 critical datasets", "around 90% of data quality incidents" detected, and "approximately 100,000 daily executions of about 18,000 tests". No precision, recall or false-positive rate is given, although the post recommends measuring them. Lessons: a sustain period before alerting, freshness as the parent alert to suppress cascades, and auto-rerun with backoff. — [Uber Engineering](https://www.uber.com/blog/operational-excellence-data-quality/)
- **Uber DQM, statistical monitor (engineering blog, 2020) [lead]**: anomaly detection on historical table statistics. — [Uber Engineering](https://www.uber.com/en-NZ/blog/monitoring-data-quality-at-scale/)
- **Write-audit-publish (WAP), Apache Iceberg docs [documented]**: with `write.wap.enabled`, writes go to an `audit-branch` that is independent of main history. "A validation workflow can validate (e.g. data quality) the state of `audit-branch`", then `fast_forward` publishes it to main. The Spark writes docs say `spark.wap.branch` supports WAP for INSERT/MERGE. — [Iceberg branching.md](https://raw.githubusercontent.com/apache/iceberg/main/docs/docs/branching.md); [Iceberg spark-writes.md](https://raw.githubusercontent.com/apache/iceberg/main/docs/docs/spark-writes.md)
- **Netflix origin of WAP [lead]**: secondary sources attribute the name to a 2017 DataWorks Summit talk by Michelle Ufford/Winters ("Whoops the Numbers are wrong!"). They also say Netflix writes to a hidden Iceberg snapshot, audits it with an internal tool and publishes only on pass, citing a 2023 Netflix talk. The primary talk was not retrieved. — [lakeFS blog](https://lakefs.io/blog/data-engineering-patterns-write-audit-publish/); [vutr substack](https://vutr.substack.com/p/how-does-netflix-ensure-the-data)
- **Airbnb Midas certification and "Wall" (engineering blog, Medium) [lead / unreachable]**: Medium returned HTTP 403 to both WebFetch and curl. Secondary summaries say Midas was a nine-step, four-review certification with mandatory data-quality checks and anomaly detection, including a "Data Review" of the pipeline's validation report. They also say it proved costly and non-scalable, so data producers asked for a lighter-weight process, which led to the later Data Quality Score work, and that "Wall" was built "to prevent data bugs". This is relevant as a partially retreated-from heavyweight process, but it rests on extracts only. — [Data Quality at Airbnb](https://medium.com/airbnb-engineering/data-quality-at-airbnb-870d03080469); [Data Quality Score](https://medium.com/airbnb-engineering/data-quality-score-the-next-chapter-of-data-quality-at-airbnb-851dccda19c3); [Wall](https://medium.com/airbnb-engineering/how-airbnb-built-wall-to-prevent-data-bugs-ad1b081d6e8f)
- **Deequ, "unit tests for data" (Schelter et al., Amazon Research, PVLDB 11(12), 2018) [documented]**: a declarative constraint API compiled to Spark aggregation queries, with incremental metric computation on growing datasets (state is kept so only the delta is scanned) and anomaly detection on time series of quality metrics. The stated motivation includes data errors "due to bugs in program code". The evaluation covers runtime and scalability plus constraint-suggestion quality. It does **not** measure how many code defects the checks catch. — [VLDB PDF](https://www.vldb.org/pvldb/vol11/p1781-schelter.pdf)
- **Usage baseline [lead]**: a dbt community forum post reports that of 684 dbt projects active in one week, "only 36% ran a test". The date is unclear and it is a community post, not a study. — [dbt Discourse](https://discourse.getdbt.com/t/how-to-get-started-with-data-testing/455)

### Inferences
- [inferred] Shadow runs, WAP audits and monitors all produce outputs that are already aggregate: row counts, checksum equality, per-check pass/fail and mismatch rates. These are natural candidates for "approved derived information". Two documented practices conflict with a strict export rule: Uber's "consistent sampling" of rows and Meta's logging of "example mismatched rows". In a protected setting, the example rows would have to stay inside or be replaced by key hashes.
- [inferred] These approaches detect a *change* relative to a baseline, or a *violation* of a declared constraint. They do not show that the baseline was correct. A shadow run in which both implementations share a bug passes. Uber's mismatches were mostly engine-semantics differences, the class that a reference-vs-new comparison is good at finding.
- [inferred] Feedback latency is a pipeline run (hours to days, with multiple validated runs before promotion, as at Uber and Meta), compared with seconds for fixture unit tests outside.

### Gaps
- No primary Netflix WAP source was retrieved. Airbnb posts are unreachable (403).
- No controlled or empirical study found that compares defect detection of production-data checks with fixture tests. Uber's "~90% of incidents detected" is self-reported, with an undefined denominator.
- No documented account found of exporting *only* pass/fail and counts from a regulated enclave (for example health or finance) for pipeline testing. This is absence of evidence found, not evidence that the practice is unsolved.

## 2. Runtime verification, assertions, design by contract, reconciliation and audit-balance-control (ABC)

### Takeaway
Empirical software-engineering studies give modest support for a link between assertions and fewer defects. In C/C++ open source the effect is small but significant. One Microsoft study found a negative assertion-density/fault-density correlation (abstract only). An industrial Java replication found only limited support. For data reconciliation (control totals, row-count conservation, checksums) and ABC frameworks, the sources found are practitioner and vendor writing, not empirical studies. Reconciliation is, however, the core validation in the documented Uber and Meta shadow migrations (section 1).

### Cited Findings
- **Casalnuovo, Devanbu, Oliveira, Filkov, Ray, "Assert Use in GitHub Projects", ICSE 2015 [documented, abstract and introduction]**: 100 popular C/C++ projects; 69 contain more than a minimal presence of assertions. "Methods with asserts do have significantly fewer defects", and "adding asserts has a small (but significant)" effect. — [UC Davis PDF](https://www.cs.ucdavis.edu/~filkov/papers/assert-main.pdf)
- **Kudrjavets, Nagappan, Ball, ISSRE 2006 (MSR-TR-2006-54) [lead]**: two Microsoft components; higher assertion density was associated with a statistically significant decrease in fault density. The authors compare this with static-analysis tools. The full text was not retrieved (the core.ac.uk link returned HTML, not a PDF). — [Microsoft Research](https://www.microsoft.com/en-us/research/publication/assessing-the-relationship-between-software-assertions-and-code-qualityan-empirical-investigation/)
- **Counsell et al., "Assert Use and Defectiveness in Industrial Code", ISSREW 2017 [documented, abstract]**: test classes of two industrial telecom Java systems; "only limited evidence to support the earlier results" of Casalnuovo. This is a partial non-replication. — [arXiv 2104.01514](https://arxiv.org/pdf/2104.01514)
- **AWS (Newcombe et al.) on assertions [documented]**: formal specs "can help engineers write better 'self-diagnosing code', in the form of assertions … An assertion checks a small, local part of an overall system invariant." — [Newcombe et al. 2014 author version](https://lamport.azurewebsites.net/tla/formal-methods-amazon.pdf)
- **Reconciliation techniques in production migrations [documented]**: row count, then row-level checksum, then sampled key-level drill-down (Uber); per-partition row count plus checksum, with mismatches logged and blocking promotion (Meta). — [Uber](https://www.uber.com/us/en/blog/how-uber-migrated-from-hive-to-spark-sql-for-etl-workloads/); [Meta](https://engineering.fb.com/2026/05/12/data-infrastructure/migrating-data-ingestion-systems-at-meta-scale/)
- **Uber cross-datacenter consistency and completeness [documented]**: row-count comparison, Bloom-filter membership, and an upstream-sample-appears-downstream test. These are conservation-style checks. — [Uber 2021](https://www.uber.com/blog/operational-excellence-data-quality/)
- **Control totals vs row counts [lead / vendor]**: practitioner and vendor pages argue that row counts miss cardinality-preserving transformation errors, so column sums or hashes should be added and results stored per run ID, drilling to keys only on mismatch. — [Varigence](https://www.varigence.com/blog/row-counts-lie-column-control-totals); [Alation docs](https://docs.alation.com/en/latest/steward/AlationDataQuality/ManageChecks/ReconciliationChecks.html); [Fivetran](https://www.fivetran.com/learn/data-reconciliation)

### Inferences
- [inferred] For entity resolution and multi-source reconciliation, conservation invariants can be checked inside on real data and exported as counts. Examples: every source record maps to exactly one resolved entity or an explicit "unmatched" bucket; the sum of per-source contributions equals target totals; no entity loses a source identifier across an incremental run. They do not need realistic fixtures. They catch loss, duplication and double-counting defects. They miss wrong-but-balanced outputs, such as a mis-merge of two entities that preserves counts.
- [inferred] The assertion literature is about general code, not data pipelines. Its transfer to in-pipeline data invariants is plausible but unmeasured.

### Gaps
- No peer-reviewed study found that measures defect detection by ABC/reconciliation frameworks in data warehousing. Kimball/Inmon-style ABC material found was practitioner or vendor material only.
- No runtime-verification (monitor-synthesis) case study specific to ETL/ER pipelines was found within the call budget.

## 3. Static and formal methods: SQL linting and static analysis, query-equivalence checking, TLA+/P model checking, typed dataframes

### Takeaway
These methods need no data at all, so they fully avoid disclosure. The evidence splits by method. Formal design modelling (TLA+) has strong documented industrial value for concurrency and fault-tolerance design bugs. Specification-to-code conformance checking failed at MongoDB Server scale and succeeded on a deliberately close-to-code spec. SQL equivalence checkers have improved fast on rewrite-rule benchmarks (2023-2024) but cover limited SQL fragments and are research prototypes. Typed dataframes and schema checks are mature OSS, but evidence of the defects they catch is mostly indirect.

### Cited Findings
- **Newcombe et al., "Use of Formal Methods at Amazon Web Services" (author version dated 2014-09-29; CACM 2015) [documented]**: TLA+ was used since 2011 on S3, DynamoDB, EBS and others. Results by system: DynamoDB replication, "Found 3 bugs, some requiring traces of 35 steps"; S3, "Found 2 bugs"; EBS, "Found 3 bugs". One bug "had passed unnoticed through extensive design reviews, code reviews, and testing". The paper says "testing the code is inadequate as a method to find subtle errors in design". Engineers "learn TLA+ from scratch and get useful results in 2 to 3 weeks". The authors know of no tools that verify executable code against the high-level spec. — [author PDF](https://lamport.azurewebsites.net/tla/formal-methods-amazon.pdf)
- **Davis, Hirschhorn, Schvimer (MongoDB), "eXtreme Modelling in Practice", PVLDB 2020 (arXiv 2006.00915) [documented]**: model-based trace-checking (MBTC) of the Server replication protocol against RaftMongo.tla was **abandoned after 10 weeks** by two engineers (4 weeks event tracing, 3 weeks spec update, 3 weeks Python post-processor). Discrepancies came from lack of close correspondence between spec and implementation. "No initial infrastructure investment can make the marginal cost of trace-checking additional specifications cheap." Post-processing bugs "could mask implementation bugs". By contrast, model-based test-case generation (MBTCG) for Realm Sync's operational-transformation merge rules took 4 weeks (2 weeks spec, 795 lines of TLA+; 2 weeks generator, 755 lines of Go). It generated 4,913 C++ tests that achieved 100% branch coverage of the merge rules, against 21% (18/86 branches) for 36 handwritten tests and 92% for AFL fuzzing after ~8M executions. It also found a non-termination bug in the mature C++ code, which led to deprecating ArraySwap. — [arXiv](https://arxiv.org/pdf/2006.00915)
- **VeriEQL, bounded SQL equivalence (He, Zhao, Wang, Wang; PACMPL OOPSLA1, April 2024; arXiv 2403.03193) [documented]**: SMT-based method that proves bounded equivalence and returns counterexample databases. On more than 20,000 benchmarks (LeetCode, Calcite, literature) it supports 77.1% of the LeetCode set, where prior work supported less than 2% of LeetCode queries. It disproves 14.9% of LeetCode pairs, and "testing tools can disprove <1%". Its counterexamples found bugs in MySQL and Calcite. "Over 95% of our benchmarks require integrity constraints." Limits: bounded only, with some pairs not disprovable within a 10-minute timeout, and a bound of 1000+ tuples needed in two cases. — [arXiv](https://arxiv.org/pdf/2403.03193)
- **QED (Wang, Pan, Cheung; PVLDB 17(11), 2024) [documented]**: a bag-semantics equivalence decider that models NULLs and integrity constraints. It verifies 299/444 Calcite and 979/1287 CockroachDB rewrite-rule pairs, more than 2x the prior state of the art (SPES). It notes that Cosette's UDP does not model NULL or outer joins. — [VLDB PDF](https://vldb.org/pvldb/vol17/p3602-wang.pdf)
- **SQLSolver (Ding et al., PACMMOD 1(4), SIGMOD, December 2023) [documented]**: uses LIA* to handle unbounded summations (projection, aggregates) and proves 346 of 359 equivalent pairs from Calcite and Spark SQL rules. The venue is SIGMOD 2023/PACMMOD December 2023, **not** 2024 as the brief suggests. — [NSF PAR PDF](https://par.nsf.gov/servlets/purl/10548354)
- **Cosette [documented]**: the README says "this repo is now deprecated. Check out our new QED solver!" — [Cosette README](https://raw.githubusercontent.com/uwdb/Cosette/master/README.md)
- **SPES [lead, via the QED paper]**: QED's authors name SPES as the previous state of the art "in terms of completeness". — [QED](https://vldb.org/pvldb/vol17/p3602-wang.pdf)
- **sqlglot (MIT; 30.35.0 released 2026-11-24; first release 2021-03-18) [documented]**: a parser, transpiler and optimizer covering more than 30 dialects. The `qualify` and `annotate_types` rules need table schemas. An AST semantic diff distinguishes "cosmetic/structural changes and functional ones", for example a subquery refactored into a CTE, to decide whether a backfill is needed. — [sqlglot README](https://raw.githubusercontent.com/tobymao/sqlglot/main/README.md); [Semantic Diff for SQL post](https://raw.githubusercontent.com/tobymao/sqlglot/main/posts/sql_diff.md); [PyPI](https://pypi.org/pypi/sqlglot/json)
- **SQLFluff (MIT; 4.5.0 released 2026-10-30; first release 2018-11-07; "Production/Stable") [documented, metadata only]**. No defect-detection evidence was found. — [PyPI](https://pypi.org/pypi/sqlfluff/json)
- **Pandera (MIT; 0.36.0 released 2026-11-10; "Production/Stable") [documented]**: dataframe schema validation for pandas, polars, pyspark "and more". Its schemas can generate data via `hypothesis` strategies (`pandera[strategies]`). — [Pandera README](https://raw.githubusercontent.com/unionai-oss/pandera/main/README.md); [data synthesis docs](https://raw.githubusercontent.com/unionai-oss/pandera/main/docs/source/data_synthesis_strategies.md); [PyPI](https://pypi.org/pypi/pandera/json)
- **Root causes in pipelines (Foidl, Golendukhina, Ramler, Felderer; arXiv 2309.07067, 2023) [documented]**: in GitHub issues, the most frequent root cause of data-related issues is data types (33%), mostly in data cleaning (35% of issues) and ingestion (34%). Other causes are symbol/character misplacement (17%), functionality (13%) and data-frame issues (11%). On Stack Overflow, data integration and ingestion is the most asked topic (47%). — [arXiv](https://arxiv.org/pdf/2309.07067)

### Inferences
- [inferred] Foidl et al.'s dominant class (data types, about a third) is the class most directly targeted by schema-typed dataframes (Pandera), Spark typed Datasets and dbt contracts, and these run outside without real data. Character/encoding issues (17%) depend more on real-data variety and are less covered by static types.
- [inferred] Query-equivalence checkers fit *refactoring* (proving a rewritten transformation is equivalent to the old one) and can produce small counterexample databases outside the protected environment, from schema and constraints only. Their benchmarks are optimizer rewrite rules and LeetCode, not ETL or ER logic with UDFs, window functions and fuzzy matching. Applicability to ER is low.
- [inferred] TLA+/P suits the *incremental processing and late-arriving-data* logic (ordering, idempotence, watermarks, retries) more than value-level transforms. MongoDB's experience suggests writing the spec close to the code and generating tests from it, rather than trace-checking a large existing system.

### Gaps
- P language (AWS) and Azure TLA+ case studies were not retrieved. Dates and figures are unverified here.
- The GitHub API was blocked, so maintenance activity for QED, SQLSolver and VeriEQL repos is unknown.
- No empirical study found on defects caught by SQL linters (SQLFluff) or dbt compile checks. The SQLCheck (SIGMOD 2020) anti-pattern paper was not retrieved.
- No study found that applies query-equivalence checking to dbt/ETL refactors in industry.

## 4. Differential and N-version testing (data diff, backtesting, reference implementation as oracle)

### Takeaway
Differential testing is the most widely documented alternative. It appears in large migrations at Uber and Meta, and is "by far the most widely implemented" property kind among Jane Street PBT users. For data jobs it runs naturally inside the protected environment and exports diff statistics. The leading OSS tool (datafold/data-diff) was discontinued in May 2024. A fork (reladiff) and other OSS comparators exist, with weaker maintenance signals.

### Cited Findings
- **Goldstein, Cutler, Dickstein, Pierce, Head, "Property-Based Testing in Practice", ICSE 2024 [documented]**: 30 interviews with Jane Street developers. "Differential properties (17/30) … were by far the most widely implemented kind of property". They are described as a "natural place to use property based testing", and PBT was hard where "a good reference implementation was not available". The mantra: "most useful when … you have a really good abstraction with a complicated implementation." — [UPenn PDF](https://cis.upenn.edu/~bcpierce/papers/icse24-pbt-in-practice.pdf)
- **Uber and Meta shadow runs** are N-version comparisons of old vs new implementations on production inputs (section 1) [documented].
- **datafold/data-diff [documented]**: the README says "As of May 17, 2024, Datafold is no longer actively supporting or developing open source data-diff." It is MIT-licensed. The last PyPI release is 0.11.2 (2024-05-17), classified "Development Status :: 2 - Pre-Alpha". — [README](https://raw.githubusercontent.com/datafold/data-diff/master/README.md); [PyPI](https://pypi.org/pypi/data-diff/json)
- **reladiff [documented]**: "Reladiff is a fork of an archived project called data-diff", MIT. The last release is 0.6.0 (2025-03-04), "Beta", with no release in about 20 months as of 2026-11-26. — [README](https://raw.githubusercontent.com/erezsh/reladiff/master/README.md); [PyPI](https://pypi.org/pypi/reladiff/json)
- **datacompy (Capital One) [documented, metadata only]**: Apache licence, 1.2.0 released 2026-10-27, first release 2018-03-28. Active. — [PyPI](https://pypi.org/pypi/datacompy/json)
- **Datafold commercial data diff in CI [vendor / lead]**: claims such as Thumbtack running diffs on "100+ pull requests per month" are vendor marketing. — [Datafold](https://www.datafold.com/blog/automated-regression-testing-data-quality/)
- **Model-generated tests as a differential oracle [documented]**: MongoDB's TLA+-generated tests checked that "the C++ and Golang implementations of the merge rules … always agree". — [arXiv 2006.00915](https://arxiv.org/pdf/2006.00915)

### Inferences
- [inferred] For the brief's setting, a diff of new code vs released code run inside on real data can export per-table counts such as rows added, removed or changed, columns changed and key-overlap. This gives regression detection on the full real-data variety without fixtures. It cannot tell intended from unintended changes, so reviewers need a declared expected-change scope. It also cannot detect bugs present in both versions.
- [inferred] Uber's handling list (float tolerance, JSON canonicalisation, excluding non-deterministic columns, timing skew of inputs) is the practical maintenance burden any in-house diff harness will meet. ER outputs with non-deterministic cluster IDs would need canonicalisation, for example comparing the partition of source records rather than the IDs.

### Gaps
- No published defect counts from data-diff use (Uber and Meta give none).
- Airbnb, Netflix and Shopify data-diff accounts not found or unreachable.

## 5. Specification-based and property-based testing (no realistic fixtures), metamorphic relations, review and observability

### Takeaway
PBT and model-generated tests check properties on arbitrary or exhaustively enumerated inputs and need no realistic fixtures. In the documented cases they reached higher coverage than hand-written tests (MongoDB: 100% vs 21% branch coverage) and found bugs in mature code. The documented cost is writing generators for inputs that satisfy preconditions, and some practitioners still want "realistic" data. Mature OSS exists (Hypothesis; Pandera strategies).

### Cited Findings
- **Jane Street interviews [documented]**: 17/30 needed generators that satisfy preconditions, such as valid postal addresses, which are "extremely unlikely to be generated by a naïve random generator". 5/30 wanted "realistic" test data. Writing generators was called "tedious" (6/30) or "high-effort" (7/30), and one participant called it "the biggest annoyance". Round-trip properties (11/30) and classical invariants (11/30) were common, and catastrophic-failure properties (7/30) give less confidence. Interviewees also mentioned difficulty judging how effective tests are. — [ICSE 2024 PDF](https://cis.upenn.edu/~bcpierce/papers/icse24-pbt-in-practice.pdf)
- **MongoDB MBTCG coverage [documented]**: 4,913 generated tests reached 100% branch coverage, against 21% for handwritten tests and 92% for AFL after ~8M executions. — [arXiv 2006.00915](https://arxiv.org/pdf/2006.00915)
- **Hypothesis (MPL-2.0; 6.170.17 released 2026-11-20; first release 2013-03-10; "Production/Stable") [documented, metadata]**. — [PyPI](https://pypi.org/pypi/hypothesis/json)
- **Pandera schema-derived Hypothesis strategies** generate dataframes that satisfy declared checks [documented]. — [Pandera docs](https://raw.githubusercontent.com/unionai-oss/pandera/main/docs/source/data_synthesis_strategies.md)
- **Review as a process gate [lead]**: Airbnb Midas used spec, design and data reviews and was later lightened because of its cost (secondary only). — [Airbnb DQS post](https://medium.com/airbnb-engineering/data-quality-score-the-next-chapter-of-data-quality-at-airbnb-851dccda19c3)
- **AWS: review is not enough for subtle design bugs [documented]**: the 35-step DynamoDB bug passed "extensive design reviews, code reviews, and testing". — [Newcombe et al.](https://lamport.azurewebsites.net/tla/formal-methods-amazon.pdf)

### Inferences
- [inferred] Relevant properties for ER and incremental processing that need no realistic data: idempotence (re-running a batch changes nothing), order-independence and associativity of incremental merges (incremental result = full recompute), permutation invariance of input order, monotonicity (adding a source record never removes a resolved link unless a rule says so), and round-trip identifier mapping. The incremental = full-recompute relation can also run *inside* on real data as a metamorphic check that exports only a boolean or diff count. This is consistent with the "differential" category being most used at Jane Street.
- [inferred] PBT generators reproduce the very problem the brief names: generated inputs are "simpler than real data". They explore edge cases that are logically valid but miss real-world oddities such as encodings, coverage gaps and reporting delays. Combining outside PBT with inside metamorphic, differential and reconciliation runs covers both.

### Gaps
- No metamorphic-testing case study specific to ETL or ER pipelines was retrieved (DBMS-testing work such as SQLancer is adjacent and was not checked).
- No empirical data on observability (lineage, freshness dashboards) as a defect-detection mechanism, beyond Uber's self-reported share of incidents.

## 6. When are these preferable to fixture-based testing? Defect classes, cost, latency, disclosure, abandoned approaches

### Takeaway
No source directly compares these approaches with fixture-based testing on the same defects. Comparative reasoning comes from case reports. Formal design modelling catches rare-interleaving design bugs that tests and reviews missed (AWS). Generated or property tests reach coverage that handwritten fixtures do not (MongoDB). Real-data shadow and diff runs catch semantic and engine differences that fixtures would not exercise (Uber). Every approach has documented failure modes: trace-checking a large existing system was abandoned (MongoDB), heavyweight certification was lightened (Airbnb, lead), and the main OSS data-diff was discontinued (Datafold).

### Cited Findings
- **Design bugs vs code tests [documented]**: AWS states that testing is "inadequate" for subtle design errors because "the number of reachable states of the code is astronomical". It treats TLA+ as complementary to testing, not a replacement. — [Newcombe et al.](https://lamport.azurewebsites.net/tla/formal-methods-amazon.pdf)
- **Abandoned: MBTC at MongoDB [documented]**: abandoned after 10 weeks. The authors conclude the marginal cost per specification never becomes cheap at Server scale, and advise future attempts to target modules in unit-test frameworks instead. — [arXiv 2006.00915](https://arxiv.org/pdf/2006.00915)
- **Abandoned or discontinued OSS [documented]**: datafold/data-diff (May 2024) and Cosette (deprecated in favour of QED). — [data-diff README](https://raw.githubusercontent.com/datafold/data-diff/master/README.md); [Cosette README](https://raw.githubusercontent.com/uwdb/Cosette/master/README.md)
- **Licence change: Soda Core v4 [documented]**: the repo LICENSE is now **Elastic License 2.0**, which forbids providing the software as a hosted service and circumventing licence-key functionality. PyPI `soda-core` 4.32.0 (2026-11-25) reports its licence as "Proprietary". Legacy v3 packages are `soda-core-{datasource}~=3.5`. — [LICENSE](https://raw.githubusercontent.com/sodadata/soda-core/main/LICENSE); [README](https://raw.githubusercontent.com/sodadata/soda-core/main/README.md); [PyPI](https://pypi.org/pypi/soda-core/json)
- **Other OSS status (PyPI, 2026-11-26) [documented, metadata]**: great-expectations 1.25.0 (2026-11-12, Apache-2.0); dbt-core 1.12.7 (2026-11-12, Apache-2.0); pydeequ 1.7.0 (2026-09-14, Apache-2.0, "Beta"); Deequ (Scala) README lists Spark 3.1-3.5 support with Deequ 2.x (licence shown only as a badge, not verified). — [GX](https://pypi.org/pypi/great-expectations/json); [dbt-core](https://pypi.org/pypi/dbt-core/json); [pydeequ](https://pypi.org/pypi/pydeequ/json); [Deequ README](https://raw.githubusercontent.com/awslabs/deequ/master/README.md)
- **Cost figures [documented]**: TLA+ learning takes 2-3 weeks (AWS). MBTCG cost 4 person-weeks and the abandoned MBTC 10 weeks for two engineers (MongoDB). Shadow validation is "computationally expensive and storage-heavy when many rows mismatch" (Uber). — sources above.
- **Monitoring gaps [documented]**: Uber reports no precision or recall figures and needed alert-noise controls (sustain periods, parent-alert suppression). — [Uber 2021](https://www.uber.com/blog/operational-excellence-data-quality/)

### Inferences (comparative matrix, all [inferred] from the cited cases)
| Approach | Runs where | Needs real-data-like fixtures? | Exports | Defect classes it catches | Misses | Feedback latency | Maturity / OSS |
|---|---|---|---|---|---|---|---|
| Fixture unit tests (baseline) | outside | yes (hand-written, simple) | n/a | logic on anticipated cases | real-data variety, unanticipated combinations | seconds | mature |
| Constraint / DQ checks on prod (Deequ, GX, dbt tests, Soda v3) | inside | no | pass/fail, metric values | type, null, uniqueness, referential, range, freshness, volume anomalies | wrong-but-plausible values, logic errors that keep constraints true | per run (hours) | mature; Soda v4 now ELv2 |
| WAP / audit branch (Iceberg, Nessie, lakeFS) | inside | no | gate result | stops bad outputs from publishing | same as the checks it runs | per run | mature (Iceberg docs) |
| Shadow / differential / data diff | inside | no | row/column diff counts, checksum equality | regressions, engine-semantics changes, refactor errors | bugs shared by both versions; can't judge intended change | one or more runs (days for promotion) | in-house harnesses; data-diff discontinued; reladiff, datacompy |
| Reconciliation / conservation invariants | inside | no | counts, sums, booleans | loss, duplication, double counting, unmatched records | count-preserving mis-merges or mis-mappings | per run | practice; no specific OSS standard |
| Runtime assertions in code | both | no | assertion failures | invariant violations at the point of failure | properties not asserted | immediate | language-native; small positive empirical effect |
| PBT / model-generated tests | outside | no (generators) | n/a | edge cases, algebraic-property violations (idempotence, incremental = full) | real-world data oddities beyond generators | seconds-minutes | Hypothesis, Pandera strategies |
| Formal design models (TLA+/P) | outside | no | n/a | concurrency, ordering, retry, late-data design bugs | code-vs-spec divergence (unless tests generated) | days-weeks to model | TLA+ mature (tool maintenance not checked) |
| SQL equivalence checking | outside | no (schema/constraints) | counterexample DBs | non-equivalent refactors | unsupported SQL features; non-SQL logic, ER | seconds-minutes | research prototypes |
| SQL lint / static analysis (SQLFluff, sqlglot) | outside | no | n/a | syntax, dialect, style, unqualified/ambiguous refs; cosmetic vs functional change | semantic errors | seconds | mature |

- [inferred] Alternatives seem preferable when the defect class depends on real-data variety (section 1/4 approaches inside), on rare interleavings or late-data orderings (formal models), or on refactors with a trusted previous version (differential/equivalence). Fixtures remain cheapest for fast local feedback on anticipated cases. No source shows any approach replacing fixtures outright. AWS explicitly treats formal methods as complementary.
- [inferred] Disclosure risk is lowest for outside-only methods (static, formal, PBT). For inside methods, risk depends on what is exported: counts and pass/fail are low-risk, while documented practices that log example rows or samples (Uber, Meta) would need adaptation.

### Gaps
- No controlled study compares fixture-based tests with any of these alternatives on the same data pipelines. Absence of evidence, not evidence of equal or unequal value.
- No study quantifies residual defects that escape prod-data monitoring or shadow runs.
- Unverified within the budget: P language at AWS, Azure TLA+ use, Netflix primary WAP source, Airbnb Wall details, the SPES paper itself, Nessie/lakeFS licence and maintenance state, TLA+ tools release cadence.
