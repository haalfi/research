# Seven state kinds decide orchestrator neutrality

Every kind of operational state the pipelines read back today (gate verdicts, "has it landed", lateness, operator acknowledgements, discovery cursors, pool limits, schedule and backfill state) sits in Dagster's own SQL tables, mostly as Dagster-serialised blobs. Only the small, exact pieces can be exported and replayed without loss: cursor strings, dynamic partition keys, pool limits and on/off flags. Event-shaped history such as materialisations, check results, ticks and backfills can be read, but every public re-import path stamps events with the import time and an empty run ID ([Dagster source, asset_methods.py @ 1.13.27](https://raw.githubusercontent.com/dagster-io/dagster/8b9a41d13e2d22b87d38160bf7332a3ab36f3d70/python_modules/dagster/dagster/_core/instance/methods/asset_methods.py)). Databricks has **no equivalent** for five of the concepts these decisions rely on: cross-run check verdicts, manually recorded check results, first-class partitions, named cross-job concurrency pools, and code-version staleness. Its run history also expires after **60 days** ([Databricks: monitor jobs](https://docs.databricks.com/aws/en/jobs/monitor)). During a feed-by-feed migration, then, a decision both orchestrators must share can live in only two places: a platform-owned ledger, or the data itself. Both options cost Dagster-native views (check UI, freshness, Declarative Automation) unless ledger state is mirrored back. The evidence on running two orchestrators side by side is thin and old. The only first-hand outcome found is Robinhood's 2019 Airflow cluster move, which kept exactly one active scheduler per DAG, switched at an interval boundary, with idempotency as the backstop ([Robinhood](https://robinhood.com/newsroom/upgrading-scaling-airflow-at-robinhood/)). No source describes a cross-orchestrator lock. On Track B, the B4 mapping flags at least eight of the nineteen concepts the pipelines use today as Dagster's own model rather than a neutral one. The Declarative Pipelines features that make Databricks attractive (expectations, AUTO CDC, the event log) are exactly the ones missing from open-source Spark ([Databricks: Python reference](https://docs.databricks.com/aws/en/ldp/developer/python-ref)). This is an options study: it gives no recommendation and no ranking.

## How to read the grades and versions

Every claim carries one of five grades. **[F] first-hand** means a practitioner report with an outcome. **[D] documented** means a vendor document, specification or source code, with version or page date. **[I] inferred** is reasoning, and is labelled as such. **[L] lead** means only a search extract was seen, so it is not verdict evidence. **[U] unreachable** marks a source that could not be fetched. Items older than about two years (before 2026-10-27 minus two years) are flagged **[>2y]**. Dagster claims are pinned to **1.13.27 (2026-10-26)**, the latest release. They come from the CHANGES.md changelog, a source checkout at commit 8b9a41d (2026-10-27) and the live docs showing "Latest (1.13.27)". Release dates come from PyPI ([PyPI dagster JSON](https://pypi.org/pypi/dagster/json)). Databricks claims carry each page's own "Last updated" date. Pages fetched on 2026-10-27 often show "Sep 11, 2026", which probably marks a bulk rename rather than a content change [I]. The Databricks product names changed again in 2026. Databricks Asset Bundles are now "Declarative Automation Bundles" ([Databricks: bundles](https://docs.databricks.com/aws/en/dev-tools/bundles/)). Lakeflow Declarative Pipelines are now "Lakeflow pipelines" ("Spark Declarative Pipelines on Lakeflow") ([Databricks: LDP landing](https://docs.databricks.com/aws/en/ldp/)). This report keeps the brief's term "Declarative Pipelines" (LDP).

The biggest weakness in the evidence is the lack of first-hand reports. **No first-hand report was found of anyone moving operational state out of Dagster, migrating Dagster to Databricks, running a cross-orchestrator lock, or keeping an in-house neutral layer through an orchestrator change.** The Dagster community forum was unreachable (DNS failure) and GitHub issue search was refused [U]. Background from the earlier sweep on another branch is used only where marked **[earlier sweep]** and was not re-verified here. It covers four points: Components/`dg` GA in 1.12 (2025-10-30); API removals in 1.13.0 (2026-04-09); storage migrations in 1.9.0; and Dagster Pipes on Databricks serverless, which couples external code to `dagster_pipes` and UC Volumes, where plain `jobs.run_now` does not.

The five symptoms from the original context are cited below as **Sy1** (feed logic stuck in orchestrator code), **Sy2** (landing steps copy-pasted), **Sy3** (vendor shapes leaking into the generic layer), **Sy4** (DQ checks across engines with different semantics) and **Sy5** (adding a feed means releasing the image that carries every feed). The original brief's RQ1–RQ5 numbering is not on this branch. Links back to those themes therefore go through the symptoms and the context.

## Track A: every state kind has three homes, and only two survive a second orchestrator

### A1. Where each kind of state can live, and what each home costs

Each of the seven state kinds can live in the orchestrator's event log and instance database (today's arrangement), in a platform-owned ledger in Postgres, or derived from the data itself (DuckLake snapshot metadata, object-store listings, the kept delivery bytes). Practitioner patterns exist for the ledger option, but the evidence for them is documentation, not outcome reports.

- **Watermark/control table.** Microsoft's Data Factory template defines "an external control table that stores a high-watermark value". The copy runs `WHERE TIMESTAMP_Column > last AND <= current`, and a stored procedure then writes the new watermark back ([Microsoft Learn, 2024-10-03, updated 2026-08-05](https://learn.microsoft.com/en-us/azure/data-factory/solution-template-delta-copy-with-control-table)) [D].
- **Audit tables in a customer-owned database.** BimlFlex writes row-count, audit-row and execution tables with parent/child execution records into the customer's own database. It argues that "nothing depends on a vendor runtime staying online to read it later" ([Varigence, 2026-06-19](https://www.varigence.com/blog/row-level-reconciliation-audit-evidence-bimlflex-writes-to-your-own-database)) [D, vendor, no regulation cited].
- **Counter-example: dbt failure tables are not a history.** `store_failures` "will always replace previous failures for the same test" ([dbt docs, updated 2026-07-18](https://docs.getdbt.com/reference/resource-configs/store_failures)) [D]. `run_results.json` exists per invocation only ([dbt docs](https://docs.getdbt.com/reference/artifacts/run-results-json)) [D].
- **Audit-Balance-Control (ABC).** ABC frameworks (batch IDs, per-step audit counts, restartability "control") were seen only as search leads ([XTIVIA](https://www.xtivia.com/blog/etl-audit-balance-control-recommendations/)) [L].
- **Fabric control/audit table.** A Microsoft Fabric post on this pattern was unreachable (HTTP 403) ([Fabric blog](https://blog.fabric.microsoft.com/blog/demystifying-data-ingestion-in-fabric-fundamental-components-for-ingesting-data-into-a-fabric-lakehouse-using-fabric-data-pipelines)) [U].

On the derived-from-data side, DuckLake keeps `ducklake_snapshot` and `ducklake_snapshot_changes` with `author`, `commit_message` and `commit_extra_info`, which `set_commit_message` can set inside a transaction. DuckLake also documents snapshot expiry ([DuckLake: snapshots](https://ducklake.select/docs/stable/duckdb/usage/snapshots); [ducklake_snapshot_changes](https://ducklake.select/docs/stable/specification/tables/ducklake_snapshot_changes)) [D; the DuckLake version was not captured].

All the ledger options share one inferred precondition: a **single delivery identity key** (`delivery_id`, for example a hash of feed, vendor identifier and content sha256) that every other table references. Without it, verdicts, waivers and arrival decisions cannot be joined across orchestrators [I]. The table below lists each option. The orchestrator-native facts in it are documented; the ledger and derived designs are inferred unless a source is cited.

Not all of this state is evidence in the same sense. On inference only (no regulatory text was fetched), four kinds answer the firm's audit questions directly. Landed deliveries answer "what was received, when, from whom". Gate verdicts show that a control operated. Acknowledgements show a human override, with its actor. Late/missing decisions show vendor oversight. Backfill requests answer "what was derived and why it changed". Cursors, pool limits and schedule toggles are operational control state, with evidential value only as change history. That matters because orchestrator retention is short or configurable. Dagster OSS keeps skipped sensor ticks for seven days by default and purges other ticks per `purge_after_days`. Runs and events are never auto-purged ([oss-instance-configuration.md @8b9a41d](https://raw.githubusercontent.com/dagster-io/dagster/8b9a41d13e2d22b87d38160bf7332a3ab36f3d70/docs/docs/deployment/oss/oss-instance-configuration.md)) [D]. Databricks keeps run history for 60 days and recommends "exporting results before they expire"; system tables keep 365 days ([monitor](https://docs.databricks.com/aws/en/jobs/monitor); [system tables](https://docs.databricks.com/aws/en/admin/system-tables/jobs)) [D]. Multi-year record-keeping periods for asset managers are assumed from memory and are **unsourced**.

### A2. What Dagster OSS 1.13.27 lets you export, and what is lost

Dagster keeps all seven kinds in its own tables. The run storage tables are `runs`, `run_tags`, `bulk_actions`, `backfill_tags` and a `kvs` table that also holds daemon cursors. The event log tables are `event_logs`, `asset_keys`, `asset_check_executions`, `dynamic_partitions`, `concurrency_limits`, `concurrency_slots` and `pending_steps`. The schedule storage tables are `instigators`, `job_ticks` and `asset_daemon_asset_evaluations` ([runs/schema.py](https://raw.githubusercontent.com/dagster-io/dagster/8b9a41d13e2d22b87d38160bf7332a3ab36f3d70/python_modules/dagster/dagster/_core/storage/runs/schema.py); [event_log/schema.py](https://raw.githubusercontent.com/dagster-io/dagster/8b9a41d13e2d22b87d38160bf7332a3ab36f3d70/python_modules/dagster/dagster/_core/storage/event_log/schema.py); [schedules/schema.py](https://raw.githubusercontent.com/dagster-io/dagster/8b9a41d13e2d22b87d38160bf7332a3ab36f3d70/python_modules/dagster/dagster/_core/storage/schedules/schema.py)) [D, source at 1.13.27]. Payload columns (`run_body`, `event`, `instigator_body`, `tick_body`, `body`) are Dagster-serialised documents. Decoding them outside Python Dagster means re-implementing that format [I; serdes not read]. The schema also moves between minor versions: 1.9.0, 1.9.3, 1.9.4, 1.9.12, 1.10.0/1.10.2 and 1.12.9 each required `dagster instance migrate` ([CHANGES.md](https://raw.githubusercontent.com/dagster-io/dagster/8b9a41d13e2d22b87d38160bf7332a3ab36f3d70/CHANGES.md)) [D; consistent with the earlier sweep's 1.9.0 storage-migration lead].

API stability frames all of this. The `@public` instance methods (`fetch_materializations`, `get_run_records`, `report_runless_asset_event`, `wipe_assets`, `delete_run`, the dynamic-partition methods) are the most stable surface. Even so, the docs place them under "Internals", whose submodule APIs "are not considered stable" ([dagster.io/docs internals](https://dagster.io/docs/api/dagster/internals)) [D, via a summarising fetch]. GraphQL "is still evolving and is subject to breaking changes" ([graphql/index.md](https://raw.githubusercontent.com/dagster-io/dagster/8b9a41d13e2d22b87d38160bf7332a3ab36f3d70/docs/docs/api/graphql/index.md)) [D]. Since 1.11.10 its log resolvers default to 1,000 rows per page [D].

Dagster's own answer for moving history to Dagster+ is a sample job, not a feature. The migration guide says Dagster+ metadata "will be empty". The `oss-metadata-to-plus` example re-posts recent materialisations through REST "as new external assets" ([oss-to-dagster-plus.md](https://raw.githubusercontent.com/dagster-io/dagster/8b9a41d13e2d22b87d38160bf7332a3ab36f3d70/docs/docs/migration/oss-to-dagster-plus.md); [example README](https://raw.githubusercontent.com/dagster-io/dagster/8b9a41d13e2d22b87d38160bf7332a3ab36f3d70/examples/oss-metadata-to-plus/README.md)) [D]. Two traps for anyone reading state back:

- `dagster asset wipe` is logical. It clears the asset index and deletes check executions but leaves `event_logs` rows in place ([sql_event_log.py](https://raw.githubusercontent.com/dagster-io/dagster/8b9a41d13e2d22b87d38160bf7332a3ab36f3d70/python_modules/dagster/dagster/_core/storage/event_log/sql_event_log.py)) [D].
- 1.13.10 fixed `get_latest_materialization_event` returning a stale pre-wipe record [D].

A whole-instance `pg_dump`/restore at the same Dagster version would carry everything [I; no doc states it]. Two discuss.dagster.io migration threads were **unreachable** [U].

### A3. Two orchestrators, one platform: the only verified rule is one active scheduler per feed

The verified record on dual running is short:

- **Robinhood (2019).** Moved Airflow 1.7 to 1.10 by building a second cluster rather than upgrading in place. Each DAG existed in both clusters during the move. The per-DAG handshake was: pause on the old cluster after its latest run, add to the new cluster with a static `start_date` equal to the next execution date, unpause, with backfills off by default. The outcome was "a couple of weeks" and "without any major issues or downtime". Idempotency was named as the ideal backstop, and non-idempotent tasks needed special care ([Robinhood](https://robinhood.com/newsroom/upgrading-scaling-airflow-at-robinhood/)) [F, **>2y**].
- **Google Cloud Composer (2026).** The current vendor equivalent of the same handshake. It notes that a DAG unpaused in both environments "runs its own copy", and that catchup "might lead to a large number of DAG runs" ([Composer, updated 2026-10-26](https://docs.cloud.google.com/composer/docs/composer-3/migrate-airflow-3)) [D].
- **Dagster Airlift.** Switches execution per DAG or per task with a `proxied` flag in YAML. - **Databricks (2026).** The guidance says "most teams migrate incrementally" and Lakeflow Jobs "is designed to coexist", but it gives no cutover mechanics ([Databricks blog, 2026-03-18](https://www.databricks.com/blog/how-move-apache-airflowr-databricks-lakeflow-jobs)) [D].
- **YipitData (2022).** Moved 600+ DAGs to Databricks Workflows with a script and called it "relatively smooth". Its tasks were already Databricks notebooks, so only the scheduler moved ([Databricks/YipitData](https://databricks.com/blog/why-we-migrated-apache-airflow-databricks-workflows-yipitdata)) [F, vendor co-published, **>2y**].
- **Unverified.** A 2-week dual run with reconciliation, then 1 week with Databricks primary, was reported in a Medium post that was **unreachable** ([Medium](https://medium.com/@nidhi2505/from-chaos-to-clarity-our-migration-journey-from-aws-airflow-to-databricks-fd6d95479394)) [U].

### A4. What the orchestrator still has to know once state leaves it

Five things stay with the orchestrator [I]:

- the static asset/job graph (lineage, step order);
- schedules and triggers, plus which feeds it owns (an ownership check at tick time);
- a trigger signal, either its own sensor (now reading the ledger) or a push;
- enough to block downstream work, either the gate function in every step or mirrored check results;
- its run identity, stamped into ledger rows as `run_ref` so the ledger links back to orchestrator logs.

Dagster's native views all key on its own events. Freshness evaluates materialisations only ([freshness docs](https://docs.dagster.io/guides/observe/asset-freshness-policies)) [D]. `all_deps_blocking_checks_passed` reads Dagster check records [D]. External assets need "an external system [to] inform Dagster" ([external assets](https://docs.dagster.io/guides/build/assets/external-assets)) [D]. So with truth in a ledger and nothing mirrored back, the following happens [I]:

- the materialisation timeline empties;
- the check UI and asset health go stale;
- freshness views fire falsely or must be switched off;
- Declarative Automation conditions such as `newly_updated` stop firing;
- backfill partition status disagrees with the ledger;
- pool views show nothing about ledger leases;
- sensor cursors shown in the UI are no longer authoritative.

On Databricks less is lost, because Lakeflow has no asset-level check or freshness model to begin with. A ledger mainly costs a dashboard over `ops.*` in place of native views [I].

| Mitigation | Mechanism | Costs and failure mode | Neutrality effect | Grade |
|---|---|---|---|---|
| M1 Pull mirror | A Dagster sensor reads ledger rows since the last sequence number and emits `AssetMaterialization`/`AssetCheckEvaluation`/`AssetObservation` through `SensorResult` [D mechanism] | Second cursor. Lag of at least one sensor interval. UI lies when the mirror stalls → mirror-lag metric | All writes originate inside Dagster, which avoids the unauthenticated REST path | [D]/[I] |
| M2 Push via REST | The ingestion library POSTs to `/report_asset_*` after the ledger commit, with an outbox for retries ([REST API](https://docs.dagster.io/api/rest-apis/external-assets-rest-api)) [D] | Non-atomic dual write. OSS endpoints are unauthenticated, so ingress or network policy is needed | The only option that also lets Databricks-run feeds appear in Dagster as a "single pane" during migration | [D]/[I] |
| M3 In-process `report_runless_asset_event` | Code with instance access writes events (public since 1.5.9, 2023-11-16, **[>2y]**) [D] | Couples the writer to the Dagster instance DB | Works against neutrality | [D]/[I] |
| M4 Databricks side | Job parameters carry `delivery_id`. `job_run_timeline` (365 days) joins to `ops.load.run_ref` [D capabilities] | No place to write check verdicts back. The ledger is the UI | Neutral | [I] |
| M5 Mirror as cache only | Gates read the ledger, never Dagster. Mirrored events carry `source=ledger, ledger_id` | Two representations of truth, event-log growth, coupling to Dagster event APIs, whose semantics moved in 1.13.7 [D] | Divergence becomes detectable | [I] |

## Track B: the neutral line runs between feed facts and orchestrator runtime

### B1. Logic in plain modules, with EL contracts that differ on who owns state

The EL libraries are already built to run without an orchestrator, with the orchestrator integration as a thin wrapper:

- **dlt** resources are plain generators run by `dlt.pipeline(...).run()` ([dlt docs: state](https://raw.githubusercontent.com/dlt-hub/dlt/devel/docs/website/docs/general-usage/state.md)) [D, dlt 1.31.0, 2026-10-07].
- **dagster-dlt** wraps a source with `yield from dlt.run(context=context)` ([dlt: deploy with Dagster](https://raw.githubusercontent.com/dlt-hub/dlt/devel/docs/website/docs/walkthroughs/deploy-a-pipeline/deploy-with-dagster.md)) [D].
- **The Dagster dlt Component** generates a `loads.py` that "can also be run directly using dlt" ([Dagster dlt component](https://raw.githubusercontent.com/dagster-io/dagster/master/docs/docs/integrations/libraries/dlt/index.md)) [D, 1.13.x].
- **Dagster's component tests** (`create_defs_folder_sandbox`, `load_component_and_build_defs`) check only that definitions load and asset keys come out as expected ([testing your component](https://github.com/dagster-io/dagster/blob/master/docs/docs/guides/build/components/creating-new-components/testing-your-component.md)) [D].

That supports a three-layer split [I]: feed-specific parse and normalise functions that take bytes in and give records out (Sy1, Sy3), tested with pytest on recorded fixtures; an EL runner, tested against local DuckDB or DuckLake; and a thin orchestrator shell with only an asset-key test. What still needs orchestrator-level integration tests is asset-key mapping to dbt sources, automation conditions, partition and backfill semantics, secret wiring, and overlap of same-named pipelines [I]. Early warning sign: a parse or landing test that needs `dagster.materialize()`, or feed code importing `dagster` outside its definitions module [I]. No first-hand source applies "functional core / imperative shell" or hexagonal architecture to orchestrated pipelines with an outcome.

For declarative definitions compiled by an adapter, the options are:

- **Dagster Components YAML.** Dagster-only. The earlier sweep found GA in 1.12 and API removals in 1.13.0 [earlier sweep].
- **Declarative Automation Bundles on Databricks.** A bundle holds source files "that include the business logic" plus tests ([Databricks bundles, 2026-09-11](https://docs.databricks.com/aws/en/dev-tools/bundles/)) [D].
- **Dagster's bridge to bundles.** `DatabricksAssetBundleComponent` is **preview** ([Dagster docs](https://github.com/dagster-io/dagster/blob/master/docs/docs/integrations/libraries/databricks/databricks-asset-bundle-component.md)) [D].
- **Airflow-only YAML generators.** dag-factory 1.1.0 (2026-05-07) and gusty 0.23.1 (2025-05-14) ([dag-factory README](https://raw.githubusercontent.com/astronomer/dag-factory/main/README.md); [gusty README](https://raw.githubusercontent.com/pipeline-tools/gusty/main/README.md)) [D].

An in-house `FeedSpec` compiled to both Dagster and bundle YAML keeps the exit cost inside one adapter. Its failure mode is drifting into orchestrator concepts. The early warning is spec fields named after one orchestrator's API [I]. dbt is the working precedent: both orchestrators consume the same project [I].

### B5. Declarative Pipelines: what not using them costs, and what using them commits to

Its imports, `@dp.table`, `@dp.materialized_view`, `@dp.temporary_view`, `@dp.append_flow`, SQL flows and `create_sink` "run without modification on Databricks". ## How the questions depend on each other

The tracks are tightly coupled [I]. The A1 ledger tables (delivery, check result, waiver, cursor lease, feed control) are the same objects A3 needs for ownership switching (S3), double-run prevention (D2, D3, D5) and cross-orchestrator dependencies (X6). The ledger is therefore one build that answers four sub-questions, or none. A4's feature losses are the price of B3's "keep decided-on state neutral" row. They are concentrated in exactly the B4 rows marked [DM] or NO-EQ (4, 5, 9, 11, 12): the Dagster features that are hardest to give up are the ones Databricks lacks anyway. That limits what a mirror (M1–M2) buys after the migration ends.

B5 depends on A1 in both directions. Option C's expectations and event log cover part of the gate-verdict and row-metadata need, but only inside Databricks. `fail` records no metrics, and there is no manual result. Option A has to rebuild those functions in the ledger.

The storage decision, still open in the original context (DuckLake vs Delta/UC), runs through several answers:

- A3 C1–C5 (consumer unawareness);
- X1–X2 (UC-only triggers);
- B1 (a dlt destination change resets incremental state);
- B4 row 16 (UC lineage misses DuckLake tables);
- B5 C (LDP outputs are UC-managed Delta).

With DuckLake retained, Databricks can join only as a runner of DuckDB code. With UC as the target, the dual-run period also becomes a dual-catalog period.

Back to the original themes:

- **Auditability:** A1's evidence classification and the retention limits.
- **Sy1 and Sy5:** answered by B1's layering and illustrated by B2's Spotify case.
- **Sy2 and the bytes-kept requirement:** the same landing step as the A1 delivery ledger (B1).
- **Sy3:** B1's parse layer. None of the EL contracts prevents vendor shapes leaking.
- **Sy4:** A1 row 1b and B3's check-logic row, both set against B4 row 4's three different blocking semantics (Dagster same-run, LDP per-flow rollback, Jobs task failure).

## Conclusion

Asking where pipeline logic should live turns out to be the easier half of the problem. Every EL contract and both orchestrators already allow plain-module logic behind a thin wrapper. The harder half is *decided-on state*: the evidence a regulated firm needs is today held in the system that is about to be replaced, in serialised, version-migrated tables whose history cannot be re-imported with its original timestamps. Dual running makes the question unavoidable rather than optional. While both orchestrators can launch a feed, whatever gates, de-duplicates or rate-limits that feed must sit somewhere both can read.

The concept map also reframes "neutral". A model can be neutral toward Databricks only by giving up the asset-centric features that make Dagster valuable today (partitions, cross-run verdicts, staleness), because Databricks has no counterpart for them. Declarative Pipelines repeats the same pattern on the other side, with its distinctive value in the parts that open-source Spark lacks. The trade-off the evidence exposes is between two costs. One is owning a small set of ledger tables plus mirrors. The other is accepting that each orchestrator's richest features stay behind when it is replaced.
