# Plain Postgres reroutes Databricks and sharpens evidence duties

With the lake corrected to plain Postgres, Databricks no longer joins "only as a runner of DuckDB code". It can reach the lake natively, but the reach is lopsided. **Governed reads** come through Lakehouse Federation (GA, read-only, live pushdown, table-level Unity Catalog grants) or through Lakeflow Connect copies into Delta. The PostgreSQL CDC connector is still **Public Preview** (since 2025-12-16); the query-based connector went GA on 2026-05-29. **Writes** go only through JDBC: a Unity Catalog JDBC connection (GA 2026-10-02 on DBR 19+, governed only at connection level) or plain Spark JDBC and psycopg, which UC does not govern at all ([Federation PostgreSQL, 2026-10-06](https://learn.microsoft.com/en-us/azure/databricks/query-federation/postgresql); [JDBC connection, 2026-10-05](https://learn.microsoft.com/en-us/azure/databricks/connect/jdbc-connection)). Serverless compute reaches a private Flexible Server directly only if that server uses the "public access" networking mode, because private endpoints are not supported on VNet-integrated servers ([PG Private Link, 2026-07-13](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-networking-private-link)). No Databricks trigger fires on a Postgres change. Consumer unawareness still works through Postgres views, but views bind to tables rather than names, so the swap has to be a view redefinition or a partition attach. dbt's `table` materialization and Spark JDBC overwrite both break that by dropping tables. On retention, no Swiss or EU text names pipeline records. Two Swiss 10-year anchors (OR 958f with GeBüV, and AMLA Art. 7) and the EU 5-year minimums (UCITS, AIFMD, MiFIR) attach only where a record is classified as a voucher, an AML document or a "key stage of the processing" of a transaction. DORA's logging RTS leaves log retention to the entity. **A 60-day run history or a 365-day system table can therefore meet only entity-set or purely operational duties.** It meets no 5-year or 10-year duty. The records the team does not yet store (check-verdict history, waivers with an actor, backfill requests, feed ownership) are exactly the ones the texts point to a firm-controlled store for. **This is not legal advice.** Every classification that decides which period applies is marked for legal or compliance confirmation. This is an options study: it gives no recommendation and no ranking.

## C1: six Databricks routes reach Postgres, and only JDBC writes

## C2: serverless needs an NCC route, and VNet integration blocks the direct one

Classic and serverless compute reach a private Postgres in different ways. **Classic** compute is VNet-injected and uses ordinary Azure networking. The Azure side needs VNet peering (direct or through a hub), a link from the Postgres private DNS zone to the Databricks VNet, and NSG allowance on port 5432 ([VNet inject, 2026-10-09](https://learn.microsoft.com/en-us/azure/databricks/security/network/classic/vnet-inject); [PG private access, 2026-07-13](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-networking-private)) [D]. Federation traffic "is directly between Azure Databricks clusters (or SQL warehouses) and the external database system" ([federation networking, 2026-10-13](https://learn.microsoft.com/en-us/azure/databricks/query-federation/networking)) [D]. **Serverless** has no VNet of its own, so it reaches private resources only through account-level network connectivity configurations (NCCs) ([serverless private link, 2026-10-16](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/serverless-private-link)) [D]. The Lakeflow Connect gateway "must run on classic compute", so CDC needs a classic path even in an otherwise serverless estate ([limits](https://learn.microsoft.com/en-us/azure/databricks/ingestion/lakeflow-connect/postgresql-limits)) [D].

The decisive precondition sits on the Azure side. Azure Database for PostgreSQL Flexible Server is on the NCC supported-resources list ([manage PE rules, 2026-10-09](https://learn.microsoft.com/en-us/azure/databricks/security/network/serverless-network-security/manage-private-endpoint-rules)) [D]. But Microsoft states that "the use of private endpoints isn't currently supported on servers created with virtual network integration". The server must use public-access networking mode, with public access then disabled ([PG Private Link, 2026-07-13](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-networking-private-link)) [D]. The in-place conversion is **[preview]**. It "typically takes about 20 minutes", the server is inaccessible for about 10, and afterwards it stays inaccessible until a private endpoint or firewall rule exists ([migrate VNet→PE, 2026-09-15](https://learn.microsoft.com/en-us/azure/postgresql/network/how-to-migrate-vnet-private-endpoint-capable-server)) [D]. If the existing server is VNet-integrated, this networking-mode decision is the most expensive part of C2 to reverse [I].

## C3: no trigger watches Postgres, so a change must become a UC object or a call

Table-update triggers watch "Unity Catalog Delta and Iceberg managed tables, Unity Catalog external tables backed by Delta Lake, materialized views, streaming tables, and Unity Catalog views or metric views that depend on supported tables", plus OpenSharing objects and system tables. Views that "depend on federated tables" or on non-UC tables are explicitly unsupported, and creating a trigger on one "still succeed[s], but no job runs are triggered" ([table update, 2026-10-05](https://learn.microsoft.com/en-us/azure/databricks/jobs/trigger-table-update)) [D]. Foreign tables are absent from the list. That a direct foreign-table trigger is unsupported is therefore inference and untested [I]. File-arrival triggers watch only UC volumes and external locations ([file arrival, 2026-10-07](https://learn.microsoft.com/en-us/azure/databricks/jobs/file-arrival-triggers)) [D]. View sources were added on 2025-11-17. OpenSharing and system-table sources went from Beta (2026-06-03) to GA (2026-09-30). No GA date for the triggers themselves was found ([RN Nov 2025](https://learn.microsoft.com/en-us/azure/databricks/release-notes/product/2025/november); [RN Sep 2026](https://learn.microsoft.com/en-us/azure/databricks/release-notes/product/2026/september)) [D].

| Route | Mechanism | Latency (only the documented figures are documented) | Failure mode → early warning | Exit cost |
|---|---|---|---|---|
| **CDC streaming table as trigger source** | Lakeflow Connect writes streaming tables, which are a supported source | Pipeline schedule (≥5 min recommended) plus start-up plus evaluation and debounce [I from D] | Connector is **[preview]**. A full refresh after failover or DDL fires a burst of runs [I]. A partial initial load can fire downstream on incomplete data [D] | Full Lakeflow Connect exit [I] |
| **Query-based streaming table** (GA) | As above with cursor ingestion | Schedule period [I] | Cursor skips [I] | Low [I] |

| **Marker file / Blob manifest** | Register the archive container as a UC external location; the manifest written last becomes the marker | "Best effort to check for new files every minute" [D] | Overwritten names do not trigger. The only documented latency figures are "every minute" (file arrival), "<60 seconds" (continuous gap) and "5 minutes" (CDC recommendation). None is an SLA. If storage later moves to Delta, table-update triggers apply directly to the curated tables, and these workarounds fall away [I].

## C4: two orchestrators on shared Postgres tables collide where tables are dropped

The earlier C1–C5 analysis carries over in a Postgres form. The table is the re-run. Postgres also supplies mechanisms the DuckLake analysis did not have.

| Earlier option | Postgres status | What breaks | What still applies |
|---|---|---|---|
| C1 stable published views | Applies | The swap target. Views bind to the underlying relation (by OID, [I]), so a rename-swap leaves them on the old table. Incompatible column changes need DROP + CREATE VIEW, which consumers can see, and grants must be reissued. Grants survive `CREATE OR REPLACE` ([PG17 CREATE VIEW](https://www.postgresql.org/docs/17/sql-createview.html)) [D] | View redefinition inside a transaction; partition-per-delivery DETACH/ATTACH under SHARE UPDATE EXCLUSIVE ([PG17 partitioning](https://www.postgresql.org/docs/17/ddl-partitioning.html)) [D] |
| C2 one dbt project, two runners | Applies only with dbt-postgres on both | The `table` materialization renames, commits, then drops the backup with `cascade` ([dbt-adapters table.sql, main 2026-10-27](https://raw.githubusercontent.com/dbt-labs/dbt-adapters/main/dbt-adapters/src/dbt/include/global_project/macros/materializations/models/table.sql); [drop.sql](https://raw.githubusercontent.com/dbt-labs/dbt-adapters/main/dbt-adapters/src/dbt/include/global_project/macros/relations/drop.sql)) [D]. Consumer views on the old table vanish. A 2019 forum case: "dbt is forced to use the cascade qualifier", and "on Postgres, there's no equivalent feature" to late-binding views ([dbt forum](https://discourse.getdbt.com/t/why-are-my-views-being-dropped-when-the-incremental-model-it-refs-is-being-updated/689)) [F, >2y] | Incremental models (append, merge, delete+insert, microbatch) update in place ([Postgres configs](https://docs.getdbt.com/reference/resource-configs/postgres-configs)) [D]. Contracts enforce not_null, PK, FK, unique and check on Postgres, but the per-platform matrix extraction was ambiguous, so it needs re-checking ([model contracts](https://docs.getdbt.com/docs/mesh/govern/model-contracts)) [D] |
| C3 write-audit-publish | Applies | — | Staging table → reconcile → MERGE/upsert plus run-log row → view repoint, all in one transaction [I] |
| C4 catalog indirection into UC | Changes meaning | No refresh lag to manage. Federation is live and read-only [D] | Databricks reads the lake; Postgres consumers see no change |
| C5 UC as the single writer | Changes meaning | Meaningless while storage is Postgres [I] | Becomes the C5 migration question |

**A Spark JDBC write is not one transaction.** `savePartition` commits each DataFrame partition separately, after the truncate or drop has already committed on a separate driver connection ([JdbcUtils.scala v4.0.1](https://raw.githubusercontent.com/apache/spark/v4.0.1/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/jdbc/JdbcUtils.scala)) [D]. Overwrite mode drops and recreates the table unless `truncate=true`. That discards dbt's indexes, grants and constraints, and with dependent views the drop fails outright [I from D]. With truncate, TRUNCATE takes ACCESS EXCLUSIVE and "is not MVCC-safe", so readers can see an empty or half-loaded table until the last partition commits ([PG17 TRUNCATE](https://www.postgresql.org/docs/17/sql-truncate.html)) [D/I]. Whether truncate is honoured for Postgres at all is itself disputed (see the conflicts section). Concurrent Spark append and Dagster upsert either block on row locks or fail on PK violations if there is a unique index; without one they duplicate [I]. The JDBC writer has no MERGE save mode, so keyed upserts need a staging table plus SQL from a driver-side connection, which is the KB pattern [D/I].

The **single-writer mechanisms** differ in what Postgres enforces. Per-orchestrator database roles with GRANTs switched per feed are the only one Postgres itself enforces [I]. `pg_try_advisory_xact_lock(hash(feed_id))`, taken in the writing transaction, releases on commit or rollback, so a crashed job leaves no stuck lease. But "the system does not enforce their use" ([PG17 locking](https://www.postgresql.org/docs/17/explicit-locking.html); [PG17 admin functions](https://www.postgresql.org/docs/17/functions-admin.html)) [D]. A feed-ownership row checked with `SELECT … FOR UPDATE` holds only by convention unless a trigger compares `current_user` with the owner [I]. Delivery-id keyed `ON CONFLICT` makes double runs converge. One caveat: during `CREATE INDEX CONCURRENTLY` on the unique index, upserts "may unexpectedly fail with a unique violation" ([PG17 INSERT](https://www.postgresql.org/docs/17/sql-insert.html)) [D]. Early warnings are all observable in Postgres [I]:

- target-table OIDs that changed (a drop and recreate happened);
- indexes or constraints missing after a run;
- per-delivery row counts that differ from the manifest;
- two `application_name`s writing one feed table, or holding its advisory lock;
- run-log rows from both orchestrators for the same delivery id.

No first-hand report covers advisory-lock leases between Dagster and Databricks, or mixed Spark-JDBC and Python writers on one table.

A 2023 forum request to port dbt-postgres to dbt-databricks has no answer ([forum](https://discourse.getdbt.com/t/how-to-migrate-your-dbt-project-from-dbt-postgres-to-dbt-databricks/7945)) [F attempt, no outcome, >2y]. Postgres dialect items (`DISTINCT ON`, JSONB operators, `generate_series`) are inferred, not verified |

For the **two-store period**, Databricks documents a reverse sync from UC into Postgres only into **Lakebase**. Synced tables are GA; only additive schema changes are allowed in Triggered and Continuous mode; and `databricks_superuser` can write to synced tables "in case you need to make urgent changes" ([synced tables, 2026-10-22](https://learn.microsoft.com/en-us/azure/databricks/oltp/projects/sync-tables)) [D]. No documented path syncs into an arbitrary Azure Database for PostgreSQL, and no documented way lets a Postgres view read Delta. Four two-store options follow, all [I] and none ranked:

- **(a) Delta master with a JDBC reverse write** (staging, then MERGE) into the table behind the consumer view. Consumers stay unaware, and the Postgres copy is derived.
- **(b) Consumers move to Lakebase.** They switch endpoint, so they are not unaware.
- **(c) Dual-write.** There is no cross-store transaction, so reconciliation must catch divergence.
- **(d) Postgres stays master** and Delta is derived through federation or Lakeflow Connect.

Each has audit consequences [I]:

- the ops schema must record per feed which store is master;
- the run log must carry both the producing run and the sync run;
- reconciliation per delivery must check type-mapping losses (TIMESTAMP and NUMERIC over 38 to string);
- the publication calendar must reference when the *Postgres* copy is ready;
- a Lakebase superuser write is an integrity exception to log.

No practitioner report with an outcome on Postgres-to-Delta migration was readable. Three were **[U]** (403), and a dbt Labs migration skill was not located.

### D2: a vendor-held log meets only entity-set and operational duties

Reading the four tables together, the answer to D2 splits three ways, all inferred from the documented periods. **No vendor-only store of 60 or 365 days can meet** any duty with a fixed multi-year period. That covers OR 958f with GeBüV (10 years, including GeBüV Art. 9 log files and Art. 4 work instructions), AMLA Art. 7 (≥10 years), and UCITS, AIFMD and MiFIR (≥5 years). It covers the "pre-amendment content ascertainable" tests too, unless the vendor store guarantees them for the full period. **A 365-day store can meet the length** of the DSV Art. 4 one-year minimum, but probably not its "getrennt vom System" separation if the table sits inside the processing platform. **Either store can meet** DORA RTS Art 12 logging and Art 8 operations records if the entity's documented, risk-assessed retention is no longer than the vendor period. It can also serve purely operational troubleshooting, for which no text requires retention. Even then, DORA Art 30(2)(b)–(d) and (3)(e)–(f) require contract terms for data locations, access, recovery and return, audit, and exit ([DORA](https://publications.europa.eu/resource/celex/32022R2554)) [D]. FINMA 2018/3 requires inspection rights and Swiss access where a significant function is outsourced [D].

The trigger is the classification, not the tool. A run log or check result that is *only* operational falls on the permissive side. The same row becomes subject to 5 or 10 years once it is the sole evidence that a vendor price behind a NAV was received and validated **⚠ D3**. Two nuances follow [I]. Dagster OSS is self-hosted, so its instance database is firm-controlled storage that never auto-purges runs, and its limits are format and meaning (serialised tables, internal history APIs, no actor field), not retention. Databricks run history (60 days) and system tables (365 days) are vendor-controlled purges ([monitor](https://docs.databricks.com/aws/en/jobs/monitor); [system tables](https://docs.databricks.com/aws/en/admin/system-tables/jobs)) [D, from R1].

## Cross-dependencies: Track C decides where Track D's records can live

The two tracks meet wherever a record that Track D may bind for 5 or 10 years is produced or touched by a Track C mechanism. All statements in this section are [I] unless a source is cited.

**Run history versus multi-year duties.** Databricks run history (60 days) and `system.lakeflow` tables (365 days) are shorter than every fixed period in Track D [D, from R1]. The Lakeflow Connect staging volume deletes after 25 days ([maintenance](https://learn.microsoft.com/en-us/azure/databricks/ingestion/lakeflow-connect/postgresql-maintenance)) [D]. Any Databricks run that produces evidence under a 5- or 10-year duty therefore needs its identity and outcome copied into a firm-controlled record before expiry. The existing Postgres run log, keyed by job run id and delivery id, is the store already in place, and it joins to `job_run_timeline` for the first 365 days.

**Where a firm-controlled Postgres record is the only option among those examined.** For **waivers with an actor and approver**, neither orchestrator offers a field (Dagster manual results carry no actor; Databricks has no equivalent), yet DSV 3(3)(a), RTS 21(c) user accountability and 72(1)(b) pre-amendment content all point at who-and-when evidence. For **check-verdict history beyond 365 days**, Dagster holds it only through an internal API and dbt `store_failures` overwrites. For **backfill requests with an approver** and **feed ownership over time**, no orchestrator table records intent or approval. Each of these is one of the five records the team does not store today. Firm-controlled Delta tables in the firm's own storage would be a second home for these records only after a C5 move. That widens the choice without ranking it.

**Writing evidence from Databricks into Postgres takes a JDBC path and a network path.** Federation cannot write. A Databricks job that records a verdict, waiver or run outcome in the ops schema must use the UC JDBC connection (GA only on DBR 19+, governed at connection level), plain Spark JDBC (not endorsed) or psycopg (ungoverned) (C1). It must also reach the server over S1, S2, S4 or a classic route (C2). Per-partition Spark commits are a poor fit for single evidence rows, so a driver-side SQL write is the shape that keeps one row per event.

**Form rules versus Postgres table mechanics.** GeBüV Art. 3 (changes detectable) and EU 72(1)(b), 16(3)(b) and 66(3)(b) (pre-amendment content ascertainable) conflict with mechanisms that drop or overwrite tables. dbt's `table` materialization drops the backup with cascade, Spark JDBC overwrite drops or truncates, and Lakeflow Connect SCD1 overwrites in place. Records in scope would need append-only or history-keeping tables (SCD2, or an event table). GeBüV Art. 9 also classes disks and SSDs as mutable media, so Postgres and Blob both need an integrity technique (hash or signature), a tamper-proof storage timestamp and kept logs. Whether the existing Blob manifests carry hashes is not stated in the brief.

**A Postgres-to-Delta move is itself a GeBüV media migration.** If the moved tables are in OR scope, GeBüV Art. 10 requires the transfer to preserve "completeness, correctness, availability and readability" and to be logged, with the log kept alongside the records. Lakeflow Connect's documented type losses breach correctness unless they are cast or recorded. Those losses are TIMESTAMP without time zone, TIME and MONEY to string, NUMERIC over 38 to string, and NaN to null ([limits](https://learn.microsoft.com/en-us/azure/databricks/ingestion/lakeflow-connect/postgresql-limits)) [D]. The two-store period's per-delivery reconciliation (C5) doubles as that transfer protocol, if it is kept.

**DSV separation and RTS clocks.** If the ops schema sits in the same database as the lake it describes, whether it is "getrennt vom System" is the same open question as for a Databricks system table **⚠ D3**. RTS 12(2)(f) clock synchronisation spans Dagster pods, Databricks compute and the Postgres server once timestamps from all three are compared in the run log.

**Outsourcing terms follow the system of record.** If Databricks run history or a Lakebase database became the only home of an evidential record, 2018/3 Rz 26–31, FinIO 17(4) and DORA Art 30 would attach to Databricks as provider. Copying evidence into the firm's Postgres or Blob archive keeps the vendor in the operational role. A Lakebase superuser write into synced tables would also be an integrity exception under GeBüV Art. 3.

**Triggers and evidence share an outbox.** An outbox table in Postgres that drives run-now calls (C3) is also a timestamped record of what was dispatched, when and for which delivery. Network policies (C2) and max-concurrency skips (C3) then appear as undispatched or skipped rows, which is the kind of failure-of-logging signal RTS 12(2)(e) asks firms to detect.

## Open: what could not be answered and what would settle it

**First-hand evidence is again almost absent.** No report with an outcome was found for any of the following: serverless to Azure PostgreSQL Flexible Server over NCC; Lakeflow Connect PostgreSQL on Azure; advisory-lock leases between two orchestrators; mixed Spark-JDBC and Python writers on one table; a Postgres-to-Delta migration; or an auditor's view of orchestrator-held evidence. A sandbox workspace against a copy of the server would settle the Databricks items. It would show whether the existing server is VNet-integrated, whether S1 or S2 carries traffic, whether Spark on DBR honours `truncate`, and whether federated reads appear in lineage.

**Databricks facts left open:** DBU rates for every option ([U], JavaScript pricing page); a GA date or roadmap for the PostgreSQL CDC connector; provider-side row filters or ABAC on foreign tables; whether audit logs record federated query text; behaviour of an SLB in front of a Flexible Server across failover; Lakebase regional availability; and a direct statement on foreign tables as trigger sources.

**Facts about the team's own records** decide several rows. These are: whether delivery offers and the run log are append-only and hashed; whether the reconciliation view's lateness decisions are persisted; what dataset assertions record; and where discovery cursors live today.

## Conclusion

The correction moves the hard part of a Databricks move from *compatibility* to *asymmetry*. DuckLake made Databricks a guest that could only run someone else's engine. Plain Postgres lets it in natively, but Unity Catalog governs what it reads more tightly than what it writes, and nothing on the Databricks side notices when Postgres changes. Any coexistence design therefore keeps Postgres as the one write target and the shared truth. The same Postgres features that make that work (views, partitions, transactional DDL, roles) are undone by the tools most likely to run against it, which drop tables to rebuild them.

Track D turns the earlier inference about evidence into a classification problem with known stakes. The texts do not ask for pipeline records as such. They ask for vouchers, AML documents and reconstructable transaction stages, with periods of 5 or 10 years and integrity tests that overwriting tables fail. The records the team has not yet built (verdict history, waivers with an actor, backfill approvals, ownership over time) are where a "yes" from compliance would bind hardest, and no vendor log examined can carry that weight alone. That makes D3's first three questions the cheapest way to narrow both tracks at once.
