# Shared decision state redraws the platform split

The evidence points to one finding the brief's four terms do not show. **Separating pipeline logic from the orchestrator is the cheap part. The expensive part is the state that pipelines decide on**: delivery landed, gate verdicts, waivers, lateness, cursors, rate limits and backfill intent. While two orchestrators run feeds side by side, that state can only live in a platform-owned ledger or in the data itself. All four extract-load contracts examined (dlt, Singer, Meltano, Airbyte) and both target orchestrators accept plain-module feed logic behind a thin wrapper. None of the four keeps raw delivery bytes for API sources, so landing and archiving stay a team-owned core step under every option. Dagster's most valuable asset-centric features are the ones Databricks has no counterpart for: partitions, cross-run check verdicts, manual check results, named concurrency pools and code-version staleness (five of nineteen concepts mapped). Binding to them is cheap today, and they are lost at migration whichever way the code is written. The evidence base is thin where the brief expected it to be. **No first-hand report describes a Dagster-to-Databricks migration, a cross-orchestrator lock, or an in-house neutral layer that survived an orchestrator change.** The only dual-run outcome is Robinhood's 2019 Airflow cluster move. Deploy independence in Dagster OSS (RQ3), handoff contracts beyond two vendor precedents (RQ4), topology beyond Dagster's own pros and cons (RQ5) and nearly all of RQ6 rest on inference, and each section says so at its top. This is an options study: it gives no recommendation and no ranking.

## How to read the grades, versions and sources

Every claim carries a grade. **[F] first-hand** is a practitioner report with an outcome. **[D] documented** is vendor documentation, a specification, a changelog or source code, given with version or page date. **[I] inferred** is reasoning, labelled as such. **[L] lead** means only a search extract was seen, so it is not verdict evidence. **[U] unreachable** marks a source that could not be fetched. **[>2y]** flags anything older than about two years (before roughly 2026-10-27). **[preview]** flags anything not generally available, including Beta, Public Preview, Early Access and experimental.

Dagster claims are pinned to **1.13.27 (2026-10-26)**, using the changelog, a source checkout and the live docs labelled "Latest (1.13.27)". One verifier in the broad sweep saw the docs index list 1.13.8; that inconsistency was not resolved. Databricks claims carry each page's own "Last updated" date. Many pages show Sep 11, 2026, which probably marks a bulk rename rather than a content change [I]. Databricks product names changed again in 2026. Asset Bundles are now "Declarative Automation Bundles" ([Databricks: bundles, Sep 11 2026](https://docs.databricks.com/aws/en/dev-tools/bundles/)). Lakeflow Declarative Pipelines are now "Lakeflow pipelines", built on Apache Spark Declarative Pipelines ([Databricks: LDP landing, Oct 22 2026](https://docs.databricks.com/aws/en/ldp/)). This report keeps the shorthand LDP.

The material comes from two research tracks. The first is a broad sweep that verified 22 claims, all from vendor documentation or tutorials, with no first-hand report. The second is the earlier follow-up study on orchestrator state and neutral pipelines, which this report draws on heavily for RQ1, RQ2 and part of RQ3. Its long tables (the seven-state placement table, the Dagster export table, the dual-run catalogue and the nineteen-row concept map) are summarised here and referred to as "the follow-up study". No new web research was done for this report.

The five observed symptoms are abbreviated as follows. **Sy1**: feed logic sits in orchestrator-specific code. **Sy2**: landing steps are copied per feed. **Sy3**: vendor shapes leak into the generic layer. **Sy4**: data-quality checks run in several engines with different outcome semantics. **Sy5**: adding a feed means releasing the image that carries every feed.

## The brief's four terms are cut in three wrong places

The brief invites a challenge to its terms, and the evidence supports one. The challenge rests on inference from documented facts; no source discusses these terms directly.

**First, decision state has no layer.** The brief defines core as feed-agnostic *mechanics* and the orchestrator as *machinery*. Neither covers the records pipelines decide on. The follow-up study found that Databricks has no store for cross-run check verdicts or manually recorded check results. It has no first-class partitions and no named cross-job concurrency pool. Its run history expires after 60 days ([Databricks: monitor jobs, Oct 15 2026](https://docs.databricks.com/aws/en/jobs/monitor)) [D]. Dagster keeps the same state in its own serialised tables, and every public re-import path stamps events with the import time and an empty run ID ([Dagster source @1.13.27](https://raw.githubusercontent.com/dagster-io/dagster/8b9a41d13e2d22b87d38160bf7332a3ab36f3d70/python_modules/dagster/dagster/_core/instance/methods/asset_methods.py)) [D]. During a feed-by-feed migration, a gate, a dedupe key or a rate limit that both orchestrators must honour therefore needs a home outside both [I]. That home is a fifth element, a **platform ledger** (delivery, check result, waiver, cursor lease, feed ownership). It can be assigned to core, but it is state rather than mechanics, and the regulated audit question ("what was received, when, from whom, what was derived") is answered there rather than in code [I].

**Second, "orchestrator" bundles runtime with observation.** Scheduling, launching, retries and isolation are runtime machinery. The brief's "observes" is different. Dagster's check UI, freshness views and Declarative Automation all key on Dagster's own events. Freshness, for example, is evaluated on materialisation timestamps only ([Dagster docs: freshness](https://docs.dagster.io/guides/observe/asset-freshness-policies)) [D]. When the facts move to a ledger, the *view* can stay with the orchestrator, but only if facts are mirrored back into it [I]. The line runs through the middle of "observes".

**Third, "ingest source" includes the fetch schedule, and that is exactly where practice splits.** The MetaOps write-up on Dagster with Airbyte puts it as "Dagster owns the clock, Airbyte owns the mechanics". It reports double scheduling unless Airbyte's own schedules are set to Manual ([MetaOps, 2026-09-10](https://metaops.solutions/blog/dagster-airbyte-integration-in-practice)) [F, partial]. The EL contracts also place incremental state differently: dlt keeps it in the destination, Singer leaves it to a runner, and Airbyte keeps it in its platform ([dlt docs: state](https://raw.githubusercontent.com/dlt-hub/dlt/devel/docs/website/docs/general-usage/state.md); [Singer SPEC](https://raw.githubusercontent.com/singer-io/getting-started/master/docs/SPEC.md); [Airbyte protocol](https://raw.githubusercontent.com/airbytehq/airbyte/master/docs/platform/understanding-airbyte/airbyte-protocol.md)) [D]. So the ingest-source/pipeline boundary moves with the EL contract chosen, not with the definition.

Two smaller observations follow [I]. "Pipeline" as a unit is itself model-specific. Dagster's unit is the asset, while Databricks splits the role across LDP datasets, Jobs tasks and Unity Catalog tables. LDP also allows only one writer per dataset ([Databricks: pipeline limitations, Oct 22 2026](https://docs.databricks.com/aws/en/ldp/limitations)) [D]. And **storage and catalog**, treated as context in the brief, decide consumer unawareness, cross-orchestrator triggers and lineage. It behaves like a layer that the other four depend on.

## RQ1: orchestration capability versus pipelining capability

**Evidence level: moderate.** Most claims are documented. First-hand evidence is limited to Spotify (2022, [>2y]), MetaOps (partial) and Yespark (vendor-hosted, short window). No first-hand source applies "functional core / imperative shell" or hexagonal architecture to orchestrated pipelines with an outcome.

### Which capabilities are runtime and which are feed facts

The orchestrator capabilities the brief lists split into *machinery* and *declared facts*. The machinery needs to see the run graph and is expensive to rebuild. The declared facts describe the feed and are cheap to keep neutral. Spotify's first-hand account supports this split. Downstream backfills, event-triggered actions and lineage instrumentation were hard to provide while orchestration lived in a library inside each workflow image, and the platform "had to build and maintain the same capabilities in two libraries" ([Spotify, 2022-03-14](https://engineering.atspotify.com/2022/3/why-we-switched-our-data-orchestration-service)) [F, >2y]. The table condenses the follow-up study's binding analysis. All rows are [I] except where marked.

### Where pipeline logic lives so it runs and is tested without an orchestrator

Under options 1B and 1C, three test layers need no orchestrator. Parse functions are tested with pytest on recorded vendor fixtures. EL runs are tested against `destination="duckdb"` or a local DuckLake. Landing is tested against a local object store [I]. Dagster's own tooling for the shell (`create_defs_folder_sandbox`, `load_component_and_build_defs`) only checks that definitions load and that asset keys come out as expected ([Dagster: testing components](https://github.com/dagster-io/dagster/blob/master/docs/docs/guides/build/components/creating-new-components/testing-your-component.md)) [D]. Some things still need a test against the orchestrator: asset-key mapping to dbt sources, automation conditions, partition and backfill semantics, secret wiring, and overlapping runs of same-named pipelines [I]. MetaOps reports asset-key drift that broke dbt lineage, which is exactly the class of bug only that layer catches [F, partial].

### Which orchestrator features are worth binding to directly

The follow-up study's concept map gives a sharper answer than general advice. The Dagster features hardest to give up are mostly the ones with **no Databricks equivalent anyway**: manual check results, partitions with mappings, named concurrency pools, code-version staleness, and user-coded sensor cursors. Others have different semantics on Databricks: blocking checks, declarative automation and freshness. Rebuilding these neutrally is only worth it if their *decisions* must survive migration [I]. Run history, the backfill launcher, the graph UI, the launcher and retries rebuild poorly and re-map cheaply, so binding to them costs little [I]. Dagster's blocking-check semantics have moved underneath users. Blocking applies only "during a run", and since 1.13.7 (2026-05-28) a *missing* blocking result lets downstream proceed ([CHANGES.md](https://raw.githubusercontent.com/dagster-io/dagster/master/CHANGES.md)) [D]. A user report of a dbt test failure that did not block a Python asset was closed "not planned" ([issue #25112](https://github.com/dagster-io/dagster/issues/25112)) [F]. Gate semantics are therefore a weak thing to bind to if they carry audit weight [I].

## RQ2: orchestrator lifecycle and replacement

**Evidence level: documented for upgrades, thin and old for migrations.** Real migrations: Robinhood 2019 [F, >2y] and YipitData 2022 [F, vendor co-published, >2y]. Current procedures: Google Cloud Composer 2026 and Dagster Airlift [D]. **None is a migration from Dagster or into Databricks with cutover detail.**

Dagster has not shipped a 2.0. The real migrations are few. Robinhood ran two Airflow clusters with each DAG in both. The per-DAG handshake was: pause the old side after its latest run, set a static start equal to the next execution date, unpause the new side, with backfills off [F, >2y]. YipitData moved 600+ DAGs to Databricks Workflows with a script and called it "relatively smooth". Its tasks were already Databricks notebooks, so only the scheduler moved ([YipitData, 2022-12-07](https://databricks.com/blog/why-we-migrated-apache-airflow-databricks-workflows-yipitdata)) [F, vendor co-published, >2y]. Databricks' 2026 guidance says "most teams migrate incrementally" and Lakeflow Jobs "is designed to coexist", but it gives no cutover mechanics ([Databricks blog, 2026-03-18](https://www.databricks.com/blog/how-move-apache-airflowr-databricks-lakeflow-jobs)) [D]. A reported two-week dual run with reconciliation was **unreachable** ([Medium](https://medium.com/@nidhi2505/from-chaos-to-clarity-our-migration-journey-from-aws-airflow-to-databricks-fd6d95479394)) [U]. One rule is shared across every verified source: **exactly one active scheduler per feed, switched at an interval boundary, with idempotent writes as the backstop** [I from F/D]. Consumer unawareness turns out to be a storage question. If DuckLake stays, Databricks can join only as a runner of DuckDB code. If storage moves to UC, the dual-run period is also a dual-catalog period [I].

## RQ3: the new-pipeline acceptance test

**Evidence level: thin.** No source establishes per-feed deploy independence in **Dagster OSS**. The claim that each code location builds into its own image with a per-location tag was **refuted 0-3** against the Dagster+ multi-project page. All topology guidance found is for Dagster+ Hybrid. Plugin and registration mechanisms have no source at all. Everything below beyond the cited Dagster and Databricks facts is [I].

The target is that a developer can develop, test, gate (CI) and deploy a new pipeline without changing core or orchestrator code, only consuming them. It splits into two independent conditions [I]. ### Growing core for a genuinely new shape

No source describes how an ingestion core grows without breaking existing feeds. The nearest precedents are the EL protocols' own versioning. Singer asks taps to follow SemVer across config, state interpretation and output ([Singer SPEC 0.3.0](https://raw.githubusercontent.com/singer-io/getting-started/master/docs/SPEC.md)) [D, >2y inferred]. The Airbyte protocol versions its messages, defaults connectors to `protocol_version` 0.2.0, and freezes an old mode: "No new Connectors should be created using Legacy state" ([Airbyte protocol](https://raw.githubusercontent.com/airbytehq/airbyte/master/docs/platform/understanding-airbyte/airbyte-protocol.md)) [D]. Options, all [I]:

| # | Option | Mechanism | Costs | Failure mode → early warning |
|---|---|---|---|---|
| G1 | **Additive extension point** | New transport or delivery pattern as a new adapter type behind an existing interface | Interface design up front | Interface forced to change → breaking core release |
| G2 | **Incubate in the pipeline, promote later** | The new shape lives in the feed's own package until a second feed needs it | Temporary duplication (Sy2 risk) | Never promoted → copies multiply |
| G3 | **Versioned core contract with a deprecation window** | Core majors and minors. Old interfaces kept for N releases, as with Airbyte's Legacy state | Maintaining two code paths | Feeds stuck on old majors |

### What deploy independence costs

Three costs recur [I]. The first is **images**: one per unit, multiplied by CI time and registry storage. The second is **version skew**. The only documented rule is one-way: orchestrator ≥ pipeline code, for Dagster+ Hybrid [D], with no stated window. Spotify's first-hand account shows the end state of unmanaged skew: "users don't always upgrade", making it "hard… to roll out fixes and new instrumentation" [F, >2y]. The third is **core compatibility**. A core fix reaches only units that rebuild, which reproduces Sy2's "fix misses the copies" at the package level. Spotify's scale (about 20,000 daily pipelines, 1,000+ repos, 300+ teams) is far beyond this context, so its regret signal transfers as a mechanism, not as a threshold.

### How this split interacts with RQ2 and RQ3

If acquisition runs as a service outside both orchestrators, the dual-run problem shrinks to post-landing steps. Discovery cursors and vendor-facing rate limits leave the orchestrator, so two orchestrators no longer race on one SFTP drop [I]. What remains shared is the ledger (H6), which then doubles as the cross-orchestrator dependency signal (X6) and the double-run guard (D5) [I]. For RQ3, a new source with a known handoff contract needs no core change. A new *contract* is the case where core must grow (G1–G4) [I]. The interaction cuts the other way for Databricks. Its native event triggers watch UC objects only, so a drop zone outside a UC external location or volume cannot trigger it directly [D, Oct 2026].

## Cross-question dependencies

The questions are coupled more tightly than their numbering suggests [I]. **The ledger is one build that answers four questions or none.** The delivery, check-result, waiver, cursor-lease and feed-ownership tables from RQ2's state analysis are the same objects RQ2's migration options need for ownership (S3), double-run prevention (D2, D3, D5) and cross-orchestrator dependencies (X6). They are also RQ4's strongest handoff (H6) and the home of RQ6's completeness and verdict rows. Choosing an orchestrator-native home for decision state in RQ1 (option 1A or 1D) therefore removes the shared-truth mechanisms from RQ2 and leaves the schedule handshake (S1/D1) and idempotency (D4) as the only dual-run controls.

**RQ1's neutral logic is a precondition for RQ2's cheap upgrades and RQ3's isolated tests, but not for RQ3's independent deploys.** Option 1B shrinks what an upgrade touches (2U4) and makes parse and EL layers testable alone. Deploy independence still needs separate units (3E) and a compatibility policy (RQ5). That makes **RQ5's topology the constraint on RQ3's deploy half and on RQ2's orchestrator-first upgrades** (2U2 needs code locations that deploy separately). T1 rules out both.

**The storage decision, open in the context, runs through RQ1, RQ2 and RQ4.** It decides whether LDP is viable (1H outputs are UC-managed Delta), whether Databricks triggers can see feeds (X1, X2, H3 are UC-only), whether consumers stay unaware (C1–C5), whether dlt incremental state survives (a destination change resets it), and whether UC lineage sees DuckLake tables at all (it does not, per the follow-up study's concept map, row 16) [D/I].

**RQ4's choice of acquisition outside the orchestrator reduces RQ2's dual-run surface.** Discovery cursors and vendor rate limits leave the orchestrator. In exchange, RQ4 must own the "is everything here" declaration that today may sit in sensors [I]. Temporal's payload limits force claim-check (references, not bytes), which in turn forces the RQ4 handoff to be an object-plus-ledger contract (H2/H6), not a message carrying data [D/I].

**RQ1's binding choices fix RQ2's losses in advance.** The Dagster features listed as worth binding to are the ones with no Databricks equivalent. Mirrors back into Dagster (the follow-up study's M1–M2) buy native views only for the migration period [I].

## Conclusion

The research changes the shape of the question more than it answers it. The brief asks where the lines fall between four layers. The evidence suggests the hard boundary is not between layers of code but between *code* and *decided-on state*. Code can be made orchestrator-neutral with tools that already exist. Decided-on state is held today in the system due to be replaced, in a form that cannot be carried across with its meaning intact. Any option in RQ1, RQ3 or RQ5 can be evaluated by one test: during the dual-run period, where does it leave the delivery record, the gate verdict and the rate limit?

The second shift concerns what "neutral" can mean. A pipeline model neutral toward Databricks must give up partitions, cross-run verdicts and staleness, because Databricks has no counterpart for them. LDP has the mirror-image property: its distinctive value lies in the parts open-source Spark lacks. The real trade is between owning a small set of platform tables plus mirrors, and accepting that each orchestrator's richest features stay behind when it is replaced. Which side of that trade fits is for the platform team to judge against its own code.
