# Eight responsibilities define a scalable agent harness

The sources support a reference framework in which an **agent harness is the runtime layer around a fixed, swappable model**. It assembles context, runs the loop, routes actions, persists state and enforces constraints. It is separate from the model, from the execution sandbox, from the durable session log, and from the platform layer that owns identity, audit and cost. Tested against the five candidate responsibilities, **Loop, Tools and Context survive intact. Memory survives only when it is redefined as durable State. Control has to be split into Verification and Governance. Execution environment and Observability have to be added.** That gives eight responsibilities, and it matches the 2026 harness literature (Guo et al.'s six-tuple, Zhang et al.'s six layers) more closely than the 2023 agent-architecture surveys. The framework maps onto all seven validation systems, but two seams show up everywhere. Context and memory share the same artifacts in every implementation, and in-loop verification exists as hooks rather than as a responsibility any product owns. Controlled studies show that the harness alone moves outcomes by 7 to 28 points on public benchmarks with the model held fixed. That makes harness design an engineering and governance concern, not a packaging detail. Interfaces are now standardized at five boundaries: tools (MCP), agent-to-agent (A2A), editor-to-agent (Agent Client Protocol), instructions and assets (AGENTS.md, Agent Skills) and telemetry (OpenTelemetry GenAI, still in Development status). Three boundaries remain open: model↔harness, permission policy, and memory. On the Copilot hypothesis, **the governance half is partly supported**: Copilot leads on cost controls, admin audit and its org→repo delegation tree, and is at parity on client policy. **The capability half is not supported as stated**: its documented features are now at near parity, and no public controlled benchmark includes Copilot as a harness. For many teams the scaling property comes from extension as data (skills, agent profiles, MCP endpoints, plugins in a pinned marketplace) beneath a centrally locked managed-policy layer. Platform-engineering practice fills the gaps where the agent literature is silent.

**Method and labels.** This report synthesizes seven research tracks run on 2026-11-11. Labels follow the brief. **[Established]** means stated in a primary full text that was read. **[Synthesized]** means combined across several cited sources, or transferred from platform-engineering practice. **[Proposed]** marks a recommendation or a framework element this report introduces. **[Inference]** marks reasoning that no source states. **[Unreachable]** marks a source that could not be read. Vendor numbers are marked *vendor claim*. Product features carry the version or doc date checked. All docs were retrieved on 2026-11-11, and none showed a "last updated" date, so the retrieval date serves as the doc date. Source tiers are kept apart. Peer-reviewed or arXiv research (tier 1) is evidence. Vendor engineering posts (tier 2) are design claims. Product docs and source code (tier 3) are implementation evidence. Specifications (tier 4) fix interfaces. Every 2026 harness paper cited here is arXiv-only and not peer-reviewed.

## The term "harness" moved from industry posts into 2026 preprints, with two competing scopes

"Harness", meaning the wrapper around an agent's model, is a 2025–2026 coinage. The canonical 2023–2024 papers speak instead of "cognitive architecture" ([CoALA, TMLR 2024](https://arxiv.org/abs/2309.02427)), "agent-computer interface" ([SWE-agent](https://arxiv.org/abs/2405.15793)), "augmented LLM" ([Anthropic, Building effective agents, Dec 2024](https://www.anthropic.com/engineering/building-effective-agents)) or a profile/memory/planning/action "unified framework" ([Wang et al.](https://arxiv.org/abs/2308.11432)) **[Established]**. The 2026 preprints converge on one functional meaning. Guo et al. use harness "to denote the runtime infrastructure that surrounds the model and realizes closed-loop agent execution … the coordinating layer that decides which observations reach the model, how context is assembled, how the agent loop advances, how actions are executed, how state and artifacts persist, and how failures are detected, governed, and recovered" ([Guo et al., arXiv 2606.20683](https://arxiv.org/abs/2606.20683)). Zhang et al. define it as "the infrastructure layer that governs context construction, tool interaction, orchestration, and verification around a language model", and formalize the harness as the controller of a closed-loop system in which the LLM is the stochastic policy ([Zhang et al., arXiv 2605.23950](https://arxiv.org/abs/2605.23950)) **[Established]**. Ren et al. (with Schmidhuber) prefer "scaffold" but state that it "is often also referred to as an agent harness" ([Ren et al., arXiv 2607.13104](https://arxiv.org/abs/2607.13104)) **[Established]**. These papers cite industry engineering posts for the term, which suggests that the word entered academia from practice. The primary posts behind the citations "Rajasekaran 2026" and "Trivedy 2026" correspond to [Anthropic's harness-design post](https://www.anthropic.com/research/harness-design-long-running-apps) and [LangChain's "Anatomy of an Agent Harness"](https://blog.langchain.com/the-anatomy-of-an-agent-harness/), both of which were read **[Inference on the correspondence]**.

The vendor definitions split into a narrow scope and a broad scope, and a framework must choose between them. In the **narrow** scope, Anthropic's Managed Agents post virtualizes "a session (the append-only log of everything that happened), a harness (the loop that calls Claude and routes Claude's tool calls to the relevant infrastructure), and a sandbox (an execution environment where Claude can run code and edit files)". The harness is stateless, and "nothing in the harness needs to survive a crash" ([Anthropic, Scaling Managed Agents, Apr 8 2026](https://www.anthropic.com/engineering/managed-agents)) **[Established, vendor design claim]**. In the **broad** scope, LangChain writes "Agent = Model + Harness … A harness is every piece of code, configuration, and execution logic that isn't the model itself", which includes sandbox and filesystem ([LangChain, Mar 2026](https://blog.langchain.com/the-anatomy-of-an-agent-harness/)). Anthropic's evals post likewise treats harness and scaffold as synonyms ([Anthropic, Demystifying evals, Jan 2026](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)) **[Established]**. A term collision also matters for an operating team. In HAL, "harness" means the *evaluation* harness that runs rollouts across VMs, and the agent wrapper is called the scaffold ([HAL, arXiv 2510.11977](https://arxiv.org/abs/2510.11977)) **[Established]**.

The sources draw the model boundary in different places, and the boundary moves with training. Toolformer puts tool-call decisions into the weights ([Toolformer](https://arxiv.org/abs/2302.04761)). MemGPT lets the model manage its own memory through function calls that the system executes and enforces ([MemGPT](https://arxiv.org/abs/2310.08560)). Xi et al. place memory and planning inside the LLM "brain" ([Xi et al.](https://arxiv.org/abs/2309.07864)). The 2026 papers pull these behaviours back out as editable harness policy, and Pan et al. go as far as recasting harness logic as a natural-language document interpreted by a shared runtime ([Pan et al., arXiv 2603.25723](https://arxiv.org/abs/2603.25723)) **[Established]**. Vendors add a meta-principle: "every component in a harness encodes an assumption about what the model can't do on its own." Anthropic's example is context resets that were added for one model generation and "had become dead weight" on the next ([Anthropic harness design, Mar 2026](https://www.anthropic.com/research/harness-design-long-running-apps); [Managed Agents](https://www.anthropic.com/engineering/managed-agents)) **[Established, vendor claim]**. The framework therefore defines the harness by function and separates durable interfaces from model-compensating scaffolding, which is expected to be deleted over time **[Synthesized]**.

The layer model below is what the framework adopts. It uses the narrow scope for the harness proper and names the adjacent layers explicitly, so that ownership can be assigned. The "workflow vs agent" axis (who decides the path) runs orthogonally to these layers. A fixed pipeline such as [Agentless](https://arxiv.org/abs/2407.01489) still has a harness, only with a hard-coded loop **[Synthesized]**.

| Layer | Definition used in this framework | Origin | Label |
|---|---|---|---|
| Model | Stochastic policy; fixed and swappable; may internalize some behaviours (tool choice, planning) | Zhang et al.; Toolformer; Guo et al. | Established |
| Harness | Loop, context assembly, action routing, verification and policy enforcement around the model; ideally stateless | Guo et al.; Anthropic Managed Agents; LangChain | Synthesized |
| Execution environment | Sandbox, VM or runner where actions run; credential-free; "cattle" | Anthropic Managed Agents; Zhang "E" layer | Established (vendor) |
| Session / state store | Append-only durable log and artifacts from which a replaceable harness resumes | Anthropic Managed Agents; Temporal Event History; Guo "S" | Synthesized |
| Agent system | One or more harnessed agents plus their topology (handoffs, orchestrator-workers, A2A peers) | OpenAI guide; Anthropic multi-agent; A2A | Synthesized |
| Environment | The external world reached through observation and action interfaces | CoALA; Guo et al. | Established |
| Platform layer | Identity, policy distribution, audit retention, cost attribution, catalogs, evaluation harness | Track 06/07 governance docs; HAL | Proposed |

## Three candidates survive, Memory becomes State, and Control splits in two

Every decomposition from 2023 to 2026 has some form of loop, action interface and memory **[Synthesized]**. That covers [CoALA](https://arxiv.org/abs/2309.02427), [ReAct](https://arxiv.org/abs/2210.03629), [Reflexion](https://arxiv.org/abs/2303.11366), [MRKL](https://arxiv.org/abs/2205.00445), [Voyager](https://arxiv.org/abs/2305.16291), [Generative Agents](https://arxiv.org/abs/2304.03442), Wang, Xi, the [context-engineering survey](https://arxiv.org/abs/2507.13334), Guo, Zhang, Ren, [Wang-HIT](https://arxiv.org/abs/2605.29682) and Pan. What changes between the eras is emphasis. The 2023 surveys describe what the agent knows and plans. The 2026 papers describe how a run is executed and governed, and only they name **verification, governance, observability and durable state** ([Guo](https://arxiv.org/abs/2606.20683); [Zhang](https://arxiv.org/abs/2605.23950)) **[Established]**. The vendor reference architectures say the same independently: durable execution ([Anthropic multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system); [Temporal](https://temporal.io/blog/of-course-you-can-build-dynamic-ai-agents-with-temporal)), tracing, evaluator agents ([Anthropic harness design](https://www.anthropic.com/research/harness-design-long-running-apps)) and the sandbox as a component of its own ([Managed Agents](https://www.anthropic.com/engineering/managed-agents)) **[Established, vendor design claims]**.

The derived taxonomy below is closest to Guo et al.'s H = ⟨I_obs, C, L, I_act, S, V⟩. It differs in two ways. It splits V into Verification and Governance, because the mechanisms, owners and failure modes differ. And it adds Observability as a cross-cutting responsibility, following Zhang's "O" layer. It is **Synthesized**. The names R3 and R8 as separate responsibilities, and the R6/R7 split, are **Proposed** elements of this framework.

| Candidate | Verdict | Derived responsibility | Basis |
|---|---|---|---|
| Loop | **Confirmed, widened** | **R1 Loop & orchestration**: step scheduling, stop conditions, retries, reflection, delegation, multi-agent handoff, loop-pathology control | Guo L "delegation, handoffs, and multi-agent coordination"; OpenAI run loop; all SDKs |
| Tools | **Confirmed, split** | **R2 Action interface**: tool definitions, routing, MCP clients, tool selection/masking | CoALA grounding; SWE-agent ACI; Guo I_act; MCP |
| (new, from Tools) | **Added** | **R3 Execution environment**: sandbox, VM/runner, network egress, credential isolation | Anthropic "sandbox"; Zhang "E"; Codex/Claude Code sandboxes |
| Context | **Confirmed, widened** | **R4 Context assembly**: instructions/profile, observation shaping, retrieval, compaction, caching, sub-agent isolation | Guo C and I_obs; Mei et al.; Anthropic context engineering; Manus |
| Memory | **Confirmed only if redefined** | **R5 State, memory & durability**: session log, checkpoints, run-state persistence, long-term memory, resume/replay | Guo S; Anthropic session; LangGraph checkpointers; Temporal |
| Control | **Split** | **R6 Verification**: in-loop tests, verifiers, evaluator agents, validation gates, repair | Reflexion; Voyager; Agentless; Guo V; Pan "validation gates" |
| Control | **Split** | **R7 Governance & policy enforcement**: permissions, approvals/HITL, guardrails, budgets, sandbox policy | Guo V; OpenAI guide; all product permission models |
| (new) | **Added, cross-cutting** | **R8 Observability**: traces, metrics, events at loop, tool and model boundaries | Zhang O; Anthropic tracing; OTel GenAI |
| Planning | **Rejected as a harness responsibility** | Model capability that R1 may scaffold (planner-executor) | Absent as a component in the 2026 sources; Starace scaffolds |
| Offline evaluation | **Moved out** | Platform-layer evaluation harness | HAL; Kapoor et al.; Anthropic evals |
| Hooks / middleware | **Reclassified** | Mechanism that implements R4–R8, not a responsibility | LangChain middleware; Claude/Codex/Copilot hooks |

Four reclassifications need justification. **Memory becomes State.** Implementations use the same files and logs both for per-call context and for persistence. Examples are CLAUDE.md, Manus's filesystem as "the ultimate context", and OpenAI's compaction session, which is itself a `Session` ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus); [OpenAI Agents SDK context docs, v0.24.0](https://github.com/openai/openai-agents-python/blob/64fbde5d02b42ae5f9db668eb0184cdb3fc9d775/docs/context.md)) **[Established]**. The only clean separation in the sources is Anthropic's: "The session is not Claude's context window". The session is recoverable storage, and the harness does arbitrary context management over it ([Managed Agents](https://www.anthropic.com/engineering/managed-agents)). The framework adopts that rule: **State is the store; Context is a per-call projection of it** **[Synthesized]**. **Durability belongs to State rather than standing alone.** In LangGraph the checkpointer *is* both memory and durability, and Anthropic's session log and Temporal's Event History play the same role. They differ only in what happens on resume: Temporal replays recorded decisions, while Anthropic re-projects the log and lets the model continue ([LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence.md); [Temporal](https://temporal.io/blog/of-course-you-can-build-dynamic-ai-agents-with-temporal)) **[Synthesized]**. **Control splits** because its mechanisms fall into two families. Verification checks whether the work is right: tests, evaluator agents, linters. Governance checks whether the action is allowed: permission rules, approvals, budgets, credential isolation. The two have different owners (the team versus the platform) **[Synthesized]**. **Multi-agent handoff stays inside R1** because every source folds it into loop or tools (Guo L and I_act; OpenAI handoffs and agents-as-tools; Claude subagents as an `Agent` tool) **[Established]**. The open single-vs-multi disagreement is treated under disagreements, below.

## The harness alone moves benchmark scores by 7 to 28 points, and more machinery is not monotonically better

The strongest primary evidence that harness responsibilities matter comes from controlled same-model studies. **SWE-agent's interface raised GPT-4 Turbo from 11.0% (shell-only) to 18.0% on SWE-bench Lite.** Ablations cost 7.7 points without the edit command, 5.3 with a full-file viewer, and 3.0 with full history in place of the last five observations. The richer interface helped, and too much context hurt ([SWE-agent, NeurIPS 2024](https://arxiv.org/abs/2405.15793)) **[Established]**. A pre-registered study of 3 scaffolds × 5 models on GAIA found that "scaffold choice alone moves measured accuracy by as much as 28 percentage points within a single model". It rejected the prediction that more capable models are less scaffold-sensitive ([Starace, arXiv 2606.08529](https://arxiv.org/abs/2606.08529), single author, arXiv-only) **[Established]**. A 176-setting ablation found that context management matters most under tight context budgets ([Fan et al., arXiv 2609.20804](https://arxiv.org/pdf/2609.20804)) **[Established]**. An independent study found "GPT-5.4 performs better with Codex than OpenCode" ([SWE-Chain, arXiv 2605.14415](https://arxiv.org/pdf/2605.14415)) **[Established]**. The counter-evidence is just as solid. A fixed three-phase pipeline (Agentless) reached 32.0% on SWE-bench Lite at $0.70 per issue and beat contemporary open agents ([Agentless](https://arxiv.org/abs/2407.01489)). Simple retry baselines beat complex agents on HumanEval at lower cost ([Kapoor et al.](https://arxiv.org/abs/2407.01502)) **[Established]**. The two sides reconcile on *fit*: harnesses should be judged by how well they shape information and size actions, not by how much machinery they carry **[Inference]**.

Quantitative vendor results should not be read as evidence. Anthropic's multi-agent system "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval" (*vendor claim*), but the same post attributes 80% of BrowseComp variance to token usage, so the result does not separate architecture from compute ([Anthropic multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)) **[Inference]**. LangChain's deepagents-cli improved from 52.8 to 66.5 on Terminal-Bench 2.0 with the model held fixed. That is the closest public vendor evidence for a harness-only change, but it is self-reported and comes from a single vendor ([LangChain](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)) (*vendor claim*). The larger cross-scaffold gaps attributed to HAL (34–48 points) appear only in Zhang et al.'s compilation, and the HAL paper itself could not confirm them ([Zhang et al.](https://arxiv.org/abs/2605.23950); [HAL](https://arxiv.org/abs/2510.11977)) **[Established as secondary; unverified in primary]**. The defensible framework statement is therefore: **"the harness materially changes outcomes" is Established; "the harness dominates the model" is Proposed** (Zhang's position-paper thesis).

Standards bodies and open specifications now pin down where a harness meets its tools, peers, clients, instructions and telemetry. The Agentic AI Foundation (AAIF), formed under the Linux Foundation on 2025-12-09, hosts MCP, AGENTS.md, goose and A2A ([LF press release](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation); [aaif.io](https://aaif.io/)) **[Established]**. The adoption figures in the LF release (>10,000 MCP servers; AGENTS.md in >60,000 projects) are claims made by the steward, not independently counted.

The gaps matter as much as the coverage **[Inference, from absence in the specs read]**. No standard covers the **model↔harness wire**, and MCP's deprecation of Sampling sends harnesses back to provider APIs. No standard covers **permission and policy**: tool allow/deny, approval UX and sandbox profiles are vendor-specific, and the only portable hint is Agent Skills' experimental `allowed-tools`. **Memory** has OTel spans but no interface. **Instruction and skill provenance** is unsigned, unlike A2A Agent Cards. This report found no primary source that catalogues these gaps formally. ISO/IEC 42001 could not be read (iso.org returned 403) **[Unreachable]**.

## Enterprise controls now converge on the client and diverge in the surrounding platform

All four coding harnesses now ship an admin-enforced managed-settings layer above project and user settings. The clearest finding in track 06 is that **Copilot's `managed-settings.json` reuses Claude Code's key names**: `permissions.deny/ask/allow`, `disableBypassPermissionsMode`, `sandbox`, `allowedMcpServers` and `strictKnownMarketplaces` ([GitHub managed settings](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-enterprise/use-managed-settings/get-started); [Claude Code settings](https://code.claude.com/docs/en/settings)) **[Established; parity judgment is Inference]**. The systems therefore no longer differ much on *client* policy. They differ in the objects around the client: GitHub orgs, repos, teams and cost centers, compared with IdP groups and workspace groups.

Several of these controls degrade as teams are added, and the merge semantics decide how **[Inference from the Established rules]**. Copilot team overrides combine across a user's teams at the **least restrictive** value, so a member of several teams can be loosened by accident ([team overrides](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-enterprise/use-managed-settings/override-settings-for-teams)). Claude Code group configurations **do not merge**, so every baseline restriction has to be restated in each group config. They are also not yet available for HIPAA organizations ([server-managed settings](https://code.claude.com/docs/en/server-managed-settings)). OpenCode drops invalid policy statements with a warning, which fails partly open. Copilot treats a malformed MCP allowlist as blocking everything, which fails closed. Configuration planes also fragment. Claude Code's MDM settings do not reach Anthropic-hosted cloud sessions. Codex cloud does not inherit device policy. A custom `ANTHROPIC_BASE_URL` skips server-managed settings entirely ([gateway caveat](https://code.claude.com/docs/en/claude-apps-gateway)). Cowork shares Claude Code's architecture but not its `~/.claude` configuration ([Cowork](https://claude.com/docs/cowork/overview)). The documents reviewed give no scale limits (maximum groups, policy API rate limits), and no independent tests of enforcement robustness exist. Every cell above comes from vendor documentation.

The RQ7 placement question resolves cleanly **[Synthesized; placement Proposed]**. **Harness responsibilities** are the controls that must run *at the point of action*: tool and permission evaluation, sandbox and network enforcement, model selection checks, hook execution, telemetry emission and local budget caps (R3, R7, R8). **Platform-layer responsibilities** are the controls that hold *organizational state*: identity and SCIM, policy authoring, versioning and distribution, audit retention and SIEM streaming, cost-center budgets and chargeback, data residency and retention, model and MCP catalogs, and offline evaluation. The evidence supports the split. GitHub's audit log explicitly excludes local session data and recommends hooks to fill the gap. Codex warns that conversation visibility is not a complete record of local actions. In both cases the platform cannot see what the harness does unless the harness emits it.

## Copilot trades harness openness for platform governance, but is not shown to be less capable

The hypothesis has two halves, and the evidence treats them differently.

**"Less capable as an agent harness": not supported as stated, and the evidence is insufficient on performance.** On documented features checked 2026-11-11, Copilot matches the other three on nearly every capability row: an interactive loop in VS Code and in CLI 1.0.109, headless `copilot -p`, an SDK in six languages, MCP in IDE, CLI and cloud, AGENTS.md/CLAUDE.md/GEMINI.md, compaction at 95%, custom agents, subagents, Agent Skills and hooks ([CLI](https://docs.github.com/api/article/body?pathname=/en/copilot/concepts/agents/copilot-cli/about-copilot-cli); [skills](https://docs.github.com/api/article/body?pathname=/en/copilot/concepts/agents/about-agent-skills); [hooks](https://docs.github.com/api/article/body?pathname=/en/copilot/concepts/agents/coding-agent/about-hooks)) **[Established]**. It leads on execution venues: ephemeral, larger, self-hosted or Windows Actions runners, cloud sandboxes that resume across clients and span repositories, and remote custom environments ([about cloud agent](https://docs.github.com/api/article/body?pathname=/en/copilot/concepts/agents/coding-agent/about-coding-agent)). It also leads on model breadth (Anthropic, OpenAI, Google, xAI, Microsoft) and on harness plurality, since VS Code lets users "work with the Copilot, Claude, or Codex agent harness" ([VS Code agents](https://code.visualstudio.com/docs/copilot/agents/overview)) **[Established]**. Its documented gaps are narrower. The cloud agent supports only a subset of hooks. The firewall covers only Bash-tool processes. Actions-based sessions are web-only and single-repo. The CLI documents no local OS sandbox, which compares poorly with Codex's default-on sandbox **[Established; sandbox comparison Inference]**. Its loop internals are undocumented **[Unreachable]**. Most importantly, **no controlled public evaluation includes Copilot as a harness**. Terminal-Bench 4.1 (updated 2026-11-11) lists Claude Code, Codex, Grok Build, mini-SWE-agent and Muse Code, and its top rows pair each vendor's harness with that vendor's own models, for example Claude Code + Opus 5.5 at 65.8% and Codex + GPT-6.1 Sol at 60.9%. These should be read as vendor-associated submissions ([tbench.ai](https://www.tbench.ai/leaderboard/terminal-bench/2.0)) (*vendor claims*; provenance not shown). SWE-Chain, TestEvo-Bench and OpenBench all omit Copilot ([SWE-Chain](https://arxiv.org/pdf/2605.14415); [TestEvo-Bench](https://arxiv.org/pdf/2607.02469); [OpenBench](https://raw.githubusercontent.com/minghinmatthewlam/openbench/main/README.md)) **[Established]**. A performance gap can therefore be neither shown nor ruled out.

**"Stronger in enterprise policy and governance": partly supported.** Copilot clearly leads on **cost controls**: hard-stop user-level budgets with cost-center variants, cost-center/org/enterprise budgets, and included-usage caps. It also leads on the **admin and cloud-agent audit trail** (180 days, SIEM streaming, agent-attributed events) and on **org→repo delegation** for the firewall, content exclusion and the policy tree. Seat assignment follows GitHub teams. It is at **parity** on managed settings, MCP allowlists, permission rules and OTel, because it adopted the same model as Claude Code. Its OTel capture classes are finer-grained, while Claude Code locks the telemetry destination more firmly. It is **weaker** on deployment (SaaS only, with no cloud-provider or self-hosted harness route). It does not log local sessions. And it has enforcement holes: user-local BYOK models, custom-agent-profile MCP servers, and firewall bypass caveats. Its retention and training terms could not be verified in this run **[Synthesized from Established docs]**.

The sourced verdict is therefore **[Synthesized]**: Copilot is best modelled as a **governed platform that hosts several harnesses**. Its own, Claude's and Codex's harnesses can run in VS Code, and its cloud agent is an execution and orchestration layer on Actions. It is not a single, weaker agent loop. The documented advantage lies in the surrounding GitHub objects, not in the harness. A same-model experiment would settle the capability half **[Proposed]**: run Copilot CLI, Claude Code, Codex and OpenCode on Terminal-Bench 4.1 or SWE-Chain with one shared model (OpenCode can use Copilot as a provider), and disclose each harness configuration as [Zhang et al.](https://arxiv.org/abs/2605.23950) recommend.

## Growth comes from extension as data beneath a locked managed layer

The architectural property that lets a harness grow from one team to many without redesign is that **new capability arrives as declarative packages rather than core code** **[Inference from Established mechanisms]**. Examples of such packages are a `SKILL.md` folder, an agent profile in Markdown, an MCP endpoint, and a plugin directory with a manifest listed in a git-hosted marketplace ([Claude Code marketplaces](https://code.claude.com/docs/en/plugin-marketplaces); [Agent Skills post](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills); [Copilot custom agents](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-custom-agents)) **[Established]**. An independent source-code study of 11 harnesses (July 2026) found that none imports a general agent framework, SKILL.md appears in 9 of 11 and MCP in 8 of 11 ([Barbaste et al., arXiv 2609.00006](https://arxiv.org/pdf/2609.00006)) **[Established]**. Across vendors, the extension vocabulary has converged: Copilot and OpenCode read Claude Code's CLAUDE.md and skills directories directly ([OpenCode rules](https://opencode.ai/docs/rules/); [Copilot instructions](https://docs.github.com/api/article/body?pathname=/en/copilot/concepts/prompting/response-customization)) **[Established]**. The scale mechanism has three distribution tiers, all of which already exist: asset formats, bundles (plugins) and catalogs (marketplaces, the MCP Registry and private sub-registries) **[Synthesized]**.

The table gives the layering model. Central and team ownership follows the Team Topologies split of platform, stream-aligned, enabling and complicated-subsystem teams **[Synthesized: transfer of platform-engineering practice; Team Topologies primary not read]**.

| Layer | Contents | Owner | Inheritance / override rule (evidence) |
|---|---|---|---|
| L0 Platform | Identity/SCIM, LLM gateway and model catalog, budgets and chargeback, audit retention, OTel collector, policy-as-code repo, internal marketplace and MCP sub-registry, evaluation harness | Platform team | Not overridable; per-group variants rendered from one template (Claude group configs don't merge; Copilot team files merge least-restrictive) |

Shared assets need artifact-repository discipline, and the agent harnesses provide most of the mechanics without the trust layer. Claude Code supports git `ref`/`sha` pins, `sha256`-pinned archives, per-marketplace auto-update policy, release channels implemented as "two marketplaces that point at different refs", read-only seed directories for CI and air-gapped fleets, and allow/block lists checked "before a download" and "again at session start". It also offers OTel install/load events and a per-plugin analytics API for deprecation decisions ([org plugin management](https://code.claude.com/docs/en/plugins/org)) **[Established]**. Trust, however, is review-based: "a Claude Code plugin you install can execute arbitrary code on your machine with your user privileges"; hooks and MCP servers run outside the sandbox. No signing or provenance scheme was found for plugins, skills or AGENTS.md ([plugin security](https://code.claude.com/docs/en/plugins/security)) **[Established; absence is Inference]**. OWASP lists agentic supply chain as ASI04 ([OWASP](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)) **[Established; full PDF Unreachable]**. Natural-language assets are the agent-specific twist on supply-chain risk: code scanners cannot vet a skill's instructions for prompt-injection behaviour **[Inference]**.

Onboarding follows the CNCF maturity vocabulary. Level 2 is golden paths "in the form of documentation and templates". Level 3 is "self-serve portals, golden-path templates". Level 4 is an ecosystem in which users extend the platform ([CNCF Platform Engineering Maturity Model v1.0](https://tag-app-delivery.cncf.io/whitepapers/platform-eng-maturity-model/)) **[Established]**. In agent terms, a new team or topic gets a template repository that scaffolds project settings requiring the org marketplace, a starter AGENTS.md, a team plugin skeleton and a default risk tier. Claude Code's documented rollout order (require plugins → seed CI → restrict → set update policy → audit) is the vendor version of that path ([org plugins](https://code.claude.com/docs/en/plugins/org)) **[Established; template is Synthesized]**. Governance scales through gateway hierarchies that tie cost to ownership. LiteLLM, for example, enforces team, member, key, customer and agent budgets but falls back to local memory during a Redis outage unless `fail_closed_rate_limit_enforcement` is set ([LiteLLM](https://docs.litellm.ai/docs/proxy/users)) **[Established]**. Telemetry grouped by RBAC group provides the matching view of use.

The scale-up evidence comes mostly from one strong case and one survey. Spotify placed a Claude Agent SDK harness ("Honk") behind its existing Fleet Management orchestration and Backstage catalog. It exposed catalog capabilities as MCP servers and kept a thin internal CLI so it could "seamlessly switch between different agents and LLMs". It reports 1,500+ merged agent PRs by November 2025 and over 2.5 million automated maintenance PRs by June 2026. The failure modes it reports are organizational: fragmentation degrades agent quality ("The fewer technologies we are world-leading in, the faster we go"), review becomes the bottleneck, and cost and unpredictability follow ([Spotify, Nov 2025](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1); [Spotify, Jun 2026](https://engineering.atspotify.com/2026/6/code-with-claude-coding-is-no-longer-the-constraint)) (*vendor self-report*). DORA 2025 finds a "direct correlation between a high quality internal platform and an organization's ability to unlock the value of AI", and finds that AI adoption still has "a negative relationship with software delivery stability" when testing and feedback loops are weak ([DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)) **[Established, survey]**. No primary report of a failed multi-team agent rollout was found. Config sprawl, MCP sprawl and shadow AI appear only in gateway-vendor marketing, so they are failure modes the vendors anticipate, not documented incidents **[Synthesized]**.

The loop, MCP tools, skills, plugins, subagents, permission rules, sandboxing, managed policy, telemetry and instruction files are discipline-agnostic. The best evidence is that Anthropic ships "the same agentic architecture that powers Claude Code" to non-developers as Cowork, producing spreadsheets, presentations and documents, extended through the same connectors, skills and plugins ([Cowork overview](https://claude.com/docs/cowork/overview)) **[Established]**. Its reserved official marketplaces include knowledge-work, legal, financial-services and life-sciences catalogs ([plugin security](https://code.claude.com/docs/en/plugins/security)) **[Established]**. ## Sources disagree on five axes and leave six gaps

The disagreements are substantive, and the framework keeps them open rather than resolving them by fiat.

**Terminology** **[Established]**. Ren prefers "scaffold", Guo prefers "harness", and HAL uses "harness" for evaluation infrastructure. The narrow (Anthropic) and broad (LangChain) scopes also differ.

**Locus of memory, planning and tool choice** **[Established]**. These sit in the model's "brain" for Xi and in the weights for Toolformer. They are separate modules for Wang. They are LLM-driven internal actions inside agent code for CoALA and MemGPT. They are externalized harness policy for Pan and Guo.

**Single vs multi-agent** **[Established]**. Cognition would "by default rule out" architectures that don't share full context and recommends a single-threaded agent ([Cognition, Jun 12 2025](https://cognition.ai/blog/dont-build-multi-agents)). Anthropic reports large gains for orchestrator-worker research, but concedes that "most coding tasks involve fewer truly parallelizable tasks" ([Anthropic, Jun 13 2025](https://www.anthropic.com/engineering/multi-agent-research-system)). OpenAI advises to "maximize a single agent's capabilities first" ([OpenAI guide](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)). Starace finds the multi-agent advantage holds within one model family but not across providers. The dispute narrows to one condition, stated by both Anthropic and Cognition: read-only, parallelizable breadth work favours isolated subagents, while write-heavy, interdependent work favours a single thread **[Synthesized]**.

**Harness vs model dominance** **[Proposed vs Established]**. Zhang's "Binding Constraint Thesis" claims dominance. Guo frames the outcome as an interaction among model, runtime, task and evaluation. Starace finds that scaffold effects do not shrink with model capability.

**Context tactics** **[Established]**. Anthropic calls compaction "the first lever" but says it "isn't sufficient" for multi-window coding, and it used resets and then dropped them. Manus warns that "any irreversible compression carries risk" and makes compression restorable. LangChain surveys RAG over tool descriptions, which Manus advises against because of cache invalidation. Anthropic advises few-shot examples, while Manus warns "Don't Get Few-Shotted". LangChain claims that the harness a model was post-trained with is not necessarily its best one, and that claim was not checked against the leaderboard.

The gaps are as follows.

1. There is no peer-reviewed formal definition of "agent harness". All formalizations are 2026 preprints **[Established absence in sources read]**.
2. There is no per-responsibility quantitative ablation (compaction alone, memory alone) from vendors, and no controlled third-party single-vs-multi-agent comparison.
3. There is no standard for permission policy, memory or the model↔harness wire. There is no signing for skills or instructions. OTel GenAI is still in Development.
4. There is no controlled benchmark that includes Copilot, and no independent test of governance enforcement for any product.
5. There is no primary evidence on scale limits, on instruction-file inheritance conflicts at scale, or on failed multi-team rollouts.
6. In-loop verification is under-specified everywhere. Products expose hooks but no verification responsibility, and Anthropic's own harness found that the model is "a poor QA agent" out of the box ([harness design](https://www.anthropic.com/research/harness-design-long-running-apps)) **[Established]**.

The result supports the framework, with qualifications **[Synthesized]**. Every system has an identifiable mechanism for R1, R2, R4, R5 and R7, so those five are real responsibilities and not artefacts of one vendor's design. Two seams recur, which is evidence about the field rather than a flaw in the mapping. The **R4/R5 seam**: the same artifact is context and memory in five of seven systems. The **R6 seam**: verification is provided only as a hook point, never as an owned responsibility, in all seven. Two systems do not map onto one row. **LangGraph** is a runtime, not a harness, and spreads the harness across four packages, as LangChain itself states when it defines the harness as "the prompt, the tools, and any middleware" ([LangChain agents](https://docs.langchain.com/oss/python/langchain/agents.md)). **Copilot** is a platform hosting multiple harnesses. The framework absorbs both by recording separately *where a responsibility executes* and *where it is configured*. The Claude Agent SDK shows why: the mechanism lives in the CLI, while the SDK supplies configuration and callbacks.

## Recommendations for a reference harness that scales with teams and topics

Every recommendation in this section is **[Proposed]**. Each one is grounded in the evidence cited above.

**Adopt the eight-responsibility taxonomy and the layer model as the shared vocabulary, and record two attributes per responsibility: where it executes and where it is configured.** This removes the SDK-vs-CLI and runtime-vs-harness ambiguity seen in the Claude Agent SDK and LangGraph. Use the narrow harness scope, a stateless loop over an external session store, because it is the only scope that makes the harness horizontally scalable and replaceable without losing state ([Managed Agents](https://www.anthropic.com/engineering/managed-agents)).

**Put durable state outside the harness behind an append-only session interface, and treat context as a projection of it.** Choose a native-durability runtime (LangGraph checkpointers) or an external engine (Temporal, DBOS, Restate) for long-running or approval-gated work. The validation matrix shows that durability is absent or external in two of the three SDKs, and approvals that live only in a live process (Claude Agent SDK `can_use_tool`) do not survive restarts.

**Make verification an owned responsibility per topic, not an optional hook.** Each team or topic onboarding should register its verifier: tests and linters for code; schema, formula, citation or compliance validators, or LLM-judge rubrics, elsewhere. Run them as managed post-action and stop hooks. This targets the weakest cross-discipline transfer and the seam observed in all seven systems.

**Centralize governance in a managed-policy layer authored as code, and render per-group variants from one template.** Keep restrictive keys non-overridable. Copilot's least-restrictive team merge and Claude Code's non-merging group configs both erode baselines when they are hand-maintained. Validate policies in CI, because OpenCode drops invalid statements. Lock the telemetry destination centrally. Enforce sandboxing by default, with `failIfUnavailable`-style fail-closed behaviour, using Codex's default-on posture as the reference.

**Route all model and MCP traffic through gateways that own identity, budgets and audit.** A gateway is the only place where cost attribution, the model allowlist and MCP audit survive multi-vendor harnesses. It also closes the holes found in Copilot (local BYOK) and Claude Code (a custom base URL skips server-managed settings), provided that policy is set at the gateway. Map gateway "teams" to catalog owners so that cost and ownership share one key. Run rate limiting fail-closed.

**Run one internal marketplace and one MCP sub-registry as the only allowed sources, with SHA pinning, auto-update off for third-party sources, CODEOWNERS review, two release channels and an eval gate before promotion.** Add internal signing or provenance attestations, because no harness verifies signatures natively and OWASP ranks supply chain in its agentic Top 10. Treat SKILL.md files and agent profiles as reviewable code. Use the platform's existing tool catalog as the source of MCP servers, following Spotify's Backstage pattern.

**Onboard teams through a golden-path template with three risk tiers delivered as managed bundles**: read-only/sandboxed, workspace-write with ask rules, and autonomous/CI with managed-only hooks and network allowlists. Promotion between tiers should require evidence from the team's verifier and telemetry. CNCF Level 3 self-service is the target and Level 4 extension the horizon.

**Keep the harness swappable behind an internal interface, and evaluate harnesses as well as models.** Harness effects of 7–28 points mean that vendor leaderboards cannot pick a harness. Run a same-model, harness-varied evaluation on internal tasks before standardizing. Include Copilot, which no public benchmark covers, and disclose configurations. Spotify's thin CLI over swappable agents is the existence proof that this avoids redesign.

**Prefer standards at every boundary that has one (MCP, A2A, AGENTS.md, Agent Skills, OTel GenAI), and isolate the three unstandardized boundaries (model wire, permission policy, memory) behind internal adapters.** Pin OTel GenAI attribute versions, because the conventions are still in Development. Track MCP's 2026-07-28 deprecations (Sampling, Roots, Logging, Dynamic Client Registration) when choosing servers.

**For the Copilot decision, choose by platform fit, not by an assumed capability gap.** Where GitHub is already the system of record and SaaS is acceptable, Copilot's cost, audit and delegation objects are a real advantage, and VS Code can host other harnesses under the same governance. Where self-hosting, sovereign routing or local session audit is required, Claude Code (via Bedrock, Vertex, Foundry or the self-hosted gateway) or OpenCode with a gateway are the documented routes.

## Conclusion

The research changes what "choosing a harness" means for a platform team. Harness features have converged so far that feature checklists no longer separate Claude Code, Codex, OpenCode and Copilot. All four read AGENTS.md, load SKILL.md skills, speak MCP and enforce managed allow/ask/deny policy, and two of them even share key names. What still separates them is where execution is isolated, which deployment routes they offer, and which surrounding platform objects carry identity, audit and cost. The scaling decision is therefore mainly a platform-layer decision, with the harness treated as a replaceable component behind standard boundaries and a locked policy layer. Spotify's swappable CLI and DORA's "amplifier" finding point the same way: platform maturity is the precondition, not an add-on.

The framework's two weakest points are also its most actionable ones. Verification is a hook in every product and a responsibility in none, and it is the concept that transfers worst to analysis, documentation and business processes. A multi-discipline harness will succeed or fail on whether each topic brings its own oracle. Policy, memory and the model wire are the three boundaries no standard governs. They are where vendor lock-in and governance drift will accumulate, so they deserve internal adapters and policy-as-code now, before the AAIF working groups settle them.
