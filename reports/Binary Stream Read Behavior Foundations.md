# Binary Stream Read Behavior Foundations

Literature review and evidence synthesis on what can happen when a binary data stream is read from a storage system.
Brief: `briefs/Binary Stream Read Behavior Foundations.md`. Track notes and verification record: `research_notes/Binary Stream Read Behavior Foundations/`. Date: 2026-11-08.

This report describes existing knowledge. It does **not** propose, design or select a taxonomy. Where it groups material, the grouping is a reading aid taken from the sources, not a proposed structure.

---

## 0. Method, conventions and limits

**Process.**
1. Nine research tracks were defined up front, each covering one body of literature (OS interfaces, language contracts, device command sets, media field studies, file-system integrity, consistency models, network/object protocols, dependability taxonomies, timing).
2. A completeness critic reviewed the nine track outputs and added three gap tracks: channel coding, the load/store and persistent-memory path, and adversarial or untrusted storage.
3. Each track searched the web, read full texts, and extracted falsifiable claims. Each claim is tied to one source the track actually read, with a verbatim quote and a locator.
4. Every claim then went to three independent verifiers. Each verifier re-read the cited source and tried to refute the claim through a different lens:
   - *fidelity*: does the quote exist at the locator?
   - *overreach*: does the claim generalise beyond the source?
   - *currency/authority*: is the version current, and is the source what it claims to be?

   A claim is **KILLED** on ≥2 refutes, **CONTESTED** on 1 refute, and **VERIFIED** otherwise.

**Outcome.**
- Claims: 212 in total, of which 208 were verified, 3 contested and 1 killed.
- Sources: 189 distinct, of which 164 were read in full, 3 partially, and 22 were unreachable. Unreachable sources are not used as evidence.
- Verifiers attached a correction to most claims. The narrative below uses the corrected reading. The matrix (§E) keeps both the extracted claim and the verifier's qualification, so they can be diffed.

**Citations.** `[NN-Cn]` refers to a row of the evidence matrix (§E). Evidence-type codes used in the matrix:

| Code | Evidence type |
|---|---|
| N | normative standard or specification |
| E | peer-reviewed empirical study |
| T | theoretical or formal result |
| I | implementation documentation |
| G | other primary engineering evidence |
| S | survey |

Statements marked *(inference)* are the track's or this report's reasoning, not something a source says. Statements about newer specification versions marked *(verifier-reported)* came from the verification pass and were not re-read by a research track.

**Known limits of this research** (details in §F.2):
- **Paywalled or member-only standards were not read.** Missing: current SPC-5/SBC-5, ACS-4/5, JEDEC, CXL, the final ISO C text, IEC 60050-192 and ISO/IEC/IEEE 24765. The SCSI and ATA findings rest on older public working drafts (SBC-3 r0 2005, ACS-3 r5 2013).
- **Some classic papers were unreachable**, including Cristian 1991, Powell 1992 and Schlichting & Schneider 1983. They appear only through secondary citation and carry no claims.
- **Availability bias in the evidence.** Empirical evidence comes mostly from a few operators and vendors (NetApp, Google, Facebook, Microsoft, CERN), and implementation evidence mostly from Linux. This reflects which sources are openly published, not that these systems are more important.
- **Planned scope.** The nine initial tracks were the lead's own choice. The critic pass reduced this anchoring risk but cannot remove it. Two areas the critic listed were not run as tracks: database storage engines, and formal verification of storage systems.

## B. Established concepts and findings

Findings are grouped by the body of knowledge in which they were established. Definitions keep source terminology. Applicability is stated where it narrows the claim.

### B.1 Operating-system read interfaces

**Short reads.**
- POSIX states that `read()` "may" return fewer than `nbyte` bytes in three cases [01-C1, contested and corrected; 02-C4]:
  - fewer bytes are left in the file;
  - a signal interrupts the call after some data was read;
  - a pipe, FIFO or special file has fewer bytes *immediately available*.
- The list is not exhaustive. Other clauses also bound or leave open the count: the offset maximum, `nbyte > SSIZE_MAX` (implementation-defined), and sockets, where `read()` is "equivalent to recv()".

**End-of-file.**
- A read starting at or after end-of-file shall return 0.
- For device special files, the result of later reads is implementation-defined [01-C2]. The spec therefore does not require end-of-file to be sticky on devices. It does not forbid stickiness either.

**Interruption.**
- If a signal arrives after some data has been read, `read()` returns the partial count. If no data had been read, it returns −1/EINTR.
- The RATIONALE notes that buffering implementations may defer moving data into the user buffer, so an early interrupt can still produce EINTR [01-C3].
- Linux applies EINTR/SA_RESTART to read only for "slow" devices (terminals, pipes, sockets). Local disk I/O is not interrupted by signal handlers [01-C11].

**Zeros, holes and unwritten data.**
- Unwritten regions of a regular file before EOF read as bytes of value 0 [01-C4].
- A hole is a contiguous zero-valued region. Not every zero run needs to be reported as a hole. Every seekable file has a virtual hole at its current size [01-C5].

**Errors.**
- EIO for a physical I/O error is only a "may fail" condition. (A separate "shall fail" EIO covers background processes reading their controlling terminal.)
- The informative RATIONALE says hardware-error behaviour is "beyond the scope" of POSIX. It also leaves the file offset after an error unspecified, while saying the offset "clearly" should not change for immediately detected errors such as EAGAIN [01-C6, 02-C5].

**Atomicity and visibility.**
- POSIX.1-2024 §2.9.7 requires that when two threads each call one of the listed functions (read, readv, pread, write, lseek, and others), each call sees all or none of the other's specified effects. The rule begins "Except where specified otherwise" and applies to files in the file hierarchy [01-C7].
- The 2017 wording covered only "regular files or symbolic links" [06-C15, superseded on scope].
- Linux before 3.14 violated this rule for the offset: reads through a shared open file description could return overlapping data [01-C8].
- After a successful `write()`, a successful `read()` of the modified bytes shall return the written data until they are modified again [05-C15].

**Memory-mapped reads.**
- POSIX requires the partial last page to be zero-filled.
- References inside the mapping to whole pages beyond the object's end shall raise SIGBUS. SIGBUS on other mapped-object errors is permitted but not required [01-C9].

**Reads after failed writeback** (implementation evidence):
- LWN (2018) reported that filesystems usually discard the affected pages and mark them clean, so a later read "will likely return something other than the data that was written" [01-C12].
- Rebello et al. (ATC 2020, Linux 5.2.11, fault injection) refined this:
  - ext4 and XFS keep the new, unpersisted data in clean pages, so readers see it until the pages are evicted and then see the old on-disk contents;
  - Btrfs reverts the in-memory state at once [01-C13, 05-C13].
- The Linux errseq_t mechanism reports writeback errors to fsync callers, per open file description. It does not report them to `read()` [01-C14, 05-C14; "not read()" is partly inference].

**Alignment for direct I/O.**
- Linux O_DIRECT alignment rules vary by filesystem and kernel and may be absent. Misaligned requests either fail with EINVAL or fall back to buffered I/O [01-C10].
- Windows unbuffered I/O requires sizes and offsets that are multiples of the volume sector size. Buffer alignment is to the physical sector size, which may not be enforced [01-C17].

**Windows specifics.**
- End-of-file is signalled differently by mode:
  - synchronous `ReadFile`: TRUE with 0 bytes read;
  - asynchronous: FALSE with ERROR_HANDLE_EOF, either from GetOverlappedResult or from the initial call [01-C15].
- On a pipe, a zero-byte successful read means the writer wrote zero bytes. A closed anonymous-pipe writer gives FALSE/ERROR_BROKEN_PIPE. A read that overlaps a range locked by another process fails [01-C16].
- `FILE_ATTRIBUTE_OFFLINE` and `RECALL_ON_DATA_ACCESS` mark data that is not locally present. Reading such a file is "more expensive than normal", for example it fetches at least some content from remote storage [01-C18].

**Asynchronous and advisory interfaces.**
- POSIX `aio_read` returns once the request is queued or initiated. Errors can surface at call time or later through `aio_error`, which reports EINPROGRESS until completion. ECANCELED follows an explicit `aio_cancel` [09-C12].
- io_uring:
  - completions are unordered unless linked or drained;
  - per-request errors arrive in the completion entry;
  - a linked timeout only *attempts* cancellation, and disk I/O that has already started may still complete [09-C13].
- Windows overlapped reads may complete synchronously, for example on cache hits [09-C14].
- Linux read-ahead and `posix_fadvise` hints are non-binding [09-C15].

### B.2 Language and runtime stream contracts

**C stdio.**
- `fgetc` returns the same value, EOF, for end-of-file and for a read error. The per-stream indicators (feof/ferror) tell them apart. The footnote saying so is informative. EOF is returned whenever the end-of-file indicator is already set [02-C1].
- After a `fread` error the file position is indeterminate, and a short count can mean either an error or end-of-file [02-C2].
- Binary streams round-trip data "under the same implementation", but an implementation-defined number of null characters may be appended. The length read back need not equal the length written [02-C3].

**Go.**
- `io.Reader` may return n>0 together with a non-nil error, EOF included. Callers "should" process the n bytes before looking at the error. This is allowed, not required: the error may instead arrive on a later call [02-C6].
- A return of 0 bytes with a nil error does not mean EOF. EOF is reserved for a graceful end. An EOF inside a structure should become `ErrUnexpectedEOF` [02-C7].
- `io.ReadFull` returns EOF only if no bytes were read, and `ErrUnexpectedEOF` after a partial read. It drops any error that arrives once the buffer is full [02-C8].

**Rust.**
- `Read::read` documents that an `Err` means no bytes were read. This is a contract on implementors and is not enforced by the compiler.
- `Ok(0)` means EOF or an empty buffer and is not necessarily permanent: a file can return more data after it is appended to [02-C9].
- `read_exact` returns `UnexpectedEof` if the input ends early. The buffer contents and the number of bytes consumed are then unspecified (bounded by the buffer size) [02-C10].

**Java.**
- `InputStream.read(byte[],int,int)` may read fewer than `len` bytes and returns −1 at end of stream.
- Its *default implementation* catches an IOException raised after the first byte and returns a short count, treating it "as if it were end of file". Subclasses that override the method need not do this [02-C11].
- `EOFException` is used mainly by data input streams. `readNBytes` returns a short count instead of throwing [02-C12].

**Python.** `RawIOBase.read` has three outcomes [02-C13]:
- 0 bytes (for a non-zero size) means EOF;
- `None` means no data is available in non-blocking mode;
- a short result can occur after the OS call returns fewer bytes.

**.NET.** `Stream.Read` returns 0 only if zero bytes were requested or no more data is expected, and may return fewer bytes before the end. The remarks say the position is unchanged after an exception, but nothing shows this is enforced [02-C14].

**Node.js and WHATWG.**
- Node.js `stream.finished` reports a premature close as `ERR_STREAM_PREMATURE_CLOSE` (since v14) [02-C15].
- In WHATWG Streams, `read()` fulfils with `done:true` on close and rejects on error. A BYOB read with `min` may return fewer elements when the stream closes. A cancelled reader also gets `done:true` [02-C16].

**Framing and truncation.**
- RFC 9112 says a close-delimited HTTP/1.1 message cannot be told apart from a truncated one. Content-Length or chunked framing makes an incomplete message detectable [02-C17, 07-C4].
- Over TLS, an incomplete close lets the client detect truncation of a close-delimited response.
- TLS 1.3 requires `close_notify` before closing the write side. A transport close without it leaves the receiver unable to know that all data arrived (the "truncation attack"). There is an exception after an error alert [02-C18]. *(Verifier-reported: RFC 8446 has been superseded by RFC 9846 (2026), with §6.1 unchanged.)*

### B.3 Block-device command sets

**NVMe** (Base 2.1, NVM Command Set 1.1; verifier-reported unchanged text in Base 2.4 and NVM CS 1.3):
- *Data on error.* When a read fails with, for example, Unrecovered Read Error or an end-to-end Guard Check Error, the controller may either stop transferring data or place the erroneous data in host memory anyway. The host is required to ignore that buffer [03-C1].
- *Status codes.* The Media and Data Integrity status codes include 81h Unrecovered Read Error, the end-to-end Guard/Application/Reference/Storage Tag check errors (82h–84h, 88h), and 87h Deallocated or Unwritten Logical Block. The check-error codes also apply to writes. A separate Do Not Retry (DNR) bit says whether resubmitting is expected to fail [03-C2]. *(Inference from Figure 106: no "recovered error" completion class exists.)*
- *Read Recovery Level.* An optional capability with 16 levels that trade completion time against error recovery. If it is supported, level 4 (nominal) and level 15 ("Fast Fail") are mandatory. How it interacts with the per-command Limited Retry bit is implementation-specific [03-C3].
- *Deallocated or unwritten blocks.* If the DULBE error is not enabled, reads return all 00h, all FFh, or either, according to DLFEAT.DRB. The value must stay the same until the block is written [03-C4].
- *Protection information for deallocated blocks.* The tag fields are set to FFh, which disables checking. For Type 1/2 namespaces, an Application Tag of FFFFh disables all PI checks. The Guard is FFh or a valid CRC [03-C5].
- *Atomicity.* After a power failure or error interrupts a write that is no larger than AWUPF and does not cross an atomic boundary, later reads return all-old or all-new data. Beyond that limit nothing is guaranteed in Single Atomicity Mode. In Multiple Atomicity Mode, each atomic subrange stays atomic [03-C6].
- *Read-after-write.* A read after a write that completed without error returns the write's data. The exception: a volatile write cache is supported and enabled, FUA is not set, no flush for that namespace completed, and main power is lost without a shutdown. Only locations still held in the cache may then return older data [03-C7].

**SCSI** (2005 SBC-3 working draft and a vendor manual; current SBC-4/5 not read):
- *Sense keys.* An unrecovered read is classed under MEDIUM ERROR or HARDWARE ERROR, and a recovered read under RECOVERED ERROR. The INFORMATION field carries the LBA involved [03-C8].
- *Error-recovery mode page.* This page lets the host allow non-clean data [03-C9]:
  - TB=1 transfers an unrecovered block, with vendor-specific contents, before CHECK CONDITION;
  - RC=1 implies the device may send erroneous or fabricated data to keep the data flow continuous;
  - with RC=0, "Data shall not be fabricated".
- *Write failures.* After a write is interrupted by power loss or a medium or hardware error, the affected blocks are indeterminate, and reads may return "old data, new data, or vendor-specific data" [03-C10].
- *Deferred errors.* Response codes 71h/73h report a condition from an earlier command that already returned GOOD (or CONDITION MET, or an INTERMEDIATE status) [03-C11].
- *Protection information.* The Guard is a CRC-16 (G(x)=18BB7h). A PI check failure on read is reported with sense key ABORTED COMMAND. In this draft, an Application Tag of FFFFh disables checking unconditionally; later revisions make this depend on protection type *(verifier-reported)* [03-C12].

**ATA** (ACS-3 r5 draft):
- *Trim.* Without DRAT, each read of a trimmed block may return different data. With DRAT the data is deterministic: any value if RZAT=0, zero if RZAT=1. In every case the data must not come from data the host sent for any other LBA [03-C13].
- *Read errors.* UNCORRECTABLE ERROR and INTERFACE CRC bits report errors. The reported first-unrecoverable LBA may lie outside the command's range, and data already transferred is indeterminate [03-C14].
- *Recovery time.* The SCT Error Recovery Control read timer caps the time the device spends processing a read, in 100 ms units. A value of 0 means unlimited recovery [03-C15].
- *Write Uncorrectable.* WRITE UNCORRECTABLE EXT makes later reads fail. Pseudo mode affects the whole physical sector, flagged mode only the specified logical sectors. The attribute persists until the sector is written [03-C16].

**SD.**
- After a discard, data is "don't care": previously written data may still be read back, partly or fully.
- After an erase, data is all 0 or all 1, as reported by DATA_STAT_AFTER_ERASE. Discard is optional and limited to SDHC/SDXC cards [03-C17].

### B.4 Field studies of media errors

**Latent sector errors (LSEs).** In NetApp data, an LSE is a sector read or write failure, or an uncorrectable ECC error, that destroys the sector's prior content. The study separates LSEs from two other error types defined by SCSI error codes [04-C1]:
- *not-ready-condition* errors;
- *recovered* errors, where the read succeeds after a retry or ECC.

Further findings on LSEs:
- **Prevalence.** 3.45% of 1.53M disks developed at least one LSE within 32 months. This is a lower bound for that population [04-C1].
- **Detection.** Most LSEs are found by background verify (scrub): 86.6% nearline and 61.5% enterprise. Only 13.4% and 19.1% are found by reads, and 19.3% of enterprise LSEs by writes [04-C2].
- **Locality and timing.** LSEs cluster in space: P(another LSE within 10 MB) ≥ ~0.5 for most models [04-C3]. They also arrive in bursts that a Pareto model fits better than Poisson [04-C8].

**Silent corruption** (NetApp, 1.53M disks, 41 months):
- **Detection.** More than 400,000 checksum mismatches were detected by storage-system checks, with no indication from the drive [03-C18].
- **Rates.** 0.86% of nearline and 0.065% of enterprise disks developed mismatches [04-C5, 05-C6].
- **Classes.** Corruption is classified by the detector that finds it (checksum mismatch, identity discrepancy, parity inconsistency). This classification belongs to the NetApp mechanisms, not to storage stacks in general [04-C4].
- **Patterns.** Mismatches cluster in consecutive blocks [04-C6]. About 8% surface during RAID reconstruction, which raises the possibility of real data loss [04-C7].

**Flash.**
- *Final read errors (Google).* These are read errors that persist after retries. The paper's text gives 20–63% of drives and 2–6 per 1,000 drive days. Its Table 2 gives different per-model figures, so the paper is internally inconsistent [04-C9].
- *Uncorrectable errors vs reads (Google).* Uncorrectable errors do not correlate with the number of reads, while correctable errors do. The authors argue that UBER (errors per bit read) is not meaningful in the field, though possibly meaningful in controlled settings [04-C10].
- *Facebook.* Errors are heavily concentrated: the top 10% of SSDs account for over 80% of errors. On read-heavy Platform E, no dependence of failures on read volume was found [04-C11].
- *Read disturb and read-retry* (lab characterisation) [04-C12]:
  - reading shifts the threshold voltages of unread cells in the same block;
  - read reclaim relies on maximum read counts that some vendors specify;
  - read-retry re-reads at shifted reference voltages, which adds latency.
- *Lost writes (NetApp SSDs).* Lost writes caused 13.54% of replacements whose reason was recorded. They were detected on read when a block was inconsistent with its signature, and blame between drive and other layers is "somewhat less clear" [04-C16].

**DRAM and other media.**
- *Google DRAM.* Errors were measured at 25,000–70,000 FIT/Mbit (also stated as up to 75,000), mostly correctable and heavy-tailed. More than 8% of DIMMs per year saw correctable errors [04-C13].
- *HPC DRAM.* A projection (not an observation) puts SEC-DED-undetected errors at up to 20 FIT per DRAM device [11-C15].
- *CERN.* A write-then-read-back probe found corruption the layered ECC/CRC protections did not report (500 errors on 100 of 3,000 nodes in about 5 weeks). The "protection doesn't work 100%" conclusion rests on that probe [04-C14].
- *Optical (NIST).* Accelerated aging tracks error rates (BLER, PI Sum8) as they rise before uncorrectable errors appear [04-C17].
- *Network path.* TCP checksum failures were measured at 1 in 1,100 to 1 in 32,000 packets despite link CRCs, with undetected errors estimated at roughly 1 in 16 million to 10 billion packets (year-2000 traces) [07-C18].

### B.5 File-system and storage-stack behaviour seen by readers

**Disk failure model.** The *fail-partial* model (Prabhakaran et al., SOSP 2005) names three ways disks fail. Failures may be transient or sticky [05-C1, 08-C11].
- entire-disk failure;
- block failure (latent sector errors);
- block corruption, which is silent: bad data is returned with no error.

**File-system failure policy.**
- The *IRON* taxonomy describes a file system's failure policy by detection level (Zero, ErrorCode, Sanity, Redundancy) and recovery level (Zero, Propagate, Stop, Guess, Retry, Repair, Remap, Redundancy). `R_Guess` returns possibly wrong contents while hiding the failure [05-C2].
- Under type-aware corruption injection, ext3, ReiserFS, JFS and (less thoroughly tested) NTFS accepted well-formed but wrong blocks [05-C3]. They handled failures with "illogical inconsistency" [08-C12].

**Limits of block checksums.**
- A checksum written together with its block cannot detect lost or misdirected writes, because stale data and stale checksum remain consistent [05-C4].
- Model checking of published parity-RAID designs, one error per stripe, sorted outcomes into data recovery, data loss (an error is reported) and corrupt data (returned undetected). Every scheme examined had flaws [05-C5, 04-C15].

**ZFS (OpenSolaris era).**
- Under injected disk corruption, ZFS never returned bad data. It reported an error when no good copy existed [05-C8].
- Checksums are verified only on reads from disk. In-memory corruption is therefore returned to readers, and corruption that happens before a flush gets a fresh, valid checksum [05-C9].

**Error propagation in Linux.** In Linux 2.6.15.4, static analysis found that 13% of error-propagating calls drop the error code. Synchronous reads in file-system code checked their errors; the violations were in read-ahead and asynchronous reads [05-C10].

**Linux file systems (Ganesan et al.).** The paper motivates its fault model with this description of default local file systems:
- ext4 and XFS have no user-data checksums and return corrupted blocks without error;
- btrfs and ZFS turn the same corruption into EIO.

This is the paper's background description, not its measurement [05-C11, 08-C17].

**Replicated systems (Ganesan et al.).** Across the eight replicated systems tested, a single local fault could cause user-visible corruption, data loss or unavailability. RethinkDB, for example, returned corrupted data silently [05-C12, 08-C18].

**Crash states (Pillai et al., OSDI 2014).** Non-atomic appends can leave a file whose size was updated before its data, so a read after a crash can see garbage. This is a possible crash state found with an incomplete tool (BOB) [05-C16].

**End-to-end argument (Saltzer, Reed and Clark).** A function such as careful file transfer needs the endpoints' knowledge to be complete. A lower-layer version "may be useful as a performance enhancement" [05-C17].

**btrfs.** btrfs checksums data and metadata by default and verifies after reading from the device. User changes to an O_DIRECT buffer during writeback can cause checksum mismatches. Mitigations depend on kernel version [05-C18].

### B.6 Consistency and concurrency models

**Registers (Lamport 1986).** Lamport defines three single-writer registers:
- *Safe.* A read that does not overlap a write returns the last value written. A read that overlaps a write may return any value in the domain, even one never written [06-C1].
- *Regular.* An overlapping read returns either the old value or one of the values being written. Two successive reads during the same write may still return new and then old.
- *Atomic.* Atomic registers forbid that new-then-old inversion [06-C2].

**Sequential consistency and linearizability.**
- *Sequential consistency* requires equivalence to one sequential order that respects each process's program order. That it imposes no real-time order is an inference from what the definition leaves out [06-C3].
- *Linearizability* requires a legal sequential order that respects the real-time order of non-overlapping operations. Pending operations are either completed or discarded [06-C4].
- Linearizability is *local*: a history is linearizable iff each object's projection is [06-C5].

**Session guarantees (Terry et al. 1994).**
- *Read Your Writes:* a read is served by a state that includes the session's earlier writes. It is not guaranteed to return the session's own value, because other writes may be visible [06-C6].
- *Monotonic Reads:* the writes relevant to an earlier read are included in any later read's server state [06-C7].

**Transactional isolation.**
- Berenson et al. (1995) distinguish broad phenomena (P) from strict anomalies (A). Examples: dirty read, a value that may never have existed [06-C8]; read skew A5A, which Snapshot Isolation precludes while admitting write skew [06-C9].
- Adya (1999) gives implementation-independent definitions: G1a, reading data written by an aborted transaction; G1b, reading an intermediate version [06-C10].

**Replicated and staleness-bounded storage.**
- Eventual consistency guarantees only convergence. It gives no recency or ordering guarantee for reads [06-C11].
- Under Δ-atomicity, a read may return a value written up to Δ time units ago (reported secondarily via Viotti & Vukolić) [06-C12].
- Read-your-writes is unattainable for highly available systems during partitions, but attainable with sticky availability. No recency bound is enforceable by systems that stay available under indefinite partitions [06-C13].
- *Probabilistically Bounded Staleness:* PBS models fed with production latency distributions predict that partial-quorum stores frequently give consistent reads within tens of milliseconds. Some configurations need more than a second [06-C14].

**Network file systems.** NFSv4 offers close-to-open semantics: absent delegations, clients revalidate cached data at OPEN through the change attribute and flush before CLOSE. RFC 7530 requires this revalidation at least for DENY=WRITE/BOTH opens [06-C16, 07-C9].

**Cloud object stores** (vendor statements, no formal semantics):
- *S3* documents per-key strong read-after-write consistency. A GET concurrent with an overwrite returns old or new data, never partial data. There is no cross-key atomicity [06-C17, 07-C13].
- *GCS* documents strong object read-after-write. Publicly cacheable objects may be served stale until their cache lifetime expires [06-C18].
- *Azure* uses snapshot isolation within a single partition, and the ETag changes on every write [07-C17].

### B.7 Network and object-storage read protocols

**HTTP ranges.**
- Range support is optional. A server may answer a Range request with a 200 carrying the full representation. A 206 may carry "a subset of the data requested", so clients must inspect Content-Range [07-C1].
- Clients cannot rely on receiving 416 for an unsatisfiable range [07-C2].
- `If-Range` prevents splicing bytes from different versions. Clients must not send a weak ETag in it, and the server applies strong comparison [07-C3].

**HTTP message completeness.**
- *HTTP/1.1:* a Content-Length shortfall makes a message incomplete. A close-delimited message counts as complete unless the connection signals an error [07-C4].
- *HTTP/2:* a content-length that does not match the DATA payload makes the message malformed. Responses defined as having no content are exempt, and data processed progressively may already have been acted on [07-C5].

**Retries and caches.**
- GET is safe and idempotent. It may be retried automatically after a communication failure that occurs before the client reads the response, and the retried response may differ [07-C6].
- A cache must not deliver a partial response without marking it 206, and may combine stored ranges only if they share a strong validator [07-C7].

**Network file and block protocols.** Short transfers are handled in three different ways:
- *NFSv4.1:* a READ may return fewer bytes with eof=FALSE (a short read). Reading at or past end-of-file returns 0 bytes with eof=TRUE [07-C8].
- *SMB2:* the server must fail the READ with STATUS_END_OF_FILE if fewer than MinimumCount bytes are available [07-C10].
- *iSCSI:* a short transfer is signalled by residual underflow flags and counts. For bidirectional commands the read shortfall has its own flag [07-C11].

**Cloud object stores.**
- *Archive tiers:* S3 Glacier and Deep Archive, and the archive tiers of S3 Intelligent-Tiering, fail GetObject with InvalidObjectState until the object is restored [07-C12, 09-C17]. Azure archive blobs are offline until rehydrated [09-C18]. GCS Archive, by contrast, is documented as online (track 07 notes).
- *Throttling:* S3 returns 503 Slow Down at high request rates, and clients are expected to back off [07-C14].
- *Ranged integrity:* GCS server checksums cover whole objects, so HTTP ranged reads cannot be validated against them; gRPC ranged reads carry per-chunk CRC32C [07-C15].
- *Transcoding:* when GCS decompressive transcoding applies, the Range header is silently ignored [07-C16].

### B.8 Dependability and failure-mode taxonomies

**Avižienis, Laprie, Randell and Landwehr (2004).**
- Service failure modes are classified along four viewpoints: domain, detectability, consistency and consequences [08-C1].
- *Domain:* content vs timing (early or late). When both are wrong the failure is a halt (silent failure is a special case) or erratic [08-C2].
- *Detectability:* a failure is signalled or unsignalled, and detectors themselves can raise false alarms or miss failures [08-C3].
- *Consistency:* inconsistent failures, where different users perceive the service differently, are "usually called" Byzantine. This viewpoint applies only when there are two or more users [08-C4].
- *Fail-halt:* a "fail-stop" system fails only by halting "to an acceptable extent" [08-C5].
- *Elusive faults:* faults whose activation is not systematically reproducible are elusive. Together with transient physical faults they form intermittent faults, whose errors are soft errors [08-C6].

**Lamport, Shostak and Pease (1982).** Two processors reading a non-faulty input while it changes can obtain different values; the remedy is to synchronise the reads with the change. For a *possibly faulty* input, only agreement among the readers can guarantee they use the same value, and even then not that it is correct [08-C7, contested and corrected].

**Schneider (1984).** A fail-stop processor has three properties: Halt on Failure, Failure Status, and Stable Storage that "can always be read" by any processor. It is an idealisation, approximated as k-fail-stop [08-C8].

**Lampson and Sturgis (1979; unpublished manuscript, published material in LNCS 105).**
- A disk `Get` returns either (good, data) or looksBad [08-C9]:
  - a soft read error, within the nR/TR bound, is an expected error;
  - a persistent read error, or an undetected error (wrong data reported good), is a *disaster* outside the guarantee.
- *CarefulGet* masks soft errors by retrying. *StableGet* falls back to a second page; its guarantee also needs ordered writes and a periodic Cleanup [08-C10].

**Gray failure (Huang et al., 2017).** Gray failure is *differential observability*: an application sees the system as unhealthy while the system's observer considers it healthy [08-C13].

**Fail-slow (Gunawi et al., FAST 2018; 101 incident reports).**
- Fail-stop, fail-partial and fail-transient faults "can convert" into fail-slow faults, and masking by retry or repair becomes "a double-edged sword" [08-C14].
- SSD reads may be retried at different voltages, and pages failing ECC are rebuilt through RAIN with N−1 extra reads [08-C15, 09-C7].
- Symptoms fall into four kinds: permanent, transient and partial slowdown, and transient stop. Time to detect was often weeks to months, and unknown for 45% of reports [08-C16].

### B.9 Timing, latency and access patterns

**Tail latency.**
- Fan-out amplifies component tails: in one Google service, a single request's p99 was 10 ms, while the p99 for all leaf requests to finish was 140 ms [09-C1].
- Deferred hedged reads cut BigTable p99.9 from 1,800 ms to 74 ms for 2% more requests. Naive hedging adds unacceptable load [09-C2].

**Slow drives (Hao et al., FAST 2016; NetApp field data).**
- Drives are more than 2× slower than their RAID-group peers in ~0.2% of disk hours and ~0.6% of SSD hours [09-C3].
- The slowdowns are mostly unexplained by workload imbalance and usually silent [09-C4]. They persist and recur [09-C5].

**Error handling as latency.** Fail-slow hardware turns the cost of masking errors into normal-case performance loss when errors are frequent [09-C6].

**SSD garbage collection.** On a real Samsung SM951, background writes made reads 15×/19×/96× slower at p90/p95/p99. Larger reads suffer more. The verifier corrected the claim's "in simulation": these were measurements, and simulation was used only for the authors' own design [09-C8].

**Disk mechanics.**
- On drive-managed SMR, logically sequential reads of partly overwritten regions are physically fragmented [09-C9].
- For HDDs, caching and read-ahead are "the most important feature to model" for service time. Aggressive read-ahead delays random reads, and partial-hit cache behaviour is poorly specified [09-C10, 09-C11].

**Timeouts.** In the Linux SCSI midlayer, a timed-out read is aborted and retried or failed with DID_TIME_OUT. Escalation goes through full error handling [09-C16].

**Device recovery-time bounds.** Device-level limits on recovery time exist only as optional features: ATA SCT ERC [03-C15] and NVMe Read Recovery Level [03-C3].

**Archive restore latency.** Restores take hours ("typically") on S3 [09-C17] and up to about 15 hours at standard priority on Azure. An Azure rehydration started through Set Blob Tier cannot be cancelled [09-C18].

**Persistent memory latency.** First-generation Optane PMM random loads take ~305 ns. Sequential loads are about 2× faster, which the authors attribute to 256-byte internal merging [11-C14].

### B.10 Channel coding and decoder outcomes

**Capacity (Shannon).** Below capacity, coding can make errors "arbitrarily small" (the theorem promises no zero error). Above capacity, equivocation stays at or above H−C [10-C1].

**Erasure, error and deletion channels.**
- In the binary erasure channel, a loss arrives as a marked '?', so its position is known, and capacity is 1−f. In the binary symmetric channel, a flipped bit carries no marker [10-C2].
- In the deletion channel, the receiver gets no sign of which bits were lost. As of 2009 its capacity had no closed form, with a lower bound of (1−p)/9 [10-C3].
- Synchronisation errors were historically handled by timing recovery separate from coding, and "this may be changing" [10-C4].

**Decoder outcomes.**
- A bounded-distance decoder has three outcomes: correct decoding; decoder failure, which is detected; and decoder error, an undetected miscorrection. Between t and d−t errors the result is always failure [10-C5].
- For Reed-Solomon codes of length ≤ q−1, the conditional decoder-error probability is below 1/t! [10-C6].
- Iterative LDPC decoding separates detected failures from undetected errors, and a fixed-iteration practice blurs the distinction [10-C7].

**CRC strength.**
- A CRC's Hamming distance depends on the polynomial and the data length [10-C8].
- The rule of thumb "P_ud ≤ 2^−r" fails for many shortened cyclic codes. The T10 PI CRC was chosen because it is "proper" [10-C9].

**Erasure coding in storage.**
- *Killed claim [10-C10].* The extracted claim reversed Plank's point. Plank says erasure codes can be more powerful than ECCs *because* erasures expose the location of the failure. Silent corruption, whose location is unknown, is the error-correction case, not the erasure case.
- PMDS codes assume that a sector hard error is a detected erasure. Their authors concede that sector ECC can miscorrect and is "often" reinforced by a CRC [10-C11].
- Windows Azure Storage treats a slow read "as if" the node were offline: it reconstructs the data in parallel and takes whichever result arrives first [10-C12].

**Flash decoding cost.**
- In the baseline LDPC SSD design, a read uses hard-decision sensing first and soft-decision sensing only if hard decoding fails, so the effort to decode shows up as read latency [10-C13].
- Read-retry, NAC and parity recovery are tried before an uncorrectable error is reported. The flow is illustrative and varies by controller [10-C14].

**DNA storage.** The DNA storage channel is an unordered multiset of molecules, read by sampling, with insertions, deletions and substitutions plus molecule loss [10-C15].

**Vendor error specifications.** One Seagate data sheet states non-recoverable read errors as "1 sector per 10E15" bits read (wording varies by model), with no test method and no undetected-error rate [10-C16]. Track notes show that "10⁻¹⁵" is used for three non-equivalent metrics.

### B.11 Load/store path, persistent memory and poison

**Intel machine-check architecture.**
- *SRAR* errors are raised at the point of consumption, and software must act before resuming that stream of execution [11-C1].
- *SRAO* and *UCNA* errors describe corrupted data that has not been consumed [11-C2].
- An SRAR error is either continuable or not continuable [11-C3].

**ACPI persistent-memory scrubbing.**
- Address Range Scrubbing (ARS) reports uncorrectable persistent-memory errors so the OS can avoid them. A range accessed before the OS has processed the report may trigger a machine check [11-C4].
- ACPI says the OS "should" clear poison only if the range is retired or will be written before it is read [11-C5].

**Arm RAS.**
- Poison is "a common technique" for deferring an error, which is then reported if the data is consumed [11-C6].
- A synchronous External abort taken to AArch64 records only the UC, UER or UEO error states [11-C7].

**SNIA NVM Programming Model.**
- Only errors that are instruction-precise, data-contained and live-reported allow real-time recovery. Anything else forces the application to restart and run crash recovery [11-C8].
- *PRECISE* and *ERROR_UNIT* are platform attributes [11-C9]. *(Verifier-reported: the final v1.2 Technical Position is available with unchanged text.)*

**Linux delivery of memory errors.**
- Memory errors reach user space as SIGBUS with `BUS_MCEERR_AR` or `BUS_MCEERR_AO` [11-C10].
- *Late kill* is the system-wide default [11-C11].
- *Path dependence:* the same pmem media error gives SIGBUS on a DAX mmap load, but EIO through `read()`. `copy_mc` reports the bytes it could not copy [11-C12].

**Poison granularity (NOVA-Fortis, 2017).** Intel uses a 64-byte poison radius, Linux reports 512-byte regions, and undetected errors are assumed to return invalid data silently [11-C13].

**Persistency semantics (Px86).** After a crash, reads can observe states impossible during normal execution when distinct locations are written without flush or fence [11-C16].

### B.12 Adversarial and untrusted storage; preservation

**Untrusted single servers.**
- Under fork consistency, a dishonest server can hide one user's changes from another. The forking is detectable once the forked users see each other's later operations. The guarantee covers files written by honest users [12-C1].
- SUNDR's freshness is weaker than replicated BFT storage. A trusted time-stamp box is a proposed mitigation, not part of SUNDR as built [12-C2].

**Impossibility results (Cachin et al.).**
- Fork-linearizable emulation of SWMR registers on a Byzantine server cannot be wait-free [12-C3].
- Sequential consistency for more than one register is impossible on such a server [12-C4].
- Linearizability cannot be ensured when the provider is faulty. Weak fork-linearizability permits wait-free protocols [12-C5].

**Byzantine quorums (Malkhi & Reiter).**
- In the threshold case, a read accepts a value reported by at least f+1 servers.
- Masking quorum systems need n>4f, and dissemination quorums for self-verifying data need n>3f.
- The resulting semantics is a safe variable: an overlapping read may return a failure value [12-C6].

**Rollback attacks.**
- Rollback presents an old but cryptographically sound state, so confidentiality and integrity protection alone do not ensure state continuity [12-C7].
- Monotonic-counter defences face problems with crash resilience and wear-out [12-C8].
- On SGX, sealing does not prevent rollback or forking [12-C9].

**Merkle-based read verification.**
- dm-verity fails the I/O on a hash mismatch. `ignore_corruption` lets reads proceed, and `check_at_most_once` detects only offline tampering [12-C10].
- fs-verity re-verifies on every page-in, giving EIO for `read()` and SIGBUS for mmap. On its own it detects accidental corruption; detecting malicious modification needs separately authenticated hashes [12-C11].

**Races.**
- A *double fetch* happens when the kernel reads the same user value twice while another thread can change it in between (90 candidate situations in Linux 4.5) [12-C12].
- With TOCTTOU, binding by name is late and re-resolved at each use, while binding by descriptor is early (UNIX, 1995) [12-C13].

**Read-induced disturbance.**
- DRAM rows can be corrupted by repeatedly activating a neighbouring row (110 of 129 DDR3 modules) [12-C14].
- NAND read disturb grows with wear [12-C15].

**Remote data checking.**
- *PDP:* detecting deletion only when data is accessed may be too late for archives. Random sampling detects a 1% deletion with high probability [12-C16].
- *POR:* the archive proves the file is retrievable, with small corruptions repaired by error-correcting codes [12-C17].

**Preservation.**
- *Fixity:* PREMIS defines fixity as comparing digests computed at different times. Its contrast with OAIS's CRC example is weaker than it looks, because PREMIS itself lists Adler-32 and the current OAIS (650.0-M-3, verifier-reported) lists CRCs, checksums and message digests [12-C18, contested].
- *LOCKSS:* rate-limited peer polls on content hashes detect and repair damage; the poll rate is a simulation-backed design goal [12-C19].

## D. Cross-source synthesis

### D.1 Principles supported by several independent sources

Each principle is stated only as far as the cited sources support it. Applicability conditions are kept.

1. **Completion status and data correctness are separate.** A successful completion does not by itself show that the returned bytes are the stored bytes. The same point is reached from all three kinds of source:
   - *Normative:* SCSI permits fabricated or erroneous data with RC=1 [03-C9]. POSIX does not model hardware errors [01-C6].
   - *Empirical:* there are field corruptions with no device indication [03-C18, 04-C14]; ext4-style file systems pass corruption through [05-C11]; ZFS returns corruption that arises in memory [05-C9]; TCP checksums miss errors [07-C18]; SEC-DED misses DRAM errors [11-C15].
   - *Theoretical:* decoder error is defined as undetected miscorrection [10-C5]. Avižienis et al. define the unsignalled content failure [08-C3].

   In the other direction, an error completion does not mean no data arrived. NVMe may DMA erroneous data, and the host must ignore it [03-C1]. ATA leaves data already transferred indeterminate [03-C14]. SCSI TB=1 transfers unrecovered blocks [03-C9].

2. **Whether something can be detected depends on where the check sits.**
   - The end-to-end argument states this as a design principle [05-C17].
   - Implementations confirm it in different ways:
     - ZFS verifies only on disk reads, not on cache hits [05-C9];
     - a checksum stored with its block cannot detect lost or misdirected writes [05-C4];
     - NetApp corruption classes are visible only at particular read points [05-C7];
     - dm-verity's `check_at_most_once` misses online tampering [12-C10];
     - GCS whole-object checksums cannot validate ranges [07-C15].
   - Gray failure makes the observer part of the definition [08-C13].
   - Field rates count only what some layer detected, so they are lower bounds (track 04/05 gaps).

3. **"Zero bytes" usually but not always means end-of-stream, and completeness is defined only relative to a framing or an expected length.**
   - 0 for a non-empty request means EOF in POSIX, Rust, Python and .NET [01-C2, 02-C9, 02-C13, 02-C14].
   - It does not in Go, where 0/nil means "nothing happened" [02-C7], or for Windows pipes, where it reports a zero-byte write [01-C16].
   - For device files, later reads are implementation-defined [01-C2]. Rust's Ok(0) is "not necessarily permanent" [02-C9].
   - A truncated stream can be told from a complete one only with framing (Content-Length, chunking, an HTTP/2 length check, TLS close_notify) [02-C17, 02-C18, 07-C4, 07-C5] or with an expected length (exact-read helpers) [02-C8, 02-C10].

4. **Partial results are a normal successful outcome in most read interfaces, but not all.** POSIX short reads [01-C1], NFSv4.1 short reads with eof=FALSE [07-C8], HTTP 206 subsets [07-C1], iSCSI residual underflow [07-C11] and Java/.NET short counts [02-C11, 02-C14] are all successes. SMB2 instead fails the READ when fewer than MinimumCount bytes are available [07-C10].

5. **Masking an error turns it into latency.**
   - Retries, ECC escalation, read-retry, soft decoding and RAIN reconstruction all spend time to avoid an error [04-C12, 08-C14, 08-C15, 09-C6, 09-C7, 10-C13, 10-C14].
   - Device interfaces expose policy knobs that trade recovery effort against completion time [03-C3, 03-C15].
   - Systems deliberately treat slow reads as erasures, or hedge them [09-C2, 10-C12].

6. **What a read returns for never-written or deallocated storage is defined per interface and differs.**
   - *POSIX regular files:* zeros [01-C4].
   - *NVMe:* deterministic 00h or FFh [03-C4].
   - *ATA:* possibly different on each read without DRAT, any value with DRAT and RZAT=0 [03-C13].
   - *SD after discard:* possibly previously written data [03-C17].

   Track 03 explicitly rejects "deallocated reads return zeros" as a cross-technology rule.

7. **A read overlapping a write may return old data, new data or, under the weakest models, arbitrary data. Which one depends on an explicit atomicity contract.**
   - *Theory:* Lamport's hierarchy [06-C1, 06-C2].
   - *Contracts:* S3 "old or new, never partial" [06-C17]; NVMe AWUPF bounds [03-C6]; the SBC-3 draft's "old, new or vendor-specific" after interrupted writes [03-C10]; POSIX all-or-none effects between listed calls [01-C7].
   - *Multi-item reads:* reads that span items can observe read skew unless a snapshot is used [06-C9, 07-C17].
   - *Mid-stream version change:* guarded locally per protocol (If-Range, ETag, change attribute) [07-C3, 07-C9].

8. **Staleness comes from caching, replication and trust contracts, not from the medium.** The sources include:
   - session guarantees and HAT [06-C6, 06-C7, 06-C13];
   - PBS [06-C14];
   - close-to-open [06-C16];
   - HTTP freshness and public caching [07-C7, 06-C18];
   - Linux page-cache behaviour after writeback failure [01-C13];
   - fork consistency and rollback [12-C1, 12-C7, 12-C9].

9. **The same underlying fault shows up differently depending on the path and the layer.**
   - A pmem media error gives EIO through `read()` but SIGBUS on a DAX load [11-C12].
   - The same block corruption is passed through by ext4 and becomes EIO on btrfs or ZFS [08-C17].
   - A local fault produces a different global effect in replicated systems [05-C12].
   - Fault types convert into fail-slow [08-C14].
   - Linux collapses NVMe status codes into a few block-layer statuses (track 03 notes).
   - SNIA states the path dependence as an abstraction: precise and contained for block reads, platform-dependent for loads [11-C8, 11-C9].

10. **An outcome may be reported later than, or apart from, the read that caused it.**
    - SCSI deferred errors [03-C11].
    - POSIX aio and io_uring completion channels [09-C12, 09-C13].
    - Writeback errors reported at fsync, not at read [01-C14].
    - Poison reported at consumption; SRAO vs SRAR [11-C1, 11-C2, 11-C6].
    - Linux late kill [11-C11].
    - Latent errors are found only on access or scrub, and their time of occurrence is unobservable [04-C2, 04-C8, 10-C11].

11. **Reads can have side effects on stored state.**
    - Read disturb and Rowhammer corrupt data that was never read [04-C12, 12-C14, 12-C15].
    - Reading an offline or recall-on-access file triggers a remote fetch [01-C18].
    - Track 03's SCSI notes also list automatic reallocation (ARRE) as a recovery action.

    RFC 9110's "safe" property concerns only the semantics the client requests [07-C6]. It makes no claim about physical side effects *(inference)*.

### D.3 Disagreements that remain open

These are design or interpretation differences, not misreadings, and they cannot be reconciled from the sources alone.

- **Data together with an error.**
  - Go allows n>0 together with an error [02-C6].
  - Rust's contract says an Err means no bytes were read [02-C9].
  - POSIX rationale rejects returning an error with a short count (track 02 notes).
  - Java's default implementation and Go's ReadFull each convert or drop late errors [02-C8, 02-C11].
- **Position after an error.** C: indeterminate [02-C2]. POSIX: unspecified [02-C5]. Rust read_exact: unspecified [02-C10]. .NET: "remains unchanged" [02-C14].
- **Whether end-of-file is sticky.** C: sticky indicator [02-C1]. Rust: not necessarily permanent [02-C9]. Go: the next read "should" return 0, EOF (track 02 notes). POSIX devices: implementation-defined [01-C2].
- **Is masking a remedy or a hazard?**
  - Lampson & Sturgis and Avižienis et al. treat masking as fault tolerance [08-C10].
  - Gunawi et al. call it a "double-edged sword" [08-C14].
  - Huang et al. argue that masking keeps failing components in service (track 08 notes).
- **Status of silent wrong data.**
  - Lampson & Sturgis (1979) classify undetected wrong data as a "disaster" outside the model [08-C9].
  - IRON, the field studies and Ganesan et al. treat it as a realistic fault that must be handled [05-C1, 03-C18, 05-C12].
  - Normative read interfaces (POSIX) still do not model it [01-C6].
- **Value of Byzantine assumptions.** Avižienis et al., citing Powell, note that conservative assumptions can lower overall dependability. Huang et al. note that BFT is unused in production and gray failure is rarely arbitrary (track 08 notes).
- **Are vendor error rates conservative?** The CERN observations fell below vendor bit-error rates, while DRAM field rates far exceeded earlier reports [04-C14, 04-C13]. The direction appears to depend on the component *(track 04 inference)*.
- **Strength vs liveness for untrusted storage.** SUNDR calls fork consistency the strongest notion achievable without online trusted parties [12-C1]. Cachin et al. prove that it forces readers to block even when the server is correct [12-C3], and FAUST weakens it to regain wait-freedom [12-C5]. This is a proven trade-off, not a factual dispute.

## F. Knowledge gaps and unresolved questions

### F.1 Gaps in the literature itself

These are gaps that the sources read either state themselves or make evident. Items marked *(inference)* come from this research's reading, not from an explicit statement in a source.

1. **No normative read semantics for hardware or unrecoverable errors.** POSIX lists EIO only as "may fail" and puts hardware errors out of scope in its RATIONALE. No standard read here says what `read()` must return for data whose writeback or fsync failed (tracks 01, 05) [01-C6, 05-C15].
2. **Truncation of unframed streams.** The language contracts read here give no byte-stream-level way to tell a complete unframed stream from a truncated one. RFC 9112 states this impossibility for close-delimited messages (track 02) [02-C17].
3. **No failure modes specific to streams.** General dependability taxonomies define none: short reads, a mid-stream error after partial data, and a mis-signalled end of stream are absent. The storage failure models (Lampson & Sturgis, IRON, Ganesan) work per page or per block *(inference, track 08)*.
4. **No principled line between "late" and "halt/omission" for a read.** Avižienis et al. leave it to the specification, and Schneider notes that timeouts need synchronised clocks *(inference, track 08)*. Normative async APIs define no per-operation deadline; timeouts are added by implementations or applications *(inference, track 09)* [09-C12, 09-C13, 09-C16].
5. **Silent-corruption rates cannot be observed directly.**
   - Rates of undetected corruption are unknown by construction, and reported rates are lower bounds [04-C1, 04-C5].
   - Only detection time is observable, not occurrence time [04-C8].
   - Root causes often cannot be identified [03-C18, 04-C16].
   - The datasets come from a handful of operators, with few independent replications (track 04).
6. **No end-to-end composition of error probabilities.**
   - No command-set specification quantifies miscorrection (track 03).
   - Decoder-error probability has no uniform lower bound [10-C6, track 10].
   - CRC strength rests on BSC or burst assumptions without an authoritative fault characterisation [10-C8, 10-C9].
   - No source combines ECC miscorrection, the CRC residual and the erasure-detection assumption into one end-to-end probability of an undetected bad read *(inference, track 10)*.
7. **No cross-technology equivalences.** None exists at the normative level for read error classes across command sets (mappings exist only in implementations such as Linux `blk_status_t`), for poison granularity across vendors [11-C13], or for mid-stream version change across protocols (tracks 03, 07, 11).
8. **Object-store consistency is specified only informally.**
   - No vendor document read says whether successive overlapping GETs can see new-then-old data, or how ranged GETs behave when racing an overwrite beyond "never partial" *(inference, track 06)*.
   - NFS close-to-open semantics leave cross-client reads between OPEN and CLOSE unconstrained *(inference, track 06)*.
9. **Consistency theory models whole values.** It covers registers, objects and transactions, not a byte stream read incrementally across many blocks or objects. Multi-object anomalies such as read skew are the nearest available concept *(inference, track 06)*.
10. **Missing empirical measurements.**
    - Truncated or version-mismatched reads from cloud object stores (track 07).
    - Read-specific latency distributions below one hour; Hao et al. merge reads and writes at hourly granularity (track 09).
    - The prevalence of fail-slow and gray failure [08-C16, track 08].
    - Drive read-cache behaviour on partial hits, which Ruemmler & Wilkes call "one of the least well specified areas" [09-C11].
    - Optical media in the field; only accelerated aging exists [04-C17].
    - NVMM error behaviour, with no public field study as of 2017 [11-C13].
    - Application-level data loss in SSD fleets (track 04).
11. **Adversarial reads.**
    - There is no formal read model for malicious devices whose content depends on the access pattern, i.e. verify-time vs use-time divergence (track 12).
    - Fixity standards assume a trustworthy stored digest; only LOCKSS addresses an adversary through replication (track 12).
12. **Deletion and synchronisation channels.** Their capacity has no closed form, and practical synchronisation codes are scarce, as of 2009 [10-C3, 10-C4].
13. **Direct-I/O alignment.** No portable normative interface exists to discover alignment requirements. Linux has STATX_DIOALIGN (6.1+); Windows uses an IOCTL [01-C10, 01-C17].

### G.2 Dependencies that govern any observed read outcome

The sources show that what a reader observes depends on factors outside the medium. Any later framework will have to say how it treats each one.

1. **The interface contract in force.** The same event is a success, a short read or an error depending on the contract: POSIX vs SMB2; Go vs Rust; the C vs .NET position rules (§D.1-4, §D.3).
2. **The observer's position and the detection mechanisms present.** See the end-to-end argument, the NetApp detection points, ZFS cache bypass and gray failure (§D.1-2).
3. **The access path.** `read()` vs mmap/DAX load vs async completion: EIO vs SIGBUS; immediate vs deferred reporting [11-C12, 09-C12].
4. **Device configuration and advertised capabilities.** The SCSI RC and TB bits, NVMe RRL, Limited Retry and DLFEAT, ATA DRAT/RZAT and ERC, dm-verity's `ignore_corruption` [03-C3, 03-C4, 03-C9, 03-C13, 03-C15, 12-C10].
5. **The concurrency, replication, caching and trust contract** (§D.1-7, §D.1-8).
6. **Framing and the reader's length expectation** (§D.1-3).
7. **Prior history:** earlier failed writes, crashes, write history on SMR, wear and accumulated reads on flash [01-C13, 05-C16, 09-C9, 04-C12].
8. **Time:** latent errors exist before they are detected [04-C2, 04-C8]; an inconsistency window [06-C14]; archive restore latency [09-C17].
9. **Version:** behaviour is documented for specific kernel, file-system, specification and product versions throughout §E. Implementation-specific findings cannot be lifted to general properties without fresh evidence.

### G.3 Conceptual tensions future work must resolve or state explicitly

- **Is a failure intrinsic or relative to an observer?** Avižienis et al. classify failure modes at the service interface. Huang et al. define gray failure by who observes it. Detectability in the field studies depends on which mechanisms exist [08-C1, 08-C13, 05-C7].
- **What granularity?** Theory and storage models work per value, register, block or codeword. Stream contracts work per call with a byte count. No source bridges the two, so this is a gap for later work [F.1-3, F.1-9].
- **Masked or failed?** A retry that succeeds is a success at one layer and a latency event, or a fail-slow fault, at another. Masking is valued in some sources and called hazardous in others (§D.3).
- **Normative silence vs measured prevalence.** The normative read interfaces do not model silent corruption, while field and fault-injection studies find it routinely (§D.3).
- **Terminology collisions.** "Fail-stop", "read your writes", "snapshot isolation", "10⁻¹⁵", "Accept-Ranges", "checksum/fixity" and "zero bytes = EOF" each carry several source meanings (§D.2). Any later work needs to say which meaning it takes, citing the source.
- **Absolute vs probabilistic guarantees.** "Shall" requirements (POSIX, NVMe) sit beside probabilistic ones: Shannon's "arbitrarily small", CRC P_ud, PBS staleness, PDP sampling, and fail-halt "to an acceptable extent" [10-C1, 10-C9, 06-C14, 12-C16, 08-C5].
- **Reads assumed side-effect-free vs physical side effects:** read disturb, Rowhammer, recall from offline storage, reallocation (§D.1-11).
- **Honest vs Byzantine storage.** Nearly all consistency and integrity guarantees assume the store reports honestly. The untrusted-storage literature proves what stops holding without that assumption [12-C3–C5].
- **Specification drafts vs current standards.** The SCSI and ATA evidence comes from superseded drafts, so device-level distinctions should be re-checked against current texts before they are relied on (§F.2).

### G.4 Strength of the available evidence, by area

| Area | Strongest evidence | Main weakness |
|---|---|---|
| Call-level read semantics (counts, EOF, interruption, atomicity) | Normative POSIX, RFCs, NVMe; consistent documentation | Hardware-error behaviour unspecified; language contracts conflict |
| Device error reporting | Ratified NVMe specifications | SCSI/ATA from old drafts; JEDEC and CXL unread |
| Prevalence of media errors and silent corruption | Large peer-reviewed field studies | Few operators; detected events only; dated hardware |
| What file systems return under faults | Fault-injection studies at top venues | Version-specific; single-fault models |
| Values returned under concurrency and replication | Formal theory, with proofs | Value granularity; cloud contracts informal |
| Timing and tail behaviour | Field studies and measurements | Hourly aggregates; anecdotal fail-slow evidence; tape and optical missing |
| Decoder and detection limits | Information and coding theory | Idealised channel assumptions; no end-to-end composition |
| Load/store-path errors | Architecture manuals; kernel docs | Vendor-specific; CXL missing; PMem field data absent |
| Adversarial reads | Formal impossibility results; kernel docs | Threat models vary; preservation standards assume trusted digests |
